# pulse — PLAN

> Real, working uptime / status monitor: scheduled probes actually hit endpoints, results stream to a live dashboard, incidents open and close themselves, and a public status page ships the artifact a real product ships.
> Brand display: **Pulse**. Repo dir: `pulse`. Portfolio slot 4, api-heavy, NestJS.

## Problem

Every senior backend / fullstack recruiter has seen a hundred CRUD dashboards. What they rarely see in a portfolio is a system that demonstrates the harder parts of real product engineering: a job scheduler that runs work on intervals with retries and concurrency control, a real-time push channel that keeps a UI live without polling, an incident state machine that turns a stream of raw results into a human-meaningful timeline, and the alerting + public-status-page surface that an actual SaaS uptime product (UptimeRobot, BetterStack, Checkly, Pingdom, Statuspage) is built around. Pulse is that system, built small but real — the probes genuinely hit endpoints, the dashboard genuinely updates from those real results, and an incident genuinely opens when checks genuinely fail. The credibility of the showcase is that nothing about the live data is faked: seed data makes the dashboard rich on first load, but everything moving forward from "now" is a real scheduled probe.

## Audience

Two concrete viewers, one design that serves both:

1. **Senior backend / fullstack recruiter (US / EU), the primary.** Arrives at the dashboard demo URL from a CV link, a HN / Reddit / X share, or a recruiter forward. Lands on a 1440 px+ desktop monitor, often opens DevTools out of habit (to confirm the live channel is real SSE, not a `setInterval` faking it). They must read "this person can build real systems — queues, scheduling, real-time, incident logic" in the **first 10 seconds**, before reading a word of the README. The wow moment delivers that proof visually: a status board that is visibly alive from real probes, and an incident that opens live in front of them.
2. **A developer who would plausibly use an uptime monitor, the secondary.** Evaluates Pulse as a product: can I add my own endpoint, pick an interval, see uptime over 30 days, get alerted when it goes down, and share a public status page? This viewer hits the create-monitor flow, the monitor detail charts, and the public status page. Mobile (down to 320 px) matters for this viewer because the public status page is the kind of link shared into Slack and opened on a phone.

The design optimises for viewer 1's 10-second judgement (the dashboard is the lead surface) while making viewer 2's flows genuinely complete and genuinely usable.

## Wow moment

**The live status board reacting in real time to real probes — and an incident opening live.**

Concretely, what holds the viewer for five seconds, on the authenticated dashboard:

- The board renders a grid of monitor cards, each with a status dot, the target host, the current uptime %, a response-time sparkline, and a "last checked Ns ago" ticker. On first paint it is already rich (seeded history) — but it is not static.
- As real probes complete on their intervals, the board updates **without a reload and without polling**: a card's "last checked" ticker resets, a fresh response-time point slides into its sparkline, the status dot does a brief pulse, and the small response-time number re-renders. The viewer who opens DevTools sees a single long-lived `EventSource` connection on `/api/stream`, not a flurry of XHR polls — that detail is deliberate, it is the proof the real-time story is real.
- The dramatic beat: a dedicated demo monitor (`flaky.pulse.demo` — a real endpoint Pulse owns that is engineered to fail on command, or a target the viewer can knock down) crosses its consecutive-failure threshold. **Live, in front of the viewer:** its dot flips amber (degraded) then red (down), an incident row materialises at the top of the board and starts counting its duration upward, the monitor's uptime % ticks down, and an "alert fired" toast confirms a webhook went out. When the endpoint recovers, the incident auto-closes, its row settles into the incident history with a final duration, and the dot returns to green.
- A one-click **"Trigger demo incident"** affordance on the dashboard makes this beat reproducible on demand for a recruiter who will not wait for an organic failure — it points the demo monitor at a failing target (or toggles the owned flaky endpoint) so the whole open-incident-then-recover arc plays out in ~30 seconds while they watch.

This is the senior signal made visual: a recruiter does not have to take the queue / scheduler / real-time / incident-logic story on faith from the README — they watch it happen.

**Reference alignment (`docs/inspirations.md`).** The board's resting state and motion register are judged against **Linear** (the "this feels alive" bar from its changelogs and command palette — micro-interaction timing, restraint, hierarchy) and **Vercel** (dark surfaces, deliberate accents, dense data without busyness — the dashboard must hold up next to a Vercel project-overview screen). The status-dot and sparkline transitions take their easing cues from Linear's `cubic-bezier(0.16, 1, 0.3, 1)`-class curves at ~200–320 ms, not a generic `linear` 600 ms. The public status page's calm, premium, "the company spent real money on this" finish is judged against **Linear** and **Stripe**. The designer-critic gates every UI milestone against at least two of these by name, zero pochwał.

## Stack flavour

**`api-heavy`.** This is the deliberate third api-heavy slot, claiming the open NestJS backend the composition tracker reserved.

Justification against `docs/conventions.md` § 10 — **four of the five hard triggers fire**, any one of which is sufficient:

- **Background jobs / queue / cron trigger.** The probe scheduler is the spine of the product: BullMQ repeatable jobs run each monitor's check on its configured interval, with retries, per-job timeouts, and worker concurrency control. This is a stateful background system (a Redis-backed queue plus a worker process), not a request-response handler. It does not survive the Next-only model.
- **WebSocket / SSE trigger.** The live status board is pushed from the server over a long-lived SSE stream as probe results land. A Next route handler cannot own a persistent fan-out channel across all dashboard clients tied to a background worker's output.
- **Heavy auth trigger.** The dashboard is private (the owner's monitors), the public status page is unauthenticated, and alert webhooks carry signed payloads — a real auth boundary with two distinct access tiers and machine-verifiable outbound signatures, not a single login form.
- **Heavy domain logic trigger.** The incident state machine (N consecutive failures opens an incident; M consecutive successes closes it; degraded vs down classification; flap suppression), uptime-percentage computation over selectable windows from a raw check-result stream, and alert de-duplication / delivery are genuine domain logic that benefits from being unit-tested in isolation from any UI. This is exactly the "test in isolation from the UI" trigger.

`web-only` is rejected outright: the scheduler alone forecloses it, and three more triggers reinforce the call. There is no honest way to build a real uptime monitor inside Next route handlers.

## Backend choice — NestJS

**Selected: NestJS (Node 22 LTS) + Drizzle ORM + PostgreSQL + BullMQ + Redis + Zod + better-auth.**

Rationale serves the two masters from `docs/conventions.md` § 11:

(a) **Fits this project.** Pulse has the largest and most layered server surface of any portfolio project to date: a scheduler module (BullMQ producer that registers / updates / removes repeatable jobs as monitors change), a worker / processor module (the probe runner with retry + timeout + concurrency), an incidents module (the state machine consuming check results), an alerts module (webhook + email delivery with signing and de-dup), a monitors CRUD module, an SSE / events module (the live channel), an auth module (better-auth integration), and a public-status module (the unauthenticated read surface). This is precisely the shape NestJS is opinionated for: dependency-injected modules with clear boundaries, lifecycle hooks (`OnModuleInit` to register repeatable jobs on boot, `OnModuleDestroy` for graceful queue drain), guards for the auth boundary, interceptors for request logging / rate limiting, and `@nestjs/bullmq` + `@nestjs/schedule` first-party integrations that make the queue and any cron sweeps idiomatic rather than hand-wired. The enterprise-patterns reputation NestJS carries is exactly what reads as credible to viewer 1 on a systems-engineering product. A thinner framework (Hono / Elysia) would force us to hand-roll module wiring that NestJS gives for free, and the wiring is not the showcase — the systems behaviour is.

(b) **Advances portfolio backend variance — this is the load-bearing portfolio axis.** Tape (slot 1) committed **Elysia on Bun** (Bun-native, max-throughput). Meld (slot 2) committed **Hono on Node** (multi-runtime, edge-ready). Pulse (slot 4) commits **NestJS on Node** — opinionated, modular, DI-and-decorator-heavy enterprise patterns: a third, deliberately _different in philosophy_ cutting-edge backend. This fills the exact NestJS slot the composition tracker reserved (root `PROGRESS.md` § tracker) and takes the portfolio to **three distinct backends across three api-heavy projects**, comfortably clearing the `docs/conventions.md` § 12 target (2–3 api-heavy, ≥ 2 backends — ideally three). After Pulse, the portfolio's backend-variance story is complete: thin-and-fast (Elysia/Bun), multi-runtime-edge (Hono), and opinionated-enterprise (NestJS) are all represented.

(c) **Runtime: Node 22 LTS.** NestJS targets Node first; BullMQ, `ioredis`, Drizzle (`postgres-js` / `node-postgres`), and better-auth are all best-paved on Node. No Bun deviation here — the engineering budget goes into the scheduler / real-time / incident systems, not runtime-compat debugging. Pin in `.nvmrc`.

The architect ratifies the deeper queue / scheduler design, the real-time contract, the incident state machine, and the deploy topology (Redis + Postgres on Fly) in follow-up ADRs at the start of implement — see "Deferred to architect" below.

## Real-time channel — SSE (Server-Sent Events)

**Selected: SSE over a single long-lived `GET /api/stream` endpoint. WebSocket is rejected for v1.**

The live channel is **strictly server → client**: probe results, status changes, incident open/close, and alert-fired notifications flow one way to every connected dashboard. The client never needs to push over the same channel — all client-originated actions (create monitor, trigger demo incident) are ordinary authenticated HTTP requests. This is the textbook SSE shape:

- **One-directional fan-out is SSE's exact use case.** WebSocket buys bidirectional framing we would never use, at the cost of a heavier protocol, a separate upgrade path, and more moving parts to reason about under a reverse proxy.
- **SSE is plain HTTP** — it traverses proxies, CDNs, and the Fly edge cleanly, carries auth via the normal cookie / header path (no separate WS auth handshake), and the browser `EventSource` API gives automatic reconnect with `Last-Event-ID` resume for free. NestJS supports it idiomatically via an `@Sse()` controller route returning an RxJS `Observable<MessageEvent>`, which composes naturally with a server-side event subject the worker publishes into.
- **The DevTools tell is a feature.** Viewer 1 opening the Network tab sees one tidy `text/event-stream` connection with named events streaming in — unambiguous proof the board is genuinely pushed, not polled. A WebSocket frame inspector would show the same liveness but with more ceremony; SSE reads as the deliberate, correct-tool-for-the-job choice, which is itself a senior signal.
- **Scale fit.** A portfolio demo has a bounded concurrent-viewer count. SSE's one-connection-per-client cost is a non-issue at this scale, and the multi-instance fan-out concern (one worker, many web replicas) is handled with a Redis pub/sub bridge the architect pins in the real-time-contract ADR (worker publishes to a Redis channel; every web replica's SSE endpoint subscribes and relays to its connected clients). v1 deploys single-instance, so the bridge is designed-in but exercised lightly.

WebSocket would be the right call if the client needed to push high-frequency state over the same socket (meld's cursor / awareness shape) — Pulse has no such need. Choosing SSE deliberately, and being able to articulate _why not WebSocket_, is the stronger signal. The architect ratifies the event envelope, the named-event vocabulary, the `Last-Event-ID` resume semantics, and the Redis pub/sub fan-out bridge in the real-time-contract ADR.

## Charting — uPlot for live time series, lightweight SVG for the rest

**Proposed (architect ratifies): uPlot for the live-updating response-time series and the monitor-detail charts; hand-rolled SVG / CSS for the sparklines, the uptime timeline/heatmap bars, and the status dots.**

The data-viz is a first-class success criterion (viewer 1 judges "crisp data-viz"), and the live board updates time series in real time, so the charting pick is weighted toward update performance and crispness over breadth of chart types:

- **uPlot** — the fastest mainstream time-series chart library, tiny (~40 KB), purpose-built for streaming numeric series with imperative `setData` updates that do not thrash React. It is the correct tool for the monitor-detail response-time chart (24h / 7d / 30d windows, thousands of points) and for any live-updating chart that must repaint on every probe without dropping frames. It is canvas-based, so it stays crisp and cheap under frequent updates. Crisp + performant is exactly the brief's bar.
- **Recharts / Tremor / visx rejected as the primary.** Recharts / Tremor (SVG, React-reconciled per point) are pleasant for static dashboards but re-render the whole chart subtree on data change — wrong for a board where many sparklines update every few seconds. visx is powerful but low-level enough that we would rebuild much of what uPlot gives for free. Tremor also leans into its own visual language, which would fight the sovereign-token design.
- **Sparklines, uptime bars, status dots = hand-rolled SVG / CSS.** These are small, numerous, and bespoke to the design language. A tiny inline-SVG sparkline (a single `<path>` from N points) and a flex row of `<div>` / `<rect>` uptime bars (green / amber / red, the classic Statuspage history bar) are cheaper, fully token-styleable, and animate via the project's single animation library without dragging a chart lib into every card. This keeps the per-card cost trivial on a board of many cards.

The architect ratifies the uPlot integration boundary (an imperative `'use client'` wrapper that owns the canvas and is fed by a TanStack Query subscription / the SSE stream, kept off the React render path) and confirms the SVG-sparkline approach holds under the live-update budget.

## Animation stack

**Motion (ex-Framer Motion)** as the single animation library, per `docs/conventions.md` § 15. No second library — and crucially, the live-updating charts do **not** go through Motion (uPlot owns its own canvas repaint; per-point chart animation through Motion would be a frame-budget disaster, the same class of mistake meld's "Canvas2D is not Motion" rule guards against).

Motion is scoped to clean-SaaS micro-interactions and live-status state transitions — exactly the state-driven register Motion is the default for:

- **Status-dot transitions.** A monitor's dot animating green → amber → red (and back) on a status change: a brief scale-pulse + color crossfade via Motion, ~200–320 ms, Linear-register easing. Driven by React state derived from the SSE stream, not a per-frame loop.
- **Incident row enter / exit.** When an incident opens, its row animates in at the top of the board via `AnimatePresence` (~240 ms ease-out); on close it settles out / collapses into history. The dramatic beat of the wow moment is a Motion `AnimatePresence` transition.
- **Card "fresh result" pulse.** A subtle highlight / ring pulse on a card when a new probe result lands, so the viewer's eye catches _which_ card just updated — the "this feels alive" Linear-changelog detail.
- **Alert-fired toast / "last checked" tick.** Toast enter / exit and the ticking "Ns ago" affordance use Motion's defaults (shadcn wires them).
- **Page / dialog / sheet transitions.** Create-monitor dialog, monitor-detail navigation, theme crossfade — shadcn + Motion defaults, `prefers-reduced-motion` respected (status pulses and incident-row motion collapse to instant state changes under reduced motion; the board stays fully functional and legible).

Not used for: the uPlot charts (uPlot owns repaint), the SVG sparklines (CSS transition on the `<path>` is enough), or any scroll choreography (there is none — this is a dashboard, not a scroll-story). GSAP and R3F are rejected: no scroll timeline, no SVG-path choreography, no 3D.

## Success criteria

All measurable, all gate v1 ship:

- **The probes are real.** A reviewer can add a monitor pointing at any public URL and watch real check results (status code, response time, up/down/degraded) accrue on its real interval. No mocked probe results for live monitors. (Seeded history for first-load richness is clearly separated and documented as seed, with live probes running forward from `now`.)
- **The live board is genuinely pushed.** DevTools shows exactly one `text/event-stream` connection on `/api/stream`; no polling XHR loop drives the board. Probe results appear on the board within ~1 s of the worker recording them (local), without a reload.
- **The wow moment is reproducible on demand.** The "Trigger demo incident" affordance reliably plays the full open-incident → alert-fired → recover → auto-close arc in ≤ 45 s while the viewer watches, every time, on the deployed demo.
- **Incident correctness.** The incident state machine is unit-tested: N consecutive failures opens exactly one incident (not N), intervening successes reset the counter, M consecutive successes closes it, flapping does not spawn duplicate incidents, and degraded vs down classification is correct. Uptime % over 24h / 7d / 30d is computed correctly from the raw result stream (unit-tested against fixtures with known expected percentages).
- **Alerting works for real on at least one channel.** Incident open / close fires a real outbound webhook (Slack / Discord incoming-webhook format is the concrete target) with a signed payload; delivery is verifiable. Any channel that is mocked (e.g., email if SMTP is not wired) is documented honestly in the README as mocked, never presented as live.
- **Public status page — Lighthouse ≥ 95 in all four categories** (Performance, Accessibility, Best Practices, SEO) on the deployed URL. This is the SEO-bearing surface: meta tags, OG image, JSON-LD (`WebSite` + a status-appropriate structured type), `sitemap.xml`, `robots.txt`. SSR / static-friendly, no client-only data dependency for first paint.
- **Auth boundary holds.** The dashboard and all monitor-mutating endpoints require auth (better-auth session); the public status page and its read endpoints are unauthenticated and expose only the monitors explicitly marked public. A reviewer cannot reach private monitor data or mutate anything without a session. Verified by an E2E test that asserts unauthenticated access is rejected.
- **Security.** Rate limiting on the public status-page read endpoints and on the auth endpoints; CSP headers (strict, no `unsafe-eval` — the meld / razors-edge lesson; verify the dashboard + uPlot run clean under it via a prod build, not `next dev`); all input validated by shared Zod schemas; outbound webhook payloads signed; `.env.example` committed, never `.env`; SSRF guard on the probe target (the prober must not be usable to hit internal / metadata addresses — block private / link-local / loopback ranges, documented).
- **Theming.** Light + dark via CSS variables + `next-themes`, respecting `prefers-color-scheme`. **Sovereign design tokens** — Pulse is a fresh clean-modern-SaaS identity; NO token reuse from tape / meld / razors-edge (`docs/conventions.md` § 14). Both themes are intentional and reviewed in their own right (the dashboard is dark-leaning premium; the public status page must read calm and trustworthy in both).
- **Responsive.** Renders correctly from 320 px upward, mobile-first. The dashboard board reflows to a single column on narrow viewports; the public status page is fully usable on a phone (it is the most-shared-to-mobile surface). Charts degrade gracefully (the response-time chart stays legible or collapses to a summary stat on the narrowest viewport).
- **Accessibility.** WCAG 2.2 AA. Full keyboard navigation of the dashboard, the create-monitor form, and the public status page. Status is never conveyed by color alone — every status dot carries a text label / icon and an accessible name (a red dot also says "Down"). Contrast ≥ 4.5:1. `prefers-reduced-motion` collapses status pulses and incident-row motion to instant state changes. Live updates are announced to assistive tech via an `aria-live="polite"` region (e.g., "monitor api.example.com is now down") without flooding it.

## Data model sketch

Ratified / refined by the architect in ADR-005. Indicative, not final.

- **users / sessions** — better-auth's tables (the owner; v1 is effectively single-tenant but the schema does not preclude multi-tenant). Monitors belong to a user.
- **monitors** — `id`, `user_id` (FK), `name`, `target_url`, `method` (HTTP/HTTPS; TCP/ping stretch), `interval_seconds`, `timeout_ms`, `expected_status` (or range), `expected_keyword` (nullable), `degraded_threshold_ms` (slow-but-up boundary), `is_public` (boolean — shows on the public status page), `is_paused`, `created_at`, `updated_at`. The scheduler keys a repeatable BullMQ job off `id` + `interval_seconds`.
- **check_results** — `id`, `monitor_id` (FK), `checked_at` (timestamptz, indexed), `status` (`up` | `down` | `degraded`), `status_code` (nullable), `response_time_ms` (nullable), `error` (nullable). High-volume time-series table; ADR-005 pins retention / down-sampling. Indexed on `(monitor_id, checked_at)` for the uptime-window + recent-checks reads.
- **incidents** — `id`, `monitor_id` (FK), `status` (`open` | `resolved`), `severity` (`degraded` | `down`), `started_at`, `resolved_at` (nullable), `cause` (the failing condition snapshot). One open incident per monitor per outage (the state-machine invariant).
- **alert_channels** — `id`, `user_id` (FK), `type` (`webhook` | `email`), `target` (webhook URL / email address), `secret` (for webhook signing), `is_enabled`.
- **alert_deliveries** — `id`, `incident_id` (FK), `alert_channel_id` (FK), `transition` (`open` | `close`), `delivered_at`, `status` (`sent` | `failed`), `response_code` (nullable). De-dup key: one delivery per (incident, channel, transition).

## Out of scope (v1)

Locked. v2 candidates only.

- **Multi-tenant SaaS surfaces** — teams, org membership, per-seat billing, roles. v1 is single-owner (the schema does not preclude it; the UI / flows do not build it).
- **TCP / ping / DNS / SSL-expiry / cron-style probe types** — v1 is HTTP/HTTPS only. TCP / ping is a documented stretch the brief allowed; it ships only if Phase 2 time-boxes cover it, otherwise it is a v2 note.
- **Email alerting as a guaranteed-live channel** — the webhook channel is the v1 real alert. Email is wired only if SMTP is cleanly available on the demo host; otherwise it is documented as mocked, not presented as live. SMS / PagerDuty / OpsGenie are v2.
- **On-call schedules, escalation policies, alert routing rules** — v1 fires every enabled channel on every transition. No escalation / routing.
- **Multiple public status pages / custom domains / per-page branding** — v1 ships one public status surface.
- **Multi-region probing** — v1 probes from one location (the worker's region). Geo-distributed probes are a v2 systems-engineering extension worth noting in the README.
- **Maintenance windows, scheduled-maintenance banners, subscriber notifications** (email/RSS subscribe-to-status) — Statuspage-tier features deferred to v2.
- **Historical down-sampling / data-warehouse rollups beyond the ADR-005 retention call** — v1 keeps a bounded raw-result window sufficient for the 30-day uptime view; long-horizon analytics is v2.

- **ADR-005** — data model + Drizzle posture (schema ratification, time-series indexing, check_results retention / down-sampling, worker connection strategy).
- **ADR-006** — deploy topology (Postgres + Redis + API/worker + web on Fly; the demo-incident mechanism; seed-vs-live coexistence).
