# pulse — Agent Notes

> Append-only cross-agent context. Every subagent reads on start, appends on end.

## Gotchas

- **SSRF guard is a hard gate — resolve-then-pin, run twice (ADR-002).** The prober must NOT do a naive `fetch(url)`. Required: (1) scheme allowlist `http`/`https` only; (2) reject credentialed URLs (`user:pass@host`); (3) DNS-resolve, validate EVERY resolved A/AAAA against the denylist, then connect to the validated IP (pin via undici custom lookup/dispatcher, or re-resolve at connect + every redirect hop) to defeat DNS rebinding; (4) `redirect: 'manual'`, follow up to 5 hops re-running the guard on each hop (never `redirect: 'follow'`); (5) 512 KB body cap. Denylist: IPv4 `0.0.0.0/8`, `10/8`, `100.64/10`, `127/8`, `169.254/16` (incl. `169.254.169.254` cloud metadata), `172.16/12`, `192.0.0/24`, `192.168/16`, `198.18/15`, multicast/reserved; IPv6 `::1`, `fc00::/7`, `fe80::/10`, and IPv4-mapped `::ffff:0:0/96` decoded + re-checked. Runs at BOTH monitor-create validation AND probe execution (DNS rebinds between them — execution is authoritative). Pure fn `assertProbeTargetAllowed(url, resolvedIps)` in `server/src/probe/ssrf-guard.ts`, unit-tested (Task 8.1). Do NOT ship the prober without it.
- **Worker -> SSE Redis bridge: the worker and the SSE server are SEPARATE processes (ADR-003 + ADR-006), so the worker cannot push into the API's in-memory RxJS subject directly.** The worker publishes every domain event as JSON to the Redis channel `pulse:events`; each API replica runs an `EventsBridgeService` (`OnModuleInit`) holding a DEDICATED ioredis subscriber connection (a subscriber connection CANNOT issue normal commands — do not reuse the BullMQ/app connection), validates with `sseEventSchema`, pushes into an in-process RxJS subject, and the two `@Sse()` routes filter that subject by scope. If you try to emit from the worker straight into an in-memory subject the API holds, nothing reaches the browser — the bridge IS the plumbing. Pub/Sub is fire-and-forget: a missed event during a reconnect gap is reconciled by a TanStack Query REST refetch on `EventSource` open (and a 256-event per-scope ring buffer serves `Last-Event-ID` for short gaps), NOT replayed from history. Postgres is the source of truth.
- **BullMQ repeatable-job reconciliation — the churn trap (ADR-002).** One repeatable job per monitor with a STABLE scheduler id `probe:<monitorId>` and `every = interval*1000`; payload only `{ monitorId }` (worker re-reads the row at run time). On create/edit/resume: remove-by-id THEN add. On pause/delete: remove only. On boot (`OnModuleInit`): reconcile against the monitors table as source of truth — add missing, sweep orphaned/paused. Do NOT key the job by `monitorId+interval` and do NOT rely on BullMQ's implicit repeat-key dedupe: changing `every` mints a new internal key, the old one keeps firing, and you accumulate ghost schedules that double-probe. The deterministic id is what makes remove idempotent and the orphan sweep possible.
- **A failing endpoint is a SUCCESSFUL BullMQ job that records a `down` result (ADR-002).** BullMQ `attempts`/`backoff` are for INFRASTRUCTURE faults only (e.g. cannot reach Postgres to write the row), never for "the target was down". A down endpoint must never be retried-as-if-broken (it would inflate the result count and corrupt uptime). Exactly one `check_results` row per probe occurrence; the write is the last step and is idempotent against a reclaimed-then-retried occurrence.
- **check_results retention is PINNED (ADR-005): 35 days raw + hourly rollups.** Raw `check_results` retained 35 days (covers the 30d uptime view with margin); `check_rollups_hourly` (`avg`/`p95`/`min`/`max` + up/degraded/down/unknown counts, PK `(monitor_id, bucket_start)`) retained 400 days. A BullMQ repeatable ROLLUP job runs every 5 min (idempotent upsert), a GC sweep runs hourly (batched DELETE). Both register in the worker's `OnModuleInit` alongside the probe schedules. Uptime reads: 24h from raw, 7d/30d from rollups + a live-incident top-up. Two DB-level correctness constraints are NOT optional: a PARTIAL UNIQUE index on `incidents(monitor_id) WHERE status='open'` (single-open-incident invariant) and a UNIQUE on `alert_deliveries(incident_id, alert_channel_id, transition)` (alert de-dup). Do not enforce these only in app code.
- **Incident state machine is a PURE reducer (ADR-004).** `reduce(state, checkResult) -> { state, effects }`, no IO inside — the engine persists rows + emits `incident.*` events from the returned effects. Defaults N=3 fail -> open exactly one incident, M=2 success -> close; the N/M debounce IS the flap suppression; degraded escalates to down on the open incident, never opens a second. Uptime: degraded counts 50% (`DEGRADED_UPTIME_WEIGHT=0.5`), a result's coverage is capped at the monitor interval, and a gap > `2*interval` is `unknown` and EXCLUDED from numerator + denominator (so restarts/pauses do not read as outages). This is the heavily-unit-tested surface (Task 8.1).
- **Alert dispatch: ONE interface, webhook REAL / email MOCKED (owner-confirmed, ADR-005).** `AlertDispatcher.dispatch(channel, incident, transition)`; the webhook impl signs the JSON body with HMAC-SHA256 (`X-Pulse-Signature: sha256=<hex>` + `X-Pulse-Timestamp`, Slack/Discord-incoming-webhook shape) and is genuinely sent; the email impl satisfies the same interface but does NOT open SMTP — it records an `alert_deliveries` row + logs the rendered message, and MUST be documented in the README as mocked (no SMTP dependency on the demo host). Never present email as live. Both go through the same de-dup unique constraint. A real SMTP transport can drop in later without touching the incident engine.
- **Demo-incident mechanism = owned flaky endpoint + Redis flag (ADR-006).** `GET /demo/flaky` on `pulse-api`, health toggled by a REDIS-backed flag (so the web process that serves the toggle and the worker process that probes both agree). `POST /demo/trigger` (authenticated) flips it to "failing" for ~40s then auto-recovers; the seeded demo monitor points at `https://<pulse-api-host>/demo/flaky` and runs the REAL probe -> incident -> webhook -> recover -> close arc. Chosen over an external failing target because it stays inside the SSRF allowlist (own public host) and needs no third-party dependency. Do NOT fake the arc — it must go through the genuine pipeline.
- **Frozen-now / seed discipline for demo data (ADR-006, reinforces the cross-cutting note).** Seed runs ONCE at deploy, idempotent on a seed-marker row, `faker.seed(<n>)` + a frozen `now`, writing historical `check_results` + `check_rollups_hourly` + closed `incidents` UP TO `now`. Live probes run forward from `now`. The boundary (history seeded, everything from now real) is documented in the README and is the credibility line. Tests/Lighthouse share the same frozen `now`; tests that assert on "live" behaviour drive the deterministic `POST /demo/trigger`, never wait on organic results (the live probes are intentionally non-deterministic). For CSP: bake the seed to a static module so faker is build-only (razors-edge fix) and set `z.config({ jitless: true })` as a global early side-effect — the SSE/Zod-envelope path validates events at runtime, so jitless Zod matters here too.
- **Deploy topology PINNED (ADR-006): split web/worker.** `pulse-api` = two Fly `[processes]` from one image: `web` (HTTP + the two `@Sse()` routes + better-auth) and `worker` (BullMQ probe + rollup + GC). Both `min_machines_running=1` / `auto_stop=off` so the wow moment never cold-starts (tape precedent) and probes keep running. `pulse-web` = separate Next app proxying the API (meld precedent incl. the transport-encoding-header strip in the catch-all). Upstash Redis + Fly Postgres, single region `fra`. Two small `postgres-js` pools (API ~10, worker ~5) — watch `max_connections`. Secrets: `DATABASE_URL`, `REDIS_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `WEBHOOK_SIGNING_KEY`, `DEMO_TRIGGER_ENABLED`, the web->api base URL/internal token. Multi-region probing is explicitly v2.

## Decisions to revisit

These are assumptions the planner left implicit or under-determined in PLAN.md / ADR-001 that downstream agents (especially the architect in Phase 0) should actively challenge rather than inherit:

- **Single process vs split web/worker for NestJS.** PLAN.md and ADR-001 speak of "the NestJS API/worker" as potentially one process or two (the HTTP/SSE API + the BullMQ worker). The architect pins this in ADR-006 (deploy topology) and it interacts with ADR-002 (does the worker run in-process with `OnModuleInit` job registration, or as a separate Nest app instance?). A split worker is more production-faithful and a stronger signal, but more deploy surface. Weigh against the demo's cost / simplicity budget. The Redis pub/sub bridge (ADR-003) is what makes a split clean — the worker publishes results to Redis, the API's SSE endpoint subscribes — so the real-time design and the process-topology decision are coupled; decide them together.
- **check_results retention / down-sampling is unpinned.** The raw check-result table is high-volume (one row per monitor per interval — a 60 s monitor is 1440 rows/day). A long-running demo needs a bounded retention window (enough for the 30-day uptime view) and possibly a rollup table for the older windows. ADR-005 must pin this or the demo's Postgres grows unbounded. Do not ship without a retention call.
- **Demo-incident mechanism is not yet chosen.** The wow moment needs the open→alert→recover→close arc reproducible on demand on the deployed demo. PLAN.md offers two shapes: (a) an owned always-on "flaky" endpoint Pulse controls that can be told to fail, or (b) a toggle that points a demo monitor at a known-failing target. The architect picks in ADR-006. Constraint: it must be safe (no SSRF bypass, no abuse vector) and must not depend on an organic failure happening while a recruiter watches.
- **SSRF guard scope.** The prober is an outbound-HTTP primitive; a malicious monitor target could point at internal / metadata / loopback / link-local addresses. The guard must run at BOTH monitor-create validation and probe-execution time (DNS can rebind between the two). The architect / backend-engineer must decide the exact blocked ranges (RFC 1918 private, 127.0.0.0/8 loopback, 169.254.0.0/16 link-local incl. 169.254.169.254 cloud metadata, ::1 / fc00::/7 / fe80::/10 for IPv6) and whether to resolve-then-validate-then-connect-to-the-resolved-IP to defeat DNS rebinding. Unit-tested (PLAN.md Task 8.1). Do not ship the prober without it.
- **Email alert channel: live or mocked?** The webhook channel (Slack/Discord incoming-webhook with a signed payload) is the guaranteed-real v1 alert. Email is wired only if SMTP is cleanly available on the demo host. If it is mocked, it MUST be documented honestly as mocked in the README (per the brief) — never presented as live. Decide during Phase 5.2; flag the call here.
- **Multi-tenant schema vs single-owner UI.** v1 is effectively single-owner (the owner's monitors). The data model carries `user_id` FKs so it does not preclude multi-tenant, but the UI / flows do not build teams / roles / billing (out of scope v1). Do not let scope creep pull multi-tenant surfaces into v1; equally, do not hardcode single-tenant assumptions into the schema that would force a rewrite for v2.
- **TCP / ping probe types are a documented stretch, not a commitment.** v1 is HTTP/HTTPS only. TCP/ping ships only if Phase 2 time-boxes cover it; otherwise it is a v2 note. Do not let it block the HTTP probe path landing.
- **uPlot React integration boundary.** uPlot is imperative and canvas-based; it must live in a `'use client'` wrapper that owns its canvas and is fed off the React render path (imperative `setData` from a TanStack Query window fetch + live appends from the SSE stream). The frontend-engineer must NOT reconcile uPlot through React state per point. Confirm CSP-clean under a prod build (not `next dev`) — same discipline as the CSP notes below.

## Cross-cutting concerns

- **Sovereign design tokens — NO reuse from tape, meld, or razors-edge** (`docs/conventions.md` § 14, ADR-001). Pulse is a fresh clean-modern-SaaS identity (Linear / Vercel / Planetscale register) — a dark-leaning premium dashboard and a calm, trustworthy public-status surface, both intentional in light and dark. Do NOT import tape's slate/cyan, meld's warm-paper/OKLCH-user palette, or razors-edge's brass-on-near-black. If anyone is tempted to shortcut by copying another project's tokens, the answer is "build Pulse's palette from scratch and document it in this file at the design-system task".
- **Dark + light both intentional** (CLAUDE.md § 4). Ship both via CSS variables + `next-themes`, respect `prefers-color-scheme`, no FOUC. The light theme is reviewed in its own right by the designer-critic, not graded as an afterthought.
- **The probes are REAL — that is the credibility of the showcase.** Live monitors get real HTTP check results (status / response time / status code), never mocked results. Seed data (faker, `faker.seed(<n>)`, deterministic, frozen-`now` for the historical windows) makes first load rich, but it is cleanly separated from live-probe data and documented as seed; live probes run forward from `now`. Do not blur this line — a faked "live" result on a real monitor would gut the whole point.
- **The real-time channel is genuinely pushed, not polled.** DevTools must show exactly one `text/event-stream` SSE connection on `/api/stream`; no polling XHR loop drives the board. This is a success criterion and the proof viewer 1 looks for. Do not "simplify" the board to a TanStack Query polling interval — the SSE push IS the showcase.
- **The streaming charts are NOT Motion.** uPlot owns its canvas repaint; the SVG sparklines use a CSS transition on the `<path>`. Motion is for React-state micro-interactions (status-dot crossfade/pulse, incident-row `AnimatePresence`, fresh-result card pulse, toast, theme crossfade) only. Per-point chart animation through Motion is a frame-budget disaster — the same class of mistake meld's "Canvas2D is not Motion" rule guards against. Do not propose a Motion-driven live chart in review; it has been considered and rejected (ADR-001).
- **CSP must be strict and must NOT rely on `unsafe-eval`** — and the dashboard + uPlot + Motion must run clean under it. This is the direct meld / razors-edge lesson: a strict CSP forbids `unsafe-eval`, and `next dev` cannot run under it, so verify any browser capture / CSP claim against a `next build && next start` PROD build, NOT `next dev`. Watch for eval sources that sneak in via faker (bake seed data to a static module so faker is build-only — razors-edge's fix) and via Zod 4's JIT probe (`z.config({ jitless: true })` as a global early side-effect — razors-edge's fix). Confirm uPlot does not need `unsafe-eval` (it should not — it is plain canvas).
- **Performance budget is sacred on the public status page — Lighthouse ≥ 95 in all four categories** (the SEO-bearing surface). It must be SSR / static-friendly with no client-only data dependency for first paint. The dashboard is auth-gated and not the Lighthouse target, but it must still feel fast (the live board updates must not jank).
- **Auth boundary is real and E2E-tested.** Dashboard + all monitor-mutating endpoints require a better-auth session; the public status page + its read endpoints are unauthenticated and expose ONLY monitors marked public. A reviewer must not be able to reach private monitor data or mutate anything without a session. Rate-limit the auth endpoints and the public read endpoints.
- **Security posture.** SSRF guard on the prober (see Decisions to revisit), signed outbound webhook payloads, all input validated by shared Zod schemas (`src/lib/schemas/`, the single source of truth imported by both `server/` and `web/` per § 5), CSP headers, rate limiting on public + auth endpoints, `.env.example` committed (never `.env`).
- **Accessibility: status is never color-alone.** Every status dot carries a text label / icon and an accessible name (a red dot also says "Down"). `prefers-reduced-motion` collapses status pulses + incident-row motion to instant state changes (the board stays fully functional). Live updates announce to an `aria-live="polite"` region without flooding it. Full keyboard nav of the dashboard, the create-monitor form, and the public page. WCAG 2.2 AA, contrast ≥ 4.5:1.
- **Determinism for tests + screenshots.** `faker.seed(<n>)` at the top of every mock/seed factory (§ 6) and a frozen `now` for the seeded historical windows, shared by the seed generator, the UI, and the Playwright/Lighthouse runs — same discipline as tape/meld/razors-edge. The live probes are intentionally non-deterministic (they are real), so tests that assert on live behaviour must drive the deterministic "Trigger demo incident" mechanism rather than waiting on organic results.
- **English-only in all files** (source, comments, ADRs, README, UI copy). Polish is for owner chat only (CLAUDE.md § 2).
- **No emojis anywhere** (source, commits, README, UI). Icons from `lucide-react` / `phosphor-icons` / `heroicons` (CLAUDE.md § 2).
- **Port hygiene.** Pick non-colliding dev ports and document them on scaffold: app dev server in the 3080+ range (tape 3000-3002 / 3055-3061, razors-edge 3070 taken), Postgres 5437+ (Mila 5434 / tape 5435 / meld 5436 taken), Redis a non-colliding port. Record the final picks here in the scaffold task.
- **Node 22 LTS pin — `.nvmrc` committed.** Backend + tooling on Node 22. NestJS / BullMQ / ioredis / Drizzle / better-auth are best-paved on Node; do not bump to Bun during implement.

## Frontend scaffold (Task 3.2, 2026-06-03, frontend-engineer)

- **Dev/prod port: 3081** (`pulse-web`, `next dev -p 3081` / `next start -p 3081`). Non-colliding: tape 3000-3002/3055-3061, razors-edge 3070, backend `pulse-api` reserves 3080 — web takes 3081. The board's SSE target is a separate origin in local dev (`NEXT_PUBLIC_SSE_URL` → the API port) but collapses to same-origin behind the `pulse-web` reverse proxy in the deployed topology (ADR-006), which is why CSP `connect-src 'self'` is sufficient.
- **Workspace shape.** `pulse-web` is picked up by the root `projects/*/web` glob (no workspace-yaml change needed). Created a project-level `projects/pulse/tsconfig.base.json` (byte-copy of the root base), and `web/tsconfig.json` extends `../tsconfig.base.json` — mirroring meld/razors-edge (each project owns its base copy; conventions §13 Trigger A extraction has not fired, this is just the established per-project mirror, not a shared-config extraction).
- **PRODUCTION CSP string (verified against `next build && next start`, the authoritative path — NOT `next dev`).** Exact value emitted on every route:
  ```
  default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; connect-src 'self'; img-src 'self' data:; font-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'
  ```
  Plus `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, `Strict-Transport-Security: max-age=63072000; includeSubDomains`. **NO `unsafe-eval`** — the load-bearing guarantee. `'unsafe-inline'` (scripts + styles) is documented v1.1 nonce-hardening debt (Next 15 emits unhashed inline hydration/theme-flash scripts; Tailwind v4 + Motion write inline styles). `connect-src 'self'` covers fetch + the `EventSource` SSE stream (single-origin proxy). Asserted by `src/__tests__/next-config-headers.test.ts` (mirrors meld/razors-edge). **The meld dev-vs-prod CSP lesson holds and was respected:** `next dev` serves the same CSP _header_ but its React-Refresh HMR uses runtime `eval` that a no-`unsafe-eval` policy would flag in the browser — that is a dev-only HMR artifact, so the authoritative zero-violation claim is the PROD build, verified here. Zod's JIT `new Function` probe is pre-empted globally via `z.config({ jitless: true })` imported as a side-effect at the layout root (razors-edge fix), which matters here because the Phase 3 live board validates SSE events at runtime against the shared Zod envelope.
- **Sovereign clean-SaaS token set (NO reuse from tape/meld/razors-edge — §14, ADR-001).** Light-canonical + intentional dark, both in `globals.css` (`:root` light, `.dark` overrides, `next-themes` `attribute="class"`). - **GOTCHA — dual-web-machine migrate thundering herd.** BOTH `web` machines run `RUN_MIGRATIONS=1` + `RUN_SEED=1` on boot.
