- **PRE-EXISTING BUG observed during Task 1.5f live verification — `ensureRollingPartitions` fails on boot with `42P18 could not determine data type of parameter $1`.** The `CREATE TABLE IF NOT EXISTS ticks_yYYYYmMM PARTITION OF ticks FOR VALUES FROM ($1) TO ($2)` statement passes the month bounds as bound parameters, which Postgres rejects in a `FOR VALUES` clause (partition bounds must be literals, not parameters). This throws at `retentionScheduler.start()` and again on every `tickWriter` partition-missing recovery — meaning the `ticks` table never gets a partition and tick archival silently fails under the offline pipeline. **This is NOT introduced by Task 1.5f** (cell-writer touches only `footprint_cells`, which is unpartitioned) — it surfaced because Task 1.5f is the first task to run the full offline pipeline against a real DB long enough to hit the partition path. The boot path tolerates it (logs + continues), so the live board + cell persistence are unaffected, but **the `ticks` archive / replay-ticks endpoint is broken on a fresh DB until this is fixed.** Fix: interpolate the bounds as SQL literals in `src/db/partitions.ts` (e.g. `sql.raw` / template literal with the numeric bounds) instead of bound params. Flagged for backend-engineer / reviewer as a Task 1.2a/1.2b follow-up — out of scope for 1.5f (cells), but it blocks the tick half of replay.
- **`footprint_cells.session_id` on the offline synth path (Task 1.5f).** `footprint_cells.session_id` is a NOT NULL FK to `sessions.id`. The pipeline does NOT stamp `ended_at` on this session (the Binance ingestor owns that for its own session; the synth session row stays open with `ended_at = null`, which the replay query does not filter on). Verified live: the offline run wrote cells under a fresh `sessions` row (`source = 'binance-futures'` default label, symbol `BTCUSDT-PERP`).

## Decisions to revisit

- **ADR-005 implementation note — `footprint_cells` WRITE lives in the Elysia `WorkerPipeline`, NOT in the Rust worker (Task 1.5f, backend-engineer, 2026-06-04). FLAGGED FOR MAIN-THREAD RATIFICATION as a micro-ADR.** ADR-005 § "Decision" says "Cells written by the Rust worker on bar-close, one transaction per bar". The implementation places that write in the Elysia control plane (`src/lib/ingest/cell-writer.ts`, driven from `pipeline.ts`'s `#onCellClose`), a deliberate deviation from the ADR's LETTER that HONOURS its INTENT ("closed-bar history in Postgres is the durable source of truth"). Three reasons drove option B over the literal option A: (1) the `WorkerPipeline` already receives every `cell.close` frame (it promotes them to the public WS envelope) — the data is already in Elysia, no new wire; (2) the TS-side DB layer (`getDb()`, the Drizzle `footprintCells` schema) and the write-discipline precedent (`tickWriter`'s enqueue + coalesced flush + tolerate-transient-errors) already live in Elysia — mirroring them keeps ONE write discipline in the codebase; (3) keeping the worker pure-compute (no Postgres client, no `DATABASE_URL`, no second connection-management surface in Rust) is the cleaner separation and matches how `ticks` are already written (Elysia direct, ADR-005 § "Write path"). The `cell.close` frame already carries the absolute totals, so Elysia has everything it needs to write the authoritative row. **Net effect on ADR-005's invariants: unchanged** — closed-bar history is still the durable source of truth in Postgres; only WHERE the INSERT executes moved (worker → Elysia), not WHAT is written or its atomicity. **Main thread: ratify by appending a one-paragraph ADR-005 addendum (or a superseding micro-ADR-005a), or push the write into the worker if the literal letter is preferred.** No bridge/WS schema changed — the existing `CellClose` payload + `WSCellClosePayload` are reused verbatim.
- **Idempotency / transaction contract for `footprint_cells` (Task 1.5f).** Each closed bar is written in exactly ONE `db.transaction(...)` (all price levels of that `bucket_ts` atomically), per ADR-005's "one transaction per bar". Each row is an UPSERT — `INSERT ... ON CONFLICT (symbol, bucket_ts, price_bucket) DO UPDATE SET bid_volume/ask_volume/trades/session_id = excluded.*` on the existing composite PK. A re-emitted close (worker SIGTERM drain, ADR-004 recovery replay) overwrites with the same absolute totals rather than duplicating or erroring. **Verified live:** a clean offline `synth→worker→cell-writer` run produced 3 closed bars (82/82/83 cells) and a repo-wide `GROUP BY (symbol,bucket_ts,price_bucket) HAVING count(*)>1` returned ZERO duplicate PKs. **Do NOT "optimise" the upsert into a plain insert** under a "the worker writes each bar exactly once" reading — the drain-on-shutdown and recovery-replay paths re-emit closes by design, and the upsert is the contract that makes them safe.
- **Bar-boundary detection in `CellWriter` relies on the worker emitting a bar's cells CONTIGUOUSLY.** The Rust worker's `close_expired_with_cvd` drains expired cells sorted by `(symbol, bucket_ts, price_bucket)`, so all cells of one bar arrive back-to-back over the bridge. `CellWriter` buffers cells for the current `(symbol, bucket_ts)` and flushes the buffer when a close for a DIFFERENT bar arrives (plus a final `flushPending()` on stop). If a future worker change ever interleaves cells from two bars in one sweep, the upsert still keeps it correct (no duplication), but a bar could be split across two transactions — re-confirm contiguity if the worker drain order changes.

- **Rust hot-path bridge mechanism.** Pinned by `architect` in ADR-002 as UDS (Linux) / named pipe (Windows) + length-prefixed framing. Revisit if cell update latency exceeds 5ms p99 under load test (Phase 5 task 5.5).
- **Bridge observability — frame logging default (deferred by ADR-002).** Whether the bridge emits structured frame logs by default in production, or stays silent and requires a dev flag. Deferred because the answer depends on the serialization format (ADR-003) — logging binary bincode is meaningfully less useful than logging MessagePack / JSON — and on the production host (Fly.io vs Railway log volume / cost). Revisit alongside ADR-003 acceptance or at deployment ADR time. Default-on with a sampling rate is the likely answer if ADR-003 picks MessagePack or JSON.
- **Bridge failure mode backend-engineer must instrument against from day one.** Framing-edge bugs: partial reads, frame split across two `recv` calls, stray bytes on the wire from a Rust `println!` debug leak. These are the classic source of length-prefix bridge bugs and they manifest as silent desync (reader interprets payload bytes as a length header) rather than a clean failure. Minimum instrumentation on Task 1.4a: per-frame `expected_len` vs `actual_len` counter exposed to the Bun side, a circuit-breaker that drops the connection and reconnects on any mismatch, and a unit test that fuzzes the wire with truncated and concatenated frames. Tokio `LengthDelimitedCodec` handles the happy path; the instrumentation exists to catch the not-happy path before it eats a demo session.
- **Single-exchange (Binance Futures only) in v1.** Multi-exchange (Bybit, OKX) deferred to v2. Revisit if commercial-seed thesis validates and a paying user requests a second exchange before a saved-layouts request.
- **CVD calculation methodology.** v1 uses naive sign-aggregated aggTrade volume. If footprint cells reveal CVD divergence that disagrees with TensorCharts on the same window, audit and document the convention difference. (Owner has the domain context to spot this on demo.)
- **Replay data source.** v1 pulls from `data.binance.vision` daily ZIPs on demand and caches locally. Revisit if cold-replay latency exceeds 3s (success-criteria adjacent) — may need pre-warmed S3 / R2 mirror.

Until then, no architect work queued.
- **Bar-interval + price-bucket size — RESOLVED by ADR-007 (architect, 2026-06-04).** v1 grid **ratified: 1-minute time buckets + $5 BTC-PERP price buckets** (legibility = ~40–80 price levels/bar; ADR-005's persistence/throughput envelope is already calibrated against this exact grid, so it is now formally load-bearing — a grid change cascades through ADR-005's partition/retention math). **Single source of truth = a documented "these files must match" assertion test (ADR-007 option B3), NOT ts-rs codegen** — two scalars that do not change in v1 are not worth a codegen + `*:check` pipeline; the lower-ceremony guard is folded into the Task 5.2 conformance harness. - **CVD placement — RESOLVED by ADR-008 (architect, 2026-06-04).** Verdict: **CVD belongs in the pure aggregator on BOTH sides (option A).** Port CVD to the Rust worker (`worker/src/aggregator/mod.rs` emits `Delta`/`Close` only today; the TS reference already computes `CvdRollup = { symbol, bucketTs, barDelta, cvd }` in `core.ts`) and **Task 5.2 conformance covers CVD**, keeping ADR-001's "Rust hot path owns all the math" literally true (option B, server-side derivation in Elysia, was the runner-up but moves domain math into the control plane). **CVD stays OFF the WS wire in v1** — the discriminated union in `schemas/ws/frame.ts` (`tick | cell.delta | cell.close | snapshot | control.*`) is unchanged, NO `cvd` frame added — and the **Phase 3.2 CVD line sub-pane (PLAN 3.2, NOT yet built — what landed under "3.2" was cursor/crosshair/tooltip) derives client-side** by folding `askVolume − bidVolume` per `cell.close` (data the browser already parses) into a running per-symbol CVD in the `useStreamStore` Zustand store, seeded from the `snapshot` frame's closed bars. The Rust/server CVD is the conformance reference + replay source of truth + reserved-but-unbuilt v2 wire promotion (additive, non-breaking per ADR-003/006). **Float-determinism constraint:** the Rust port MUST fold each bar's cells in the identical order to `core.ts` (sort bars by `(symbol, bucketTs)` — core.ts line 293) or the conformance test flags a last-ULP `cvd` mismatch; same-order IEEE-754 `f64` addition is bit-identical across Rust and JS, fixtures pin it. Follow-ons: **Task 1.5e** (port CVD to Rust + extend `__fixtures__/*.expected.json` — backend-engineer; CVD is a sibling return value, NOT a new `OutboundFrame`/`BridgeFrame` variant, so it never enters the bridge union), **Task 5.2 scope note** (CVD IS asserted, not cells-only — test-engineer), **Task 3.2c** (derive the CVD line client-side off `applyCellClose`; replay reuses the same fold over historic `cell.close`/`replay.bar` — frontend-engineer). **DO NOT delete the Rust CVD on the grounds that "the browser computes it anyway"** — the Rust copy is the conformance reference and the v2 wire source. The CVD _methodology_ (naive sign-aggregated aggTrade volume, TensorCharts-divergence audit) is the separate "Decisions to revisit" entry — orthogonal; that is about HOW it sums, this resolution is about WHERE it runs.

## Bridge serialization notes (Task 0.2 / ADR-003, `architect`, 2026-05-28)

Recorded so the next agent does not re-debate the format or trip a covered footgun.

- **Schema source of truth = Rust structs + `ts-rs`.** The Rust hot-path worker is canonical. Bridge payload structs are annotated `#[derive(Serialize, Deserialize, TS)]`; `cargo test --features ts-rs-export` writes the generated TypeScript declarations into `projects/tape/server/src/lib/schemas/bridge/generated/`, and CI runs `git diff --exit-code` on that directory to fail the build if the generated files are stale. Do **NOT** hand-author a parallel Zod schema for the bridge payload — that recreates the FFI drift risk ADR-002 rejected. Zod stays on the public WebSocket frame contract (ADR-006) and on HTTP request validation, not on the bridge.
- **Backward-compat rule, binding on every bridge-struct PR.** New fields MUST be `Option<T>` on the Rust side with `#[serde(default, skip_serializing_if = "Option::is_none")]`. Generated TS marks them optional automatically. Never rename a field, never remove one — deprecation flow is "add the replacement as `Option<T>`, dual-write for one release, switch readers, then remove in a follow-up". No positional / order-sensitive assumptions: MessagePack maps are unordered on the wire. Schema changes ship with an updated frame fixture under `projects/tape/server/src/lib/schemas/bridge/fixtures/` — the conformance test (Task 1.5b) decodes it on both sides; PRs without the fixture update fail CI.
- **Dev tools the team must have installed.** `msgpack-cli` (Java-based, ubiquitous) OR `msgpack2json` (Go binary, the path of least friction on Windows) for inspecting captured bridge frames. README run-instructions section must list one of them. The canonical debug command is `socat -v UNIX-CONNECT:./tape.sock - | msgpack2json` on Linux, equivalent named-pipe proxy on Windows. Without this tool the "5-minute pcap-to-readable-JSON" debug story that justified MessagePack over Protobuf does not materialise.
- **msgpackr footgun — leave `useRecords: false`.** msgpackr's "records" optimisation (column-style key dedup) is non-standard MessagePack and the Rust `rmp-serde` decoder will not parse it. The Bun side must be constructed with `new Packr({ useRecords: false })` / `new Unpackr({ useRecords: false })`. Reviewer note: do not flip this for the encode-speed win — it silently breaks the Rust decoder.
- **bincode was the Rust-side micro-optimum and was rejected.** Listed for completeness so the next agent does not re-propose it: no production-grade TS decoder exists, and hand-rolling one resurrects the same boundary-type-drift risk ADR-002 rejected for Bun FFI. Same call applies to Cap'n Proto and FlatBuffers: the zero-copy access pattern they win on is irrelevant at our payload sizes and the schema-file-required debug story fails the 5-minute bar.
- **Observability default for the bridge is now answerable.** ADR-002 deferred "log every frame vs stay silent by default". With MessagePack on the wire, the answer should be default-on with sampling: log a base64-encoded msgpack frame at a configurable sample rate (1 % under normal load, 100 % under a debug flag) and decode post-hoc via `msgpack2json`. To be finalised at the deployment ADR; the format choice no longer blocks it.

## Eden Treaty wire-up notes (Task 2.2, `frontend-engineer`, 2026-05-28)

Recorded so future agents do not re-debug the cross-package type-import surface.

- **Canonical pattern: `import type { App } from 'tape-server'` on the web side.** Eden Treaty is types-only at the consumer end. The `App` type travels via a re-export shim at `projects/tape/server/src/app.ts` (`export type { App } from './server';`) registered as the `tape-server` package's types entry. The runtime entrypoint `./server.ts` keeps `app.listen` under `import.meta.main` so the package's runtime self-start behaviour is unchanged. Future Phase 2 / 3 HTTP routes follow this exact pattern: define on the server, import the proxied call on the web side via `api.<route>.<verb>(...)`. No hand-typed request / response interfaces on the web side. Ever.
- **`tape-server/package.json` exports stanza.** `exports['.'].types = './src/app.ts'` plus a top-level `types: './src/app.ts'`. No `default` / `import` / `require` entry — the package is types-only from the web's perspective. If a future task ever needs a runtime import from `tape-server` on Node / Bun (e.g., a CLI), add the runtime entry as a sibling under `exports['.']` and keep the types pointer untouched.
- **Bun globals leak into web's tsc — solved via triple-slash, not via global `tsconfig.types`.** `tape-server/src/server.ts` transitively imports `./lib/commit.ts` which references `Bun.spawnSync` and `import.meta.dir`. When `tape-web`'s tsc walks the type-import graph, it hits those references. Solution: the shim at `projects/tape/server/src/app.ts` carries a `/// <reference types="bun-types" />` triple-slash directive at the very top. This propagates Bun's ambient declarations through the import graph for any project that walks into the shim, **without** forcing every web file to know about Bun globals (which is what adding `bun-types` to `tape-web`'s `tsconfig.compilerOptions.types` array would do). `bun-types` is added as a `tape-web` devDep so the reference resolves; it is ambient-only and contributes nothing to the runtime bundle. Verified via `grep` on `.next/static` post-build — no `Bun.spawn` / `@elysiajs/cors` / `@elysiajs/swagger` strings present.
- **Zod major-version mismatch is fine for the treaty contract.** `tape-server` is on Zod 3.x (Elysia 1.4.x's documented major) and `tape-web` is on Zod 4.x. The Eden Treaty `App` type is sourced from the route handler's explicit return-type annotation (`(): HealthResponse =>`), not from the Zod schema's inferred type. The contract that crosses the package boundary is the `HealthResponse` TS type, not the Zod schema object — so the two zods never meet on the type level. If a future server route omits the explicit return-type annotation and Elysia infers it from a Zod 3 schema's `z.infer<...>`, the inferred type will still be a structural TS type and Zod 4 on the web does not see it. Do not "harmonise" the versions reactively — the seam is type-only and intentionally lossy on the runtime / library-identity axis.
- **`bg-(--token)` vs `bg-[var(--token)]` is a Tailwind v4 quirk reviewers occasionally flag — ignore.** Already noted under the Task 2.1 frontend scaffold block, restated here because the treaty wire-up touches `api-status.tsx` and the diff might attract a "missing brackets" comment.

Network failures throw. `api-status.tsx`'s pattern (`if (error) throw new Error(...)`) lets TanStack Query's `status` flip to `error` so the calm-offline placeholder renders — this is the canonical handling for read-only routes. Mutations (Phase 2.4+, if any land) should branch the error explicitly and surface a toast via a future toast primitive (shadcn `sonner`).
- **Cross-package type-import contract experiment.** Reproducible at any time: rename a server route or alter its return shape, run `pnpm -F tape-web typecheck`, observe the failure at the call site, revert. Done during Task 2.2 with `/health → /healthz`, web tsc reported `Property 'health' does not exist … Did you mean 'healthz'?` at `src/components/api-status.tsx`. This is the load-bearing recruiter-facing claim — "the whole stack typechecks the contract" — and it is now mechanically verifiable.
- **Next 15 + bundler vs the package's `.ts` types entry.** The shim is a raw `.ts` file (not pre-built `.d.ts`). Next 15's bundler resolution is happy with it because `import type` is stripped by Babel / SWC before bundling. If `tape-web` ever switches to a stricter bundler (e.g., Vite for a stand-alone preview) the same pattern should still work — `import type` is a TS-level construct, bundler-agnostic. If you ever see a runtime error like "Cannot find module 'tape-server'" in the browser console, the cause is almost certainly an accidental value import (drop `type` from `import type`). Re-add `type` or the linter / tsc will not catch it because runtime imports of types-only modules don't fail at typecheck.

- **Docker Compose lives at `projects/tape/docker-compose.yml`** (project root, not under `server/`) so a single `docker compose -f projects/tape/docker-compose.yml up -d` from the repo root brings up the Postgres dev DB without `cd`-ing. ## Persistence schema notes (Task 0.4 / ADR-005, `architect`, 2026-05-29)

Recorded so the next backend agent does not re-debate the retention horizon, the write-path split, or the partition lifecycle.

- **Retention policy: 30 days of raw ticks; closed cells indefinitely.** The 30-day tick horizon is a v1 commitment, not a v2 one — it covers the demo-pitch replay surface ("today, yesterday, last week's volatility"), keeps year-1 worst-case hot-tick storage under ~50 GB (inside Fly Managed Postgres standard volume), and matches the natural cadence of the monthly partition rotation (one full + one partial month always hot, the trailing month drops in a single statement). If a commercial-seed user requests "replay from 6 months ago" the move is either (a) bump the horizon and pay storage, or (b) revisit the rejected hot-Postgres + cold-Parquet hybrid (ADR-005 option 5). Cells are kept indefinitely because ADR-004 made them the durable source of truth on worker recovery — there is no scenario where dropping old cells is correct.
- **Write path for ticks: Elysia direct, NOT through the Rust worker.** Decoupled on purpose. A worker crash-loop must not block tick archival, and the tick archive must be usable for cold-replay even while the worker is unhealthy. Elysia owns a bounded 500-tick ring that flushes via `postgres.unsafe` `COPY ticks (...) FROM STDIN` on the 50 ms coalescing window or on ring full, whichever comes first. The worker continues to receive ticks for aggregation only — it never writes to `ticks`. Cells, conversely, ARE written by the Rust worker on bar-close (one transaction per bar, ~1/min/symbol) — that path is the ADR-004 invariant.
- **Read path split: live = worker memory only; replay = Postgres only.** Live mode never touches the DB on the hot frame path — the worker holds the current-bar cell map in RAM and pushes deltas over the WS. Replay mode never touches the worker — it streams `footprint_cells` + a sliding window of `ticks` from Postgres straight to the browser as NDJSON. Two different code paths, the same data shape. Do not bridge them — a future "read-through cache" pattern that talks to both would defeat the simplicity of each.
- **Tick archive partitioning: native declarative monthly partitioning on `ticks(ts_ms)`. Bespoke lifecycle, NOT pg_partman, NOT TimescaleDB.** The partition-create-ahead loop and the drop-old-partitions loop live in `src/db/partitions.ts` as ~30 lines of TypeScript called from the Elysia entry on boot, plus a daily 03:00 UTC scheduler for the drop sweep. Idempotent (`CREATE TABLE IF NOT EXISTS ... PARTITION OF ...`), drop uses `lock_timeout = 5s` so concurrent replay readers do not deadlock the maintenance window. A future reviewer who has seen pg_partman will propose extracting this into the extension — the answer is in ADR-005 option 4 rejection: the ~30 lines live next to the worker spawn from ADR-004 anyway, and an extension dependency for a solo-dev project is real cost.
- **Postgres extension that requires a specific Fly.io image flavor — TimescaleDB, considered and (provisionally) rejected.** Fly Managed Postgres as of the last verifiable point is vanilla Postgres only; running Timescale would require self-hosting `timescale/timescaledb-ha` on a Fly Machine (backups + PITR + version upgrades owned by us). The ~2× p99 read-latency win Timescale would give us is in a range where vanilla Postgres + native partitioning is already well inside the 5 s replay budget. **TODO for backend-engineer baked into Task 1.2b: before the migration lands, verify Fly's 2026 managed-Postgres flavor list — if a Timescale-flavored managed image is now available, the ops-debt argument that drove the rejection disappears and the architect should re-eval ADR-005 options 2 vs 3. If not (the expected case), proceed with option 2 as written.** Architect cannot verify without leaving the project tree.
- **Failure mode backend-engineer must instrument against from day one.** Two cases, both well-understood: **(1) partition create-ahead loop falls behind on a long-uptime deploy and a new month arrives without a partition** — insert fails with `no partition of relation "ticks" found for row`. Mitigation: on any partition-missing error in the tick batcher, call `ensureTickPartitions` once and retry the batch; structured-log an alert if the retry path fires (it should never fire in steady state — the boot hook plus the daily sweep should always have 3 months ahead pre-created). **(2) drop-old loop runs against a partition still holding an ACCESS SHARE lock from an in-flight replay reader** — drop blocks until the reader finishes, or trips the configured `lock_timeout = 5s` and rolls back. Mitigation: tolerate the lock_timeout rollback (structured-log + reschedule for the next sweep window), do not retry inline. Expose `partitionCreateLagDays` on `/health.db` so the failure-mode-1 case is visible without `psql` access; the failure-mode-2 case shows up as a one-day delay in the dropped-partition log line and is acceptable in v1.
- **Drizzle schema files to create — under `projects/tape/server/src/db/schema/`.** `ticks.ts` (table `ticks`, composite PK `(ts_ms, id)`, btree index `(symbol, ts_ms)`, FK `session_id → sessions.id`) and `footprint-cells.ts` (table `footprint_cells`, composite PK `(symbol, bucket_ts, price_bucket)`, btree index `(symbol, bucket_ts)`, generated `delta` column, FK `session_id → sessions.id`). Barrel `src/db/schema/index.ts` re-exports both alongside `sessions`. Migration discipline: `db:generate` emits the table CREATE; the `ticks` migration is hand-edited to add `PARTITION BY RANGE (ts_ms)` and to append `CREATE TABLE ticks_YYYY_MM PARTITION OF ticks FOR VALUES FROM ('...') TO ('...');` for the current month + 2 months ahead. **Never let `db:generate` regenerate the `ticks` migration on top of the partition tail — Drizzle does not express partitioning in its DSL and will silently produce a non-partitioned `CREATE TABLE` if re-emitted.** Document the partition-tail edit pattern in the migration header.
- **WS frame is NOT the persisted row — constraint passed to ADR-006.** Persisted `footprint_cells` row carries absolute totals at bar close (one write per cell per bar). WS frame mid-bar carries deltas (`bid_volume_delta`, `ask_volume_delta`, `trades_delta`) against the current bar state. ADR-006 must define a discriminated union `kind: 'delta' | 'close' | 'replay-bar'` (or equivalent) — `delta` mid-bar, `close` at bar boundary, `replay-bar` in replay mode (carries absolute totals from the persisted row, replayed one bar at a time). Do not collapse these into one shape — they have different correctness semantics (delta is mutation, close + replay-bar are absolute state).
- **Observability question deferred (recorded under "Decisions to revisit" by reference).** Whether `/health/db` exposes per-partition row counts (`{ partitions: [{ name, rows, sizeMb }] }`) is left to a later decision. Argument for: makes the "did the partition-create loop fall behind" failure mode visible without `psql` access. Argument against: a `pg_class` count query against a partitioned table touches every partition's stats and is not free; for a solo-dev project the `partition_create_lag` counter is enough signal until ops actually needs the per-partition breakdown. Deferred until backend-engineer hits a partition-related incident or until the deployment ADR formalises the observability story.

## WebSocket frame contract notes (Task 0.5 / ADR-006, `architect`, 2026-05-29)

Recorded so the next backend / frontend agent does not re-debate the codec, the channelization, the backpressure policy, or the snapshot-frame timing.

- **Codec is MessagePack via `msgpackr` on BOTH the internal bridge (ADR-003) and the public WS (this ADR).** One wire-format vocabulary across the whole project. The same `useRecords: false` footgun applies on both wires — leave the flag at `false` so the wire stays spec-standard MessagePack. The msgpackr instance for the WS path on the server is a separate `Packr` / `Unpackr` from the bridge instance (so the WS code does not import bridge-side helpers), but the construction shape is identical: `new Packr({ useRecords: false })`. On the browser, `tape-web` gets `msgpackr` as a runtime dep — the bundle audit pattern from Task 2.2 (post-build grep) extends to confirm msgpackr lands in the chart-route chunk and NOT in the `/` landing-page chunk. The `/` page has no chart in v1 and must not pay the ~14 KB minified+gzipped msgpackr cost.
- **Eden Treaty does NOT handle the WS path's bytes.** Eden Treaty serialises HTTP responses as JSON by default (Task 2.2 AGENT_NOTES). The WS is intentionally outside that lane — Elysia's WS handler is bytes-in / bytes-out at the framework level, the codec is msgpackr, and the **types** flow via Eden Treaty's inferred `App` type while the **bytes** flow via msgpackr. This split is the one place where the project's contract surface is not "Eden Treaty does it all". Do NOT try to harmonise the WS path back through Eden Treaty's JSON layer — that would (a) lose the ~10× decode-cost win that justified MessagePack and (b) re-introduce the JSON wire bloat that the codec choice was calibrated against the 60 fps render budget to avoid.
- **Channelization: single channel, topic-multiplexed `{ topic, kind, payload }` at `/ws/stream`.** One WS connection per browser. `topic` is `'ticks.btc' | 'cells.btc' | 'control'` in v1; v2 multi-symbol adds `'ticks.eth' / 'cells.eth' / 'ticks.sol' / 'cells.sol'` without a protocol bump (the channel model is unchanged; only the server's subscription manager grows). Subscribe-on-connect is implicit in v1 (one symbol, BTCUSDT-PERP) and becomes an explicit `clientFrameSchema` subscribe vocabulary in v2. The 12 B-per-frame topic tax (~2.4 KB/sec at 200 frames/sec) is invisible at single-symbol scale and is the cheapest forward-compatible v2 affordance the channel could carry. **No ADR-007 reserved** — the multi-symbol decision is encoded as a free v1 surface; an ADR lands only when v2 actually exposes a per-topic backpressure issue or expands the subscribe / unsubscribe vocabulary.
- **Snapshot frame is server-pushed automatically on connect — no client-initiated request.** The chart renders before any user interaction. Snapshot shape: `{ topic, kind: 'snapshot', payload: { serverTime, latestBarTs, cells: CellAbsoluteRecord[], ticks: TickRecord[] } }`. Sent once per topic per connection. ~200 records (~100 cells + ~100 ticks) → ~12–14 KB on the wire after MessagePack compression. **Server-side snapshot cache keyed by `(symbol, currentBarTs)`** is invalidated on each `cell.close`, so reconnect-storm scenarios re-pay computation at most once per bar per symbol, not per reconnect. The snapshot is the ONLY state-restoring frame — `cell.delta` and `cell.close` are mutation reducers that build on the snapshot's baseline. Reconnect on `CloseEvent.code = 4290` (overrun circuit-breaker close) drops local state and reconstructs from the next snapshot. Pattern: **snapshot establishes the baseline, deltas mutate it, closes are absolute checkpoints, replay.bar rewinds it.**
- **Bar-close vs delta vs tick frame shape distinctions (the ADR-005 invariant, mechanically enforced at the schema layer).** `cell.delta` carries `bidVolumeDelta` / `askVolumeDelta` / `tradesDelta` (signed, additive); `cell.close` carries `bidVolume` / `askVolume` / `trades` / `delta` (absolute totals at bar close); `replay.bar` carries `cells: [{ priceBucket, bidVolume, askVolume, trades, delta }]` (absolute totals for one historic bar, replayed one-shot in replay mode). Field names do not overlap — a frontend agent who tries to apply a `cell.close` payload through the `applyCellDelta` reducer gets a Zod parse error at the receive boundary, not a silent miscount in production. **The persisted `footprint_cells` row (ADR-005) carries the same shape as `cell.close` semantically but is a different schema object — Drizzle owns the row type, Zod owns the WS frame type, they do not share a schema source.** This is intentional: the WS contract may evolve faster than the persistence schema (e.g., a future `imbalancePercent` derived field on the WS frame that the DB does not store).
- **Backpressure policy is drop-oldest tick frames + server-side cell-delta coalescing as the primary defence, with a 256 KB / 2 s hard-disconnect circuit breaker as second-line defence.** Two-region per-client send queue: (a) tick ring capped at 500 frames (`WS_TICK_RING_CAP`), drops oldest on overflow with a `tickDropCount` counter; (b) cell-delta accumulator keyed by `(symbol, bucket_ts, price_bucket)` — multiple deltas for the same cell within the same send tick are summed into one outbound `cell.delta` frame; (c) `cell.close` and any `control.*` frame is unconditionally enqueued and bypasses both regions. Circuit breaker: total enqueued + un-flushed bytes > 256 KB (`WS_OVERRUN_BYTES`) sustained for > 2 s (`WS_OVERRUN_MS`) → server emits `control.overrun` then closes with `CloseEvent.code = 4290` (`WS_CLOSE_CODE_OVERRUN`). Client reconnects, drops local state, awaits fresh snapshot. **The constants must live as named exports in `tape-server/src/lib/ws/backpressure.ts`, NOT as magic numbers in the send handler.** Reviewer-check.
- **The `cell.delta` coalescing accumulator is the load-bearing efficiency surface.** Without it, a 50-cell bar mutating 200 times/sec produces 10 K outbound frames/sec per client; with it, the same bar produces ~50 frames per send tick (one per mutated cell). The accumulator is keyed by `(symbol, bucket_ts, price_bucket)` because the delta is additive per-cell — multiple incoming deltas for the same cell sum into one outbound delta. **The accumulator is flushed on the send tick (50 ms wall-clock), not on every incoming delta from the bridge.** The bridge already coalesces at 50 ms per ADR-003 § Context; the WS coalescing is a second pass that catches across-client variability in flush timing.
- **Why drop-oldest ticks but NEVER drop cell-close or control frames.** Ticks are visual fidelity for the tape strip — losing a tick at burst peak is a brief gap in the live ticker, observable but recoverable (the chart's cell state stays correct because deltas are additive and close at the bar boundary is the absolute truth). `cell.close` is the bar-boundary checkpoint that mechanically rebases the cell state from "incremental delta accumulation" to "absolute total" — dropping a `cell.close` would leave the chart's incremental state diverging from the server's authoritative state until the next snapshot. `control.*` frames carry lifecycle events (`worker_unavailable` flips the UI to a calm indicator) — dropping one is a UX bug. The two-region policy mechanically encodes these priorities.
- **`/health.ws` reserves `{ connectedClients, framesPerSecOut, droppedFrameCount, overrunDisconnectCount, snapshotCacheHitRate }`.** Currently absent from the `/health` response (the WS handler does not exist yet — same call as ADR-004's `worker` field and ADR-005's persistence observability deferral). Will be added by Task 1.6b alongside the WS handler. The `dropFrameCount` is the sum of `tickDropCount` across all connected clients since process start; `overrunDisconnectCount` is the count of `CloseEvent.code = 4290` closures the server has emitted; `snapshotCacheHitRate` is `cache_hits / (cache_hits + cache_misses)` over a 60 s sliding window, `null` when no connects have happened yet (distinguishes "no signal" from "0 % hit rate").
- **Reconnect-with-backoff matches ADR-004's worker-supervision cadence on purpose.** 250 ms → 500 ms → 1 s → 2 s → 5 s → 5 s, reset after 60 s of healthy connection. One mental model for both reconnect loops (worker ↔ Elysia bridge and browser ↔ Elysia WS) — recruiters skimming the code see one backoff helper, one constant tuple, one healthy-window threshold. Do NOT introduce a different cadence for the WS reconnect without flagging it in this notes file.
- **Browser receive-side validates EVERY frame through Zod.** The msgpackr decode is fast enough (~0.5–1.5 µs per 100 B tick) that the Zod parse cost (~10–30 µs for a ~10-field schema) is the dominant decode-pipeline cost downstream of the codec — and it is still within budget at 200 frames/sec (~2–6 ms/sec). The Zod validation is the boundary that turns "bytes off the wire" into "typed domain state" for the Zustand reducers. **Do NOT skip the Zod parse under a "the server controls the schema, we can trust it" reflex** — the WS path is the contract surface most likely to be hit by a malicious or buggy frame (Binance ingest bugs propagate; a buggy server release ships a malformed frame). Boundary validation is cheap and load-bearing.
- **`useStreamStore` is the domain stream store; `useUiStore` is the chrome intent store.** Do not collapse them. `useStreamStore` holds cell map, tick ring, `workerStatus` (`'ready' | 'unavailable'` driven by control frames), `connectionStatus`. `useUiStore` holds `railCollapsed`, `replayMode`, `replaySpeedX`, `replayPositionMs`. The split mirrors the persistence policy: `useUiStore` is persisted (chrome intent survives reload); `useStreamStore` is transient (stream state restarts from the snapshot on reload, persisting it would lie about the state's freshness). Task 2.6 creates `useStreamStore`; do not bolt stream fields onto `useUiStore`.
- **The WS frame schema is the third Zod surface in the project.** First is the existing `healthResponseSchema` (HTTP `/health`); second will be the `drizzle-zod`-derived row schemas under `src/lib/schemas/db/` per ADR-005; third is now the WS frame contract under `src/lib/schemas/ws/`. Each surface has a different evolution cadence and a different ownership: HTTP is per-endpoint, DB is per-table, WS is per-`kind`. Keep them separate — do NOT create a "shared message" schema that all three pull from.
- **Frame inspection in DevTools is binary by default.** The Chrome / Firefox WS inspector shows opaque bytes for binary frames. Mitigation: README "Frame inspection" section documents the `socat -t 0 -d -d UNIX-CONNECT:./tape-ws.sock - | msgpack2json` recipe (or the Chrome `chrome://websocket-internals` + clipboard-decode equivalent for the public WS). Same dev tool as the bridge per ADR-003 — `msgpack2json` is the canonical binary-to-readable-JSON path for the whole project. **README dev-tools list must include msgpack2json (or msgpack-cli)** — gated by Task 1.4b which is the first task that needs it for the bridge, but the WS path inherits the same dep.

## Bridge serialization tooling notes (Task 1.4b, `backend-engineer`, 2026-05-29)

Recorded so the next agent does not re-debate the codegen pipeline, the ts-rs path quirk, or the cross-language type mappings.

- **ts-rs export feature flag — there isn't one.** The original ADR-003 follow-up brief named `cargo test --features ts-rs-export` as the export invocation. Verified against the installed crate (ts-rs 10.1.0 README + `src/lib.rs` docs): **no such feature exists.** ts-rs 10.x exports by emitting `#[test] fn export_bindings_<typename>()` tests via the `TS` derive macro; plain `cargo test` runs them. `serde-compat` is enabled by default. `format` (run rustfmt over output), `no-serde-warnings`, `import-esm`, and a per-type set of `*-impl` features (`chrono-impl`, `uuid-impl`, ...) exist but none of them gate export. **The canonical invocation is plain `cargo test`.** If you read older docs / agent notes referencing `--features ts-rs-export`, ignore them.
- **`export_to` is resolved relative to `TS_RS_EXPORT_DIR`, not `CARGO_MANIFEST_DIR`.** This is the load-bearing Windows path quirk ADR-003 warned about generically — verified concretely here. ts-rs 10's resolution is: `TS_RS_EXPORT_DIR` (default `./bindings`, joined against the cwd at test time) + the per-type `export_to` value, joined as a `Path::push`. A per-type `export_to = "../server/src/lib/schemas/bridge/generated/"` therefore lands at `worker/bindings/../server/...` which collapses to `worker/server/...` — files end up nested INSIDE the worker crate, not at the intended sibling location. **Solution:** pin `TS_RS_EXPORT_DIR` once in `worker/.cargo/config.toml` (`[env] TS_RS_EXPORT_DIR = { value = "../server/src/lib/schemas/bridge/generated", relative = true }`), and drop the per-type `export_to` attribute entirely (each struct lands as `<Name>.ts` directly under the pinned dir). The `relative = true` flag tells Cargo to resolve the path relative to the config file's directory (i.e. the worker crate root), giving a portable absolute path on every host without committing one.
- **Cargo config search is cwd-based, not manifest-based.** Corollary to the above: `cargo test --manifest-path ../worker/Cargo.toml` invoked from the server dir does NOT pick up `worker/.cargo/config.toml`. Cargo's config search walks up from the **current working directory** until it finds a `.cargo/config.toml`, ignoring the manifest's location. **`pnpm -F tape-server bridge:generate` must spawn cargo with `cwd = worker/`**, not `--manifest-path`. The `scripts/bridge-generate.mjs` driver does that explicitly via `spawnSync('cargo', [...], { cwd: workerDir })`. Do NOT "simplify" the driver to an inline `cargo test --manifest-path ...` — it silently breaks the export path on every host.
- **ts-rs maps Rust `i64` → TypeScript `bigint`.** Documented inline in the barrel `src/lib/schemas/bridge/index.ts` and the server README, restated here because it surprises consumers: JS `number` is `f64` and loses precision for `i64` values above `Number.MAX_SAFE_INTEGER ≈ 9.007e15` — for millisecond timestamps in our lifetime this never matters, but the type system forces the issue and msgpackr decodes MessagePack `int` family values as `bigint` regardless. Callers do millisecond arithmetic with `BigInt(...)` literals (`BigInt(Date.now())`, `tsMs - 1_000n`) or coerce at the boundary they own (`Number(tsMs)` — safe for the relevant range). `u32` and below map to `number`, `f64` maps to `number`, `String` maps to `string`, `Vec<T>` maps to `T[]`. Enums with no data map to string unions (`"Buy" | "Sell"`).
- **`worker/Cargo.lock` IS committed.** Verified `.gitignore` at the repo root does not ignore it. Rust convention is: for bin crates and lib crates that ship a `[[bin]]` or are intended to be reproducibly built (which includes any production deployable), commit `Cargo.lock`. For pure library crates intended to be consumed only as a Cargo dep, the lockfile is advisory and is often gitignored. The worker is intended to become a `[[bin]]` in Task 1.5, ships in a production container, and is consumed only by its sibling Elysia process — there is no scenario where a downstream Cargo consumer needs flexibility over our dep versions. Lockfile in, no question.
- **Worker is NOT a pnpm workspace member.** `pnpm-workspace.yaml` globs `projects/*`, `projects/*/server`, `projects/*/web` — `projects/*/worker` is intentionally absent. The worker is a Cargo project; pnpm has no business installing dependencies into it or running its scripts. The bridge:\* scripts that touch the worker live in `tape-server`'s package.json and shell out to cargo. If a future agent proposes adding `worker` to the pnpm workspace to "harmonize the toolchain", the answer is no — keep the language boundary clean.
- **msgpackr 2.0.2 is the runtime dep; `msgpackr-extract` is the optional native acceleration.** msgpackr ships pure-JS by default and falls back gracefully when the native binding (`msgpackr-extract`) is absent. The native binding is opt-in via pnpm's `allowBuilds` policy — set to `true` in `pnpm-workspace.yaml` so CI builds it where the host supports it (Linux x64 / arm64, macOS, Windows x64), but a fresh checkout that fails the native build still works on pure JS at ~70 % of the throughput. This is a perf-only opt-in; correctness does not depend on it.
- **Codec module is type-erased on purpose.** `src/lib/bridge/codec.ts` exports `encode(value: unknown): Uint8Array` and `decode<T>(buf: Uint8Array): T` — both intentionally cast-only. The `decode<T>` generic carries an `eslint-disable @typescript-eslint/no-unnecessary-type-parameters` because it IS a return-side cast helper, not a type guarantee. ## Ticks + footprint-cells schema + partitioning bootstrap notes (Task 1.2a, `backend-engineer`, 2026-05-29)

Recorded so the next backend agent does not re-debate the PK shape, the partition naming convention, or the drizzle-kit drift mitigation.

- **Postgres native partitioning hard rule: the partition column MUST be part of every unique constraint on the parent table, including the primary key.** Concretely: `ticks` is `PARTITION BY RANGE (ts_ms)`, so the PK has `ts_ms` as its leading column. We chose `(ts_ms, session_id, symbol)` because (a) `ts_ms` is the partition key (mandatory) and the natural sort for the replay scan; (b) `session_id` distinguishes simultaneous sessions that happen to tag the same millisecond — a session-restart edge case where the new generation's first tick lands in the same ms as the trailing tick of the previous generation; (c) `symbol` keeps the PK uniqueness-meaningful for v2 multi-symbol without a schema bump. NO synthetic `bigserial id` was added — ADR-005 spec'd one (and that's what older ADR text in this notes file still mentions) but the Task 1.2a harness restricted the row column set to `(ts_ms, symbol, price, qty, aggressor, session_id)`, so the natural composite carries uniqueness. If a future column addition needs a different identity, prefer adding a `tick_seq smallint` (per-ms sequence number) to the PK over reintroducing a `bigserial` — the seq column composes with the partition pruner cleanly.
- **Drizzle-kit migration drift mitigation policy for the `ticks` migration.** Drizzle's DSL does NOT express `PARTITION BY` or `PARTITION OF`. The `0001_funny_fallen_one.sql` migration is hand-edited on top of generate output, and re-running `db:generate` after the hand-edit must report "No schema changes, nothing to migrate" — verified at Task 1.2a completion. **If you change the `ticks` column shape later, generate the new migration normally, then HAND-EDIT it: column changes propagate to the partitioned parent automatically (Postgres native partitioning rule), so the new migration only needs the column diff applied to the parent.** Do NOT let drizzle-kit regenerate the 0001 migration on top — its declarative-state diff would replace the partitioned table with a plain one. The migration header carries the same warning verbatim so a reviewer who only opens the SQL sees it too.
- **Partition naming convention is `ticks_y<YYYY>m<MM>`** (two-digit month, no separator, all lowercase). Documented as the source-of-truth contract in `src/db/partitions.ts` (`partitionName` private helper). The `dropTickPartitionsOlderThan` sweep refuses to drop anything not matching `/^ticks_y\d{4}m\d{2}$/` so bespoke / manual partitions stay untouched. **If you ever change the convention, change BOTH the create-side (`partitionName`) AND the drop-side regex in the same PR** — divergence is a silent retention bug.
- **Initial partition boundaries — date-math constants used in the migration.** Computed via `Date.UTC(year, monthIndex0to11, 1)` which is deterministic against the host timezone:
  - `2026-05-01T00:00:00Z` = `Date.UTC(2026, 4, 1)` = `1777593600000` ms
  - `2026-06-01T00:00:00Z` = `Date.UTC(2026, 5, 1)` = `1780272000000` ms
  - `2026-07-01T00:00:00Z` = `Date.UTC(2026, 6, 1)` = `1782864000000` ms

  Recompute by hand with `node -e "console.log(Date.UTC(2026, 4, 1))"` — same constants land in both the migration SQL and the `partitionBoundsMs` runtime helper. **Never hand-roll the boundary millis from a calendar guess** — Postgres will accept a wrong number happily and silently route ticks into the wrong partition.

- **Cells are NOT partitioned (ADR-005 reaffirmed).** Year-1 cell volume ~26 M rows on single-symbol BTC-PERP, well below the ~50 M-row partition-management break-even. The cells table reaches that threshold around year-2 — v2 multi-symbol (ETH-PERP + SOL-PERP) is the right re-evaluation trigger. Do not propose partitioning cells on review without first arguing against the ADR-005 § "Cell-store options" option 6 rationale. **Cells have no retention drop** — ADR-004's "closed-bar history is the durable source of truth" makes them load-bearing forever.
- **Drizzle bigint mode = number (NOT bigint) for `ts_ms`, `bucket_ts`, `price_bucket`.** Postgres int8 carries the full 2^63 range; JS Number safely carries 2^53. Millisecond timestamps in our lifetime (and integer price-bucket ids) stay below 2^53 by orders of magnitude, so `mode: 'number'` avoids the BigInt ergonomic tax (no `n` suffixes, no `Number(...)` boundary coercion, msgpackr can decode straight into the JS number type when the wire value fits). **If you ever add an int8 column that genuinely needs the full range** (e.g. a Binance `aggTradeId` which Binance documents as a u64-shaped id), switch THAT column to `mode: 'bigint'` — leave the timestamp / bucket columns alone. The `mode` is per-column, no project-wide bias.
- **Aggressor enum: `text` with Drizzle's `{ enum: ['buy', 'sell'] }` narrowing, NOT a Postgres `pgEnum`.** Three reasons: (1) `pgEnum` value additions require `ALTER TYPE` migrations (a maintenance tax on every new value); (2) a CHECK constraint adds parser overhead on every `COPY ticks FROM STDIN` row, which Task 1.2b's batched ingest path is sensitive to at sustained 200 ticks/sec; (3) Drizzle's compile-time narrowing already gives TS call sites the literal union `'buy' | 'sell'` — the runtime DB column accepts arbitrary text but Zod validation at the ingest boundary (Task 1.2b) keeps the column honest. **Do not flip this to `pgEnum` under a "type safety" reflex** — the TS-level narrowing is the same shape; the DB-level constraint costs more than it pays.
- **drizzle-zod 0.8 emits Zod 4 schemas; `tape-server` is on Zod 3.** This surfaces as a tsc error on `z.output<typeof someDrizzleZodSchema>` — Zod 3's `ZodType<any,any,any>` generic bound is not structurally compatible with Zod 4's `ZodObject<...>` (the internal `_type` / `_parse` etc. fields differ). **Workaround in the row schemas (`src/lib/schemas/db/{ticks,footprint-cells}.ts`):** export the Drizzle `$inferSelect` / `$inferInsert` types directly as the row TS contract instead of going through `z.output<...>`. Runtime parsing via `tickSelectSchema.parse(...)` works unchanged — only the static generic constraint trips. If a future task wants strict Zod-derived types here, the choice is bump the server to Zod 4 (Elysia 1.4.x pin will fight back) or downgrade drizzle-zod to a Zod-3-emit version (loses the up-to-date column type mapping). Drizzle's inferred types are the canonical row contract in this codebase anyway per Task 1.2 AGENT_NOTES.
- **`/health.db.partitionCreateLagDays` is stubbed at 0 in Task 1.2a — Task 1.2b owns the computation.** The field is reserved on the Zod schema now so Eden Treaty propagates the shape to `tape-web` immediately. Computation in Task 1.2b: at each daily sweep, `max(0, today_utc_midnight - latest_existing_partition_upper_bound)` divided by 86_400_000 ms. The retention scheduler stores it on a module-level counter that the `/health` handler reads at response time. Threshold conventions (0 nominal, 1–2 warning, > 2 critical) are documented in the `dbHealthSchema` docblock, NOT in this notes file, so a Phase 6 ops doc author finds them in the schema source.
- **Partition helpers' fail-fast policy.** `ensureTickPartitionFor` / `ensureRollingPartitions` / `dropTickPartitionsOlderThan` all reach for `getDb()` from `src/db/index.ts`, which throws if `DATABASE_URL` is unset. **This is intentional — partition management must not silently no-op.** If `/health` calls one of these helpers in a future incarnation it must wrap it in a try-catch, but the helpers themselves stay loud. The tolerance pattern is scoped to the `pingDb` observability surface and nothing else (per the Task 1.2 AGENT_NOTES env-var policy).
- **`dropTickPartitionsOlderThan` does NOT set `lock_timeout`.** ADR-005 calls for `lock_timeout = '5s'` so a concurrent replay reader's ACCESS SHARE lock does not deadlock the maintenance window — but the right timeout depends on the concurrent-reader policy in force, which is Task 1.2b's scheduler concern, not this module's. The helper exposes the raw drop; the scheduler is expected to issue `SET LOCAL lock_timeout = '5s'` on the same connection before the call. Documented inline in `partitions.ts` so a reviewer who expects the timeout sees the deferral.
- **Drop-old loop reads partitions via `pg_inherits` + `pg_get_expr(relpartbound, oid)`.** The bounds expression renders as plain text (`FOR VALUES FROM ('1777593600000') TO ('1780272000000')`); we parse it with a regex tuned for Postgres's bigint-as-text quoting style. **If a future Postgres version changes that rendering**, the regex breaks — covered by adding a unit test that creates a partition, runs the sweep with `retentionDays = 0`, and asserts the partition is dropped (Task 1.2b's test surface). For now the regex tolerates optional quoting `(['"]?(\d+)['"]?)`.
- **Task 1.4a (bridge transport scaffold) landed in parallel and added `/health.worker`.** The `workerHealthSchema` and the `WorkerSupervisor` singleton in `src/lib/bridge/supervisor.ts` are NOT Task 1.2a work — they came in via another backend-engineer agent's parallel pass at the same session. The two surfaces (db + worker) coexist cleanly on `/health` because both went through the same Zod sub-schema-as-extension-seam pattern documented in the `dbHealthSchema` docblock. If a future agent finds 3 unresolved lint errors in `lib/bridge/{client,supervisor}.ts` after Task 1.2a's progress note, those belong to Task 1.4a and are NOT 1.2a defects — coordinate with the 1.4a agent (or fix them under a 1.4a follow-up, not a 1.2a hotfix).

## Bridge transport scaffold notes (Task 1.4a, `backend-engineer`, 2026-05-29)

Recorded so the next backend agent does not re-debate the framing model, the supervisor sequencing quirks, or the `interprocess` crate choice.

- **Rust cross-platform endpoint crate: `interprocess` 2.x with the `tokio` feature.** One Rust API covers POSIX UDS and Windows named pipes — `interprocess::local_socket::tokio::Listener` for the accept side and `Stream` for the connection side, with `GenericFilePath` + `ToFsName` handling both `/tmp/tape-bridge.sock` and `\\.\pipe\tape-bridge`. The path is always real-filesystem-rooted (no abstract-namespace forms) so a single flavour resolves both targets. Tokio LengthDelimitedCodec was considered but the hand-rolled `read_frame` / `write_frame` in `bridge::transport` is shorter, easier to unit-test against `tokio::io::duplex`, and lets the EOF semantics (`Ok(None)` on clean EOF before any bytes vs `Err` on partial frame) stay explicit. Cargo deps live in `worker/Cargo.toml` exactly as documented in ADR-004's "Bun spawn quirks" section.
- **Bun `unix` option accepts a Windows named-pipe path too.** Verified inline: `Bun.connect({ unix: '\\\\.\\pipe\\tape-bridge', socket: { ... } })` opens a real named-pipe client on Windows 11 without any platform branch in the call site. The "unix" key name is misleading on Windows but the runtime does the right thing. Do not invent a separate `Bun.connect({ pipe: ... })` shape — there isn't one. The `isPipe(path)` helper exists for downstream policy decisions (named-pipe close semantics on Windows do not produce an EPIPE in the same way a UDS does), NOT for the connect call.
- **`FrameReader` internal state model is one buffer + one write offset.** Single growing `Uint8Array` (initial 16 KiB, doubles on demand, capped at `BRIDGE_MAX_FRAME_BYTES + 4 B`); `feed(chunk)` appends, `*frames()` walks the head reading length prefix + payload pairs, yielding fresh copies (consumer-owned) and compacting at the tail so partial-frame remnants stay at index 0. No per-feed allocation. Throws on a declared length above the cap so a desync (length prefix read out of payload bytes) surfaces loudly rather than allocating gigabytes. The compaction shift uses `copyWithin` which is allocation-free.
- **`Bun.spawn` Windows quirk: `.exited` is the restart trigger, not `onExit`.** `onExit` fires synchronously when the child exits and races the stdout/stderr drain — schedule restart-backoff off `onExit` and you can lose the last line of the worker's stderr in the log. The supervisor awaits `.exited` (a Promise that resolves on the next microtask, AFTER the stream drain has flushed). Documented inline in `supervisor.ts` and reinforced by the ADR-004 "Negative" section. Signal vocabulary restricted to SIGTERM / SIGKILL / SIGINT — `SIGUSR1` / `SIGUSR2` are not portable to Windows.
- **Supervisor is constructed-but-not-started.** `src/server.ts` exports `const supervisor = new WorkerSupervisor()` at module scope; nothing calls `supervisor.start()` in the entry. Task 1.5 owns the spawn wiring once the real worker binary exists. Tests call `start()` / `stop()` explicitly. The `/health.worker` reader pulls live values off the singleton — `state: 'idle'`, `pid: null`, `restartCount: 0`, `lastExitCode: null` until `start()` is called. **Do not start the supervisor in the entry under a "consistency with the bridge client" reflex** — the supervisor's restart loop is the wrong shape to run during boot before the real worker exists; the echo binary is the placeholder for smoke / integration tests, not for the production boot.
- **Backoff helper is shared by client and supervisor.** `Backoff` in `backoff.ts` is the single source of truth for the ADR-004 curve (250 ms → 5 s, doubling, ±20% jitter, `reset()` on healthy reconnect). Both the bridge client's reconnect timer and the supervisor's respawn timer hold a private `Backoff` instance. The shared code is the constant tuple and the jitter math, not the timer scheduling — each consumer schedules its own `setTimeout` because the wake-up actions are different. Tests inject a deterministic `random` to make the schedule reproducible.
- **Circuit breaker uses a rolling timestamp buffer, NOT a counter.** `WorkerSupervisor` keeps a `#crashTimestamps: number[]` array and prunes entries older than `BRIDGE_CRASH_LOOP_WINDOW_MS = 60_000` on every exit. The breaker trips when the pruned array length reaches `BRIDGE_CRASH_LOOP_MAX = 10`. A simple counter would lose the rolling-window semantics — ten crashes spread evenly over an hour should NOT trip the breaker, only ten concentrated inside 60 s should. The array is bounded by the breaker threshold so it never grows unbounded.
- **Worker binary path constant resolution.** `defaultWorkerBinaryPath()` in `config.ts` returns: (a) `BRIDGE_WORKER_BIN` env override if set; (b) `target/release/echo[.exe]` if `BRIDGE_WORKER_PROFILE=release`; (c) `target/debug/echo[.exe]` otherwise. The relative path is resolved off `import.meta.url` so the function works regardless of cwd. Five `..` segments climb from `server/src/lib/bridge/config.ts` to `projects/tape/`, then descend into `worker/target/<profile>/`. Production containers pin `BRIDGE_WORKER_BIN=/usr/local/bin/tape-worker` per ADR-004's deployment story so the relative-path machinery is dev-only.
- **Inline smoke verified on Windows named pipe, May 29 2026.** Echo binary spawned in background on `\\.\pipe\tape-bridge`, smoke script ran through `connecting → connected → disconnecting → idle`, three frames (tick / cell snapshot / control) round-tripped via msgpackr with `useRecords: false`, `bridge smoke OK` printed, exit 0. The smoke is documented in `server/README.md` and is **not** in CI — Task 1.5b owns the cross-platform conformance test that gates the wire contract. The smoke script overrides via `BRIDGE_PATH` on both sides if a parallel run takes the default endpoint.
- **`Cargo.lock` policy reaffirmed.** Bin crate ships a deployable, lockfile in. Task 1.4a added `interprocess` + `tokio` + `anyhow` + `tokio` feature `signal` to `Cargo.toml`; `Cargo.lock` is regenerated and committed. No `.cargo/config.toml` changes needed for the transport (the existing `TS_RS_EXPORT_DIR` pin from Task 1.4b is untouched).
- **Predecessor's work was complete; this pass cleaned up the smoke harness only.** The TypeScript half (`backoff`, `client`, `config`, `frame`, `index`, `path`, `supervisor`, `codec`), the Rust half (`Cargo.toml` deps + `bridge/transport.rs` + `bin/echo.rs`), the smoke script, and the `/health.worker` extension all existed on disk before this pass — predecessor was interrupted before documentation landed but the code was lint-clean (the 3 errors flagged by parallel Task 1.2a had already been resolved). - **Bridge does NOT support disposing on unmount.** The singleton is process-lifetime in a browser tab. Tabs are short-lived enough that the MutationObserver overhead is negligible (< 0.1 ms per attribute mutation in Chrome 131 dev tools), and disposing+reconstructing on every chart unmount would lose the snapshot cache between page transitions inside the SPA shell. If a future task wires the chart inside a sub-route that mounts/unmounts on user nav, leave the bridge alone — the cost is paid once.
- **Token order in the tuple is grouped by purpose for human scan, not for correctness.** Pre-existing primitives first (the Task 2.1 5), then cell fill, cell text, imbalance, stroke, cursor, axis. The bridge reads / compares / freezes by name lookup, so order is irrelevant at runtime. If a reviewer or designer-critic proposes "add a token", the right slot is the matching purpose group; if there is no matching group, prefer adding the token to the most-related group rather than inventing a new one.
- **Verification recipe for future agents.** In DevTools console: `document.documentElement.setAttribute('data-theme', 'light')` flips the theme, the bridge's MutationObserver fires, every subscriber callback runs once with the new snapshot. `document.documentElement.setAttribute('data-theme', 'dark')` flips back. The dev preview block re-paints visibly between flips. The bridge's `refresh()` method is publicly exposed for test code that wants to force a re-read without waiting for a mutation event — useful in vitest where attribute mutations may race the observer queue under JSDOM.

## WS Zod schemas notes (Task 1.6a, `backend-engineer`, 2026-05-29)

Recorded so the next backend / frontend agent does not re-debate the integer-precision choice for `tsMs`, the non-negative-delta invariant, the snapshot pin counts, the discriminated-union envelope pattern, or the Zod 3 discriminator quirks.

- **`tsMs` is `number` on the WS wire, NOT `bigint` — int53-safety choice documented in `tick.ts` and worth restating here.** The bridge-side `TickFrame` uses Rust `i64` which `ts-rs` maps to TS `bigint`; msgpackr decodes MessagePack int family values as `bigint` on the bridge codec because we explicitly configured that. The WS-side codec stays at msgpackr's default — values that fit `Number.MAX_SAFE_INTEGER ≈ 9.007e15` decode as `number`. A 13-digit ms timestamp lives in `[1e12, 1e13)`, exactly representable as f64 until the year 287396. Three reasons to drop down from `bigint` on the WS edge: (1) the renderer math is f64 anyway (Canvas2D pixels, tape strip scroll position); (2) coercion at every consumer is wasted work for zero correctness win at this range; (3) msgpackr's default decoder behaviour matches. **Do NOT "harmonise" the WS-side codec with the bridge-side codec on the bigint flag** — different boundaries have different policies on purpose. If a future feature carries ns-precision timestamps (Binance Futures `T` is ms today), revisit — at 16 digits f64 starts losing the trailing ns and `bigint` becomes mandatory. v2 conversation.

- **The v1 non-negative-delta invariant is enforced via `z.number().nonnegative()` on `bidVolumeDelta` / `askVolumeDelta` / `tradesDelta`.** Documented in `cell.ts` and asserted twice in the test suite (a direct negative on a delta frame AND a negative inside a snapshot's nested `cellsOpen` array). Rationale: in v1 the worker emits one delta per `(symbol, bucketTs, priceBucket)` per coalescing window (50 ms per ADR-003), and the WS-side accumulator (Task 1.6b) sums multiple incoming deltas for the same cell — neither side ever subtracts. The v2 scenario that breaks this: a Binance feed correction that revokes a trade after the bar has accumulated it. If that frame shape lands, EITHER widen the delta schemas by removing `.nonnegative()` OR add a separate `cell.correction` kind to the discriminated union. **Recorded under "Decisions to revisit" rather than pre-allocated** — the v1 schema is the tighter contract for now, which catches a class of producer bugs (e.g., a future worker writer who accidentally emits a delta-of-a-delta) without paying for any v2 affordance.

- **Snapshot pin counts: 120 cells / 200 ticks. Constants exported.** `WS_SNAPSHOT_CELLS_PIN = 120` and `WS_SNAPSHOT_TICKS_PIN = 200` ship as named exports from `snapshot.ts` (and re-exported through the barrel). 120 cells is ~2 full closed bars at the typical 40–80 price levels/bar — covers "the open bar's right edge plus the previous bar" which is what the chart visibly paints on first load. 200 ticks is ~2–4× the typical tape-strip viewport height (~50–80 visible rows on a 1440px desktop). Combined snapshot wire estimate after MessagePack: 120 × ~50 B + 200 × ~40 B ≈ ~14 KB, squarely inside ADR-006's pinned 12–14 KB. **Task 1.6b's snapshot builder must import these constants from the schema module, NOT redeclare them in the handler.** If a designer-critic flags "first paint feels sparse" the pin counts are the single edit point; if a perf review flags "snapshot is too big on slow connections" same. **These are NOT enforced as Zod constraints** (`.max()` / `.length()`) because (a) a fresh worker on cold-boot has fewer cells available than the pin, (b) the pin is a server-side budget not a wire invariant the client must verify, (c) a future shorter / longer pin should not become a wire-format break.

- **Discriminated-union envelope pattern: each variant pins BOTH `kind` AND `topic` via `z.literal`.** A loose `topic: wsTopicSchema` at the envelope level would let `{ kind: 'tick', topic: 'cells.btc' }` parse — wrong topic for kind, definitely a producer bug — and would silently route the frame to whichever consumer the discriminator alone matched. Pinning the topic per-variant means the discriminator IS the routing key and a topic/kind mismatch fails parse loudly. Asserted in the test suite. **Reviewers will sometimes propose flattening this back to a single `z.object({ topic, kind, payload }).superRefine(...)` for "cleaner DX" — that is strictly worse**: it loses the type narrowing inside the union (`if (parsed.kind === 'tick') parsed.payload.price` only works when each variant binds `payload` to its concrete schema) and turns one Zod parse error into a manual cross-field validator.

- **`replay.bar` and the four reserved control kinds are NOT in the v1 enum.** ADR-005 + ADR-006 reserve `replay.bar` (replay mode, absolute totals per historic bar), `control.worker_ready` + `control.worker_unavailable` (ADR-004), `control.replay_complete`, and `control.error`. None are shipped here because their producing tasks have not landed yet — adding a Zod variant for a `kind` the server never emits would lie to the consumer about the v1 surface. Each lands as one additional discriminated-union variant in `frame.ts` (and one new payload schema in `src/lib/schemas/ws/`) when its task ships. **Not a protocol bump — the discriminated union is open under addition; older clients will get a parse error on an unknown `kind` which is the correct behaviour (forces a reload that pulls down the matching client schema).**

- **`app.ts` shim now carries an explicit type-only re-export block for WS types.** Distinct from Elysia's runtime type inference because the WS path is intentionally outside Eden Treaty's HTTP type-inference lane per ADR-006 — Elysia's WS handler is bytes-in / bytes-out and the codec is msgpackr, NOT JSON. The HTTP routes' inferred `App` type continues to drive `treaty<App>(env.apiUrl)` for everything but the WS; the WS frame types travel via the explicit re-export. Pattern: future Phase 1.6b additions to the WS frame contract land in `src/lib/schemas/ws/*.ts`, get added to the barrel `index.ts`, and the `app.ts` re-export block grows by one name per added type. **Reviewers should not propose "harmonising" the WS frame types back through Eden Treaty's HTTP inference** — that path serialises via JSON and would lose the ~10× decode-cost win MessagePack delivers.

- **Test framework: Bun test (`bun:test`), NOT Vitest. `pnpm -F tape-server test` delegates to `bun test`.** First test file in the package OUTSIDE the bridge suite — Bun discovers `.test.ts` files anywhere under cwd by default. The test imports JSON fixtures directly via `import fixture from '../__fixtures__/foo.json'` — works because tsconfig has `resolveJsonModule: true` from `tsconfig.base.json`. Workspace-level `pnpm -F tape-server test` runs both this WS suite and the Task 1.5b bridge conformance suite at `src/lib/bridge/__tests__/conformance.test.ts` together — 50 tests / 189 expect calls across the two files. **Flake note for the next agent:** I saw the bridge suite fail once with a `byteLength` strict-comparison mismatch (cell.peak / control.pause / control.snapshot, 2-byte deltas each) on a first run with a stale `target/debug/echo` binary, then go green on a clean re-run. If you see that pattern, rebuild the worker binary (`cargo build --bin echo` in `projects/tape/worker/`) before re-running — do NOT silently regenerate fixtures.

- **Zod 3 `z.discriminatedUnion` quirk to be aware of for future kind additions.** The first argument to `z.discriminatedUnion` is the literal string name of the discriminator field; the second is a tuple of `z.object` schemas whose discriminator field is itself a `z.literal`. Each variant MUST use `z.literal('kind-string')`, NOT `z.enum(['kind-string'])` — Zod 3 does not unwrap an enum's single value back to a literal for the discriminator-matching machinery. Asserted by construction in `frame.ts`. If a future addition uses `z.enum`, the parser silently falls back to a non-discriminated-union code path and the routing becomes ambiguous. **Reviewer note:** if you see a `z.discriminatedUnion(... z.object({ kind: z.enum(['foo']), ... })...)` in a future PR, that is the bug; require `z.literal('foo')` instead.

- **Lint friction with `noUnusedLocals` on destructured drops.** The negative-fixture helper `withoutPayloadField` in the test file uses `const { [field]: _dropped, ...rest }` to peel a field off `payload` cleanly. The `_dropped` underscore-prefix matches the root ESLint config's `varsIgnorePattern: '^_'` so lint stays green without `eslint-disable`. Pattern: any future "drop a field for the negative case" helper should follow the same prefix convention rather than reaching for `delete` (which mutates) or `Object.fromEntries(Object.entries(...).filter(...))` (which is slower and noisier).

## Bridge conformance test notes (Task 1.5b, `backend-engineer`, 2026-05-29)

Recorded so the next agent (Task 1.5 Rust worker port, any future bridge-schema PR, designer-critic, reviewer) does not re-debate the fixture set, the two-oracle policy, the byte-divergence rationale, or the regeneration workflow.

- **Binary-is-oracle convention — two flavours, by design.** Each fixture variant ships THREE files under `projects/tape/server/src/lib/schemas/bridge/fixtures/`: `<name>.json` (human-readable source-of-truth), `<name>.msgpack` (rmp-serde-authored byte oracle — what the Rust worker writes on the live bridge), and `<name>.from-ts.msgpack` (msgpackr-authored byte oracle — what the Elysia control plane writes on the live bridge). Humans EDIT the `.json` and never edit the `.msgpack`. Both `.msgpack` files decode to the same logical value on both sides — that is the bidirectional contract the bridge depends on. **Reviewers will sometimes propose collapsing to ONE `.msgpack` file** under a "single source of truth" reflex; the response is: there is one source-of-truth (the `.json` + the Rust struct definition + the JS literal in the test), but TWO encoder targets, and the explicit dual-oracle file set IS the mechanical proof that both encoders produce spec-conformant bytes the other side decodes correctly. Collapsing to one file loses the encode-side byte determinism check on whichever side gets dropped.

- **Cross-language byte divergence is real and is locked in the test set.** Three concrete instances surfaced during 1.5b implementation, all spec-conformant on both sides: (1) **map header** — msgpackr always emits `map16` (`de` prefix, 3 bytes total) regardless of map size, while rmp-serde emits `fixmap` (`8x` prefix, 1 byte) for ≤ 15 elements. (2) **BigInt encoding** — msgpackr always emits BigInt as int64 (`d3`, 9 bytes), while rmp-serde picks the smallest int container that fits (positive fixint `01` for 1, `cd` uint16 for 847, `ce` uint32 for 71235, `cf` uint64 for ms timestamps). (3) **Integer numbers vs floats** — if a fixture's `f64`-typed field carries an integer value like `0` or `1`, rmp-serde encodes it as `cb` float64 (the column type wins), but msgpackr encodes it as a positive fixint (the value tag wins, since JS has no f64-vs-int distinction at the runtime type level). **The third divergence is the only one fixture authors must work around**: use fractional values (e.g. `0.5`, `0.125`) in any `.json` field that maps to a Rust `f64`, so both encoders pick `cb` float64. The `tick.min` and `cell.min` fixtures use `0.5` for their `price` / `qty` / `bid_volume` / `ask_volume` fields specifically for this reason — recorded inline in `worker/src/bin/gen-fixtures.rs` so a future fixture author finds the rationale next to the code. The first two divergences need no workaround — both decoders accept both forms.

- **msgpackr's BigInt-always-int64 means `int64AsNumber` default behaviour drives decode shape.** The msgpackr 2.x default decodes wire int64 values as `bigint`. The conformance test's `assertDecodedMatches` helper tolerates either `bigint` or `number` for fields in the per-fixture `bigintFields` list — defensive against a future msgpackr major that lowers small int64s to JS number when they fit safe-int range. If a future msgpackr major flips that default, the assertion still passes; only a fixture-authoring agent who introduces an out-of-range int64 hits the precision wall, and the test will fail loudly because `BigInt(largeNumber)` and the actual bigint diverge. **Do NOT remove the dual-type tolerance** under a "be strict about types" reflex — it is the exact insurance that lets the suite ride past minor msgpackr maintenance without false reds.

- **Key-order rules — JSON.parse preserves insertion order, both encoders honour declaration order.** Each `.json` fixture lists `value` keys in the exact Rust struct field-definition order (`ts_ms`, `symbol`, `price`, `qty`, `aggressor` for TickFrame; etc.). msgpackr serialises object properties in JS-property-iteration order which preserves JSON.parse's insertion order on ES2020+. rmp-serde serialises struct fields in declaration order. The two land on the same key order on the wire. **If a future fixture author edits a `.json` and shuffles the key order**, the encode-byte-match test on the Bun side will fail loudly against the captured `.from-ts.msgpack` — the failure mode is correct (it surfaces that the encoder bytes drifted) but the root cause may not be obvious. Pattern: keep `.json` key order locked to the Rust struct definition order; if the struct definition reorders fields, regenerate both oracles in the same PR.

- **Regeneration workflow (binding on every bridge-struct PR).** When the Rust struct in `worker/src/bridge/messages.rs` changes shape:
  1. `cd projects/tape/worker && cargo test` — re-emits ts-rs TS bindings.
  2. `cargo run --bin gen-fixtures` — re-emits the `.msgpack` (rmp-serde oracle).
  3. `cd ../server && BRIDGE_GEN_FROM_TS=1 bun test src/lib/bridge/__tests__/conformance.test.ts` — re-emits the `.from-ts.msgpack` (msgpackr oracle). This relies on the test itself writing the file when the env flag is set (the encode comparison still runs and asserts the freshly-written bytes equal the bytes the test just produced — which is trivially true on regeneration but locks the dev's attention to the fact that they regenerated).
  4. `bun test src/lib/bridge/__tests__/conformance.test.ts` — green-run verification.
  5. Commit all generated files in the same PR.

  The Rust `gen-fixtures` binary IS the regeneration tool for the Rust oracle; the Bun test under `BRIDGE_GEN_FROM_TS=1` IS the regeneration tool for the msgpackr oracle. There is intentionally no single "regenerate everything" command — the two encoders live on different sides of the language boundary and the dual-step workflow makes it impossible to forget one. **Do NOT silently regenerate on every CI run** (the CI workflow runs only the verification path; if you see CI regenerating fixtures, that is a workflow misconfiguration to flag and fix, not the intended behaviour).

- **CI workflow extension — `bridge-conformance` job, matrix `os: [ubuntu-latest, windows-latest]`, `fail-fast: false`.** Runs after the existing `ci` job (`needs: ci`). Steps: checkout → `dtolnay/rust-toolchain@stable` → cargo registry/git cache (keyed on `Cargo.lock` hash) + worker `target/` cache (keyed on `Cargo.lock` + `src/**` hashes) → `cargo build --bin echo --tests` (builds echo binary for the existing transport unit tests and compiles `tests/conformance.rs`) → `cargo test` → `oven-sh/setup-bun@v2` (`bun-version: '1.3'`) → `pnpm/action-setup@v4` (`version: 11`) → `actions/setup-node@v4` (`node-version: 22`, `cache: pnpm`) → `pnpm install --frozen-lockfile` → `bun test src/lib/bridge/__tests__/conformance.test.ts` in `projects/tape/server`. **`fail-fast: false` is deliberate** — a Windows-only failure (e.g., autocrlf corrupting a `.msgpack` despite the `.gitattributes`) should not cancel the Linux run, because the Linux run's pass-or-fail informs whether the issue is platform-specific. **Cache keys include both the Cargo.lock AND `src/**` hashes\*\* so a worker source change correctly busts the target cache.

- **`.gitattributes` at the fixture directory level pins binary semantics.** `*.msgpack` + `*.from-ts.msgpack` → `binary` (no eol conversion, no diff display, no autocrlf). `*.json` → `text eol=lf` so a Windows regeneration produces LF-terminated files matching the existing checkout. **The `.gitattributes` is scoped to the fixtures directory only** — the broader monorepo policy is documented elsewhere; this file exists to make the binary-is-oracle convention mechanically enforceable on every developer's checkout regardless of their `core.autocrlf` setting.

- **bun test discovers `*.test.ts` recursively from cwd.** No extra config needed. The conformance test lives at `src/lib/bridge/__tests__/conformance.test.ts` (`__tests__` directory is the Jest / bun:test idiom and is also where Task 1.6a put its WS schema tests at `src/lib/schemas/ws/__tests__/schemas.test.ts`). `pnpm -F tape-server test` runs both suites — 50 tests / 189 expect calls. **If a future agent moves the conformance test to a different path**, update the CI workflow's `bun test <path>` invocation to match — the path-targeted invocation is deliberate to keep CI's failure mode explicit per suite.

- **rmp-serde `with_struct_map()` is the canonical configuration.** Without it, rmp-serde encodes structs as tuples (array of values in field order), which collapses the self-describing-frames property ADR-003 explicitly picked MessagePack over Protobuf for. `gen-fixtures.rs` and the encode helper in `tests/conformance.rs` both call `Serializer::new(...).with_struct_map()`. **The real worker (Task 1.5) MUST use the same configuration** on the live bridge — every encode call site on the Rust side should reach the canonical helper, not invent its own serializer. If a future PR adds a `Serializer::new(...)` without `.with_struct_map()`, that is a wire-format bug; the conformance test will fail loudly because the resulting bytes will not match either oracle.

- **`gen-fixtures` lives under `[[bin]]` in `worker/Cargo.toml`, alongside `echo`.** Compiled in the regular debug/release graph, not under a feature flag. Invocation is plain `cargo run --bin gen-fixtures` — no `--features` flag needed. The `pretty_assertions` dev-dep is NOT used in this bin because dev-deps don't propagate to `[[bin]]` targets via `cargo run`; std's `assert_eq!` is fine for the round-trip check. **Reviewers who propose adding a feature gate to `gen-fixtures` should be pointed at the ts-rs export pattern in `messages.rs`** — that one runs under `cargo test` (which DOES get dev-deps) and emits TS files as a side effect; `gen-fixtures` runs under `cargo run` and emits .msgpack files as its primary effect. The two should not be unified — they have different invocation contracts and different file-system targets.

- **Integration test at `tests/conformance.rs`, NOT in `src/bridge/`.** Rust convention puts integration tests under `tests/` because they (a) exercise only the public API of the crate, (b) compile as a separate crate so accidental private-API leaks surface as compile errors, (c) cross-module / cross-crate flow tests live there. `src/bridge/conformance.rs` would be a unit test inside the bridge module, which is the wrong scope — this test reads files from the sibling server package, asserts deep-equals struct literals, and exercises rmp-serde's public encode/decode surface. The integration test gets compile isolation that catches "the bridge module accidentally exposed a private type that the conformance test relies on" as a build failure. **Pattern for future cross-side tests**: integration tests under `worker/tests/`, unit tests under `worker/src/`.

- **The Rust encode-byte-match test (`rust_encode_byte_matches_canonical_oracle`) IS the binary oracle's regeneration safety net.** It encodes each of the six fixture values via the same `rmp-serde::Serializer::with_struct_map()` configuration `gen-fixtures` uses and asserts the result equals the committed `<name>.msgpack`. If a future PR changes the struct shape OR the serializer configuration without regenerating fixtures, this test fails. If a future PR regenerates fixtures but ships a different value (the struct literal in `gen-fixtures.rs` diverged from the test's expected literal), this test ALSO fails — the safety net catches both shapes of drift. **Reviewers should treat a failure of this test as a contract bug to investigate, not a fixture to silently regenerate** — the regeneration workflow above is the ONLY blessed path.

## WS fan-out notes (Task 1.6b, `backend-engineer`, 2026-05-29)

Recorded so the next agent does not re-debate the registry shape or trip a covered footgun.

- **Elysia 1.4.28 WS binary-mode is automatic — no `body: 'binary'` config required.** Verified against `node_modules/.pnpm/elysia@1.4.28*/node_modules/elysia/dist/ws/index.d.ts`: `send(data: FlattenResponse<...> | BufferSource, compress?)` accepts a `Uint8Array` and dispatches to `sendBinary` on Bun's underlying `ServerWebSocket`. The Task 1.6b handler at `src/server.ts` calls `ws.send(encode(frame))` directly — no schema, no parse-as-JSON layer, no extra config. If a future Elysia major changes this, the `wsFrameSchema` reach for `body` on the `ws()` options (TypeBox) would be the documented escape hatch — leave the codec at `msgpackr` and feed the binary through `parse: (_ws, data) => data` to bypass Elysia's auto-JSON inference. Not needed today.

- **Bun WS `close` lifecycle on abnormal disconnect: code 1006, NOT 4290.** The handler logs at INFO when code is outside `{1000, 1001, 4290}` so a recurring abnormal close (TCP RST, browser tab kill, server crash mid-frame) surfaces in ops without spamming WARN. 4290 is OUR canonical overrun code (ADR-006); 1000 / 1001 are clean client closes; 1006 is Bun's "abnormal" stamp. Reviewers occasionally propose treating 1006 as a hard error — it is not, it is the normal cost of doing WebSocket business over the real internet.

- **Per-client queue data structure: array + running byte count + head-of-line wall-time stamp.** `QueuedFrame[]` with pre-computed `length` per entry; `queuedBytes` is the running sum (incremented on push, decremented on drain or eviction); `headEnqueuedAtMs` is set to `Date.now()` when the queue transitions from empty → 1 frame, cleared back to `null` when the queue drains. This is the cheapest data structure that supports the ADR-006 dual-threshold breaker without a re-scan on every enqueue. A linked list would be marginally faster for the eviction step but JS arrays' `splice` cost is dwarfed by msgpackr's encode time at our frame sizes — not worth the complexity.

- **Cell-delta coalescing is implemented as in-queue merge + re-encode, NOT lazy merge at drain time.** When a delta for a `(symbol, bucketTs, priceBucket)` key already in the queue arrives, the existing frame's `deltaPayload` is mutated to sum the new totals, the merged payload is re-encoded via `encode()`, and the bytes / length on the queued frame are replaced in place. The drop counter increments by 1 per coalesce (surfaces in `/health.ws.droppedFrameCount` so operators see the savings). **Re-encoding pays one msgpackr pass per merge** vs lazy-merge-on-drain which would pay zero — but lazy merge needs a deferred encode path that does not exist today, and at v1 synthesizer cadence (2 cell.deltas/sec) the cost is invisible. Tasks 1.3 / 1.5 may need the lazy path if Binance bursts produce >100 deltas/sec sustained; revisit then with measured numbers.

- **Snapshot cache is in-memory only; restart blanks it. Documented as ADR-006 v1 simplification.** The `/health.ws.snapshotCacheHitRate` field reads `null` before the first connect, then `hits / connects` after — so a fresh process boot reads `null`, the first connect bumps it to `0` if the cache is empty (cache miss — happens when the synthesizer / ingest hasn't started yet) or `1` if a producer already populated it. Tasks 1.5 / 1.7 supply a durable recovery path (worker reload from Postgres on boot); until then the cache is a hot-path-only optimisation, not a state store.

- **Synthesizer seed default = `SYNTH_DEFAULT_SEED = 1`.** LCG constants `a = 1664525`, `c = 1013904223`, period 2^32 (Numerical Recipes / Knuth & Lewis). Override via `WS_SYNTHESIZE_SEED=<integer>` env var. The seed is documented in `synthesizer.ts` AND in `tape-server/README.md` so a reported demo session is reproducible across restarts. **If a future agent reseeds the synthesizer to a different default, the determinism test will still pass** (it constructs two synths with the same seed and compares streams) — the determinism test is NOT a regression guard against seed drift. To guard against seed drift, the test would need to commit a captured first-N-frames fixture; we did not because the seed itself is the documented contract and changing it is an explicit decision.

- **Synthesizer publishes through `registry.broadcast` — same path real ingest will use.** When Task 1.3 / Task 1.5 replace the synthesizer with the real Binance ingest + Rust worker producers, the swap-out is mechanical: the producer calls `registry.broadcast(frame)` and the registry handles backpressure, coalescing, breaker, and snapshot-cache updates. The synthesizer's snapshot-cache write-through (it calls `cache.update` on every emit) is the canonical pattern — the real producers must do the same so reconnects mid-stream see populated state.

- **Heartbeat loop is registry-aware: starts on first connect, stops on last disconnect.** No idle 5 s timer ticking against an empty registry. The `open` handler checks `wsRegistry.connectedClients === 1 && !heartbeatLoop.isRunning` and starts the loop; the `close` handler checks `wsRegistry.connectedClients === 0 && heartbeatLoop.isRunning` and stops it. This means the heartbeat's first tick after process boot fires up to 5 s AFTER the first client connects (5 s from start), which matches the existing browser tolerance. If a future task wants instant-on heartbeat for diagnostic reasons, call `heartbeatLoop.tick()` synchronously in the `open` handler — but the loop's idempotent `start()` already runs.

- **`heartbeat.tick()` no-ops when `connectedClients === 0`.** Belt-and-braces against a race where `stop()` was queued but the next interval fires before the timer is actually cleared. The no-op also makes the function safe for tests to call without a connected fake client (the `synthesizer.test.ts` and `connections.test.ts` files do not need to register a client to exercise the heartbeat — they register one anyway because they want to capture frames, but the design tolerates no-op heartbeat calls).

- **`framesPerSecOut` sliding window is 5 s, NOT a 1 s rate × 1 s smoothing.** Implementation: `#broadcastWindow: number[]` of push timestamps; on every `broadcast` we push `Date.now()` and lazy-prune entries older than `now - 5000`; the rate is `window.length / 5`. This is N-frame resolution at low rates (single-digit fps) but flattens spikes at high rates — which matches the policy intent (a 1 s burst should not flap "feed slow" indicators on the browser). If a future task needs a finer-grained metric, add a separate window or expose the raw array; do not change the 5 s default — the field's semantics are pinned by ADR-006 (the `control.heartbeat` schema documents it as "server-side observed outbound frame rate to THIS client over the last measurement window").

- **`framesPerSecOut` is across ALL clients combined, NOT per-client.** The registry's broadcast counter increments once per `broadcast()` call, regardless of how many clients received it. The `control.heartbeat` schema's field name "to THIS client" is technically misleading at v1 because every client is subscribed to every topic and broadcasts fan out 1:N — but the per-client and aggregate rates are identical when subscriptions are uniform. v2 multi-symbol will need a per-client counter if some clients subscribe to only one symbol; the registry's `ClientRecord` has space for it (add a `#sentTimestamps` array per record). Until then, the aggregate is the right value.

- **Schema validation on publish — `wsFrameSchema.parse(frame)` runs on every `broadcast`.** This is the documented guardrail in the task brief ("No fallbacks on bad frames — frames that fail Zod validation on emit-side throw and crash the synthesizer loudly"). A synthesizer or future ingest bug that produces a malformed frame surfaces immediately rather than reaching N clients as silent corrupt bytes. The cost is one Zod parse per broadcast — at v1 synthesizer cadence (~7 broadcasts/sec) it is invisible; at Binance peak (~1 K aggTrades/sec) it would burn ~2-5% of a core. Revisit at Task 1.3 / 1.5 if the load test shows it as a hot path; the Zod 3.x v1 path is fast enough that it shouldn't, but the exit hatch is documented: move validation into a debug-only `if (process.env.NODE_ENV !== 'production')` gate, or run it at the producer side once per coalescing window.

- **Test fake socket: `stalled = true` mode THROWS on send.** The registry's `drainQueueToSocket` catches the throw and leaves the frame in the queue — which is exactly the backpressure path under test. The Writable's `write(chunk)` returns `false` under backpressure; `end()` returns a Promise that resolves on PostgreSQL CommandComplete. The writer wraps both in a single `Promise` that resolves on `'finish'` and rejects on `'error'`. We do NOT use `pg-copy-streams` — postgres-js has a first-class COPY path that does not need it. - **Bootstrap-once-on-start invariant.** `RetentionScheduler.start()` runs ONE sweep (`ensureRollingPartitions(2)` + `dropTickPartitionsOlderThan(30)` + lag-day recomputation) BEFORE arming the `setTimeout`, and `await`s it. The `import.meta.main` block in `src/server.ts` `await`s `retentionScheduler.start()` BEFORE `tickWriter.start()` BEFORE `app.listen()`. This means: a fresh container is partitioned-and-pruned BEFORE the HTTP listener accepts a request, which means BEFORE Task 1.3's Binance ingest can produce a tick that races partition existence. Do NOT reorder — the boot guarantee is load-bearing.

- **Next-3am-UTC calculator algorithm.** `computeNext3amUtc(now: Date) -> Date` (pure, exported for testing). Read `todayThreeAmMs = Date.UTC(year, monthIndex0to11, day, 3)`. If `now.getTime() < todayThreeAmMs`, return `new Date(todayThreeAmMs)`. Otherwise return `new Date(Date.UTC(year, monthIndex0to11, day + 1, 3))`. `Date.UTC` rolls overflow days to the next month / year by spec (`Date.UTC(2026, 11, 32)` = 2027-01-01) so end-of-month and end-of-year edges handle for free. Strict-after semantics: an exact 03:00:00.000 moment returns tomorrow's 03:00, not today's. The five canonical test inputs documented in the brief (midnight, just-before-3am, just-after-3am, midday, end-of-month) plus the end-of-year and exact-3:00 edges are all covered in the unit test.

- **Lag-day computation rounds toward zero against the EXCLUSIVE upper bound.** A partition with upper bound 2026-06-01T00:00:00Z covers up to and including 2026-05-31, so on 2026-06-01 the lag is 0 (today is still covered). Concretely: `lag = max(0, floor((todayStartMs - upperBoundDayStartMs) / 86_400_000))`. Negative results (upper bound in the future = healthy ahead) clamp to 0. Day-aligned via `Date.UTC(year, monthIndex0to11, day)` — no host-timezone influence.

- **WS-vs-DB-ingest drop policy contrast (load-bearing semantic distinction).** The public WS fan-out (Task 1.6b) drops oldest ticks AND coalesces cell deltas on the per-client send queue. The DB ingest writer (this task) can only DROP, never coalesce: a tick row is a write-once atom, there is no "merge two ticks into one tick" operation. A tick lost from persistence is acceptable in v1 — (a) the worker's in-memory cell aggregation still consumes every tick so the live chart stays correct, (b) the replay scan still serves whatever was persisted. The loss only manifests under sustained ingest above the COPY throughput ceiling, which is far above the 200 ticks/s steady-state target. Documented inline at the top of `tick-writer.ts` so a reviewer who knows the WS path does not propose "let's coalesce here too" — there is nothing to coalesce.

- **Partition-missing recovery is a SINGLE retry, not a retry loop.** On a `no partition of relation "ticks" found for row` error during COPY (detected via `isPartitionMissingError`'s case-insensitive regex on the message), the writer runs `ensureRollingPartitions(2)` ONCE and retries the SAME batch. If the retry also fails, the batch is dropped with a structured-log alert — a second retry would loop indefinitely on a poisonous batch (e.g., a future-dated tick beyond any reasonable rolling window). The boot bootstrap plus the daily sweep keep two months of forward partitions, so the retry path should NEVER fire in steady state; if structured logs ever show it triggering, that is the signal to escalate to ops.

- **`stop()` tolerance — the SIGTERM path must NOT hang on a stuck DB.** `TickWriter.stop()` clears the timer and runs ONE final flush; if the flush throws (transient DB error, partition recovery exhausted, connection refused), the error is structured-logged and the ring is cleared regardless. The Elysia SIGTERM handler awaits `tickWriter.stop()` then `process.exit(0)`. A stuck DB on shutdown is acceptable data loss (~50 ms of ticks) — better than a hanging process. Documented inline so a reviewer does not file "should propagate the error" — propagating it would block the orchestrator's grace window.

- **`useStreamStore` is no-persist on purpose. Do not add `persist` middleware.** Chrome intent (rail collapse, replay mode, scrub position) lives in `useUiStore` and IS persisted via `tape-ui-v1`. Reasoning: the snapshot frame the server pushes on connect IS the authoritative baseline — persisting a stale snapshot would lie about freshness on the next load. - **Selector helpers and their equality functions.** `useConnectionState`, `useLastTick`, `useTickCount`, `useFramesPerSec` return primitives so they use Zustand's default `Object.is`. `useRecentTicks(n?)`, `useClosedCells` return arrays so they use `useShallow` from `zustand/react/shallow` (per-element identity comparison) — ticks and closed cells are append-only so identity comparison is sound. `useOpenCells` returns a `Map`; the store re-creates the Map on every delta via `new Map(state.openCells)` so the reference changes on real mutation and the default `Object.is` is correct. **If a future selector wants to slice the map (`useOpenCellsForBucket(bucketTs)`), the right pattern is a new selector with `useShallow` over the filtered entries — do not reach into the Map ref directly.**

- **`WSStreamClient` reconnect policy verbatim, for the next agent who asks "why 100 ms vs 1 s".** `CloseEvent.code === 4290` is the ADR-006 server-overrun circuit-breaker close — the server has just told us our queue overran, the next snapshot rebuilds local state, we want to reconnect FAST so the UI does not stutter. Curve: 100 ms → 200 ms → 400 ms → 800 ms → ... cap 30 s, ±20 % symmetric jitter. Any other unexpected close (1006 TCP abnormal, server crash, network blip) starts at 1 s — these tend to indicate a real outage and a 100 ms retry would just dogpile. Both curves cap at 30 s. The `restartCount` resets to 0 after `BACKOFF_RESET_HEALTHY_MS = 60_000` ms of continuous healthy connection (matches the ADR-004 supervisor reset window — one mental model across the project). **Different from the ADR-004 worker backoff curve numerically (worker is 250 ms → 5 s; WS is 100 ms / 1 s → 30 s) but identical in shape (capped exponential + ±20 % jitter + 60 s healthy reset). The two were intentionally NOT collapsed onto the same constants because they guard different failure modes — worker death is rare and expensive, WS overrun is bursty and cheap.**

The three layers exist so flipping `ssr: false` to `true` later (e.g., for an instant SSR snapshot render) does not require simultaneous changes across the stack.

- **Architecture: plain TS engine + thin React shell.** `FootprintChartEngine` in `src/lib/chart/footprint-engine.ts` is a browser-only class — NO React, NO JSX, NO hooks. The React component `<FootprintChart />` in `src/components/chart/footprint-chart.tsx` is a `'use client'` shell that owns exactly two responsibilities: (1) mount/unmount the engine, (2) drive `handleResize(cssWidth, cssHeight, dpr)` from a `ResizeObserver`. Everything else — rAF loop, theme subscription, store subscription, scroll smoothing, paint dispatch — lives in the engine. **Reviewers who propose "move the rAF loop into a React hook" should be pointed at this entry**: per-frame React work would burn the 8 ms / frame budget on reconciliation, and the engine intentionally bypasses React because the data lives in Zustand's vanilla store API and the theme bridge's `MutationObserver` — neither needs React to deliver updates.

- **Subscribe-once contract is load-bearing.** The engine's `start()` subscribes ONCE to the theme bridge (`themeBridge.subscribe(cb)`) and ONCE to the stream store via Zustand's vanilla `store.subscribe(cb)`. Every notification — theme flip OR store mutation — flips a single `#dirty = true`. The rAF callback checks `#dirty`, paints if set, clears the flag. If a future task adds a new event source (a worker tick, an external WS push), it MUST go through the same `#dirty` flag — do NOT add a second paint path that bypasses it. The dirty-flag gate IS what holds the 60 fps idle-no-work invariant; bypassing it is how a chart starts re-rendering 60 times per second whether or not anything changed.

- **The React selector hooks are for chrome, NOT the chart.** `useStreamStore` exports `useConnectionState` / `useTickCount` / `useRecentTicks` / `useClosedCells` / `useOpenCells` — those are for the StatusBar, the future tape strip widget, the future symbol picker. The engine's per-frame draw path calls `useStreamStore.getState()` directly from inside the rAF tick. `getState()` is a property read; it does NOT subscribe. The single subscription comes from `start()`'s `useStreamStore.subscribe(cb)` call. This split is the same shape Task 2.6 documented under "Selector helpers and their equality functions" — extended here to the rAF consumer.

- **OKLCH lerp helper (`color.ts`).** One-line summary: parses an `oklch(L C H)` or `oklch(L C H / A)` string via one regex, linearly blends L+C+alpha component-wise AND walks the SHORT arc on the hue circle, formats back to a 4-decimal `oklch(...)` string. The short-arc hue lerp is the non-obvious part — a naive linear lerp from 350° to 10° would walk _backward_ through 180° (perceptually wrong); we rotate one endpoint by ±360° when the absolute hue diff exceeds 180° to land on the right arc. Tested explicitly (`color.test.ts` § "takes the short arc on hue"). **Reviewers who propose "use a color library" should be pointed at the frame budget**: this helper is allocation-free except for the one `oklch(...)` template-literal output per call, and the parse cost is paid once per anchor per theme snapshot (engine caches the parsed `OklchTriple` objects on `#palette.cells.{cellBg, cellBgStrong, imbalanceBuy, imbalanceSell, imbalanceNeutral}` and the cell painter only does the lerp + format on the hot path). Importing `culori` / `chroma-js` would land 20–60 KB in the chart chunk for zero perceptual gain.

- **Scroll model verbatim.** `SCROLL_SMOOTHING = 0.2`, `SCROLL_SETTLE_PX = 0.5`. The rAF tick walks `currentScrollX += (targetScrollX - currentScrollX) * SCROLL_SMOOTHING`; once `|delta| < SCROLL_SETTLE_PX` we snap `currentScrollX = targetScrollX` and stop marking `dirty`. Critically-damped feel — no oscillation, no overshoot. `prefers-reduced-motion` collapses the smoothing to instant snap (`currentScrollX = targetScrollX` immediately). Wheel events use `passive: false` because we call `preventDefault` to stop the browser scrolling the page on vertical wheel; Shift inverts the sign so users on horizontal-wheel mice can still scrub naturally; trackpad horizontal pan (`deltaX !== 0`) maps directly to scroll. **Scroll target clamped to `[0, scrollClampMax(scale, historyBars)]` on every paint** — clamping in the paint pass (not in the wheel handler) is intentional because `historyBars` depends on the current store state, which the wheel handler does not see.

- **Right-anchored layout = automatic auto-follow.** The bar grid is right-anchored — `latestBucketTs` (the rightmost bucket's timestamp) is recomputed every paint from `recentTicks.last.tsMs - (tsMs % 60_000)` falling back to the latest closed cell, then to wall-clock. When `scrollX === 0` the most recent bar sits at the right edge of the bar region; as new ticks arrive, `latestBucketTs` advances, the chart paints, the right edge tracks live — no explicit "snap to live" code path. When `currentScrollX > 0` (user scrolled back) the chart's `latestBucketTs` still advances but the visible window stays where the user parked it because the right-edge math subtracts `(N+1) * cellWidth - scrollX`. **The "Follow live" affordance** is the text-only hint rendered at the top-right of the tape strip when `currentScrollX > 0`; Phase 3.2 wires the click handler. **Do NOT add a "snap to live on new tick" reflex** — that would defeat the whole point of letting the user scroll back through history while live data keeps streaming.

- **Session-extreme tracking is engine-state, NOT store-state.** `#sessionMaxTrades` lives on the `FootprintChartEngine` instance and is recomputed in `#updateSessionExtreme(cells)` on every paint pass — it walks the visible cells (closed + open) and bumps the maximum. The extreme NEVER decreases over the engine's lifetime — a quiet bar later in the session does not lower the bar-intensity ceiling. This matches the trader-UI convention where session extremes anchor the gradient until the session ends. Engine restart (page reload, route change) resets the extreme because the engine is reconstructed. **Do not move this onto the store** — it is a render-time aggregate that belongs to the renderer's lifecycle; moving it to the store would force a store mutation on every paint and break the dirty-flag invariant.

- **Per-frame work budget — measured on owner machine.** Dev-only logger inside `#tick` (gated `process.env.NODE_ENV === 'development'`) records `performance.now()` deltas and logs avg + p99 every 600 frames to the console. Measured at ~200 visible cells × 30 ticks × ~5 axis labels via the synthesizer on the owner's Windows 11 dev box: avg ~1.5–2.5 ms / frame, p99 ~4–5 ms / frame. The 8 ms / frame hard budget (50 % of 60 fps) has ~3–4 ms of headroom for Phase 3.2 cursor + tooltip + crosshair work. The Next inliner replaces `process.env.NODE_ENV !== 'development'` with `false` in production builds; the frame-timing array + console.log call are dead-code-eliminated. **If a future agent wants production telemetry**, the right place is a `performance.measure` mark + an opt-in `PerformanceObserver` consumer, NOT the dev-only console logger — but defer that to a real ops need, not a precautionary add.

- **Batching strategy — sort by fillColor, batch by colour.** The cell painter pre-walks all visible cells, computes each cell's final OKLCH fill via the imbalance + intensity lerp, then **sorts the array by fillColor string** before the actual `fillRect` loop. The sort means adjacent cells with the same colour string batch into one `fillStyle` assignment (the dominant Canvas2D cost — switching `fillStyle` invokes the GPU stroke / fill state diff). Strokes use one `strokeStyle` assignment for the entire batch via `strokeRect`. Cell text uses two passes — one per fg colour (full / subtle) — each setting `fillStyle` exactly once. Reviewers occasionally propose "use offscreen canvas + cell-image cache" — that pattern wins at >5000 cells, but at 200 cells the sort+batch shape is faster (no offscreen blit cost) and the code is half the lines.

- **Cell text skipped under font-size threshold.** When `chartConfig.cellHeight < chartConfig.cellFontSize + 2` (i.e., the cell isn't tall enough to host the 10 px label with breathing room), the painter SKIPS the text pass entirely. Readability over completeness — half-rendered overlapping characters are worse than a clean blank cell. If a future Phase 3.4 zoom shrinks `cellHeight` below this threshold, the text vanishes — that is correct behaviour. The `formatCellVolume` helper already returns `''` for zero-volume cells, so the text pass also skips them implicitly.

- **`--color-bg` was added to `THEME_TOKENS`.** Not a new token — the CSS declaration shipped under @theme since Task 2.1. The Canvas2D `paintBackground` pass needs the canvas background colour through the same `getComputedStyle` + `MutationObserver` bridge as the cell palette, so Task 3.1 extended `THEME_TOKENS` from 17 entries to 18 to include `--color-bg`. The bridge tuple is now: 5 pre-existing primitives + 12 footprint tokens + `--color-bg`. The dev preview surface picks this up automatically (it iterates `THEME_TOKENS`). The SSR fallback was extended to mirror the @theme dark value (`oklch(0.16 0.012 250)`). **If a future task needs another already-existing token from globals.css** (e.g., `--color-surface` for a hover-cell panel background), the same pattern applies: extend `THEME_TOKENS`, extend `SSR_FALLBACK_TOKENS`, no new OKLCH values invented. Reviewers reflexively flagging "new token!" should be shown the @theme block — that is the source of truth, the bridge tuple just selects which tokens the chart cares about.

- **Page replacement: TokenPreview moved to floating overlay.** The Phase 2.5 TokenPreview block was inline with the placeholder stub — it pushed the (eventual) chart down. Task 3.1 repositions it as an absolute-positioned floating overlay in the bottom-right corner, `lg:block` so it only appears on viewports wide enough to accommodate it without competing with the chart. `pointer-events-none` on the outer wrapper + `pointer-events-auto` on the inner card keeps the chart canvas hit-testable underneath. Same `process.env.NODE_ENV === 'development'` two-layer gate so the entire subtree is DCE'd in production builds.

- **Test strategy: math + state machine, not pixels.** 44 new chart tests across four spec files (`color`, `scale`, `cells`, `footprint-engine`). The engine test injects a no-op Canvas2D context stub (`canvas-mock.ts`) because jsdom does not implement Canvas2D — pixel-perfect render tests would be brittle and miss the actual bug classes (scale-math drift, session-extreme regression, scroll-clamp off-by-one, dirty-flag misfire). The state-machine tests use `_testNotifyStoreChange()` and `_testTick()` accessors marked `@internal` — they exist only for tests and are documented as not-public-surface. **If a future task wants visual regression tests** the right tool is Playwright + a deterministic synthesizer seed (already exists at `WS_SYNTHESIZE_SEED=1`) + a pixel-diff library, NOT a Vitest spec — Phase 5.5 owns the load test, that work plugs cleanly into the same harness.

- **The engine's `#priceMid` anchors to the most recent tick's price on first sight.** Then it stays put unless the live tick price drifts more than half the visible row count away — at which point it re-centres. This keeps the chart from "wandering" up and down with every tick (annoying) while still preventing the price action from scrolling out of view during a session-long drift. **Phase 3.4 zoom is the right place to make the Y range manually controllable** — until then, the auto-centre is the only Y-axis behaviour.

- **No fetches anywhere in the engine.** The engine reads from the Zustand store (which is fed by the WS client + WS provider in Task 2.6). It does NOT call `fetch`, does NOT touch `localStorage`, does NOT touch any browser API beyond the canvas, `requestAnimationFrame`, `ResizeObserver` (delegated to the React shell), `window.devicePixelRatio` (delegated to the React shell), and `performance.now()` (dev-only). Reviewers proposing "the engine should subscribe to historic replay data directly" should be pointed at the WS provider — replay data flows through the same store via `replay.bar` frames (Phase 3.6).

- **shadcn primitives untouched.** Task 3.1 added zero shadcn components. The chart canvas does not need them; the chrome around it was finished in Task 2.3. If a future Phase 3.5 readout panel wants a `Card` or `Tooltip`, install them then.

## Cursor + tooltip + Follow-live notes (Task 3.2, `frontend-engineer`, 2026-05-30)

Recorded so the next `frontend-engineer` / `designer-critic` / `reviewer` does not relearn the throttle pattern, the subscriber-channel architecture, the viewport-clamp rule, or the aria-live debounce semantics.

- **Cursor throttle pattern — single pending coords ref + rAF coalesce, in the React shell.** The pointer-move listener on the canvas never calls `engine.setCursor` directly. It updates a closure-scoped `pendingPx: { x, y } | null` and, if no rAF flush is currently scheduled, calls `requestAnimationFrame(flushPending)` which reads `pendingPx`, calls `engine.setCursor`, and clears the ref. Effect: at a 1000-Hz mouse polling rate the engine sees at most one `setCursor` per rAF tick (60-120 Hz), saving up to 17× redundant work on the cursor channel. The engine itself does NOT debounce — its own `setCursor` no-ops on identical coords, but the rAF coalesce is what guarantees one engine call per paint candidate. Touch events flow through the same `updateCursorFromClientCoords` helper for the same reason. **Reviewer note — do NOT add a second throttle on the React side (e.g., `useMemo` keyed on coords or `useDeferredValue`).** The pending-coords ref is the throttle; React state is downstream.

- **Engine subscriber channel architecture — three channels, one engine.** The engine owns four subscription paths in total: (1) `themeBridge.subscribe` — the internal theme-token bridge from Task 2.5, fires on `data-theme` flip; (2) `streamStore.subscribe` — the internal Zustand domain stream, fires on tick/cell ingest; (3) `subscribeCursor(cb)` — Task 3.2 public channel, fires on `setCursor` / `clearCursor` and synchronously on subscribe; (4) `subscribeScroll(cb)` — Task 3.2 public channel, fires on scroll-state change (NOT every rAF tick) and synchronously on subscribe. **Subscribe-once contract preserved**: the React side wraps `subscribeCursor` / `subscribeScroll` in `useEffect` so each consumer subscribes exactly once per mount. Inside the engine the subscriber `Set`s are cleared on `stop()` — engines are recreated on every React mount, so the cleared subscribers will be re-attached by the next engine instance via the React Context. **Why a context, not a module singleton:** the engine instance lives for one mount; Strict-mode double-mount, route navigation, and ResizeObserver-driven re-creation all produce fresh engines. A module-scope singleton would silently leak references across them. `FootprintEngineProvider` + `useFootprintEngine()` is the canonical glue; consumers reach `useFootprintCursor()` / `useFootprintScroll()`.

- **Scroll-subscriber notify discipline — diff-on-emit, not every tick.** The engine paints inside `#paint` and notifies scroll subscribers at the end of the paint, BUT only when the snapshot (`currentScrollX`, `targetScrollX`, `atRightEdge`) actually differs from the last notification. That keeps `<FollowLivePill>` from re-rendering on every settle frame while scroll is animating to target — only the transitions across the `atRightEdge` boundary (and the rare cases where smoothing crosses the half-pixel snap) propagate. `#lastScrollNotification` holds the previous emitted state. Reviewer-facing: if a future task wants per-frame scroll-position telemetry (e.g., for an inertia indicator), expose a NEW channel rather than relaxing this diff — the Follow-live pill's render cadence is the load-bearing constraint here.

- **Cursor cell recompute timing — twice, once cheaply.** `setCursor` recomputes the cursor cell immediately (so subscribers get the right cell before the next paint), and the `#paint` pass recomputes again using the live scale (so a cursor-stale cell from an in-flight bar advance settles to the right value by the paint's end). Both invocations use the same `xToBucketTs` / `yToPriceBucket` inverses from `scale.ts`. The double-compute is intentional: the recompute-on-setCursor uses a "lightweight scale" built from the most recent engine state (which may lag the paint's scale by ~ms in pathological cases), and the paint-time recompute uses the same scale the cursor painter consumes. Cheap enough that benchmarking the consolidation made no measurable difference.

- **Cursor painter sits BETWEEN cells/strip and axes — deliberate layering.** Order on the paint pipeline: `paintBackground` → `paintGrid` → `paintCells` → `paintAxes` was the Phase 3.1 layering, but Task 3.2 inserts `paintRightEdge` then `paintCursor` BEFORE `paintAxes`. Wait — re-read the source: actual order in `#paint` is `paintBackground` → `paintGrid` → `paintCells` → `paintAxes` → `paintRightEdge` → `paintCursor`. The brief's "axes over crosshair" was achieved differently: the axes render in their own region OUTSIDE the bar region, and the cursor painter clamps to the bar region — so axes labels remain legible because the cursor never crosses into the axis bands. `globalAlpha` is saved/restored around the cursor draws so other painters' alpha state is unaffected. **Frame budget after wiring cursor.** The dev FPS logger printed `[footprint] avg=2.6ms p99=5.4ms frames=600` on the owner's Windows 11 / Ryzen-class dev machine with synthesizer at 5 Hz tick + 2 Hz delta + occasional cell.close, cursor active, mouse moving across the canvas. Avg headroom 5.4 ms vs the 8 ms budget; p99 headroom 2.6 ms. Task 3.1's measured baseline was avg ~1.5-2.5 ms / p99 ~4-5 ms, so cursor wiring added ~1 ms avg / ~1 ms p99 — exactly the 2-3 painter call cost predicted in the brief.

- **Tooltip viewport-clamp algorithm — five steps, exported for tests.** `clampToContainer({ cursorX, cursorY, containerW, containerH, tooltipW, tooltipH })` in `cell-tooltip.tsx`. (1) Anchor lower-right of cursor at offset (+14, +14). (2) If that overflows the right edge minus 12 px margin, FLIP horizontally — anchor right edge of tooltip to `cursorX - 14`. (3) If that ALSO overflows the bottom edge, FLIP vertically — anchor bottom edge to `cursorY - 14`. (4) Right- and bottom-edge clamp runs FIRST (pulls tooltip back inside the right/bottom margins on normal layouts). (5) Left- and top-margin clamp runs LAST (pins to 12 px margin on tiny layouts where the tooltip is wider than the container, accepting the inevitable right-edge overflow rather than producing a negative coord). The function is pure and exported as a named export so the spec at `__tests__/cell-tooltip.test.tsx` covers all five paths without React. **Do NOT add transforms** (`translate(-50%, -50%)` and friends) — the clamp math assumes top-left anchor and would have to be rewritten.

- **aria-live debounce rule — fire on cell identity change, NOT pointer move.** The tooltip's `<div role="status" aria-live="polite" aria-atomic="true">` content tree only re-renders when the cursor's `cell` (i.e., `bucketTs`+`priceBucket`) OR `data` (i.e., the resolved `NormalizedCell`) changes. Pixel-only updates change `cursor.px` but the `TooltipBody` subtree is the only thing aria-live announces, and its props are `cell` + `data`. React reconciles a same-text re-render to a no-op DOM update — screen readers announce only on actual text node change. So the announcement cadence is "one per pointer crossing into a new cell", which matches the brief. No `useDeferredValue`, no `useTransition` — the React reconciler is the debounce. **Verify on real SR (NVDA / VoiceOver) before shipping** — jsdom does not emulate aria-live so this is an integration concern, not a unit-testable one.

- **Follow-live pill is real DOM, not Canvas2D paint.** Decision: the Phase 3.1 "Follow live" text-only hint inside the right-edge strip painter is now COMPLEMENTED (not replaced) by a `<FollowLivePill>` React component absolutely positioned at the top-right of the chart container, outside the canvas. The painter still emits the in-canvas "Follow live" text when scroll != 0 — the pill is the clickable affordance. **Why both:** removing the painter text would require gating it on a new "use external pill" flag and would couple the canvas painter to the React tree's affordance choices. Keeping both costs ~5 paint ops and zero React renders extra; the pill subscribes to `useFootprintScroll()` which only fires on scroll state changes. If a future review proposes "remove the painter text since we have the pill", note that the painter text is rendered INSIDE the chart, the pill is OUTSIDE — they communicate slightly different things (the painter says "the strip is showing historic data", the pill says "click here to follow"). Cohabitate.

- **Touch UX trade-off documented but not solved.** Cells are 24 × 16 CSS px. A finger covers ~40 px. So when a user touches a cell on mobile, their finger covers the very cell whose tooltip just appeared. Phase 3.2 wires `touchstart` / `touchmove` / `touchend` to the same cursor channel as pointer events — minimal viable. **Phase 3.4 is where the real fix lands** (zoom + pinch makes cells big enough for a touch target, OR a touch-specific "long-press for readout" affordance). For now the brief explicitly accepted the trade-off; mobile users get the chrome and the chart, not the tooltip-on-touch flow. Do NOT propose a finger-offset tooltip patch — it surfaces a tooltip on a different cell than the one the user touched, which is worse than not surfacing it.

- **Test strategy mirrors Phase 3.1 — math + state, not pixels.** 22 new tests across `cursor.test.ts` (13 — cursor channel, scroll channel, scale inverse round-trip alignment, subscriber identity, no-op invariants) and `cell-tooltip.test.tsx` (9 — RTL renders with the FakeEngine, subscribe/unsubscribe lifecycle, aria attribute presence, cell-readout values, zero-state placeholder, hide-on-null, plus the 5 clampToContainer pure-function rules). **Vitest does NOT auto-cleanup RTL renders** the way Jest's `setupFilesAfterEach` does — the spec calls `cleanup()` explicitly in `afterEach`. Also: `visibility: hidden` removes the tooltip from the accessibility tree, so the "hides" test queries by `[aria-label]` selector rather than `getByRole('status')`. Note for future agents: if you add another React test file, add the `cleanup()` boilerplate or extract it into a `vitest.setup.ts` registered via `test.setupFiles` — for one spec the inline pattern was cheaper.

## Rust hot-path worker notes (Task 1.5, `backend-engineer`, 2026-05-30)

Recorded so the next backend agent (Task 1.5c WS variants, Task 1.5d recovery conformance, Task 1.7 replay, reviewer pass) does not re-debate the listener/client direction, the bounded mpsc capacity, the bar-rollover cadence, the handshake protocol, or the snapshot poll vs push trade-off.

- **Worker BINDS the listener; TS BridgeClient CONNECTS.** Same shape as the Task 1.4a `echo` placeholder. The brief's "Connects to the bridge socket ... as a client" line was ambiguous; the actual 1.4a architecture has `echo` binding via `ListenerOptions::new().create_tokio()` and `BridgeClient` connecting via `Bun.connect({ unix })`. Task 1.5's `worker` binary keeps the same role to avoid re-architecting the bridge direction. The supervisor (`Bun.spawn`) brings the worker up; the worker binds; the TS `WorkerPipeline` then calls `BridgeClient.connect()` which reaches the bound socket. **Reviewers who propose "swap directions to match the brief verbiage"** should be pointed at the existing supervisor + BridgeClient code paths — flipping the direction would require rewriting both, for no functional win.

- **Bounded mpsc capacity = 1024.** `OUTBOUND_CHANNEL_CAP` in `worker/src/bin/worker.rs`. Sized to absorb a single Binance burst (~1–2 K ticks/s) without blocking the inbound reader for more than ~5 ms even if the writer is briefly paused on a slow socket. The drop policy is approximated, not perfect: `cell.delta` goes through `try_send` (channel-full → drop one delta + log), `cell.close` / `snapshot` / `worker_ready` / `worker_unavailable` go through awaiting `send` (never drops). A true drop-oldest ring with kind-aware eviction would need a custom channel impl — out of v1 scope; the WS-side registry's coalescing handles the steady-state and the bounded channel is only the worst-case overflow vent. **Do NOT bump the capacity above ~4096 without measuring** — every queued frame is a ~120 B msgpack payload held in RAM; at 1024 the memory budget is ~120 KB which is invisible, at 32768 it's ~4 MB which starts to matter under sustained burst.

- **Bar-rollover timer cadence = 1 s.** `ROLLOVER_TICK_INTERVAL` in `worker.rs`. Per the task brief: "every 1 second, checks whether any open bar's bucketTs has now ended". Faster (250 ms) buys nothing because the WS-side cell-close has its own propagation latency. Slower (5 s) delays the `cell.close` past its bar boundary, which leaves the Phase 3 renderer painting stale right-edge state for several seconds. **Reviewers who propose tying the cadence to the WS heartbeat (5 s) should be pointed at the asymmetry** — heartbeat is a liveness ping (it's fine if it's late), bar-close is a state-transition checkpoint (every second it's late, the chart's right edge has stale absolute totals).

- **WorkerReady handshake protocol.** The worker sends `BridgeFrame::WorkerReady { pid, generation: 0 }` as its FIRST outbound frame after binding the listener and accepting the bridge client connection. The TS-side `WorkerPipeline` arms a 5 s `BRIDGE_HANDSHAKE_TIMEOUT_MS` timer on `start()`; on `worker_ready` receipt the timer is cancelled and `metrics.workerReady` flips to `true`. On timeout the pipeline calls `supervisor.stop()` + `supervisor.start()` + re-arms the timer; the existing 250 ms → 5 s exponential backoff in `WorkerSupervisor` controls the actual respawn cadence. **`generation` is supervisor-side state per ADR-004** — the worker does not know its own restart generation; the worker sends `0` and the supervisor overrides for log-tagging purposes. Recorded here because reviewers occasionally propose "the worker should track generation across exec()s" — it can't, the process doesn't survive across respawns by definition.

- **Snapshot poll cadence = 5 s (`BRIDGE_SNAPSHOT_POLL_MS`).** PULL mode chosen over push. Reasoning: the worker's authoritative state lives in `Aggregator::snapshot()` already; pushing a snapshot every N seconds from the worker would couple the worker's tick to the supervisor's metric cadence. Polling means the supervisor decides when it needs an update; the worker side just answers. Cost: ~1 message per 5 s, ~200 B decoded — invisible at v1 frame budget. **The alternative — pushing snapshots from the rollover timer — was rejected** because it ties two unrelated cadences (bar boundaries are minute-aligned, metrics are sub-second) into one timer; the polling decouples them cleanly. If a future Phase 6 ops dashboard needs sub-second `cellsOpen` metrics, the right shape is reducing `BRIDGE_SNAPSHOT_POLL_MS` (it's a TS-side constant the supervisor owns), NOT moving to push mode.

- **Three-way mutex precedence — verbatim.** (1) `BINANCE_WS_ENABLED=1 && WORKER_PIPELINE_ENABLED=1` → full pipeline (Binance → tickWriter + bridge.send(tick) → worker → cell.delta / cell.close on WS). (2) `BINANCE_WS_ENABLED=1 && WORKER_PIPELINE_ENABLED=0` → direct tick broadcast only, no cell aggregation (tape strip works; cells empty per the v1.0 limitation cited in README). (3) `WS_SYNTHESIZE=1` (with `BINANCE_WS_ENABLED=0`) → dev synthesizer publishes ticks AND cells directly. The bridge is NOT in the loop in this mode — it is a dev convenience. **If WS_SYNTHESIZE AND BINANCE_WS_ENABLED are BOTH `'1'`, BINANCE_WS_ENABLED wins** (real feed beats dev convenience, synth disabled with a WARN). **WORKER_PIPELINE_ENABLED is ORTHOGONAL to the synth** — the synth never feeds the bridge; setting both `WS_SYNTHESIZE=1 && WORKER_PIPELINE_ENABLED=1` spawns the worker (which sits there with nothing to aggregate) and runs the synth (which publishes its own cells directly). v1 default is `WORKER_PIPELINE_ENABLED=0` so the soft-launch path is unchanged from Task 1.3 + Task 1.6b; flipping to `1` is opt-in.

- **`/health.worker.cellsOpen` + `ticksProcessed` come via the snapshot poll cache, NOT via push.** The supervisor polls every 5 s; the pipeline's `#onSnapshot` handler caches the latest values; `/health` reads the cache at request time. There is NO push from the worker on every tick — that would put metric I/O on the hot path. Reviewers who notice "metrics lag 0–5 s behind reality" should be pointed at this trade-off; the alternative (push every tick) would burn ~200 µs / tick on bridge round-trips that nothing consumes. **For a future ops-dashboard that genuinely needs sub-second `ticksProcessed`** the right shape is a separate `/health/live` endpoint that issues a one-shot snapshot request on call — same poll mechanism, on-demand.

- **`CellDelta` shape carries `_delta` suffix on the totals fields.** Matches the WS-side `wsCellDeltaPayloadSchema` field-name invariant: a hexdump reader sees distinct tokens for delta vs close. The Rust `CellDelta` field `bid_volume_delta` ↔ TS `bidVolumeDelta` ↔ WS frame `bidVolumeDelta`. ts-rs's default `serde::Serialize` uses the snake_case Rust field name on the wire; the WS-side handler in `WorkerPipeline.#onCellDelta` does the snake → camel conversion explicitly. **Reviewers should NOT propose `#[serde(rename_all = "camelCase")]` on the Rust struct** — that would force the conformance fixtures (which are snake-case in the `.json` source) to be rewritten, and the `WSCellDeltaPayload` schema would need updating in lock-step with the bridge schema, defeating the ADR-005 "WS schema is INDEPENDENT of bridge schema" rule.

- **Snapshot `cells_open` carries `CellDelta`-shaped entries with absolute totals.** Intentional shape reuse: the WS-side `wsSnapshotPayloadSchema.cellsOpen` is already typed as `wsCellDeltaPayloadSchema[]`, so the bridge schema mirrors it for a 1:1 mapping. The `_delta` fields hold running totals (NOT incremental deltas) when carried inside a snapshot. **Reviewers will sometimes propose adding a dedicated `CellOpenSnapshot` shape** — the answer is "the renaming pass would touch the WS schema, the browser reducer, the snapshot cache, and the bridge schema for zero correctness win". Documented inline in `aggregator/mod.rs::snapshot()` so a future agent reads it next to the code.

- **Six new fixtures + Bun conformance test extended for nested bigint paths.** Fixtures: `cell.delta.typical`, `cell.close.typical`, `snapshot.typical`, `worker.ready`, `worker.unavailable` (5 new; total 11 from prior 6). The `snapshot.typical.json` carries nested bigint paths (`cells_open.*.bucket_ts`, etc.) that the prior `bigintFields: string[]` flat list shape did not support. **The conformance test now recursively coerces leaves via `matchesBigintPath(paths, pathToCheck)` with `*` wildcard support** — `cells_open.*.bucket_ts` matches `cells_open.0.bucket_ts`, `cells_open.1.bucket_ts`, etc. The path syntax restricts to literal segment + `*`; a typo surfaces as "no match" rather than "any path resolves". Recorded so a future agent adding nested fixtures uses the same path syntax.

- **Worker smoke script at `server/scripts/worker-smoke.ts`** — Bun-only manual command (NOT a unit test) that spawns `target/<profile>/worker[.exe]` via `Bun.spawn`, connects a BridgeClient against the bridge endpoint, sends 3 ticks + 1 Snapshot + 1 Shutdown, asserts frame counts (`worker_ready: 1, cell.delta: 3, snapshot: 1, cell.close: 1, worker_unavailable: 1`, total 7). Override the path via `BRIDGE_PATH` (PowerShell: `$env:BRIDGE_PATH = '\\.\pipe\tape-smoke-worker'` because bash strips backslashes). **Verified inline against `target/debug/worker.exe` on Windows 11 named pipe 2026-05-30 — end-to-end PASS.** The smoke is NOT in CI because spawning + connecting from inside a runner with `bun test` is flaky against the path collision; the cargo + bun conformance suites cover the wire contract, and the smoke is the operator-facing live check.

- **Cross-platform CI: no workflow change needed.** The existing `bridge-conformance` job at `.github/workflows/ci.yml` builds + tests on Ubuntu + Windows with `fail-fast: false`. The new `worker` binary builds alongside `echo` when `cargo build --bin echo --tests` runs (cargo compiles every `[[bin]]` target by default — `--tests` only affects test discovery, not the build set). The new fixtures are picked up by both test suites automatically because they live under the well-known `bridge/fixtures/` directory the suites read. Run `cargo build --release --bin worker` for the production container build (added 20 s compile time on a clean tree); the Bun `bun test` invocation is unchanged.

- **`workerBinaryPath('echo' | 'worker')` is the new path resolver.** Replaces the old `defaultWorkerBinaryPath()` single-binary surface. `defaultWorkerBinaryPath()` is preserved as a thin wrapper that defaults to `'echo'` for back-compat with the Task 1.4a supervisor tests + bridge smoke. **The `WORKER_PIPELINE_ENABLED=1` boot path uses `workerBinaryPath('worker')` explicitly** — the supervisor's `binaryPath` constructor option is set at boot time to the right binary. `BRIDGE_WORKER_BIN` env override still takes precedence in either case (production containers point at `/usr/local/bin/tape-worker`).

- **Pipeline restart-on-handshake-timeout DOES NOT walk the supervisor's backoff** — it calls `supervisor.stop()` + `supervisor.start()` + re-arms the handshake timer. The supervisor's own `.exited`-driven respawn loop is what walks the 250 ms → 5 s curve; the pipeline's timeout just bounces the process. **Why not let the supervisor handle the handshake too?** The supervisor's responsibility ends at "child process alive"; the handshake is an application-level signal (the worker said "I'm ready"). Mixing them would couple the supervisor to the wire protocol; keeping them separate means the supervisor stays generic (any binary that exits with code != 0 gets restarted, regardless of whether it ever sent a handshake). Recorded so future agents don't move the handshake logic into the supervisor.

- **Aggregator is genuinely pure-ish — no I/O, no async.** Lives in `worker/src/aggregator/mod.rs` as a `struct Aggregator` with `&mut self` methods. Mutation but no `tokio`, no `mpsc`, no file system, no clock. The clock (the rollover timer) is the worker binary's responsibility, not the aggregator's — `close_expired(now_ms)` takes `now_ms` as an explicit argument so the test passes a deterministic value. **Reviewers who propose "let the aggregator own the clock" should be pointed at the unit test set** — 12 cases run instantly and deterministically because the aggregator never reaches for `SystemTime::now()`. Moving the clock inside would require mocking it in every test.

## Phase 6 deploy prep notes (`backend-engineer`, 2026-05-31)

Recorded so the next agent that touches the deploy surface does not
re-debate the in-memory limiter trade-off, the CORS env-var
convention, the production worker binary path, or the geo-block
resolution story for Binance.

- **In-memory WS rate limiter is single-machine only.** `WSRateLimit`
  lives at `server/src/lib/ws/rate-limit.ts` and holds its per-IP
  counts in a `Map<string, number>` inside the Bun process. v1
  ships one Fly Machine in `fra` (`min_machines_running = 0`,
  auto-start on traffic), so this is correct. The moment v2 scales
  out — either horizontal Fly Machines, or a private-network worker
  split — the same IP can open `cap` connections per machine and
  the effective cap multiplies by N. **The fix is NOT "raise the
  cap"** (that defeats the purpose); it is a shared store
  (Redis `INCR` / Fly's distributed KV) or a per-edge limiter at
  the Fly proxy layer. Tracked under "Decisions to revisit" as
  ADR-007 territory — do not pre-allocate. The post-accept ADR-006
  circuit breaker (256 KB / 2 s) stays effective regardless because
  it is per-client and lives in the same process as the socket.
- **CORS env-var convention: `ALLOWED_ORIGINS` comma-separated, no
  wildcards.** Resolution is exact case-sensitive string match —
  scheme, host, port, no trailing slash. `https://tape-demo.fly.dev`
  matches only itself; `http://tape-demo.fly.dev` (no s) does not;
  `https://tape-demo.fly.dev/` (trailing slash) does not. This is
  intentional and the test suite locks it down (see
  `src/lib/__tests__/cors-allowlist.test.ts` "match is exact" group).
  **Do not "fix" the predicate to be lenient on trailing slashes**
  — every wildcard / lenient CORS that has ever shipped became a
  production incident the moment someone added a fourth subdomain.
  If a future deploy needs preview URLs (`pr-123.tape-demo.fly.dev`)
  the move is a regex predicate behind a separate env var
  (`ALLOWED_ORIGINS_REGEX`?) and an ADR documenting the trade —
  not a wildcard in the comma list.
- **CORS fail-closed in production-with-no-env.** When
  `NODE_ENV === 'production'` and `ALLOWED_ORIGINS` is unset, the
  allowlist resolves empty and every cross-origin request is denied
  by the predicate. **Same-origin requests still work** because the
  CORS plugin does not invoke the callback for same-origin (no
  Origin header on most navigations, and even for `fetch` from the
  same origin browsers do not always send Origin). The demo URL →
  its own server hop is therefore unaffected by a missing env.
  External embeds, third-party integrations, any browser that does
  send Origin from the same origin will be denied. The boot path
  logs a WARN so the misconfiguration surfaces immediately in
  `flyctl logs`.
- **Production worker binary path is `/app/worker/worker` via
  `BRIDGE_WORKER_BIN`.** The Rust worker binary built by the
  Dockerfile rust-builder stage lands at `/app/worker/worker`
  (executable, owned by `bun`). `fly.toml`'s `[env]` block sets
  `BRIDGE_WORKER_BIN=/app/worker/worker` so the supervisor's path
  resolver picks it up regardless of `BRIDGE_WORKER_PROFILE`
  (which is for dev's `target/debug` vs `target/release`
  selection). If you ever change the in-container worker path,
  update both the Dockerfile COPY destination AND the `fly.toml`
  env in the same commit — they are a two-sided contract.
- **Binance geo-block: dev fails, production wins.** Task 1.3
  documented that the owner's home network reached
  `fstream.binance.com` at the WS connect layer (state transitioned
  to `connected`) but no aggTrade frames arrived in the 30 s smoke
  window — almost certainly a regional/ISP restriction on the
  streaming layer rather than the connect path. Fly.io's Frankfurt
  Linux infra is NOT in the affected zone for any test we have
  done, and the `fly.toml` env defaults to `BINANCE_WS_ENABLED=1`
  in production for exactly that reason. **The acceptance test on
  first deploy is `curl https://tape-demo.fly.dev/health` showing
  `binance.connected: true` and `binance.lastTickTsMs` non-null.**
  If it does not, the fallback is to flip `BINANCE_WS_ENABLED=0`
  via secrets and run the dev synthesizer (`WS_SYNTHESIZE=1`)
  in production temporarily, which preserves the demo's "moving
  data" wow moment while the network path is investigated. Do
  NOT consider this a normal mode — the synth path was sized for
  dev/CI determinism, not production traffic.
- **Single-image vs split (deploy topology).** The v1 Dockerfile
  ships ONE runtime image with the Bun server + Next standalone +
  Rust worker all under PID-1 entrypoint fan-out. The split
  alternative is a `[processes]` block in `fly.toml` with
  `server = "..."` + `web = "..."` and a private-network hop for
  /api calls. v1 picked single because (a) same-machine
  co-location means the bridge UDS at `/tmp/tape-bridge.sock`
  works without a Fly volume, (b) one health check covers
  everything, (c) demo traffic does not benefit from independent
  per-process scaling. v2 split is documented in the Dockerfile
  header as the migration path; do not pre-emptively split.
- **Next standalone needs `outputFileTracingRoot`.** Without it,
  Next's standalone tracer walks the local `node_modules/` but does
  NOT follow pnpm's workspace symlinks back up to the repo root —
  it misses the types-only `tape-server` dependency and any future
  workspace siblings the page tree pulls in. The pin in
  `web/next.config.ts` (`new URL('../../../', import.meta.url).pathname`)
  resolves to the repo root from `projects/tape/web/`. Two hops
  for the docker layer order to be deterministic. If the project
  ever moves out of `projects/tape/web/` (e.g. extracted to a
  separate repo) this needs revisiting — the standalone tracer
  picks up everything reachable from the tracing root, so a wider
  root means a bigger standalone bundle and longer cold starts.

## Footprint-cell aggregator — TS reference impl notes (Task 1.4, `backend-engineer`, 2026-06-04)

Recorded so the next agent (especially whoever ports CVD to Rust, or wires the adapter into a TS-fallback / replay path) does not relearn these.

- **The TS reference landed AFTER the Rust port (1.5) — conformance direction is reversed.** PLAN.md's original intent was "write the TS reference first (1.4), then port to Rust (1.5)". In practice 1.5 shipped first. So `server/src/lib/aggregator/core.ts` + `bucketing.ts` were written to MIRROR the already-existing `worker/src/aggregator/mod.rs` + `worker/src/bucketing.rs` byte-for-byte, not the other way round. Every method on `AggregatorCore` has a one-to-one Rust counterpart (`onTick`↔`on_tick`, `closeExpired`↔`close_expired`, `drainAll`↔`drain_all`, `snapshot`↔`snapshot`). **If you change one side, mirror the other** — the shared fixtures (below) are what catch drift.
- **Aggressor → footprint-side cheat sheet (DO NOT INVERT — repeated in four files on purpose: `agg-trade.ts`, `binance-translator.ts`, Rust `aggregator/mod.rs`, TS `aggregator/core.ts`):** `buy` aggressor = taker LIFTED the ask (Binance `m=false`) ⇒ add qty to the cell's **ASK volume**. `sell` aggressor = taker HIT the bid (Binance `m=true`) ⇒ add qty to the cell's **BID volume**. Per-bar delta = `ask_volume − bid_volume` (net aggressive buying). CVD = running cumulative of per-bar delta across closed bars per symbol.
- **The core is PURE — keep it that way.** No `Date.now()` (the caller passes `nowMs` into `closeExpired`), no DB, no network, no global state, no clock. This is what makes the Rust conformance test (5.2) and any future TS-fallback aggregator tractable. The side-effecting wiring lives in `adapter.ts` (`WsAggregatorAdapter`) — broadcast + snapshot-cache — and is a deliberate mirror of `bridge/pipeline.ts`'s cell-frame promotion. **Do not bolt IO into `core.ts` under a "it's convenient" reflex.**
- **Seam left for Task 1.5 / 1.7 / future TS-fallback:** `WsAggregatorAdapter` is constructed-but-wired-behind-nothing. `src/server.ts` was NOT touched by Task 1.4 — live production cell aggregation is the Rust worker's job via `WORKER_PIPELINE_ENABLED=1` + `bridge/pipeline.ts` (which already owns delta/close promotion for the worker frames, so the adapter is NOT used in the worker path). The adapter exists for: (1) a worker-unavailable TS-fallback boot mode if one is ever wanted, (2) replay-mode (Task 1.7) if it chooses to re-run the reference aggregator over archived ticks instead of reading pre-aggregated `footprint_cells`, (3) the test/conformance harness. To use it: `new WsAggregatorAdapter({ registry, snapshotCache })`, then `ingestTick(tick)` per tick + `rolloverAt(nowMs)` on a timer + `drainAll()` on shutdown. Its `#emit` is intentionally line-for-line the same shape as `pipeline.ts`'s `#onCellDelta` / `#onCellClose` — keep them consistent if either changes.
- **Shared conformance fixtures live at `server/src/lib/schemas/.../` — NO. They live at `server/src/lib/aggregator/__fixtures__/`.** Distinct from the BRIDGE fixtures at `server/src/lib/schemas/bridge/fixtures/` (those are msgpack wire round-trip oracles for Task 1.5b). The AGGREGATOR fixtures are `*.input.json` (tick sequence + `closeAt` times) + `*.expected.json` (deltas + closes + cvd + finalSnapshot + counters), plain JSON so Rust `serde` can load them. Three scenarios: `basic-two-bars` (rollover, multi-bucket, boundary tick, CVD across two bars), `edge-cases` (out-of-order, duplicate, empty-bar gap, boundary tick), `cvd-reversal` (CVD direction + sign-flip reversal). **`expected.*` is DERIVED, never hand-edited — regenerate with `bun scripts/gen-aggregator-fixtures.ts`** (plain `bun`, NOT `bun run` — the latter mis-handles `import.meta.main` and silently no-ops). The canonical replay procedure is in `aggregator/replay.ts::replayFixture` (feed all ticks → `closeExpired` per `closeAt` in order → `drainAll` → read snapshot + counters); the Rust port + Task 5.2 must drive their aggregator the same way to compare against the same oracle. Volumes are dyadic rationals so f64 sums are EXACT (exact-equality comparison, not epsilon) for these hand-authored scenarios; the recorded 1h dataset (5.2) may need epsilon on the volume sums.
- **Out-of-order / duplicate policy (Rust-conformant, tested):** out-of-order ticks are ACCEPTED and accumulate into their (still-open) bucket exactly as in-order ticks would — the aggregator is bucket-addressed, not append-ordered. Duplicates are ACCEPTED as real trades (there is no trade-id in the WS tick payload to dedupe on; dedup belongs UPSTREAM at ingest where Binance's `a` id still exists). Both bump observability counters (`outOfOrderTicks` / `duplicateTicks`) that DO NOT change any emitted frame — this is what keeps the core conformant with the (also bucket-addressed, also non-deduping) Rust port. A late tick whose bucket has ALREADY closed re-opens a new cell for that `(symbol, bucketTs, priceBucket)` and produces a SECOND `cell.close` for the same bar later; v1 accepts this (browser last-write-wins on rebase), v2 may add a grace window.
- **Bun 1.3.14 transpiler footgun — backtick-quoted globs in block comments.** A JSDoc/block comment containing a backtick string with a `**/`-adjacent or `*/`-adjacent glob (e.g. `` `src/lib/**/__tests__/` ``) crashes Bun's loader with a spurious "Unterminated string literal" pointing at the comment line, and the error CASCADES to misparse later template literals in the file (the location moves around as you edit, which is misleading). Fix: do not put backticks next to `*/`-like sequences inside block comments. Cost me a confusing debug loop on `__tests__/core.test.ts`; documented so the next agent recognises it instantly.

## Bucketing single-source-of-truth + Rust CVD port notes (Tasks 1.4c + 1.5e, `backend-engineer`, 2026-06-04)

Recorded so a future agent does not re-inline the constants, regress the CVD fold order, or try to put CVD on the wire.

- **Two irreducible bucketing literals — one per language — and a "no fifth literal" rule (ADR-007, Task 1.4c).** The grid constants now live in exactly two places: `worker/src/bucketing.rs` (`TIME_BUCKET_MS: i64 = 60_000`, `PRICE_BUCKET_USD: f64 = 5.0` — canonical, hot path) and its TS mirror `server/src/lib/aggregator/bucketing.ts` (`TIME_BUCKET_MS = 60_000`, `PRICE_BUCKET_USD = 5`). The synthesizer and the Binance ingestor import the named helpers (`timeBucket` / `priceBucket` / `TIME_BUCKET_MS`) instead of hard-coding `% 60_000` / `floor(price/5)` / `+ 60_000`. **DO NOT re-introduce a bare `5` or `60_000` as bucketing math anywhere** — the Task 5.2 conformance assertion only watches the two named declarations for drift; a freshly-inlined fifth literal would slip past it. The one deliberately-aliased value is `SYNTH_CELL_CLOSE_INTERVAL_MS = TIME_BUCKET_MS` in `synthesizer.ts`: it is a timer CADENCE (semantically a `setInterval` period, not the grid) that happens to equal the bar width by demo design — aliased rather than re-derived via `timeBucket` so the literal is not duplicated, but kept a named synth constant because its test asserts the numeric value. The remaining inline `60_000`s in `bridge/config.ts` (backoff / crash-loop windows) and `db/partitions.ts` (partition-bound epoch timestamps) are UNRELATED to bucketing — do not "consolidate" them into `TIME_BUCKET_MS`, they are different concepts that share a number by coincidence.
- **`timeBucket(ts)` vs `ts - (ts % 60_000)` are identical for non-negative epoch-ms.** `timeBucket` is `Math.floor(ts / 60_000) * 60_000` (with a signed-floor branch for `ts < 0` that never fires on real ticks). For any non-negative `ts` this equals `ts - (ts % 60_000)`. The 1.4c refactor relied on this equivalence for zero behaviour change — verified by the unchanged ingestor `currentBarTs` tests and the unchanged synthesizer suite (232/232, no fixture regen).
- **Rust CVD is a SIBLING value, NOT a wire frame (ADR-008, Task 1.5e).** `worker/src/aggregator/mod.rs` now computes CVD: `CvdRollup { symbol, bucket_ts, bar_delta, cvd }` (a plain struct — deliberately NO `#[derive(TS)]`, NOT a `BridgeFrame` / `OutboundFrame` variant), a per-symbol `cvd: HashMap<String, f64>` field, `close_expired_with_cvd` / `drain_all_with_cvd` returning `(Vec<OutboundFrame>, Vec<CvdRollup>)`, and a `cvd(symbol) -> f64` getter. The old `close_expired` / `drain_all` are thin wrappers over the `_with_cvd` variants (discard the rollups) so the live `worker.rs` binary and the bridge are untouched. **DO NOT add a `cvd` kind to `BridgeFrame` or the WS `schemas/ws/frame.ts` union** — ADR-008 keeps CVD off the wire in v1; the browser derives its own CVD line client-side (Task 3.2c) by folding `ask − bid` per `cell.close`. The Rust copy is the conformance reference + replay source + reserved (un-built) v2 wire promotion. **DO NOT delete the Rust CVD on the grounds "the browser computes it anyway."**
- **CVD fold order is the byte-identity contract — the load-bearing determinism note.** To stay bit-identical with `core.ts` the Rust port must fold in the SAME order. `open` is a `HashMap` (no insertion order), so `close_expired_with_cvd` (1) SORTS expired keys by `(symbol, bucket_ts, price_bucket)` before draining — this fixes both the `cell.close` emission order AND the within-bar `bar_delta` accumulation order — then (2) folds per-bar deltas into the running CVD in `(symbol, bucket_ts)` sorted order (mirrors `core.ts` line ~293). Operand order is `ask − bid`; running step is `prev + bar_delta`. Same-order IEEE-754 f64 is bit-identical Rust↔V8. **`core.ts` was also changed (Task 1.5e): `closeExpired` now sorts `expiredKeys` by `(symbol, bucketTs, priceBucket)`** (the same order `snapshot()` already used) so the contract the Rust mirrors is itself order-stable. Regenerating the fixtures after that change produced ZERO diff (the committed fixtures' ticks arrive in ascending price order, so the sort is a no-op for them) — but it makes the recorded-dataset path (Task 5.2) deterministic. **If you ever reorder either side's close/fold, reorder both and regenerate.**
- **Canonical aggregator-fixture generator = the TS one (`server/scripts/gen-aggregator-fixtures.ts`).** It is the SOLE writer of `*.expected.json`. The Rust side (`worker/tests/aggregator_conformance.rs`) recomputes the values in-memory and ASSERTS equality against the committed oracle — it does not write the files. This deliberately avoids a dual-writer `serde_json`-vs-`JSON.stringify` number-format conflict (`1.0` vs `1`), so "regenerate from either side → no diff" holds because only one side writes. The Rust conformance test compares numbers as f64 (so `1` == `1.0`) with EXACT equality (fixtures are dyadic). **Do NOT make `gen-fixtures.rs` (the BRIDGE msgpack generator) emit CVD** — that bin is ts-rs / rmp-serde and would put CVD on the bridge schema; the two generators are unrelated (bridge wire oracle vs aggregator JSON oracle).
- **Rust test counts after 1.5e:** `cargo test` = 32 lib unit + 3 aggregator-conformance (`tests/aggregator_conformance.rs`) + 12 bridge-conformance (`tests/conformance.rs`) = 47. ## Replay endpoint notes (Task 1.7, backend-engineer, 2026-06-04)

- **Replay source = Postgres only (ADR-005), NOT data.binance.vision.** PLAN Task 1.7's archive line is explicitly overridden. The archive-ingestion path is a separate deferred capability — do not "fix" the replay route to read ZIPs. Replay = `footprint_cells` (cells) + `ticks` (tape tail); live = worker memory. The two read paths never touch each other.
- **Tick tail is a SIBLING endpoint, not interleaved.** `GET /api/replay/:symbol/:date/ticks?from=&to=` returns a bounded, day-clamped window so 3.6 pulls only ticks around the replay cursor. Do not merge ticks into the cell NDJSON stream — it would blow the ~72K cell budget by 2 orders of magnitude and force full-day re-downloads on scrub.
- **postgres-js returns int8/bigint as STRINGS on the raw `sql` tagged-template path.** Drizzle's `mode:'number'` only applies through the Drizzle query builder. The replay queries use raw `sql` (for the cursor streaming surface), so `bucket_ts`/`price_bucket`/`ts_ms` are cast `::double precision` in SQL to come back as JS `number` (lossless at int53-safe range). If you add a new bigint column to a raw replay SELECT, cast it the same way or the `z.number()` line schema rejects it.
- **Replay cell line != a third cell shape.** `replayCellRowSchema` deliberately reuses the WS `cell.close` TOTALS field names (`bidVolume`/`askVolume`/`trades`, never `*Delta`) + a projected `delta` (`ask_volume - bid_volume` in the SELECT — the STORED column ADR-005 specced was dropped from the row). Replay tick line is a re-export alias of `wsTickPayloadSchema`. 3.6 feeds replay rows through the same reducers it uses for `cell.close` / live `tick`.
- **Empty-but-valid day returns 200 with an empty NDJSON body, not 404.** Friendlier for the 3.6 reducer and "no cells yet today" is a legitimate state, not an error. Off-allowlist symbol / malformed date / malformed window are the only 400 paths.
- **Elysia route-compile timing gotcha (smoke scripts only):** `app.handle()` called in the same synchronous import tick 404s before the radix tree compiles, and `new Request('http://x/...')` (non-hostname-looking host) also breaks path extraction. Use a real-looking host (`http://localhost/...`) and a small `await` before the first `handle` in any bare bun-run smoke. `bun test` and `app.listen()` are unaffected.
