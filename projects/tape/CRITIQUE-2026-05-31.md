## 1. Wow moment status

**Not at the polish level PLAN.md committed to.** The wow moment in
PLAN.md is *"Canvas2D-rendered footprint chart streaming LIVE BTC-PERP
tick data ... at 60 fps under thousands of trades/sec"* with concrete
sub-promises: (a) footprint cells with bid/ask histograms, (b) delta
number bottom-right of each bar, (c) CVD line in a sub-pane, (d) live
tape ticker animating in from the right at real speed, (e) hover
reveals aggregated bid / ask / delta / imbalance for the cell, (f)
replay scrub at 1× / 5× / 30×.

What ships in Phase 3.1 + 3.2 vs that promise:

- **Cells** — present, but only as a single-color imbalance tint per
  cell. The promised *"bid/ask volume per price cell rendered as
  horizontal histograms inside each bar"* is absent. `paintCells`
  draws one `fillRect` per cell with one mixed OKLCH color; there is
  no intra-cell bar split between bid and ask. The visual signal is
  qualitatively weaker than the brief asked for — a cell where bid =
  ask renders identically to a cell where bid = 0 and ask = total at
  the same overall imbalance vs neutral, because the renderer collapses
  to a single hue. TensorCharts / Bookmap / Sierra Chart all draw the
  split. This is the headline gap.
- **Delta number bottom-right of each bar** — absent. The bar (the
  vertical column of cells representing one minute) has no per-bar
  total-delta print. Cell text is the *total* volume `bid+ask`, not
  delta. PLAN.md mentions both; only the volume label is wired.
- **CVD sub-pane** — absent. Phase 3.2 in PROGRESS.md claims "cursor +
  crosshair + cell tooltip + clickable Follow-live affordance — landed
  2026-05-30" but PLAN.md Phase 3.2 is *"Canvas2D CVD line sub-pane,
  sharing the same rAF loop as the footprint"*. The committed Phase
  3.2 task was silently re-scoped. The CVD pane is the second
  load-bearing piece of the brief's footprint identity (footprint +
  CVD divergence is the entire product thesis), and it is not on the
  surface.
- **Live tape ticker animating in from the right at real speed** —
  partially present as `paintRightEdge` in 80 px-wide vertical strip
  inside the canvas. It is *not* "animating in from the right"; it is
  a redraw of the last N ticks at the rAF cadence, with no entry
  motion. The screenshot shows it as a static cyan / red number stack
  that the eye reads as a column of digits, not as a stream. Compared
  to TensorCharts / Aggr.trade live tapes (the explicit benchmark in
  PLAN.md problem framing), this reads as a passive log.
- **Cell hover with aggregated bid / ask / delta / imbalance%** —
  present via `CellTooltip`. This is the one promised piece that
  cleanly delivers.
- **Replay 1× / 5× / 30×** — UI present (Task 2.4 ReplayBar) but
  unwired to data; clicking "Enter replay mode" shows a slider with
  zero data behind it. Out-of-scope for the Phase 3.1/3.2 critique
  but worth noting because a recruiter will click it.

Concretely: the chart paints, scrolls, hovers correctly. It does not
yet *read* as a footprint chart to a trader because the bid/ask split
inside each cell — the literal etymology of "footprint" in this
context — is collapsed to a single color. The wow moment as written
is not landed. It will be landed only when the intra-cell histogram +
per-bar delta print + CVD sub-pane are wired.

## 2. Typography

**Three observations, ranked by severity.**

1. **No variable-font axis use anywhere.** Inter and JetBrains Mono are
   both loaded as static cuts (regular + medium; weight 500 used in
   the BrandMark only). Klim Type Foundry's specimens
   ([klim.co.nz](https://klim.co.nz/)) are the explicit benchmark in
   `docs/inspirations.md` § Type & layout, and Linear's marketing
   site demonstrates `font-variation-settings` for weight axis
   animation on stat counters; both reads as "designed type", whereas
   this app currently reads as "type set in two weights". Inter is a
   variable font (`InterVariable`); the engine is paying the static
   font bytes without using any of the affordance. The cell text in
   the chart is at 10 px JetBrains Mono regular — at that size, a
   `wght 350` cut would read clearer than `400` on dark, but no
   weight tuning happens. **High** severity for a portfolio piece
   that names Klim as the bar.

2. **The brand mark is undersized and underweighted relative to its
   role.** `BrandMark` is `text-base font-medium tracking-tight` —
   16 px, 500 weight, in the same monospaced face as the data. The
   word "Tape" in the top-left corner has the visual weight of a
   status label, not a brand. Compare Linear's nav `Linear` wordmark,
   which uses a deliberately tightened display cut at a larger size
   than body and carries weight contrast against neighbouring nav
   items. The Tape brand mark and the `BTCUSDT-PERP` symbol pill have
   roughly the same visual weight — the eye can't tell which is the
   product and which is the data. Recruiter's first second goes to
   the symbol pill, not the brand.

3. **Tabular numerals are configured but the chart's price-axis
   labels still drift horizontally because `formatPrice` returns
   variable-length strings.** `globals.css` sets `font-variant-numeric:
   tabular-nums` on `[data-numeric]` and tables — good. But the
   y-axis labels in `painters/axes.ts` go through
   `Math.round(price).toString()` for prices ≥ 10, so adjacent labels
   read `71210` / `71215` / `71220` (5 chars each, fine) but at a
   range break could be `71995` / `72000` (5 chars each), and on
   transitions into the next 10k they jump from 5 to 6 chars at
   100000. More importantly the price labels are drawn at
   `textAlign: 'left'` with `axisYRegion.x + 7` as the X — left-edge
   aligned with no decimal alignment. A price ladder reads
   correctly only when decimal points line up; integer-only does not
   teach the eye where the column is. Stripe's pricing tables
   demonstrate this — every numeral aligns to the same decimal
   column with `text-align: right` and `font-variant-numeric:
   tabular-nums` together. Axis labels here should be right-aligned
   to the inside of the axis band, not left-aligned 7 px from the
   tick.

## 3. Hierarchy & layout

**Eye path in the first second: the cyan accent dot on `BTCUSDT-PERP`
in the top bar, then the dense cluster of imbalance-colored cells in
the middle of the chart, then the right-edge price axis.** That is
roughly where the brief wanted it — the chart is the focal point.

But the layout has three accidental quirks that break that path.

- **The chart is mostly empty.** In the reference screenshot, the
  rendered cells occupy about 30 % of the canvas width on the right
  side; the left ~70 % is the grey grid with no data. This is honest
  to the data state (synth has only generated ~30 min of bars) but
  the layout does not handle the empty state — there is no "warming
  up", no skeletal hint, no centred message. The viewer sees a chart
  that looks broken until they realise the bars are on the right.
  Linear's empty states are the benchmark here (empty inbox /
  project / cycle screens are explicitly designed surfaces). Vercel's
  dashboard does the same on a fresh project. **Medium-high**
  severity for a demo URL.
- **The price axis on the right has no decimal alignment AND no unit
  hint.** Bare `71210`-style numbers float along the right edge. A
  trader will read this as price within five seconds; a recruiter
  who is not a trader will read it as "numbers". A `$` prefix or a
  `USD` label on the top tick costs one render and converts the
  axis from "numbers" to "price". Already a known defect on the
  ledger.
- **The right-edge tape strip and the price axis are visually
  indistinguishable from each other.** The strip is a column of
  cyan / red `price qty` rows in the same 10 px JetBrains Mono cut
  as the axis labels. There is no separator, no surface tint, no
  type weight delta between the two. From three feet away the eye
  reads one merged "right column of numbers". The brief commits the
  tape strip as a load-bearing piece of the footprint identity —
  it deserves its own surface treatment (a faint `--color-surface`
  band, or a 1 px `--color-border` vertical hairline). Currently
  `paintRightEdge` paints directly onto `--color-bg` with no
  background.

Whitespace is doing some work — `paddingY: 8` and `paddingLeft: 8`
on `chartConfig` keep the bar grid off the edges — but the chart's
**right padding** (`axisYWidth + rightStripWidth = 136 px`) makes
the bar grid abruptly stop 136 px from the right edge of the canvas.
Visually this reads as a hard rectangular cut, not a deliberate
margin. Rauno Freiberg's site ([rauno.me](https://rauno.me/)) is
the benchmark for "restraint, type, deliberate motion" — Rauno
never wastes a pixel without earning it. Here we waste 80 px
(`rightStripWidth`) of valuable chart real estate on a tape strip
that competes visually with the axis it sits next to.

## 4. Microinteractions

The promise from `docs/inspirations.md` is that microinteractions
match Linear's command palette feel. Reality:

- **Theme toggle does not animate.** `next-themes` is configured with
  `disableTransitionOnChange` (correct, to avoid the FOUC), and the
  Canvas2D engine repaints on `data-theme` flip via the bridge —
  also correct. But the chrome surfaces snap from dark to light
  with zero choreography. Linear's theme switch is a crossfade at
  ~180 ms with the page-chrome and the active surface morphing
  together; here it is a hard color swap. PLAN.md § Animation stack
  explicitly lists *"Theme toggle (light/dark crossfade respecting
  prefers-reduced-motion)"* — that crossfade is not landed. **High**.
- **The theme toggle's hit target reads as plain text.** The button
  is `theme: system` / `theme: light` / `theme: dark` rendered as
  font-mono text in a 1 px-bordered chip. No icon, no glyph, no
  state preview. Compared to Linear's three-state segmented control
  with sun / monitor / moon icons, this reads as a debug affordance.
  `lucide-react` is already in the bundle (Task 2.3 imported four
  icons); add `Sun` / `Moon` / `Laptop` and a Radix `ToggleGroup`
  similar to the replay speed selector. **Medium**.
- **Cell hover has no anticipation cue.** The cursor crosshair +
  focus-ring stroke arrive at the same instant the cursor reaches
  the cell. Linear's nav links use a 100–150 ms ease-out on the
  underline + the foreground color to make the target *feel*
  responsive. The footprint cursor is binary: not-there / there.
  Adding a 60–80 ms eased pulse on the focus-stroke alpha would
  cost nothing and read as "alive". **Low** but recurring.
- **Follow-live pill fade-in (180 ms opacity) is correct duration
  but missing the translate.** `motion.div` animates opacity 0→1
  only. The eye does not register a pure opacity fade at small
  surfaces (~80 px wide) — it reads as "did something appear?". A
  4 px translate-from-top synchronized with the opacity is the
  standard Linear / Vercel pattern. Currently the pill just
  materialises out of the void in the top-right corner.
- **Replay bar height transition** is on the same 220 ms easeOutCubic
  the SideRail uses (correct — single curve constant per AGENT_NOTES
  Task 2.4). The transition itself is fine. What is broken is what
  happens **inside** the bar after expansion: the slider, the
  "Back to Live" button, and the speed toggle all appear instantly
  via conditional render. The bar expands smoothly to 56 px and
  then *pops* its contents in. Either stagger the contents with a
  ~60 ms fade-in trailing the height animation, or hold the contents
  off-DOM until the height transition is half-complete. Compared to
  Linear changelog detail expansions, this reads as a layout
  thrash. **Medium**.
- **Tooltip fade is correctly 120 ms** per `CellTooltip` source.
  However the tooltip has `visibility: hidden` toggled in lockstep
  with `opacity: 0`, which means it disappears instantly the moment
  `cursor === null` rather than respecting the 120 ms fade-out.
  Either move `visibility: hidden` behind a `transition-delay:
  120ms` declaration or drop the visibility toggle entirely (the
  `pointer-events-none` is the actual non-interactive guarantee).
  **Low**.

## 5. Motion & timing

- **One easing constant for the whole app** (`[0.33, 1, 0.68, 1]`
  easeOutCubic at 220 ms) — this is correct per AGENT_NOTES and is
  cheaper than the alternative of every component picking its own
  curve. **No defect here.**
- **But the curve is wrong for the chart's scroll smoothing.** The
  `FootprintChartEngine.#advanceScroll` uses a fixed `SCROLL_SMOOTHING
  = 0.2` linear interpolation per frame, which is a critically-damped
  approximation but reads as a *deceleration without anticipation*.
  Compared to Stripe's [docs sidebar scroll]
  (cubic-bezier(0.16, 1, 0.3, 1) over ~320 ms) or Linear's command
  palette item selection, the chart's scroll feels heavy and
  rubber-banded at the end. The settle-snap at `0.5 px` makes the
  last frame visibly jump because the geometric series gets us to
  ~0.4 px and then the snap closes the gap. Replace with a fixed
  spring (Motion's `spring` config — `stiffness: 240, damping: 30,
  mass: 0.6`) and the snap-jump disappears. **Medium**.
- **No choreography across surfaces.** Opening the MobileRail slides
  the aside in at 220 ms easeOutCubic and fades the overlay at the
  same duration — but the two animations are *parallel*, not
  *staggered*. The overlay should lead by ~40 ms so the dimmed
  context registers before the panel pushes in. This is the Linear
  command palette / sheet pattern (overlay leads, panel trails);
  here both arrive at the same moment, which reads as a single
  "blink" rather than a layered transition. **Low**.

## 6. Color & contrast

**Token discipline is good.** Every component reads from CSS variables
(`bg-(--color-surface)` etc.) and the Canvas2D engine reads tokens
via the bridge — no raw hex anywhere. Light mode parity is genuine
(both modes redefine every consumed token). The OKLCH palette is
thoughtful (consistent hue 250 chroma 0.01–0.015 across the neutrals;
imbalance buy/sell at 152 / 28 hue for perceptual opposition).

That said:

- **`--color-fg-subtle` on `--color-bg` is 5.5:1.** Per AGENT_NOTES
  Task 2.3 this passes AA for normal text (≥ 4.5:1) but it is the
  tightest pair on the page and it is the one used for the status
  bar's `Ticks` / `Last tick` labels. On the reference screenshot
  the status bar text reads as grey-on-grey and the eye fights it.
  Already a known defect on the ledger — confirming. **High**, because
  it is on a 12 % vertical of the viewport that the recruiter sees
  in the first second.
- **`--color-cell-cursor` is `oklch(0.82 0.16 195)` (cyan) — the
  same accent hue as the brand**. The crosshair, the BrandMark area,
  the SymbolIndicator's `Activity` icon, the SideRail's active-state
  inset shadow, and the ReplayBar's Live pip all use the same hue.
  Five surfaces, one color. There is no hierarchy via hue — every
  accent is the *same* accent. Linear's accent system reserves the
  primary accent for the single most important call-to-action on a
  page (the "New issue" button); secondary accents (success / warning
  / data) carry the rest. Here, the cursor (data) and the brand
  (chrome) and the live pip (status) all read at the same visual
  priority. **Medium**.
- **`--color-bid` and `--color-ask` are theme-tuned for AA on the
  chrome surfaces but were not re-verified for AA against
  `--color-cell-bg-strong`.** Dark mode `--color-cell-bg-strong` is
  `oklch(0.4 0.04 220)`; the cell label color `--color-cell-fg` =
  `oklch(0.94 0.005 250)` clears, but the strip's `--color-bid`
  text (used in `paintRightEdge`) over a strong-volume cell behind
  would not be a cell-on-text situation (the strip is separate
  region) — that's fine. The risk is on light mode: `--color-ask` =
  `oklch(0.55 0.2 28)` on `--color-bg` = `oklch(0.985 0.005 100)` is
  ~3.8:1 — fails AA for normal text. The strip prices and the
  tooltip "Ask vol" label use these tokens. **High** for light mode.
- **Focus ring (`--color-focus-ring`) is `oklch(0.82 0.18 195)` —
  same hue family as `--color-accent` and `--color-cell-cursor`.**
  Visible on dark (good) but on light mode at `oklch(0.55 0.18
  200)` the contrast against `--color-bg` (L 0.985) is ~4.1:1 for
  the outline pixels — adequate per WCAG 1.4.11 non-text-contrast
  (3:1) but tight for a focus indicator on a critical replay slider.
  **Low**.

## 7. Responsive integrity

Walked the four breakpoints in AGENT_NOTES Task 2.3 mentally —
source confirms `< 768` mobile, `768–1023` tablet, `≥ 1024` desktop,
`< 480` compact. The chart, per PLAN.md, hides below 768 and the
layout collapses to tape-only.

- **320 px.** TopBar: BrandMark + PanelLeft toggle + SymbolIndicator
  (collapsed "BTC-PERP") + ApiStatus + ThemeToggle in a single 48 px
  row. With ApiStatus at ~95 px wide ("Checking API" + dot) and
  ThemeToggle at ~88 px ("theme: system"), the right cluster is
  ~183 px wide. Plus brand (~52 px) + PanelLeft button (~32 px) +
  gaps (~24 px). Total ~291 px — fits, but barely, and "BTC-PERP"
  pill (~92 px) crashes into the right cluster if the locale
  changes "Checking API" to a longer string. **No code change needed
  yet but the budget is < 30 px of slack — fragile**. The
  `<main>` region shows the empty stub message (since chart is
  hidden by no explicit rule — actually I see no `md:`-only gate
  on the FootprintChart import, the chart renders at 320 px and
  paints nothing because the canvas is 320 × ~400 px and the
  bar region after `paddingLeft + rightStripWidth + axisYWidth =
  144 px` is ~176 px wide, fitting ~7 bars). PLAN.md said the
  layout collapses to tape-only below 768 — this is **not
  implemented**. The chart paints on mobile and looks broken.
  **Blocker** for the mobile recruiter view.
- **768 px.** SideRail auto-collapses to 56 px icon-only on first
  mount per the Zustand bootstrap effect — correct. Chart region
  is ~712 px wide, ~600 px tall (after TopBar + ReplayBar + StatusBar
  vertical chrome). Bar region ~568 wide, ~570 tall → ~23 visible
  bars and ~35 price rows. Density is fine. **OK**.
- **1024 px.** SideRail expanded to 240 px. Chart region ~784 wide,
  ~600 tall. Bar region ~640 wide, ~570 tall. **OK**.
- **2560 px.** Chart region ~2320 wide. Bar region ~2176 wide → 90
  visible bars (1.5 hours). Cell width stays at 24 px (no zoom in
  v1 per scale.ts docblock). The chart fills the viewport but the
  StatusBar text and the SideRail's `workspace` label remain at the
  same 10 / 11 px font size — they read as "tiny" on a 4K monitor.
  Phase 3.4 is named as the zoom phase; the responsive text scaling
  is not on the roadmap. **Medium** — the demo URL will be opened
  on 27"+ monitors by senior recruiters.
