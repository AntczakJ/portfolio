Root cause + fix + proof:
  - **Root cause (traced + confirmed via prod build on :3070).** Each animated section sets up GSAP asynchronously and independently via `useGsapEffect` (`loadGsap().then(...)`), and each used to call `ScrollTrigger.refresh()` in isolation at the end of its own setup. The hero pin is `{ idle: true }` (deferred to `requestIdleCallback`), so it is frequently CREATED LAST — after the downstream gallery pin. `ScrollTrigger.refresh()` recomputes triggers in their internal LIST ORDER (= creation order by default), and a pinned trigger's pin-spacing only shifts the triggers that refresh AFTER it. So the gallery (created first) measured its `start: 'top top'` against a document WITHOUT the hero's ~190vh (1710px) pin-spacer, landing its pin start exactly 1710px too early. **Confirmed in the prod build:** gallery trigger `start` read 3788 instead of the correct ~5498 (delta == the hero pin length 1710); at the services-centered scroll position (scrollY 3914) `servicesInView:true` AND `galleryPinned:true`/`trackTranslated:true` — reproduced on 3/3 buggy runs. Even adding the coordinated refresh alone did NOT fix it (refresh recomputed in stale list order); the missing piece was sorting.
  - **Fix (robust, order-independent — `src/lib/gsap/refresh-coordinator.ts`, NEW).** A tiny shared coordinator: `requestGlobalRefresh()` debounces all sections' refresh requests into ONE `ScrollTrigger.sort()` + `ScrollTrigger.refresh()` on the next frame after the LAST section registers (plus a `window` `load` refresh and a debounced `resize` refresh). **`ScrollTrigger.sort()` is the crux** — it reorders the internal list by `refreshPriority` then document position, so the upstream hero pin precedes the gallery and its pin-spacer is applied BEFORE the gallery is measured, regardless of which chunk loaded first. Wired into `useGsapEffect` (every setup calls `requestGlobalRefresh()` on completion); the per-component isolated `ScrollTrigger.refresh()` calls were REMOVED from `blade-hero.tsx`, `gallery-section.tsx`, `blade-sweep-divider.tsx` (which also dropped their now-unused `ScrollTrigger` destructure).

- **D-A11Y-1 (keyboard).** The service/barber/date/slot options are `<button role="radio">` with NO keydown handler. Verified: the radio receives focus, but neither Enter nor Space activates it. (Mouse + the happy path work; keyboard selection does not.) This contradicts the AGENT_NOTES "radiogroup … keyboard-operable" claim. **This is a WCAG 2.1.1 keyboard failure — a real a11y blocker for the quality bar.**
- **D-A11Y-2 (focus management).** Focus does NOT move to `#wizard-step-heading` on step advance. The heading is focusable directly (`h2[tabindex=-1]`), but the wizard's `setTimeout(80ms) -> heading.focus()` never lands it (focus stays on `<body>` after every advance — radio-click OR Continue button). The specced focus-on-advance a11y contract is inert in the prod build. Likely the 80ms fires before AnimatePresence mounts the incoming heading / before paint.
