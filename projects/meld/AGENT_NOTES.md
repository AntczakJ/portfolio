# meld — Agent Notes

> Append-only cross-agent context. Every subagent reads on start, appends on end.

## Gotchas

- **The `onMessage` raw-`MessageEvent` path is now FULLY REMOVED from the web client (Task 2.5c, frontend-engineer 2026-06-02, ADR-011).** The gotcha immediately below documents the `9b06f7e` `onMessage` raw-`MessageEvent` trap — it is now HISTORICAL. As of Task 2.5c, `web/src/lib/yjs/provider.ts` no longer wires ANY `onMessage` callback (not even a defensive no-op — per ADR-011, a no-op still registers a listener on the provider's emitter `forEach` surface, which is the exact fragility class being eliminated). Control messages arrive via the `onStateless: ({ payload }) => ...` config callback instead; the `9b06f7e` dual-shape `MessageEvent` defensive handler is GONE because nothing custom rides raw `'message'` frames anymore — the provider's own handler is the sole consumer of the `'message'` event. The old exported `handleProviderMessage` (TEXT/BINARY discrimination) is replaced by `handleStatelessControlMessage(payload: string, onUnknown?)`, which guards `JSON.parse`, `safeParse`s the SAME `welcomeFrameSchema` (payload shape unchanged per ADR-011), and dispatches to `useWelcomeStore.setWelcome`. The `9b06f7e` `onMessage`-wiring regression test was removed (it guarded a path that no longer exists) and replaced by a `createBoardProvider onStateless wiring` suite. **DO NOT reintroduce an `onMessage` callback** — if a future task needs to observe raw frames, prefer the framework's typed callbacks (`onStateless`, `onSynced`, `onAwarenessChange`) over re-opening the `'message'` emitter surface. The next gotcha is kept only as the cautionary record of WHY the `onMessage` path was dangerous.
- **HocuspocusProvider 4.1 `onMessage` config callback receives the RAW browser `MessageEvent`, NOT `{ event, message }` (CRITICAL — frontend-engineer 2026-06-02; HISTORICAL as of Task 2.5c — see the note ABOVE; the `onMessage` path is removed).** The provider's published `onMessageParameters` type declares `{ event, message }`, but that type does NOT match the runtime emit for the `onMessage` config-callback path. At runtime `attachWebSocketListeners` does `const onMessageHandler = (payload) => this.emit("message", payload)` where `payload` is the raw `MessageEvent` straight off `ws.addEventListener('message', ...)`. The original wiring in `web/src/lib/yjs/provider.ts` destructured `onMessage: ({ event }) => handleProviderMessage(event, ...)` — `.event` off a `MessageEvent` is `undefined`, so `handleProviderMessage(undefined)` hit `typeof event.data` and threw `TypeError: Cannot read properties of undefined (reading 'data')` on every incoming frame. **Why catastrophic, not cosmetic:** our `'message'` listener is registered BEFORE the provider's own y-protocol sync listener, the emitter dispatches via `forEach`, and a SYNCHRONOUS THROW in one listener aborts that loop — so the framework's own sync + awareness handler never ran. Result: Yjs document sync AND awareness were completely dead over the wire while the socket itself stayed connected (`/health.ws` showed `connectedClients: 2, roomCount: 1` but nothing propagated, no cursors, the page logged the TypeError ~4×). **The fix (DO NOT REINTRODUCE):** `onMessage` must accept BOTH shapes and MUST NOT throw — `const event = raw instanceof MessageEvent ? raw : raw.event; if (!event) return;` — and `handleProviderMessage` early-returns on a nullish event as a belt-and-braces second guard. Regression coverage lives in `web/src/lib/yjs/__tests__/provider.test.ts` under the `createBoardProvider onMessage wiring (raw MessageEvent regression)` describe block (it mocks `@hocuspocus/provider`, captures the real `onMessage` closure, and invokes it with a RAW `MessageEvent`). The pre-existing tests only called `handleProviderMessage` directly with a synthetic event, so they never exercised this closure — that is the test gap that let the bug ship to the deployed demo.
- **The `"Unexpected end of array"` pageerror — ROOT-CAUSE RESOLUTION RATIFIED by ADR-011 (architect 2026-06-02; implementation queued, NOT yet landed).** Root cause (independent of the `onMessage` fix above, framework-internal): HocuspocusProvider's websocket-level message handler unconditionally runs `new Uint8Array(event.data)` + `new IncomingMessage(...).peekVarString()` on EVERY frame, including our ADR-004 TEXT control frames (welcome / overrun / board-deleted). For a string `event.data`, `new Uint8Array(string)` yields a zero-length array and `peekVarString` on an empty decoder throws "Unexpected end of array". HARMLESS to functionality (browser `addEventListener` error reporting does not stop other listeners or future frames — binary sync + awareness still process), but a red console error once per board load on a portfolio demo. **ADR-011 ratifies the architect call: MOVE control messages off raw TEXT frames onto Hocuspocus's Stateless message channel** (server `Connection.sendStateless` / `Document.broadcastStateless`; client `onStateless: ({ payload }) => ...`). A stateless message IS a valid y-protocol envelope (`MessageType.Stateless = 5`), so the provider decodes + routes it instead of choking — eliminating the error AND deleting the fragile raw-`MessageEvent` `onMessage` interception that caused the `9b06f7e` sync-killer. The one-byte-binary-prefix alternative was considered and rejected (fights framework internals — the exact class that produced `9b06f7e`). Implementation is queued as Task 1.X-stateless (backend) + Task 2.5c (frontend). DO NOT re-flag this as an open architect question — it is decided; see ADR-011.
- **Hocuspocus Stateless API — verified signatures for the ADR-011 implementation (architect 2026-06-02).** Read against the installed 4.1.0 type defs; cite these in the Task 1.X-stateless / Task 2.5c code docblocks. **Server (`node_modules/.pnpm/@hocuspocus+server@4.1.0_*/node_modules/@hocuspocus/server/dist/index.d.ts`):** `Connection.sendStateless(payload: string): void` (line 779) — use for `welcome` (per-connection) on the `connected` hook and for `control.overrun` (per-connection) before the `4290` close; the connecting `Connection` is on `connectedPayload.connection` (line 519) — the SAME hook + handle the current `meld-welcome-emit` extension already reads, so the welcome migration is just swapping the send call inside `welcome.ts`. `Document.broadcastStateless(payload: string, filter?): void` (line 104) — use for `control.board-deleted` in the retention sweep (replaces the per-connection `webSocket.send` loop). `MessageType.Stateless = 5` (line 336). NOTE: `sendStateless` wraps the string in a y-protocol envelope (NOT a raw TEXT frame) — that is the whole point; it is why the provider decodes it instead of choking. **Client (`@hocuspocus+provider@4.1.0_*/.../dist/index.d.ts`):** config callback `onStateless: (data: onStatelessParameters) => void` (line 352) where `type onStatelessParameters = { payload: string }` (lines 162–164) — a clean `{ payload: string }`, NO `MessageEvent` ambiguity (this is exactly why ADR-011 deletes the raw-`MessageEvent` `onMessage` trap). `MessageType.Stateless = 5` (line 92) confirms the provider decodes the opcode natively. The provider extends `EventEmitter` so `provider.on('stateless', ...)` also works, but standardize on the `onStateless` CONFIG callback (constructed alongside the provider, no separate `.on()` to tear down).
- **Hono dev runtime — `tsx` not `tsc-watch` (Task 1.1, backend-engineer 2026-05-31).** Picked `tsx watch src/server.ts` for the `dev` script and `node --import tsx src/server.ts` for `start`. `tsx` is the lower-friction path on Node 22: a single dep, ESM-native, no separate transpile-then-run handshake, and `tsx watch` does the source-edit restart loop without a side process. `tsc-watch --onSuccess "node dist/server.js"` was considered and rejected because it (a) writes a `dist/` we then have to gitignore separately, (b) doubles the dev-loop latency (tsc emit + node spawn) vs tsx's in-process transform, and (c) cleanly separates `dev` and `build` in a way that hides the production-mode source map quirk under one more layer. `build` is `tsc --noEmit` (typecheck-only) for Task 1.1 — a real bundle target (esbuild / tsup / `tsc` emit + `node dist/...`) is deferred to the Phase 6 deploy-prep task, mirroring tape's path where the production bundle landed late.

- **Per-tool drawing-commit contract — live LOCAL preview + ONE Yjs op at gesture END (ADR-010 pin, architect 2026-06-02).** Canonical rule for EVERY drawing tool: render in-progress feedback on the LOCAL preview canvas from an IN-MEMORY draft, and commit to Yjs exactly ONCE inside a single `doc.transact` at the natural end of the gesture (pointerup / Enter / blur / drag-end). NO tool writes to Yjs on pointermove or keystroke cadence. **freehand/pen:** points accumulate in the in-memory `FreehandDraft` and paint on the preview canvas during the drag; pointerup commits the whole stroke once (`createShape({ kind: 'freehand', initialPoints: <full list> })` → one root `set`). Decimation while sampling: min-distance 2 px OR 16 ms gate, hard ceiling 2000 points. **rect/ellipse:** already this pattern (canonical). **drag/move/resize (Phase 3.2b):** preview ghost during the gesture, ONE op on drag-end. **text:** commits on Enter/blur, not per keystroke. This is BOTH the freehand-bug fix AND the client-side DoS mitigation (one op/stroke, not ~60/sec) — they are the same change. Do NOT reintroduce live per-point Yjs writes for "watch them draw live"; that is the deferred F3 option (v1.1/v2: ~5-10 Hz batched append + `observeDeep`, with a documented bandwidth/`maxRate`-headroom cost).
- **The engine's shape-root `observe` STAYS SHALLOW — do NOT switch to `observeDeep` (ADR-010 pin, architect 2026-06-02).** `engine.ts:363` uses `this.#shapesMap.observe(...)` (shallow root `Y.Map.observe`). The freehand bug was NOT "the observer is too shallow" — it was that the overlay wrote points into a shape's NESTED `Y.Array` on every pointermove, and a shallow root observer correctly does not fire on a nested mutation, so the stroke never repainted live. The ADR-010 fix REMOVES those live nested writes (points go to the in-memory draft + preview canvas instead) and commits one ROOT insert on pointerup — a root-key change the existing shallow observer already catches. So `observeDeep` is NOT needed and must NOT be added: it would re-couple paint cost to mutation depth (every nested edit of every shape — future text edits, drag/resize — would fire the dirty flag), undoing ADR-008's one-boolean-flip-per-root-change discipline. If a future task "fixes" a missing repaint by reaching for `observeDeep`, STOP — the right fix is almost always to commit the mutation as a root-level change, not to deepen the observer.
- **Client-side op-rate guard sits UNDER the server `maxRate: 100` (ADR-010 pin).** A token-bucket guard caps client op emission at `CLIENT_OP_RATE_CEILING = 40` ops/sec sustained + `CLIENT_OP_BURST_ALLOWANCE = 20` ops burst, calibrated as a fraction of the server `maxRate: 100` (ADR-002) so a runaway client self-limits BEFORE earning a user-visible `4290` close. A `doc.transact` is ONE op regardless of shape count (a 50-shape paste = one op = legitimate, never throttled). If `maxRate` ever changes, recalibrate the client ceiling — the relationship is documented in code. The `4290` overrun UX reuses the EXISTING ADR-009 `<ConnectionBanner />` + `<OfflineAriaLiveRegion />` chrome (NO toast dependency — `sonner` is absent) with overrun copy + `retryAfterMs` + a provider disconnect/reconnect-after-`retryAfterMs` cycle; local edits stay in the Y.Doc and sync on reconnect. The overrun frame already arrives via ADR-011's `handleStatelessControlMessage` → `onUnknownControlFrame` route (currently a dev-warn) — Task 3.X-commit-contract directs that route to the real handler.

- **Drizzle bytea ↔ Yjs Uint8Array coercion (ADR-003 pin).** Drizzle ORM 0.30.x on the `postgres-js` driver exposes `bytea` columns as `Buffer`, while `Y.encodeStateAsUpdate` returns `Uint8Array`. Inside the Hocuspocus `Storage` adapter: **write path** wraps the Yjs blob with `Buffer.from(uint8.buffer, uint8.byteOffset, uint8.byteLength)` before passing to Drizzle; **read path** wraps the Drizzle `Buffer` with `new Uint8Array(buffer.buffer, buffer.byteOffset, buffer.byteLength)` before returning to Hocuspocus. If the project upgrades to Drizzle 0.31+ (which exposes `bytea` as `Uint8Array` natively on `postgres-js`), the coercion becomes a no-op — the comment lives on as a load-bearing historical pin. Do NOT delete it under a "remove dead code" review pass.
- **Yjs encoded-state baseline (ADR-003 reference number).** A 200-shape whiteboard with 1000 edits encodes via `Y.encodeStateAsUpdate(doc)` at ~20–100 KB before Yjs's deletion-set GC sweep, ~10–60 KB after. v1's PLAN.md ceiling targets hundreds of shapes per board, not thousands — even a 10× safety multiplier sits comfortably inside Postgres bytea's 1 GB row limit. This is the reference number the chunking-not-needed-in-v1 decision is built on; if a future feature (e.g., images, multi-page boards, complex Y.Text history) pushes the encoded blob past ~10 MB, revisit the ADR-005 candidacy for chunking.
- **Per-board `board_ops.seq` is in-memory monotonic, NOT a Postgres global serial (ADR-003 pin).** The `seq` column is assigned inside the adapter's `appendOp` from a per-board counter that is seeded on adapter boot by `SELECT MAX(seq) FROM board_ops WHERE board_id = X`. This keeps the sequence per-board monotonic (the load-bearing property for the `WHERE seq > snapshot_seq` SELECT path) without coordinating a global sequence across boards. If the adapter ever gains a multi-instance deployment, this counter becomes a shared-state hazard — for v1 single-instance Node deployment it is fine.
- **WS control frames are TEXT frames, NOT Yjs binary opcodes (ADR-004 pin).** The y-websocket protocol is BINARY-only (`0x00` sync, `0x01` awareness, unknown opcodes silently ignored). meld's application-level control frames are JSON over WebSocket TEXT frames — `connection.send(JSON.stringify(payload))` on the Hocuspocus side, `if (typeof event.data === 'string') handleControl(event.data) else handleYjs(event.data)` on the browser side. The branch is one LOC. Yjs binary frames are untouched; the `WebsocketProvider` ignores TEXT frames natively, so the control TEXT layer is strictly additive to the y-websocket wire. Do NOT propose smuggling control payloads inside `0x80+` reserved opcodes — that path was considered and rejected because an opcode-prefix bug routes a control frame into the Yjs sync handler and crashes the protocol decoder mid-board-session (much worse blast radius than the TEXT/BINARY split's "skip malformed control, Yjs path untouched"). Hocuspocus docs primarily show BINARY-frame examples for custom out-of-band data — TEXT is supported by the underlying `ws` library but is the less-trodden path; backend-engineer Task 1.X-control verifies on the smoke test.
- **WS welcome-frame canonical payload (ADR-004 pin, quotable in README).** Server emits exactly once per connection inside Hocuspocus `onConnect` after origin-check passes. Fields: `kind: 'welcome'`, `session: { id (16-char base32), emojiName (codepoint from `src/lib/identity/emoji-names.ts` allowlist), color: { l, c, h } (OKLCH triplet deterministic from session id) }`, `board: { id (base32-12, echo of :boardId), createdAt (ISO 8601 UTC), connectionCount (post-connect, this client included) }`, `origin` (the `MELD_ALLOWED_ORIGINS`-validated origin echoed for client-side defence-in-depth cross-check against `window.location.origin`), `serverTime` (ISO 8601 UTC, for client clock-skew measurement), `protocolVersion: 1` (load-bearing forward-compat marker; v2 servers emit `2` and v1 clients fail fast with a structured warning before closing cleanly — no silent data loss).
- **WS overrun-frame payload (ADR-004 pin, ties ADR-002 backpressure to a wire reason code).** Server emits IMMEDIATELY BEFORE the framework-level close with code `4290` (ADR-002 backpressure boundary). Fields: `kind: 'control.overrun'`, `reason: 'queue.overflow' | 'rate.exceeded' | 'message.too-large'` (discriminated from which Hocuspocus boundary fired — `maxMessageSize`, `maxRate`, or `timeout` respectively), `closeCode: 4290` (echoed for client-side log correlation), `retryAfterMs` (server's suggested cool-off before reconnect; e.g., 1500). The client's `WebsocketProvider` reconnect-backoff multiplies `retryAfterMs` with its own backoff curve to prevent a reconnect storm if all 50 connections of a board hit `control.overrun` simultaneously. A symmetric `control.board-deleted` frame (kind, boardId echo, `closeCode: 4404`) precedes ADR-003's nightly retention sweep deletes that race with live sessions.
- **Heartbeat policy: protocol-level WS ping ONLY in v1 (ADR-004 pin).** Hocuspocus delegates to the `ws` library which surfaces `pingInterval` — configured explicitly to `30_000 ms` in the server bootstrap (grep-able, not implicit-from-defaults). The browser receives ping frames at the protocol layer (transparent to JavaScript) and the platform responds automatically. The application-level `'heartbeat'` discriminator stays RESERVED in the v1 vocabulary as a type-only stub so v1.1 can light it up without breaking the wire — v1.1 reactivates it IF the deployed demo's load-balancer idle-timeout eats protocol pings under cross-region routing (Fly.io and Railway have shipped 60 s idle timeouts in the past, and protocol ping CAN be eaten by some intermediaries). Cadence on reactivation: 25 s (under typical 60 s idle-timeout floor). The reserved-stub kind in v1 is intentional dead schema — same "intentional dead code with documented reactivation path" convention as better-auth. Do NOT delete it under a "remove dead code" review pass.
- **WS v2 extension reservation pattern (ADR-004 pin).** The discriminator namespace is split: `control.*` is the namespace for "server-initiated event the client must observe BEFORE the server does the thing" — disconnects, permission events, tier limits (examples: `control.permission-revoked`, `control.tier-limit-reached`, `control.auth-required`, `control.maintenance-window`). Bare verbs (`welcome`, `heartbeat`, `settings.update`, future `board.bookmark`, `cursor.snap-to`, `presence.follow-user`) are the steady-state channel for client-driven or routine server-driven app-level state. Adding a kind WITHOUT removing or renaming an existing one stays on `protocolVersion: 1`. Removing or renaming bumps to `protocolVersion: 2` and v1 clients fail fast per the welcome-frame `protocolVersion` literal check. This split is the load-bearing v2 extension contract; do NOT propose a single flat namespace in a review pass — it forecloses the "server is about to do X" channel that ADR-002's backpressure path and ADR-003's retention sweep both depend on.
- **Anonymous session cookie attributes verbatim (ADR-005 pin, quotable in README security section).** `Name: meld_session`, `Value: <UUID v4 36-char hyphenated lowercase>`, `HttpOnly: false` (JS-readable for first-paint identity card render — XSS-readability delta is zero in v1 because anonymous identity has no write authorization tied to it), `Secure: true` in production (`NODE_ENV === 'production'`) / `false` in dev (localhost parity), `SameSite: Lax` (NOT `Strict` — share-link from email/Slack must set cookie on first cross-site arrival; v1 has no iframe-embed so `None` is not a candidate), `Path: /`, `Domain` UNSET (host-only — future `api.meld.example.com` does NOT silently share the session), `Max-Age: 31536000` (1 year). - **Emoji whitelist convention (ADR-005 pin).** 128 single-codepoint emoji from Unicode 15.1 animals + nature + food + drink subsets, sorted lexicographically by Unicode codepoint hex, NO ZWJ sequences / skin-tone modifiers / regional indicator pairs (so string slicing + equality stays single-codepoint-safe), frozen `as const` in `meld-server/src/lib/session/emoji-names.ts`. Each entry is `{ codepoint: string; name: string }` where `name` is a lowercase ASCII aria-label (`"otter"`, `"fox"`, `"peach"`, `"sushi"`). 128 = 2^7 — clean power-of-two modulo space for uniform FNV-1a distribution. **The append-only contract is load-bearing**: reordering the array silently re-assigns every visitor's identity. Any future curation edit MUST append to the end of the array, never reorder, never delete. Top-of-file comment documents the contract. `meld-web` does NOT bundle the whitelist — the welcome frame carries the codepoint string directly.
- **Multi-tab awareness rule (ADR-005 pin).** Each WebSocket connection is its own awareness identity — Hocuspocus's framework-default distinct `awarenessId` per connection is preserved. `connection.context.sessionId` is carried alongside as a stable tag (populated from the cookie at `onConnect`). Frontend avatar-stack code DOES NOT deduplicate by `sessionId` — two tabs of the same browser show as two avatar pills, both with the same emoji-name and color (the cross-board identity thread). This is the deliberate "two tabs = two cursors" UX: the wow moment is "open a second tab and see another cursor appear in real time", and collapsing same-`sessionId` connections into one pill would visually defeat the demo. Other viewers intuit "that person has two tabs open" because the two pills share the same emoji-name and color. Do NOT propose a deduplication pass in review — it has been considered and rejected.
- **v2 auth migration sketch (ADR-005 pin, two-sentence summary).** When better-auth lights up: cookie name stays `meld_session`, value becomes a signed better-auth token, attributes tighten to `HttpOnly: true` (auth tokens are XSS-exfiltratable in a way anonymous identity is not), Hocuspocus `onConnect` resolves the token to a `userId` via the better-auth adapter, welcome frame's `session.id` becomes the userId AND anonymous-fallback visitors get `guest:<uuid>` so the client distinguishes authenticated from guest in the avatar stack. The first-paint identity card client-render rewires through Next.js `cookies()` SSR-injected hydration instead of `document.cookie` reads — JS cannot read the `HttpOnly` cookie any more. Migration is additive (no wire-format breakage); v2 documented in `meld-server/src/lib/session/README.md`.

## Decisions to revisit

- **Hono WebSocket adapter choice.** **Closed by ADR-002 (2026-05-31): Hocuspocus server mounted on the same Node `http.Server` as Hono.** Hono owns HTTP control routes, Hocuspocus owns `/ws/board/:boardId`. Room registry IS the Hocuspocus `Server.documents` map — do NOT build a parallel `Map<boardId, WSSharedDoc>` registry. Origin check via `onConnect` hook reading `MELD_ALLOWED_ORIGINS` env var (shared with HTTP CORS), close code `4401` on miss, fail-closed in production. Backpressure ADOPTED in v1 via Hocuspocus config (`maxRate: 100`, `maxMessageSize: 1 MB`, `timeout: 30_000 ms`), close code `4290` matches tape ADR-006 shape.
- **Hocuspocus extension-hook quirks for backend-engineer day-one instrumentation.** (a) `onStoreDocument` debounce config has two knobs — `debounce` (idle window before flush) and `maxDebounce` (max time between flushes regardless of activity); ADR-003 must pin both, not just one. (b) `connection.context` is mutable across the connection lifetime but reads inside hooks see the snapshot at hook-entry time — if ADR-004's welcome frame depends on session-id rotation mid-connection, this becomes a race; current design (welcome frame is one-shot at `onConnect`) avoids the race. (c) `onAwarenessChange` fires after the framework's 16 ms tick coalescing window, NOT on every raw awareness frame — observability counters in `/health.ws` must NOT use `onAwarenessChange` as a per-frame counter source; use `onChange` for that. (d) Hocuspocus's `Server.documents` is a `Map<documentName, Document>` and `Document.getConnectionsCount()` is sync — safe to call inside the `/health.ws` HTTP handler.

## Cross-cutting concerns

- **Frame contract is the integration boundary.** Zod schemas in `src/lib/schemas/` are the single source of truth for non-Yjs control frames (welcome, board metadata, overrun). Both server (Hono handler) and client (Yjs `WebsocketProvider` wrap) import from the same file. Per `docs/conventions.md` § 5. ADR-004 will pin the exact shape.
- **Yjs sync + awareness frames pass through unchanged.** The y-websocket protocol is its own binary format. Do NOT validate Yjs frames against Zod — they are opaque to our schema layer. Validation happens at the Yjs protocol layer (which is the responsibility of `y-websocket-server` on the backend and `WebsocketProvider` on the frontend).
- **Reduced motion.** `prefers-reduced-motion` must disable Motion transitions on cursor smoothing AND on avatar-stack enter / exit. The interpolated cursor falls back to instant snap-to-position; the avatar stack falls back to no-animation enter / exit. Reviewer-checked.
- **OKLCH color assignment is deterministic from session id.** Hash `session_id` into a slot in the ~12-color palette. Same session id = same color across reloads. Two different session ids = different colors (modulo palette size). Documented in `src/lib/identity/color-assignment.ts` (shared between server welcome-frame generator and client awareness state seeder).
- **Backpressure on the WebSocket fan-out.** Per-client send-queue cap (suggest 256 frames). Drop oldest Yjs sync messages on overflow — but Yjs's sync handshake should self-heal because the next sync round catches the dropped delta. Awareness frames are coalesced server-side per-room per-tick (16 ms window). Reviewer-checked in backend Phase 1.4.
- **Snapshot writer correctness invariant.** Any snapshot written to Postgres must replay to the same in-memory `Y.Doc` state via `Y.applyUpdate(newDoc, snapshotBytes)`. Conformance test in Phase 5.2 enforces this on a synthetic op stream.
- **Compaction sweep atomicity.** When the compaction sweep merges N incremental updates into one snapshot row, the operation must be atomic against concurrent readers — readers may see the pre-merge chain OR the post-merge snapshot but never a torn state. Use a single transaction with `is_compaction = true` flag + `superseded_at` timestamp on older rows, never delete-then-insert.
- **Recovery loss bound (ADR-003 pin) — quotable in README architecture section.** On server crash mid-write: at most the sub-second fsync window of ops that the server received but had not yet flushed via `onChange` to Postgres, AND only for edits whose originating client also disconnected without buffer flush in the same window. Surviving Yjs clients re-broadcast their unack'd local ops on reconnect via the y-websocket sync handshake, so the persisted-state loss is bounded by the intersection of "in-flight on the server" AND "originating client also gone". The 5 s `debounce` and 30 s `maxDebounce` affect ONLY the snapshot (the cold-start fast path), NOT durability of individual ops — `board_ops` rows commit on every sync-update frame.

## Implicit assumptions the brief left for downstream agents to challenge

- **That Yjs's wire format is sufficient for presence latency targets.** Yjs's binary update encoding is 30–60 % smaller than Automerge's on typical whiteboard sessions, well inside the 100 ms perceived-latency budget on a typical network. Challenge only if a recorded session reveals systemic frame-size growth.
- **That `y-websocket-server`'s `setupWSConnection` handles per-room broadcast fan-out correctly out of the box.** It does — the reference implementation is the canonical pattern for the whole Yjs ecosystem. ADR-002 will verify this against the chosen Hono adapter.
- **That Canvas2D (not WebGL / WebGPU) is the right rendering layer.** Canvas2D suffices for the v1 shape count (target: hundreds of shapes per board, not thousands). WebGPU is reserved for the optional project #6 in the portfolio plan and would over-complicate this one.
- **That Postgres bytea is the right persistence target for Yjs document binaries.** Below the chunking threshold (~1 MB per row, which Postgres handles fine without TOAST pessimisation) this is trivial. ADR-003 will pin the chunking strategy for larger boards.
- **That anonymous session cookies are sufficient identity for the v1 demo.** They are — the wow moment is the CRDT, not the auth flow. Cross-device cross-browser identity is v2 (better-auth activation).
- **That v1 single-board-per-URL is sufficient demo surface.** It is — the share affordance + "open new tab" path delivers the wow moment without a multi-board navigation surface. Multi-board navigation / "my boards" list is v2.
- **That the y-websocket protocol's reconnect-and-resume semantics work without our intervention.** They do — the protocol is designed for offline-edit / reconnect-merge, which is exactly the wow moment we need. Challenge only if the 30-tab stress test (Phase 5.4) reveals a systemic loss.

## Task 1.4 — Hocuspocus bootstrap on shared http.Server (2026-05-31)

- **Hocuspocus 4.1 API verification — exact method names.** ADR-002's planning brief referred to `Server.attach(httpServer)` and `Server.documents` as the integration points. Against the installed `@hocuspocus/server@4.1.0` (verified by reading `node_modules/@hocuspocus/server/dist/index.d.ts`), the actual surface is:
  - **No `Server.attach()` exists.** The high-level `Server` class owns its own `http.Server` internally (constructor calls `createServer(this.requestHandler)` at upstream `Server.ts` ~line 1427 in the bundled esm). It routes upgrades through `crossws/adapters/node`, NOT raw `ws`.
  - **Correct integration pattern for "mount on the same http.Server as Hono"**: use the lower-level `Hocuspocus` class (also exported from the package) + `ws.WebSocketServer({ noServer: true })` + a hand-rolled `httpServer.on('upgrade', handler)` listener. `Hocuspocus.handleConnection(ws, request, defaultContext)` returns a `ClientConnection` with `handleMessage(data: Uint8Array)` and `handleClose({ code, reason })` — these are what an external WS adapter calls from its own `message` / `close` event handlers. The signatures are stable per the published `.d.ts` file.
  - **`documents` is on the `Hocuspocus` instance** (`Map<string, Document>`), NOT on the `Server` wrapper. Backend code that needs the room registry calls `meldWs.hocuspocus.documents` (a `Map`) or — preferred — `meldWs.hocuspocus.getDocumentsCount()` / `getConnectionsCount()` (synchronous getters that mask the internal iteration).
  - The `connection.context` ADR-002 named is also stable: `onConnect` returns a value of type `Context` (typed via `Hocuspocus<Context>` generic), which becomes accessible on `payload.context` for every subsequent hook.
- **Path-filter wrapper pattern (one paragraph).** Hocuspocus 4.x's stock `Server` class accepts WS upgrades on every path. Since we mount on the same `http.Server` as Hono via `noServer`-mode `ws`, the upgrade-event handler must path-filter manually. Pattern in `src/lib/ws/server.ts` `attach(httpServer)`: the handler reads `request.url`, slices off the query string, runs against `WS_BOARD_PATH_RE = /^\/ws\/board\/([A-Za-z0-9_-]+)$/`. On miss, raw `socket.write('HTTP/1.1 404 Not Found\r\nConnection: close\r\nContent-Length: 0\r\n\r\n'); socket.destroy()` — no WS handshake, no `ws.WebSocketServer` invocation. On match, the Origin allowlist check runs at the upgrade level (HTTP 403 reject before `handleUpgrade` — defence-in-depth against the `onConnect` hook ALSO running), then `wss.handleUpgrade(request, socket, head, ws => bridgeConnection(ws, request, boardId))`. The pre-upgrade Origin check is the canonical place to refuse — `onConnect` runs AFTER the WS handshake completes, so an accept-then-immediate-close looks worse to clients than a clean HTTP 403 at the upgrade boundary.
- **Backpressure config mapping — Hocuspocus 4.1 vs ADR-002.** ADR-002 named three knobs: `maxRate: 100 msg/sec/client`, `maxMessageSize: 1 MB`, `timeout: 30_000 ms`. Hocuspocus 4.1 supports two of three:
  - `timeout: 30_000` — `Configuration.timeout` field. Wired.
  - `maxMessageSize` — NOT in `Configuration`. - **Per-board `op_seq` concurrency strategy — `INSERT ... SELECT MAX(op_seq) + 1` is the v1 single-instance path.** Inside `onChange` the adapter issues a single SQL statement:

  ```sql
  INSERT INTO board_ops (board_id, op_seq, update)
  SELECT $1::uuid, COALESCE(MAX(op_seq), 0) + 1, $2
  FROM board_ops
  WHERE board_id = $1::uuid
  ```

  **CORRECTED 2026-06-02 (CRITICAL prod-crash fix). The claim below this paragraph that this was "race-free for v1" / "a theoretical not-empirical concern" was WRONG and crashed the live demo.** The framework's per-document `saveMutex` guards the in-memory `Y.Doc` integration, NOT the `onChange` DB write — `onChange` runs AFTER the doc is updated and is fired fire-and-forget, so two concurrent same-board edits (the NORMAL case once collaboration works — two tabs drawing at once) BOTH reach the unguarded `INSERT ... SELECT MAX+1`, both read the same `MAX(op_seq)` under READ COMMITTED, and one INSERT raises `23505` on `board_ops_board_id_op_seq_unique`. Because the `onChange` promise is unawaited, the rejection became an `unhandledRejection` and Node's default policy terminated the process (live Fly log: `Key (board_id, op_seq)=(<uuid>, 37) already exists` then the Node version banner + exit; health 0/1). **The fix (now in `appendOp` in `storage.ts`):** each append runs inside `db.transaction` taking `pg_advisory_xact_lock(hashtextextended('board_ops:' || board_id, 0))` BEFORE the SELECT-MAX + INSERT — same-board appends serialize (second waits for first to COMMIT, then reads the post-commit MAX), different boards take different lock keys and do not contend. A bounded retry on 23505 (`OP_SEQ_MAX_RETRIES = 5`, recompute MAX+1 each attempt, count on `opSeqRetries`) is defense in depth; we NEVER `ON CONFLICT DO NOTHING` (it drops the op and corrupts the monotonic replay contract). 23505 detection walks `err.cause` — Drizzle WRAPS the postgres-js error so `err.code` is undefined and `err.cause.code` is the real `23505` (verified empirically; a naive `err.code` check would silently never retry). Empirical proof recorded in the reproduce-then-fix test: with the lock, 50 concurrent same-board appends → 50 contiguous ops, 0 retries, 0 errors; with the lock disabled (retry only), 40-way contention → process stays alive but ~11 ops dropped — so the advisory lock is the load-bearing zero-loss mechanism and the retry+catch are the survive-anyway net. **Multi-instance deployment is STILL a shared-state hazard for the advisory lock** if two PG backends resolve the lock independently (they would not on one Postgres instance, but a future pgbouncer transaction-pooling or multi-DB topology could split it); the v2 horizontal-scale answer remains (a) the advisory lock as-is on a single shared Postgres, (b) a Redis INCR keyed by `boardId`, or (c) the CF Durable Objects single-writer shape (ADR-001/002). v1 is single-instance per ADR-001/ADR-006 so the lock is sufficient and correct.

  HISTORICAL (now superseded — preserved so a reviewer sees what the wrong reasoning was):

- **Atomic write isolation level: PostgreSQL default (READ COMMITTED) is sufficient.** The snapshot UPSERT + ops DELETE pair lives inside ONE `db.transaction(...)` envelope; that BEGIN/COMMIT alone is what guarantees readers never observe a torn state. The reason READ COMMITTED suffices (vs SERIALIZABLE): the load path's WHERE filter is `op_seq > last_compacted_op_seq`, and inside the transaction we first UPDATE `boards.last_compacted_op_seq` and THEN DELETE ops up to and including the new value. A concurrent reader inside the transaction window sees either (a) the pre-UPDATE `boards` row (old `last_compacted_op_seq`, ops still in `board_ops` — reader replays the full pre-compact chain), or (b) the post-COMMIT state (new `last_compacted_op_seq`, deleted ops — reader replays nothing past the snapshot). Either reading is internally consistent; no torn state is possible. The single-instance v1 deploy means there is exactly one writer per board at a time (the Hocuspocus instance owning the document) anyway, so the only "concurrent" reads come from the load path on a different board OR a `/health.db.storage` snapshot read — neither of which can race the boundary. Do NOT escalate the isolation level to SERIALIZABLE in a review pass — it would impose per-transaction read-set tracking for no v1 correctness gain.

- **Per-board ops counter lives inside the extension factory closure, NOT module scope.** `createStorageExtension({ opsFlushThreshold })` returns a fresh `Extension` with its own closed-over `pendingOpsCount: Map<documentName, number>`. The module-level `storageExtension` singleton is what the live `server.ts` boot uses; tests that need isolation construct a separate extension via the exported `createStorageExtension` factory. **Hot-reload (dev `tsx watch`) resets the counter on every save** — acceptable because Hocuspocus's own debounce timer ALSO resets on hot reload, so the worst case is one missed early-flush per dev restart, and the next regular debounce window catches up. The seed-on-load logic computes the un-flushed count from `opsRows.length` (rows where `op_seq > last_compacted_op_seq` and the snapshot row is current) — equivalent to "ops the snapshot does not yet cover". A post-crash startup where ops are present but the snapshot is stale seeds the counter at that count, and the next single op may immediately trigger an early flush — exactly the correct catch-up behaviour.

- **Snapshot byte size baseline observed during smoke (the load-bearing number ADR-003 promised).** A single `Y.Map.set('shape1', { type: 'rect', x: 10, y: 20 })` encodes as **46 bytes** via `Y.encodeStateAsUpdate(doc)`. ADR-003's reference number is `~25 KB for a 200-shape board with 1000 edits` — 543× above the single-op baseline, which scales roughly linearly with op count (Yjs's binary update format ships the deletion set + the struct list, both of which grow with edit volume). The 25 KB ceiling sits 41,943× below Postgres bytea's 1 GB row limit, so chunking is unambiguously out of scope for v1 per ADR-003. The byte-size baseline is recorded in `/health.db.storage.snapshotBytes` and a rolling average can be derived as `snapshotBytes / snapshotCount` for any monitoring tool — the smoke's value of 46 bytes / 1 snapshot is the bottom of the curve.

- **`last_compacted_op_seq bigint NOT NULL DEFAULT 0` is the column ADR-003 named but Task 1.2 deferred.** The Task 1.2 brief explicitly left this for Task 1.3 to land "either as an inline migration or via re-derivation from MAX(op_seq) at store time". Inline migration was chosen — `drizzle/0001_absent_the_fallen.sql` adds the column with DEFAULT 0 (so existing boards do not need a backfill, the snapshot path will set it correctly on the next flush). The Drizzle schema diff in `meld-server/src/db/schema/boards.ts` is a single `bigint('last_compacted_op_seq', { mode: 'number' }).notNull().default(0)` field; the `mode: 'number'` is acceptable for v1 because op counts will not exceed Number.MAX_SAFE_INTEGER (2^53) — at the current load rate (10–50 ops/sec/board ceiling per ADR-003) a single board would need ~5 million years of continuous writes to overflow. If a future deployment needs the bigint to live as a `bigint` JS type, the `mode: 'bigint'` flip is one character and a casting pass through the Storage adapter — flag in v2 if it ever becomes load-bearing.

- **`HocuspocusProvider` (the canonical client) speaks a proprietary wire format, NOT the raw y-websocket binary protocol.** ADR-002 mentioned `WebsocketProvider` from `y-websocket` as the canonical client; Hocuspocus 4.1 ships ITS OWN provider package (`@hocuspocus/provider`) and the server-side protocol is a SUPERSET of y-websocket: every message starts with a `lib0/encoding.writeVarString(documentName)` (or `documentName\0sessionId` when session-aware multiplexing is enabled — the default in v4), then the y-websocket binary opcode bytes. An Auth message handshake (MessageType.Auth = 2) is required before the framework runs `onConnect` / `onAuthenticate` and begins applying sync updates. **The canonical `WebsocketProvider` from `y-websocket` will NOT work against a Hocuspocus server** — it speaks the bare y-websocket protocol without the documentName prefix and the Auth handshake. **Implication for Task 2.5 (frontend):** the planned `WebsocketProvider`-based Yjs client wiring needs to switch to `HocuspocusProvider` (or implement the documentName-prefix wrapper by hand) for v1's Hocuspocus-server backend. The wow-moment two-tab demo MUST drive the canonical client matching the canonical server — frontend-engineer's Task 2.5 is the boundary where this decision lands; flag it now so the right dep is selected at scaffold time. The Task 1.3 smoke uses `@hocuspocus/provider` directly to side-step this issue.

- **Smoke script (`scripts/storage-smoke.ts`) shape and reason for `@hocuspocus/provider`.** The smoke does `POST /api/boards` → open a `HocuspocusProvider` with a fresh `Y.Doc` → write a shape → wait through the 5 s debounce (+1.5 s buffer = 6.5 s wall-clock) → destroy provider → open a fresh provider with a NEW empty `Y.Doc` → assert the shape survives the round trip. Confirms the full ADR-003 path: `onChange` ops insert + `onStoreDocument` snapshot + compaction in the same transaction + `onLoadDocument` snapshot+ops replay on reconnect. The smoke ALSO logs `/health.db.storage` before and after so the counter motion is visible in the run output. Two devDeps added (`@hocuspocus/provider` + `lib0` — the latter is transitively needed by the provider's WS adapter). Both are dev-only, do NOT ship to production runtime. Cannot run on a fresh checkout without Postgres + a live `meld-server`; documented as the per-project README's manual two-terminal verification step.

- **`isPersistableBoardId` UUID v4 guard is belt-and-braces.** The path filter in `src/lib/ws/server.ts` already narrows the `boardId` URL segment to `[A-Za-z0-9_-]+` — anything else 404s before the WS handshake. The Storage adapter ALSO runs a UUID v4 regex against `documentName` and short-circuits non-uuid strings to `null` on `onLoadDocument` (returns null, framework starts with empty doc — no DB error) and to no-op on `onChange` / `onStoreDocument` / `onConnect` (skips the persistence path). The guard makes the WS upgrade work for synthetic test boards without polluting the persistence layer with junk rows. Production board ids are always UUIDs (Task 1.6 `POST /api/boards` mints via `randomUUID()`), so the production code path always hits the persistable branch.

- **`/health` envelope final shape after Task 1.6 + parallel Task 1.7a wave.** `{ status: 'ok', commit, ts, db: { connected, latencyMs, storage: { snapshotCount, snapshotBytes, opsAppended, compactionRuns, replayFromOpsCount } }, ws: { connectedClients, roomCount, controlFramesOut, controlFramesDropped, rateLimitedCount }, boards: { count: number | null }, session: { sessionsMintedThisProcess, sessionsLoadedFromCookie } }`. REFRESH CONCURRENTLY every 5 min`, (b) a `board_count` row in a `system_counters` table updated by the `POST /api/boards` route + the ADR-003 retention sweep in the same transactions that mutate `boards`. ## Task 1.5 — retention scheduler + compaction sweep (2026-05-31)

- **`computeNext3amUtc(now)` algorithm verbatim.** `const todayThreeAm = Date.UTC(year, month, day, 3, 0, 0, 0); if (now < todayThreeAm) return todayThreeAm; else return Date.UTC(year, month, day + 1, 3, 0, 0, 0);`. The `day + 1` rollover handles end-of-month and end-of-year by spec — `Date.UTC(2026, 11, 32)` returns `2027-01-01` and `Date.UTC(2026, 4, 32)` returns `2026-06-01` because `Date.UTC` normalises overflow. Strict-after at exactly 03:00:00.000 → tomorrow's 03:00 UTC. Mirrors tape's `tape-server/src/lib/ingest/retention-scheduler.ts` exactly so a future portfolio-wide retention helper can extract without re-litigation. Test inputs covered: midnight UTC, just-before-3am, just-after-3am, midday, end-of-month edge, end-of-year edge, exact 03:00.

- **Daily 03:00 UTC cadence — `setTimeout`-rescheduling pattern.** ONE `setTimeout` armed at a time. On `start()`: run boot sweep (catches up since container boot) → arm `setTimeout(handler, next3am - now)`. Inside the handler: run sweep → `.finally(() => scheduleNext())` which computes the next 03:00 UTC anchor from the post-sweep clock. The "run then reschedule" pattern is what keeps the cadence anchored on the wall clock — if a sweep drifts past 03:00 by N ms, the next fire still anchors on the NEXT 03:00 UTC, not on `now + 24 h`. `setInterval` was considered and rejected because it does NOT drift-correct against system clock changes (NTP step, container migration to a host with a different clock).

- **Compaction sweep — `setInterval` is the right primitive here.** Cadence is rolling 6 h, not wall-clock-anchored. Missing one fire by seconds is acceptable. NO boot-bootstrap — the first fire happens after one interval. Distinct from retention which IS wall-clock-anchored and DOES need boot-bootstrap. Pin: do NOT "tidy up" by unifying the two scheduler patterns — they have different correctness invariants.

- **`BOARD_RETENTION_DAYS` env handling.** Read inside the `RetentionScheduler` constructor via `readBoardRetentionDaysFromEnv()` (NOT at module load — a `.env` change between test runs is respected without reloading the module). Default `30`, non-numeric / negative falls back to default with a warn log. The retention SELECT parameterises the interval as `(${days}::text || ' days')::interval` because Postgres rejects bound parameters inside an INTERVAL expression; the `Number(...)` floor in the reader is what keeps the cast safe.

- **Compaction sweep threshold (`WS_COMPACTION_OPS_THRESHOLD`).** Read via `readCompactionOpsThresholdFromEnv()` with default `100`. The backlog for room X is computed as `MAX(op_seq) FROM board_ops WHERE board_id = X` minus `boards.last_compacted_op_seq` — two round-trips per room. Acceptable for v1 because the sweep runs at most every 6 h and the v1 room cardinality target is single-digit. A future optimisation would replace this with a single JOIN; not justified for v1.

- **Boot + shutdown wiring pattern (`src/server.ts`).** Construct schedulers at module load (NOT inside the `isEntryPoint` block) so the `/health` handler can read their metrics without an import cycle. Start them INSIDE the `httpServer.listen()` callback (so they only run when the process is actually serving). `retentionScheduler.start()` is awaited inside `void ...catch(...)` so the listen callback does NOT block on the boot sweep — a sweep failure logs but does NOT abort. `compactionSweep.start()` is sync. SIGINT/SIGTERM handler stops BOTH schedulers BEFORE `meldWs.close()` so a sweep does not race the WS close path.

## Task 1.X-control — WS control-frame Zod schemas + welcome / overrun emit + token-bucket rate-limit (2026-05-31)

Passing a `string` to `.send()` writes a TEXT frame via the underlying `ws` library per RFC 6455; passing `ArrayBufferLike` writes a BINARY frame. This is the ADR-004 TEXT/BINARY split. The welcome + overrun emit pipelines use `connection.webSocket.send(JSON.stringify(payload))` for TEXT frames. Note: Hocuspocus's own `Connection.send(message: Uint8Array)` is the BINARY path for y-websocket sync/awareness — `sendStateless(payload: string)` ALSO sends BINARY (wraps the string inside a `MessageType.Stateless = 5` opcode frame), so do NOT reach for `sendStateless` thinking it writes TEXT — only `webSocket.send(string)` does.

- **Hocuspocus 4.1 `beforeHandleMessage` extension hook — verified verbatim, exact name matches the ADR-002 brief.** Verified against `node_modules/@hocuspocus/server/dist/index.d.ts` line 365 (`beforeHandleMessage?(data: beforeHandleMessagePayload<Context>): Promise<any>`) and the ESM source line 877 where `instance.beforeHandleMessage(callback)` is wired during `createConnection`. - **Token-bucket rate-limit math — verbatim params.** Bucket capacity 100, refill 100 tokens/second (10 ms per token), per-`socketId` keyed `Map<string, {tokens, lastRefillMs}>`. On consume: `elapsed = now - lastRefillMs; refill = Math.floor(elapsed / 10); tokens = min(capacity, tokens + refill); lastRefillMs += refill * 10`. On bucket empty: `wsMetrics.recordRateLimited()` + `emitOverrunAndClose(payload.connection, {reason: 'rate.exceeded', retryAfterMs: 1000})` + throw `{code: 4290, reason: 'rate.exceeded'}`. Bucket released on `onDisconnect`. **Why a token bucket, not a fixed-window count:** a fixed-window cap admits a 2× burst at the window boundary (199 messages in 20 ms passes a "100 per second" check); the token bucket admits ONE 100-burst then enforces the long-run rate strictly. Click-spam during the wow-moment demo (10–20 rapid shape edits) passes; sustained 200 msg/sec spam closes the connection within tens of milliseconds.

- **Wire-visible rate-limit behaviour vs metrics-count discrepancy.** When the bucket empties, the rate-limit hook throws on EVERY subsequent message in `Connection.processMessages`' drain loop until the framework's `connection.close` actually finishes. Each drained-message throw increments both `wsMetrics.rateLimitedCount` AND `wsMetrics.overrunDisconnectCount` — so on a 200-message flood the metrics may show `rateLimitedCount=57, overrunDisconnectCount=57` even though the WIRE behaviour is exactly ONE overrun TEXT frame + ONE close-4290 event on the client side. ## Task 2.5b — brand-corner identity badge notes (2026-05-31)

- **Next 15 Server Components CANNOT write to the response cookie store — load-bearing pin for any future SSR-cookie-mint task.** Calling `cookies().set(...)` from a Server Component throws (`Error: Cookies can only be modified in a Server Action or Route Handler`). - **Badge color-ring transition timing — 320 ms easeOutCubic, `useReducedMotion()` snaps to 0 ms.** Picked 320 ms over the earlier 200 ms / 500 ms options because: 200 ms reads as instant on a 60 Hz display (the transition completes inside 12 frames and the eye barely catches the lerp); 500 ms reads as sluggish next to the rest of the chrome (theme toggle is 180 ms, tooltip delay is 300 ms). 320 ms sits between the two — long enough that the ring color upgrade is perceptible as "ah, identity confirmed", short enough that a quickly-clicking user does not see the chrome lag the click. easeOutCubic `[0.33, 1, 0.68, 1]` matches the theme-toggle's cubic-bezier choice from Task 2.3. `useReducedMotion()` falls back to `duration: 0` which Motion treats as "snap instantly" — no overshoot, no jitter, no inert-but-still-running animation frame. - **Hydration safety pattern for the cookie-driven identity badge — one component, two states, no render fork.** Both the server render and the first client render call `useIdentity(initial)` against an empty `useWelcomeStore`. This is the load-bearing pattern for any future identity-driven chrome surface (avatar stack in Task 3.2, presence cursors in Task 3.1): SSR the cookie-derived shape with a neutral default for the per-board fields, then upgrade in place when welcome lands. Do NOT propose a `useEffect`-gated client-only render to "fix" a perceived hydration risk — the risk is structurally impossible here because the welcome store is empty on first paint.

- **Light/dark theme switch via CSS custom property — `--badge-ring` (light) + `--badge-ring-dark` (dark).** Both variables are set on the wrapper element's `style` attribute. The class composition `border-(--badge-ring) dark:border-(--badge-ring-dark) [[data-theme='dark']_&]:border-(--badge-ring-dark)` consumes whichever variable matches the current theme — pure CSS branching, no `next-themes` subscription inside the component. The duplicate dark selector (`dark:` and `[[data-theme='dark']_&]:`) covers both the Tailwind dark-class strategy AND the meld `data-theme="dark"` attribute strategy because next-themes is wired with `attribute="data-theme"` per `app/providers.tsx` (Task 2.3). - **`data-mintedAt` attribute on the badge wrapper — debug aid, NOT a stable contract.** The wrapper element gains `data-mintedAt="initial" | "cookie" | "ws-onConnect" | "fallback"` so a Playwright deploy-verification test (ADR-007 territory) can assert the badge transitioned from `"initial"` (SSR + first client render) to `"cookie"` (most common welcome state) without spelunking the component tree. ## Task 0.8 — ADR-009 offline-mode UX contract pins (2026-05-31)

- **Connection-state detection rule (ADR-009 pin, load-bearing for the entire Phase 3.3 surface).** `meld-web/src/lib/hooks/use-connection-status.ts` exports `useConnectionStatus()` returning `'live' | 'offline' | 'reconnecting'`. The hook subscribes to BOTH `HocuspocusProvider.status` (via `provider.on('status', cb)`) AND `navigator.onLine` (via `window.addEventListener('online' / 'offline', cb)`). ## Task 3.2 — Drawing primitives + toolbar + pointer pipeline (frontend-engineer, 2026-05-31)

- **Y.Map per shape, not plain JSON. Required for CRDT field-level merges.** Each shape is a `Y.Map<unknown>` inserted into the root `doc.getMap('shapes')` keyed by the shape's UUID v4 id. A plain JSON value (`map.set(id, {x, y, ...})`) makes `map.set(id, {...next})` the only mutation primitive — a single field change rewrites the entire object, and concurrent edits last-write-wins on the whole shape (User A's drag-x and User B's recolor cancel each other). Y.Map per shape gives per-field Yjs CRDT semantics — both edits commute, both survive. **Verified by the round-trip test** at `lib/shapes/__tests__/types.test.ts > Y.Map per shape round-trips through Y.applyUpdate > two users moving the same shape concurrently both survive` — User A moves `x=250` while User B sets `colorSlot=5` on the same shape, both edits survive in both docs after cross-`applyUpdate`. Do NOT propose collapsing to plain JSON in a review pass — it has been considered and rejected on the CRDT-correctness axis.
- **`Y.Map.get()` on a DETACHED Y.Map returns `undefined` and emits a Yjs warning to stderr** (`Invalid access: Add Yjs type to a document before reading data.`). The bug surfaced during Task 3.2 test authoring: the first iteration of `createShape` returned the Y.Map and the caller did `ymap.get('id')` to extract the id BEFORE attaching to the document — the read returned `undefined` and the stderr noise polluted every test run. **Fix:** `createShape` returns `{ id, map }` and the canonical insert pattern is `const { id, map } = createShape({...}); doc.transact(() => rootMap.set(id, map));`. Multi-`set` on a detached Y.Map DOES work (stored in `_prelimContent` and replayed on attach), but READS on a detached map do not. The pattern documented in `types.ts` JSDoc — do NOT regress to a "read id from the returned map" call site.
- **`doc.transact` for every mutation. Atomic awareness propagation.** Every shape mutation (insert via `rootMap.set(id, createShape({...}))`, update via `updateShape(map, patch, sessionId)`, delete via `rootMap.delete(id)`, freehand append via `appendFreehandPoint(map, point, sessionId)`) is wrapped in `doc.transact(() => ...)` so the Yjs awareness peers see ONE update message per logical edit, not one per field touched. Without the transact boundary, a rectangle insert would fire 11 separate awareness updates (one per common field + two per-kind fields). The single-transact contract is the load-bearing wow-moment property — a rectangle landing in Tab B fires as one observer event, not eleven.
- **Tool-store persist key: `meld:tool` (Zustand persist, version 1).** The `meld:<scope>` convention adopted here is the going-forward pattern; older stores (`useUiStore`'s `meld-ui-v1`) stay where they are. The `merge` config validates rehydrated `tool` + `lastUsedTool` against `isToolKind` so a hand-edited localStorage value (or a v2-schema replay into a v1 client) falls back to the initial state, not a crashed setter.
- **Keyboard shortcut set:** `V` select, `R` rectangle, `E` ellipse, `P` freehand, `T` text, `Escape` revert-to-last (toggles between `'select'` and the last drawing tool). ## Phase 3.3 — Presence cursors (2026-05-31)

- **Cursor write throttle cadence (Phase 3.3, frontend-engineer 2026-05-31).** Local `pointermove` writes `awareness.setLocalStateField('cursor', { x, y })` gated by `nowMs - lastCursorWriteMsRef.current >= 30 ms`. 30 ms ≈ 33 fps awareness updates, well under the 60 fps engine paint cadence — the engine's lerp loop smooths between samples on the receiving side, so a sparser awareness stream still reads as a fluid cursor. 30 ms is also the rate cap that keeps us well under Hocuspocus's `maxRate` extension (ADR-002 backpressure, currently `100 msg/sec/client`); at sustained pointer motion meld emits ~33 cursor frames + ~6 shape-update frames per second, comfortable margin to the 100-frame ceiling. **No rAF gating** — the awareness update IS the rate limiter; an rAF coalescer would shift the throttle into the engine and couple it to paint cadence (counter-productive — cursor latency should NOT scale with paint cost). **`pointerleave` writes `cursor: null`** so the engine's opacity ramp fades the remote cursor out over ~200 ms; the throttle is bypassed on the null write because off-canvas is a discrete transition that should land immediately. **`pointerenter` writes the new position immediately** AND resets `lastCursorWriteMsRef` to 0 so a returning peer's cursor appears at the entry point, not the stale fade-out spot. **Unmount cleanup writes a final null** in a `useEffect` cleanup so a torn-down provider does not leave a stale cursor for remote peers.
- **Critical-damped lerp tau calibration (Phase 3.3, frontend-engineer 2026-05-31).** `tau = 30 ms` in the formula `currentX += (targetX - currentX) × (1 - exp(-dt / tau))`. At dt = tau ⇒ 63% gap closure per frame, at dt = 4 × tau (~120 ms) ⇒ 98.2% closure, at 7 × tau (~210 ms) ⇒ 99.9% closure. Combined with the 0.5 CSS px settle threshold (`Math.abs(target - current) > 0.5` to keep advancing, else snap to target), the cursor lands within 0.5 px of target at ~120 ms and parks exactly on target shortly after. The threshold prevents floating-point creep on subsequent ticks — without it the asymptotic lerp would keep flipping `cursorDirty = true` at sub-pixel epsilon forever. **Calibration empirically matches Figma's perceptual cursor feel** (the ADR-009 reference point); a smaller tau (e.g., 20 ms) would feel rubber-banded, a larger one (50 ms) would feel laggy under fast pointer motion. **The lerp runs INSIDE the engine's rAF tick, NOT a Motion wrapper** — per ADR-008 the cursor canvas is a paint target, not a DOM target.
- **Opacity ramp timing (Phase 3.3, frontend-engineer 2026-05-31).** 200 ms linear ramp for both fade-in (peer enters canvas, opacity 0 → 1) and fade-out (`cursor: null`, opacity 1 → 0). Computed as `opacity ± dt / 200ms` per tick; capped at `opacityTarget` so it never overshoots. Fade-out reaching opacity 0 EVICTS the peer entirely from the cursor map; re-entry recreates the entry with a snapped position. Linear, not eased, because the visual scale is too small for an ease curve to read (~14 px arrow + 18 px pill at 200 ms is sub-perceptual for non-linearity). Same ramp duration matches the ADR-009 banner slide-in / aria-live announcement cadence so the chrome motion budget feels coherent.
- **Emoji font cross-platform notes (Phase 3.3, frontend-engineer 2026-05-31).** Canvas2D `fillText` renders emoji via the OS color emoji font: Apple Color Emoji on macOS / iOS, Segoe UI Emoji on Windows 10/11, Noto Color Emoji on most Linux distros (Ubuntu / Fedora / Arch ship it by default). The painter's font string is `10px Inter, ui-sans-serif, system-ui, -apple-system, "Segoe UI", Roboto, sans-serif` — the browser falls through the sans cascade for the plain-ASCII `emojiName` portion, then through to the platform emoji font for the codepoint range that lacks a glyph in the named sans. **No `@font-face` declaration for emoji** — the platform handles it. The ADR-005 emoji whitelist is 128 single-codepoint Unicode 15.1 animals + food, all rendered correctly on the three majors as of 2026-05; no ZWJ sequences or skin-tone modifiers so the single-codepoint `fillText` call is byte-stable across platforms. **Gotcha (none observed in v1 but documented for v1.1):** Linux Chromium without `noto-fonts-emoji` package installed will fall back to monochrome outline glyphs from DejaVu Sans — extremely rare in 2026 but the failure mode is "you see a grayscale fox instead of a color fox", NOT a crash. The `emojiName` text still renders so the peer is identifiable. If a deployed-demo user reports gray emoji, the answer is "install `noto-fonts-emoji`".
- **Engine `boardId` dep + per-peer `colorSlot` derivation (Phase 3.3, frontend-engineer 2026-05-31).** `BoardEngine` constructor deps gained `boardId: string`. On every awareness sync the engine derives each peer's `colorSlot = colorSlotFor(identity.sessionId, boardId)` via the same client-side FNV-1a mirror the shape painter + welcome-frame use. Three derivations agree: server welcome frame's `session.color` (computed via `meld-server/src/lib/session/color.ts:colorSlotFor`), client shape painter's `colorSlot` field on the Y.Map (computed via `web/src/lib/identity/fnv1a.ts:colorSlotFor`), client cursor engine's per-peer color slot (also via `web/src/lib/identity/fnv1a.ts:colorSlotFor`). A peer's cursor matches their shapes match the welcome-frame card. If the awareness identity ever ships `colorSlot` directly on the wire (v1.1 candidate), the engine can drop the local FNV-1a call — but the duplication today is intentional per ADR-005's documented cross-package convergence.
- **CursorState eviction on `setLocalSessionId` (Phase 3.3, frontend-engineer 2026-05-31).** When the welcome frame lands AFTER a remote peer has already been added (unusual but possible if two clients connect simultaneously and the local welcome arrives a frame later), the engine's cursor map may briefly contain a peer whose `sessionId` matches our local `welcome.session.id`. `setLocalSessionId(id)` walks the map and evicts any such entry. The walk is O(map size) which is bounded by ADR-005's 8-slot wheel (~8 max simultaneous peers in the v1 demo), so the cost is irrelevant. **Without this eviction the local cursor would briefly double-render** — the OS pointer plus the canvas-painted glyph, with a slight offset between the OS hotspot and the canvas tip. Documented + tested.
- **Two-tab manual-smoke gating note (Phase 3.3, frontend-engineer 2026-05-31).** The Phase 3.3 brief asked for a two-tab smoke run from this shell. The bash session has no browser context, so the smoke is owner-driven per the checklist in the Done entry. All wire-level correctness is covered by Vitest: `engine.test.ts > cursor map sync` (10 cases — populate / remove / update / lerp convergence / fade evict / re-entry snap / dirty-flag motion gate / local-id exclusion), `cursors-painter.test.ts` (7 cases — empty / zero viewport / fill+stroke+label / palette resolution / opacity skip / multi-cursor / clamp), `use-awareness.test.ts` (4 new cursor cases on top of the Phase 2.5a baseline). ## Phase 4.1 — designer-critic review themes (designer-critic, 2026-05-31)

- **The brand wordmark is the load-bearing first-impression surface (D-01).** A semibold 18 px Inter "Meld" with `tracking-tight` is the Tailwind default heading; it carries zero identity. ## CRITICAL prod-crash fix — op_seq race + crash-safety (backend-engineer, 2026-06-02)

- **Resilience policy is ASYMMETRIC and deliberate — REVIEWER read this before judging the process handlers. NARROWED 2026-06-02 (supersedes the prior "process-wide LOG-and-KEEP-RUNNING for BOTH handlers" note below this paragraph).** The earlier policy logged-and-stayed-alive for BOTH `unhandledRejection` AND `uncaughtException`. The reviewer correctly flagged the `uncaughtException` keep-alive as broader than the incident required: Node explicitly documents that resuming after an arbitrary `uncaughtException` leaves the process in an UNDEFINED state, so an unconditional keep-alive masks genuinely fatal faults and hides real bugs. **The policy + the handlers now live in `server/src/lib/process-resilience.ts` (extracted from the inline block in `server.ts`) so the decision is unit-testable without spawning a process.** Asymmetric by design:
  - **`unhandledRejection` → LOG + STAY ALIVE.** This is the ACTUAL fire-and-forget `onChange` incident. A rejection that escaped to here is, by construction, one we did not await — the throwing frame already unwound and returned a (rejected) promise, so it cannot have torn a SYNCHRONOUS transaction in the in-process state. Recoverable classes (dropped/retried DB write, delayed snapshot flush) re-derive from the persisted ops-log on the next client sync. Crashing loses every live board's in-memory room; surviving does not. Staying up is correct.
  - **`uncaughtException` → LOG + BOUNDED best-effort flush + `process.exit(1)`.** Undefined process state → the correct recovery is a clean platform restart, NOT a blanket keep-alive. We log full structured detail, run a best-effort `flush` (`meldWs.close()` — release the port, flush pending stores) RACED against a bounded `UNCAUGHT_EXCEPTION_GRACE_MS = 500` window (so a hung flush cannot wedge the dying process), then exit non-zero. Fly restarts the Machine on a non-zero exit; the in-memory rooms reconstruct from the ops-log on reconnect (same recovery path the rejection branch leans on, with a process restart in front). Exit is idempotent (`exited` guard) so the flush-settle and the grace-timer cannot double-exit.
  - **What is UNCHANGED:** the per-boundary try/catch in `changeImpl`, the `.catch` on every `void storeDocumentHooks(...)` (storage early-flush + compaction-sweep `flushRoom`), and the try/catch in `connectImpl` remain the FIRST line of defense and are the primary crash-safety from `5c520e6` — this narrowing only changes the last-resort net's `uncaughtException` arm. Recoverable async faults are caught at the boundary and never reach the process handlers. Boot-time fail-closed throws (empty `MELD_ALLOWED_ORIGINS` in production, missing `DATABASE_URL`) run at MODULE LOAD before the event loop yields and are NOT delivered to `uncaughtException` (verified by the reviewer) — they still abort directly. The SIGINT/SIGTERM graceful `shutdown` (`process.exit(0)`) is a separate handler in the entry-point block, untouched.
  - **Tests:** `server/src/lib/__tests__/process-resilience.test.ts` (node:test) pins the pure `decideResilienceAction` helper (`unhandledRejection` → `stay-alive`, `uncaughtException` → `exit-after-grace`) and the installer wiring via an injected fake `process` + injected timer (NO real process spawn — the brittle case avoided): rejection logs/stays/no-exit/no-flush; uncaughtException logs/flushes-once/exits `1`; double-exit dedupe when flush AND grace-timer both settle; exit-anyway when the flush itself rejects. `installProcessResilience` takes injectable `logError`/`flush`/`setTimer` deps purely for this testability.

All three unawaited sites are now guarded. `connectImpl` already had its own try/catch (it touches `last_active_at` best-effort). `loadDocumentImpl`/`storeDocumentImpl` are awaited so a throw there surfaces as a framework-handled error, not a process crash — left as-is.

- **GOTCHA (smoke, not the contract) — `HocuspocusProvider` connects to `configuration.url` VERBATIM; the document `name` does NOT go in the URL.** `HocuspocusProviderWebsocket` does `new WebSocketPolyfill(this.url)` where `this.url === configuration.url` (esm `get serverUrl`/`get url`, lines 358–366) — it never appends `name`. The document name rides inside the y-protocol Sync message, not the path. So a provider client MUST be constructed with the FULL board path baked into `url` (`ws://host/ws/board/<id>`), exactly like the web app's `composeBoardUrl`. My first smoke pass used `url: ws://host:PORT` + `name: boardId` and got a SILENT failure — no welcome, no error, no server connection log — because the bare-root upgrade was 404'd by the `/ws/board/:boardId` path filter in `server.ts attach()` before any hook fired. Fix: put the path in `url`. (The `name` is still passed for the framework's own document keying.) This is a client-construction quirk, not a server-side concern — flagging it so the next person writing a provider-backed Node script does not lose 10 minutes to it.

- **GOTCHA — passing per-connection upgrade headers (Origin, Cookie) through the provider requires subclassing the `WebSocketPolyfill`.** The provider calls `new WebSocketPolyfill(url)` with ONLY the url — no options object — so you cannot pass `{ origin, headers }` through the provider config. The smoke binds them by subclassing `ws.WebSocket` and hard-coding the third `options` arg in the subclass constructor (`super(address, protocols, { origin, headers })`). Needed because the server's Origin allowlist + the ADR-005 cookie-read extension both read upgrade-request headers. In the browser this is a non-issue (the browser sets Origin automatically and sends cookies same-origin); it only bites Node provider clients (smoke/E2E harnesses).

- **`broadcastStateless` does NOT close sockets — the 4404 close stays per-connection.** ADR-011 replaced the board-deleted per-connection SEND loop with one `Document.broadcastStateless`, but the framework broadcast only writes the stateless frame; it does not touch the socket lifecycle. So the retention sweep still iterates `doc.getConnections()` for the per-connection `connection.close({code:4404})` pass AFTER the single broadcast. Counter semantics preserved by capturing `doc.getConnectionsCount()` BEFORE the close pass and incrementing `controlFramesOut` once per delivery — if you read the count after closing, you would count 0 deliveries. The `RetentionConnection` test/abstraction interface lost its `webSocket.send` (now close-only); per-room broadcast tracking moved onto a new `RetentionDocument` fake (`makeFakeDocument`) in `retention-scheduler.test.ts`.

- **Send-then-close FIFO for `control.overrun` held in practice but was NOT independently stress-verified here.** The smoke covers welcome (the once-per-load error path — the actual ADR-011 target). The overrun send-then-close ordering (`sendStateless` enqueues ahead of `close` on the same `ws` buffer) is verified-equivalent by construction (same socket, synchronous FIFO enqueue) but the existing 50-connection backpressure stress test is the place to re-confirm `onStateless`-before-`onclose(4290)` if a reviewer wants empirical proof. Flagged in ADR-011's Consequences as a behaviour to re-confirm rather than assume.

- **No `.env.example` change.** Pure transport swap — no new env vars, no config knobs. The `/health.ws` counter names (`controlFramesOut`, `controlFramesDropped`, `overrunDisconnectCount`, `rateLimitedCount`) are all unchanged; `controlFramesOut` now counts stateless sends (transport-agnostic by design).
