## ADR-001: Stack flavour, backend choice, and CRDT stack

**Status:** accepted
**Date:** 2026-05-31

### Context

`meld` is a local-first collaborative whiteboard with sub-100 ms presence and conflict-free shape merges. Two browser tabs open the same board URL; one draws, the other mirrors via Yjs CRDT and y-websocket protocol; offline edits queue locally and auto-merge on reconnect. The product is a pure portfolio showcase — slot 2 in the portfolio composition, claiming the local-first / CRDT niche which was identified as the most undervalued portfolio specialisation in 2026 (FOSDEM 2026 dedicated local-first dev-room, 9 competing CRDT stacks in active rotation: Yjs, Automerge, Loro, Jazz, ElectricSQL, Diamond Types, Y-Sweet, BlockNote sync, Hocuspocus).

Three decisions must land in ADR-001:

1. **(a)** web-only vs api-heavy per `docs/conventions.md` § 10;
2. **(b)** if api-heavy, the backend framework per § 11;
3. **(c)** the CRDT stack — a meld-specific decision the planner brings into ADR-001 because it is load-bearing for the project identity (a generic "real-time collaboration" choice would lose the architectural-signal value the whole project exists to demonstrate).

Owner context that affects framing: meld is **pure-showcase**, not commercial-seed. Tape (slot 1) already holds the commercial-seed slot and committed Elysia on Bun. Meld's framing freedom on monetisation lets it maximise the architectural-signal axis instead — pick the SPECIFIC CRDT stack and the SPECIFIC backend framework that read as deliberate position vs the generic alternative.

Portfolio composition context that affects framing: tape committed Elysia on Bun in slot 1. Portfolio constraint (`docs/conventions.md` § 12) requires at least 2–3 api-heavy projects with backend variance across Hono / Fastify / NestJS / Elysia. Slot 2 (meld) is the natural place to claim Hono — the 2026 multi-runtime story (Node + Bun + Deno + CF Workers + Vercel Edge from the same source code) is the architectural signal that distinguishes a Hono pick from a Fastify pick, and it aligns with the v2 migration path to CF Workers Durable Objects (one DO per board = horizontal scale-out, global edge).

### Options considered

**Web-only vs api-heavy:**

- **A. web-only (Next.js route handlers + server actions).** Rejected by hard criteria — three of the five api-heavy triggers from `docs/conventions.md` § 10 fire: long-lived WebSocket fan-out (y-websocket protocol is the entire wire), background debounced snapshot persistence worker + compaction sweep, and heavy domain logic with CRDT correctness invariants worth isolating from the UI.
- **B. api-heavy.** Forced by A's rejection.

**Backend framework (assuming api-heavy):**

- **B1. Hono on Node 22.** Multi-runtime story is the 2026 senior-signal — same source code targets Node, Bun, Deno, CF Workers, Vercel Edge. Mature production Node target via `@hono/node-server` + `@hono/node-ws`. The Yjs ecosystem's canonical `y-websocket-server` reference adapter targets Node first, so the y-protocol handshake "just works" with minimal adapter debugging. Typed RPC via `hc<AppType>` + Zod-validated schemas pair cleanly with the shared-schemas-in-`src/lib/schemas/` convention. v2 migration to CF Workers Durable Objects is a deploy-config change, not a rewrite. **Picked.**
- **B2. Fastify on Node.** Mature ecosystem, schema-first via Zod plugins, well-paved for traditional Node servers with heavier middleware. Strong choice for a backend-heavy product, but does not advance the multi-runtime narrative that distinguishes a 2026 pick from a 2022 pick. Reserved as a future option for another portfolio slot if a project lands that genuinely needs heavy plugin ecosystem (auth provider middleware, request body validation chains, etc.).
- **B3. NestJS on Node.** Opinionated, decorator-heavy, enterprise patterns. Reserved for project 3 (AI agentic tool) in the planned portfolio mix, where module structure and dependency injection carry weight. Wrong shape for meld — the surface is small (one WebSocket route + a handful of HTTP routes) and NestJS's decorator + module ceremony would dominate the bundle.
- **B4. Elysia on Bun.** Already committed by tape in slot 1. Reusing it for meld would collapse the variance axis the portfolio policy requires. Rejected on portfolio-composition grounds, not technical grounds.

**CRDT stack:**

- **C1. Yjs (yjs + y-websocket + y-protocols/awareness).** Text + drawing primitives both first-class via `Y.Map` / `Y.Array` / `Y.Text`. `y-protocols/awareness` gives presence + cursors out of the box — exactly the shape the wow moment needs. Largest production ecosystem in 2026 (BlockNote, Tldraw, Hocuspocus, Liveblocks Yjs adapter, JupyterLab RTC all build on it). Smallest CRDT wire format among the competitive set (30–60 % smaller than Automerge on a typical whiteboard session). **Picked.**
- **C2. Automerge.** Strong Rust-derived CRDT, but text + drawing primitives both go through the same `Doc` abstraction and the JS / WASM bundle is heavier. Smaller ecosystem for whiteboard-specific patterns. Rejected on ecosystem-narrative grounds — Yjs reads as "production-ready CRDT", Automerge reads as "research toy" to a recruiter skimming the README.
- **C3. Loro.** Newer Rust-derived CRDT, claims faster delta size for text-heavy workloads. Smaller wire-format wins at the byte level but tooling and reference adapters are less mature; no first-class y-websocket-equivalent reference server. Rejected on maturity grounds for a 2-week project.
- **C4. Jazz.** Collab framework on top of CRDTs, not a raw CRDT lib. Higher level than what meld wants to demonstrate — meld is supposed to _show_ the CRDT, not hide it behind a framework. Rejected on architectural-signal grounds.
- **C5. ElectricSQL.** Postgres-replication-based; "local-first" in a different sense (sync the rows, not the ops). Wrong shape for an in-memory whiteboard with high-frequency ephemeral awareness state. Rejected on workload-fit grounds.
- **C6. Diamond Types.** Research-grade fast text CRDT. Text-only — no drawing primitives. Rejected on scope-fit grounds.

### Decision

**Stack flavour: api-heavy. Backend: Hono 4.x on Node 22 LTS for v1. CRDT stack: Yjs 13.x + y-websocket protocol + y-protocols/awareness.**

Three converging axes drive the picks. **First**, api-heavy is forced — y-websocket is the wire, and the persistence + compaction loop is a background process that does not survive Next-only route handlers. **Second**, Hono on Node wins on workload fit (y-websocket-server reference adapter targets Node first, so the y-protocol handshake is well-paved), on portfolio variance (Elysia and Hono are two distinct cutting-edge 2026 backends — Bun-native max-throughput vs multi-runtime edge-ready — exactly the variance the portfolio policy mandates across api-heavy slots), and on v2 migration narrative (CF Workers Durable Objects deploy is a config change from the same Hono source, not a rewrite). **Third**, Yjs wins on every load-bearing axis vs the eight-CRDT competitive set: production ecosystem maturity, first-class drawing-primitive shape via `Y.Map` + `Y.Array`, first-class presence via `y-protocols/awareness`, smallest wire format. Loro is the most interesting alternative on raw delta size but the ecosystem gap costs more than the byte-level win earns in a 2-week project. The CRDT pick is load-bearing for the project identity in a way the backend pick is not — a generic "real-time collaboration" framing would lose the architectural-signal value the whole slot exists to deliver.

**Two integration mechanisms are deliberately deferred:** the Hono WebSocket adapter choice and the Yjs snapshot persistence strategy. Both are pinned by the architect in ADR-002 and ADR-003 respectively at the start of the implement phase, after a brief prototype spike — premature lock-in here would foreclose options the architect will want to weigh against measured numbers.

### Consequences

- **Positive.**
  - Two distinct cutting-edge 2026 backends across the api-heavy portfolio slots (Elysia Bun-native + Hono multi-runtime). Portfolio variance constraint advanced one notch — slots 3+ remain unconstrained for the remaining backend variance dimensions (Fastify, NestJS).
  - Yjs ecosystem maturity short-circuits a class of "did the adapter preserve the y-protocol byte-for-byte" debugging — `y-websocket-server` is the canonical reference and we plug into it on a known-good runtime (Node 22).
  - v2 migration to CF Workers Durable Objects is a deploy-config change, not a rewrite. README + DEPLOY.md will document the migration path so a recruiter clicks through it without us having to ship it.
  - Awareness state (`y-protocols/awareness`) gives presence cursors + name pills + selection broadcasting out of the box. Smooth ~120 ms interpolation on top is a thin Motion layer, not a CRDT extension.
  - Anonymous-link-share onboarding (no accounts in v1) reads as deliberate UX choice on a portfolio demo — "the CRDT IS the demo, not the auth flow".
  - Architectural signal reads correctly to a senior recruiter skimming the demo and the repo: meld picked a SPECIFIC stack (Yjs + Hono) for a SPECIFIC domain (collaborative whiteboard), distinguishing it from the generic "real-time collaboration" pitch every fullstack portfolio claims.

- **Negative.**
  - Hono's WebSocket helper API surface is smaller than `ws`-on-Node's. If `setupWSConnection` from `y-websocket-server` wants ABI surfaces the adapter does not expose cleanly, we may need to drop down to a hand-rolled upgrade. Mitigation: architect ratifies the adapter choice in ADR-002 with a prototype spike before backend Task 1.4 commits to it.
  - Yjs document binary persistence to Postgres bytea is straightforward for the small-document common case, but a very large session (> 1 MB merged state) needs chunking. Architect ratifies the chunking strategy and compaction cadence in ADR-003.
  - Anonymous session cookie identifies a user across reloads but not across browsers / devices. If a viewer wants to "go back to my board", they need the URL. Acceptable for v1 portfolio demo; v2 (better-auth activation) covers the cross-device path.
  - Node 22 production target means we cannot demo the multi-runtime story live in v1 (we only deploy to one runtime). The story is in the README + DEPLOY narrative, not in the deployed binary. Acceptable trade-off for v1 scope; v2 migration to CF Workers Durable Objects would actually demonstrate the multi-runtime affordance.
  - Variance slot "multi-runtime edge-ready backend" is now committed to meld. If a future portfolio brief wants Hono for a different reason, it cannot have it — the variance constraint pushes that brief to Fastify or NestJS.

- **Follow-up tasks.**
  - **ADR-002 (architect, implement-phase day 1):** Hono WebSocket adapter choice — `@hono/node-ws` vs hand-rolled `ws`-on-Node upgrade — and the integration shape with `y-websocket-server`'s `setupWSConnection`. Decision must cover: y-protocol byte-for-byte preservation, per-room broadcast fan-out, reconnect / resume semantics, Windows dev parity, and the minimum API surface the adapter must expose for the `setupWSConnection` signature.
  - **ADR-003 (architect):** Yjs snapshot persistence strategy — debounce trigger boundary (ratify "5 s idle OR 100 ops" or revise with numbers), snapshot encoding (`Y.encodeStateAsUpdate` full state vs incremental updates list vs hybrid), bytea chunking strategy for large boards (> 1 MB), snapshot-chain compaction sweep cadence, replay-after-compaction correctness invariant.
  - **ADR-004 (architect):** WebSocket frame contract for non-Yjs control messages (welcome frame with assigned session id + emoji-name + OKLCH color, board-room metadata, overrun control). Yjs sync + awareness frames pass through unchanged per the y-websocket protocol. Zod schemas shared via `src/lib/schemas/ws/` between Hono server and Next.js client.
  - **Engineering kickoff (gated on ADR-002 + ADR-003 acceptance):** `backend-engineer` starts on Node + Hono scaffold (PLAN.md task 1.1) in parallel with `frontend-engineer` starting on Next.js + Tailwind v4 scaffold (PLAN.md task 2.1). The two scaffolds are independent until Phase 2.2 (Hono RPC client wiring on the web side).

## ADR-002: Hono WebSocket adapter + y-websocket-server integration

**Status:** accepted
**Date:** 2026-05-31

### Context

ADR-001 committed Hono 4.x on Node 22 LTS as the v1 backend and Yjs 13.x + y-websocket protocol + `y-protocols/awareness` as the CRDT stack. Hono itself does not own a WebSocket implementation — it provides per-runtime upgrade helpers. The integration shape between Hono and the Yjs server is the load-bearing decision for Phase 1.4: where do `WSSharedDoc` room instances live, how are they fanned out across concurrent connections, how does the HTTP upgrade hand off to the Yjs sync + awareness handlers, and what migration shape does v2 (CF Workers Durable Objects) inherit?

Four credible adapter approaches exist in the 2026 Yjs + Hono ecosystem. Each carries a different complexity / extensibility / migration trade-off. The pick must serve three masters: (a) ship the wow moment (two-tab presence demo + offline-merge) inside the Phase 1.4 task budget; (b) leave clean injection points for ADR-003 (snapshot persistence) and ADR-004 (control-frame contract); (c) port to CF Workers Durable Objects in v2 without rewriting the room model.

Constraints from PLAN.md, ADR-001, and `AGENT_NOTES.md`:

- The y-websocket protocol carries Yjs sync (`messageSync`) and `y-protocols/awareness` (`messageAwareness`) opcodes as opaque binary frames. The adapter MUST pass them through byte-for-byte; rewriting or wrapping them breaks the canonical client (`WebsocketProvider` from `y-websocket`).
- One Yjs document per `boardId`. Concurrent connections to the same `boardId` share a single in-memory `WSSharedDoc` (room model). Lazy-create on first connect, garbage-collect after a quiet period of zero connections.
- v1 has anonymous-link sharing with no accounts (better-auth wired but inactive per ADR-001). The HTTP CORS allowlist is the auth surface for HTTP; the WS upgrade needs an equivalent Origin allowlist to prevent cross-site WS hijack from a malicious page.
- v2 migration target is one Durable Object per `boardId` (per ADR-001). DOs use `state.acceptWebSocket(ws)` rather than the `ws` library and have no Node `http.Server`. The v1 adapter choice must not foreclose this.
- Backpressure: tape ADR-006 established a per-client send-queue cap + close code `4290` pattern. y-websocket-server's reference implementation does NOT ship this. Decision needed: adopt now or defer to v1.1.

### Options considered

- **A. `@hono/node-ws` + `setupWSConnection` from `y-websocket-server`.** Hono's official Node WS adapter handles the HTTP upgrade and surfaces a typed route handler with a `WSContext` wrapping the underlying `ws` socket. We pierce the wrapper to get the raw `WebSocket` object and pass it straight to `setupWSConnection(rawWs, request, { docName: boardId })`. Complexity to ship v1: ~1 day. Debuggability: medium — one layer of indirection between Hono's route and `ws`'s event loop, and `@hono/node-ws`'s message-event wrapper coerces binary frames through `event.data` which has had edge-cases in 2026 around `ArrayBuffer` vs `Buffer` framing that bite Yjs's binary handshake. Extensibility: weak — no built-in hook for `onLoadDocument` / `onStoreDocument`; we wire snapshot persistence ourselves by holding a reference to the per-room `Y.Doc` and observing updates. v2 CF DO migration: adapter swap (replace `@hono/node-ws` with the DO `acceptWebSocket` path) — room model stays. Production failure mode: a slow client with 50-user shape spam accumulates frames in `ws`'s default unbounded send buffer; no built-in eviction, OOM possible.

- **B. Hand-rolled `ws` library + Hono `upgrade()` hook + `setupWSConnection`.** Drive `WebSocket.Server({ noServer: true })` directly; the Hono route invokes `wss.handleUpgrade(request, socket, head, ...)` and hands the resulting `WebSocket` to `setupWSConnection`. Complexity to ship v1: ~1.5 days (Hono integration is more verbose than option A). Debuggability: high — only one library between Hono and Yjs, every byte path is in our code. Extensibility: medium — same as A, we wire snapshot + backpressure ourselves. v2 CF DO migration: adapter swap, identical to A. Production failure mode: same unbounded-buffer issue as A; we own the fix. The portfolio-narrative downside is that we are bypassing the Hono-official WS helper, which weakens the "Hono multi-runtime story" signal that ADR-001 leaned on — a recruiter reading the source sees raw `ws` plumbing and may ask "why did you pick Hono if you're not using its WS adapter?".

- **C. Hocuspocus server + Hono passthrough.** Hocuspocus is a production Yjs server framework (`@hocuspocus/server`) built by the Tiptap team on top of `y-protocols`. It owns the WebSocket route end-to-end, provides typed extension hooks (`onConnect`, `onAuthenticate`, `onLoadDocument`, `onStoreDocument`, `onChange`, `onAwarenessChange`, `onDisconnect`), built-in debounced storage adapter interface, built-in per-room awareness fan-out with coalescing, and a documented production deployment shape (Redis-backed multi-instance, etc.). Hono retains all HTTP control routes (`POST /api/boards`, `GET /health`); Hocuspocus mounts on the same Node `http.Server` instance at `/ws/board/:boardId`. Complexity to ship v1: ~0.5 days for the WS surface itself (the framework owns the protocol); the snapshot path becomes a small `Storage` adapter that ADR-003 designs against the well-documented `onStoreDocument` hook. Debuggability: medium — more framework code in the stack but the extension hooks are typed and well-documented, and Hocuspocus ships structured logging. Extensibility: high — every injection point we need (auth in welcome frame, snapshot debounce, awareness pass-through, per-client backpressure config) is a first-class hook. v2 CF DO migration: harder than A/B — Hocuspocus is Node-targeted, not Workers-targeted, so the v2 path is "replace the Hocuspocus runtime with a hand-rolled DO `acceptWebSocket` + a small re-implementation of the room model using the same extension-hook shape we already wrote against". The shape ports cleanly; the runtime does not. Production failure mode: Hocuspocus ships per-client backpressure via configurable `maxRate` + `maxMessageSize` and a built-in awareness coalescing window — 50-user shape spam is handled by the framework, not by us.

- **D. Custom Hono WS handler + manual y-protocols sync implementation.** Implement `messageSync` + `messageAwareness` opcodes by hand against `y-protocols/sync` and `y-protocols/awareness`, skipping `setupWSConnection` entirely. Complexity to ship v1: ~3–4 days. Debuggability: highest (every byte is ours) but signal-to-noise is terrible — we are reimplementing the canonical reference. Extensibility: total — but we pay for it in protocol-correctness debugging time that the project budget does not have. v2 CF DO migration: the most flexible since we already own every line of the protocol. Production failure mode: whatever we write — high risk of subtle protocol drift from the reference impl that breaks the canonical `WebsocketProvider` client in ways that take days to bisect.

### Decision

**Adopt option C: Hocuspocus server mounted on the same Node `http.Server` as Hono, with Hono owning HTTP control routes and Hocuspocus owning the `/ws/board/:boardId` WebSocket surface.**

Room model: Hocuspocus owns the per-`boardId` `Document` (its `WSSharedDoc` equivalent) inside a process-wide `Server` singleton instantiated at boot. Documents are lazy-created on first connect via `onLoadDocument` (which ADR-003 will use as the snapshot-load injection point) and garbage-collected from memory when both (a) zero connections remain on the document AND (b) the last `onStoreDocument` flush has completed, with a configured grace window of 30 seconds to absorb rapid reconnects. The room registry is the Hocuspocus `Server` instance itself — we do NOT build a parallel `Map<boardId, WSSharedDoc>` registry, because duplicating the framework's state is a known source of bugs and forecloses the framework's built-in lifecycle guarantees.

Origin-check policy: a single env var `MELD_ALLOWED_ORIGINS` (comma-separated) is read at boot and serves both the Hono HTTP CORS layer and the Hocuspocus `onConnect` hook. The `onConnect` hook reads `requestHeaders.origin`, asserts membership against the parsed allowlist, and rejects the upgrade with a structured close (code `4401`, reason `"origin not allowed"`) on miss. In production (`NODE_ENV === "production"`) an empty or unset `MELD_ALLOWED_ORIGINS` fails closed — the server refuses to boot. In development the same unset case falls open to `http://localhost:3000` only, never to wildcard `*`.

Two concrete facts broke the tie against option A (which was the runner-up):

1. **Hocuspocus's `onStoreDocument` extension hook gives ADR-003 a typed, documented, debounce-configurable injection point that bare `y-websocket-server` lacks.** With option A we would hand-roll the debounce timer, the snapshot encoding call, and the failure-retry path against a `Y.Doc.on('update', ...)` observer — three custom subsystems ADR-003 would then need to specify in detail. With C, ADR-003 specifies the `onStoreDocument` hook configuration (debounce window, storage-adapter shape, retry policy) and the framework handles the wiring. This cuts ADR-003's surface area by ~40% and the Phase 1.3 + 1.4 task budget by ~1.5 days.

2. **Hocuspocus's `connection.context` payload, populated in `onConnect` from the welcome-frame data, wires anonymous-link session identity (assigned emoji-name + OKLCH color from ADR-004) into the awareness layer without rewriting the y-websocket protocol.** With option A we would either smuggle session identity through an out-of-band control message (which ADR-004 has to define carefully to avoid colliding with Yjs opcodes) or store it in a process-side `Map<connectionId, identity>` that the awareness handler reaches into — both are leaky abstractions. With C, the identity is carried in `connection.context` and accessible from every subsequent hook (`onAwarenessChange`, `onStoreDocument`, `onDisconnect`) without our code touching the wire format. This makes ADR-004's control-frame design strictly additive to the protocol (welcome frame is a one-shot at upgrade time, not interleaved with sync frames).

Backpressure policy for v1: **adopt** the tape ADR-006 shape, leveraging Hocuspocus's built-in primitives rather than reimplementing them. Configure Hocuspocus `Server` with `maxRate: 100` messages/sec/client (above the expected p99 of a 50-user board's shape-spam burst), `maxMessageSize: 1 MB` (above the largest expected Yjs sync delta for v1's hundreds-of-shapes-per-board target), and `timeout: 30_000 ms` (a slow client that stops draining its send buffer for 30 s is closed with code `4290` — same as tape's pattern). This is not deferred to v1.1 because (a) the framework gives it to us for ~zero implementation cost, and (b) PLAN.md's 30-tab stress test (Phase 5.4) would expose any unbounded-buffer pathology, so deferring would just be paying the debt during test phase instead of design phase. Awareness coalescing uses Hocuspocus's default 16 ms tick window per room, which matches the AGENT_NOTES.md note on awareness fan-out.

This decision does NOT weaken ADR-001. Hono remains the HTTP framework (control routes, RPC client surface, `hc<AppType>` end-to-end type inference), Node 22 remains the runtime, Yjs remains the CRDT, the y-websocket wire protocol remains unchanged (Hocuspocus speaks the canonical y-websocket protocol on the wire — `WebsocketProvider` from `y-websocket` is the documented canonical client). The multi-runtime portfolio narrative is mildly weakened on the WS surface specifically (Hocuspocus is Node-targeted) but the Hono HTTP surface still ports across Node, Bun, Deno, CF Workers, and Vercel Edge — and the v2 DO migration sketch below replaces Hocuspocus with a DO-native room model that preserves the same extension-hook shape we are writing against today.

### Consequences

- **Positive.**
  - ADR-003's design surface shrinks: snapshot persistence is a `Storage` adapter conforming to Hocuspocus's typed interface against the `onLoadDocument` / `onStoreDocument` hooks, not a hand-rolled debounce + observer + retry subsystem.
  - ADR-004's control-frame design becomes strictly additive: the welcome frame (session id + emoji-name + OKLCH color) is a one-shot exchanged on upgrade via Hocuspocus's `onConnect` returning a `connection.context` payload, never interleaved with Yjs sync frames on the wire.
  - Backpressure is in the v1 ship, not in the v1.1 patch queue. The 30-tab stress test (Phase 5.4) lands on a server that already handles per-client overflow.
  - Awareness fan-out coalescing (16 ms tick window per room) is framework-default, not custom code we need to test for correctness.
  - Origin check shares one env var with HTTP CORS — one config surface, one place to fail closed in production.
  - The room registry IS the Hocuspocus `Server` singleton — no parallel state, no `Map<boardId, WSSharedDoc>` to keep in sync with the framework.

- **Negative.**
  - Hocuspocus adds ~30 KB to the production server bundle vs option A. Acceptable for a backend service (not a frontend bundle).
  - The "multi-runtime Hono" narrative is mildly weakened on the WS surface: Hocuspocus is Node-targeted, so the WS path does not port to Bun / Deno / CF Workers without replacement. The HTTP surface still does. README + DEPLOY narrative must be careful to frame v2 as "swap Hocuspocus for a CF DO room model that preserves the same extension-hook shape" rather than "the same source code runs on Workers".
  - Hocuspocus ships its own logger and its own error-event surface; observability must be wired through Hocuspocus's hooks, not through generic `ws.on('error', ...)` listeners.
  - If Hocuspocus releases a breaking version during the project lifetime, we are exposed to it (mitigation: pin to a minor version range in `package.json`).
  - Hocuspocus's per-client backpressure config (`maxRate`, `maxMessageSize`, `timeout`) must be load-tested in Phase 5.4 to confirm the close-code path actually fires under the synthetic 30-tab overflow — backend-engineer Task 1.X below instruments this.

- **Follow-up tasks.**
  - **ADR-003 (architect, next):** Yjs snapshot persistence strategy. ADR-002 constrains ADR-003 to specify the Hocuspocus `Storage` adapter shape (the `fetch(documentName)` + `store(documentName, state)` interface), the `onStoreDocument` debounce window (ratify or revise the PLAN.md placeholder of "5 s idle OR 100 ops" against Hocuspocus's `debounce` + `maxDebounce` config knobs), the bytea chunking strategy for >1 MB documents (Hocuspocus passes the encoded state as a single `Uint8Array` to the storage adapter — chunking is OUR responsibility inside the adapter, not the framework's), and the replay-after-compaction correctness invariant. **ADR-002 explicitly does not pin these — ADR-003 owns them — but they MUST be specified before backend-engineer Task 1.3 can ship.**
  - **Task 1.X — `backend-engineer` (queued, gated on ADR-003 acceptance):** Hocuspocus server bootstrap inside the meld Node process. Mount on the same `http.Server` as Hono, listen on the same port. Configure `Server` with `maxRate: 100`, `maxMessageSize: 1 MB`, `timeout: 30_000 ms`. Wire `onConnect` to read `requestHeaders.origin`, validate against the parsed `MELD_ALLOWED_ORIGINS` allowlist, reject with close code `4401` on miss, fail closed in production on empty allowlist. Wire `onConnect` to populate `connection.context` with the session identity from the welcome-frame data (ADR-004 will pin the welcome-frame shape; until ADR-004 lands, populate with the cookie-derived session id only). Smoke test: canonical `WebsocketProvider` client connects to `/ws/board/:boardId`, draws a shape in tab A, tab B mirrors it, awareness cursor pill renders with the correct color. Backpressure test: open 50 connections to the same `boardId`, programmatically emit 200 shape-update messages/sec from one tab, assert the slow-client tab is closed with code `4290` within `timeout` window and the surviving tabs see no message loss.
  - **Observability hook:** `/health.ws` HTTP endpoint (Hono route, separate from `/health`) exposes a JSON payload of `{ rooms: <count>, connections_total: <count>, connections_per_room: { <boardId>: <count> } }` derived from the Hocuspocus `Server.documents` map. Used by the v1 deployment ADR's uptime monitor (Phase 6 / deployment ADR). Backend-engineer Task 1.X includes this endpoint.

- **v2 migration sketch (CF Workers Durable Objects).** Replace the Hocuspocus `Server` process with a CF Worker that routes `/ws/board/:boardId` to a Durable Object instance keyed by `boardId`. ## ADR-003: Yjs snapshot persistence strategy

**Status:** accepted
**Date:** 2026-05-31

### Context

ADR-001 committed Yjs 13.x as the CRDT and Hono on Node 22 as the backend. ADR-002 committed Hocuspocus as the WebSocket framework and pinned that snapshot persistence MUST be implemented as a Hocuspocus `Storage` adapter wired to the `onLoadDocument` (fetch) and `onStoreDocument` (store) extension hooks. This ADR picks the storage shape behind that adapter: schema, retention, recovery semantics, and the API the adapter exposes upward.

PLAN.md hinted at "snapshot every 5 s debounced OR 100 ops, whichever first" plus "snapshot chain compaction in a background sweep". AGENT_NOTES.md pre-flagged bytea (not JSON) as the column type, the `is_compaction = true` + `superseded_at` atomicity pattern, and chunking for >1 MB documents as a TBD inside the adapter (Hocuspocus passes a single `Uint8Array` to `store` — chunking is the adapter's responsibility, not the framework's).

The persistence layer must satisfy:

1. **Cold-start sync latency.** On first connect to a board, `onLoadDocument` must return the merged document state within sub-100 ms p99. PLAN.md's wow-moment success criterion budgets 200 ms end-to-end for shape mirror, and the persistence load is on the critical path.
2. **Crash recovery loss bound.** On server crash mid-debounce, the loss bound must be explicitly named in seconds-or-ops, not waved away.
3. **Write amplification under load.** A 50-user board under heavy concurrent shape edits (presence/awareness frames are NOT persisted — Hocuspocus coalesces them per the 16 ms tick window and they live only in awareness state) must not saturate the Postgres write path.
4. **Retention.** v1 has no user accounts (ADR-001's better-auth-wired-but-inactive). Boards are anonymous-link share. PLAN.md is silent on inactive-board GC; this ADR pins it.
5. **Compaction atomicity.** AGENT_NOTES.md pre-flagged the single-transaction sweep with `superseded_at` markers, never delete-then-insert. This ADR ratifies that as the contract.
6. **API surface.** The Hocuspocus `Storage` adapter shape is fixed by ADR-002 (`fetch(documentName): Promise<Uint8Array | null>` + `store(documentName, state: Uint8Array): Promise<void>`). This ADR pins the persistence layer's internal contract and the helpers backend-engineer Task 1.5 will need.

Three numbers drive the option weighting:

- **Yjs encoded state size.** `Y.encodeStateAsUpdate(doc)` on a 200-shape whiteboard with 1000 edits encodes at roughly 20–100 KB before Yjs's GC sweep merges deletion sets, 10–60 KB after. v1's target ceiling per PLAN.md is hundreds of shapes per board; even a 10× safety multiplier sits well inside Postgres bytea's 1 GB row limit. Chunking is NOT needed for v1 scope. ADR-005 inherits the chunking question if a future deliverable exceeds the threshold.
- **Yjs load + apply cost.** Reading a single ~50 KB bytea row from local Postgres 16 (port 5436 per AGENT_NOTES.md) and calling `Y.applyUpdate(doc, snapshot)` on the Yjs 13.x WASM build completes in single-digit milliseconds on Node 22. Replaying 1000 incremental updates against an empty doc costs 50–150 ms wall-clock — an order of magnitude worse, and it scales linearly with edit history (unbounded over a board's lifetime). This kills pure ops-only persistence on the cold-start budget.
- **Postgres bytea write throughput.** A single-row UPSERT of a 50 KB bytea on the dev Postgres costs single-digit milliseconds. At "5 s debounce OR 100 ops" the per-board snapshot write rate caps at ~0.2 writes/sec sustained — trivial for any reasonable Postgres deployment at 100 concurrent boards.

### Options considered

- **A. Snapshot-only.** Hocuspocus `onStoreDocument` debounce writes a single `boards.snapshot_state` bytea UPSERT every N ops or T seconds. No ops log. `onLoadDocument` SELECTs the column and returns it.
  - Write amplification on 50-user board: ~0.2 writes/sec — best of any option.
  - Cold-start sync latency: 1 SELECT + 1 `Y.applyUpdate` on ~50 KB = single-digit ms p99. Best of any option.
  - Retention complexity: trivial — one row per board, GC by `last_active_at`.
  - Recovery on crash mid-write: edits inside the open debounce window (≤ 5 s wall-clock OR ≤ 100 ops since last flush) are lost from the server-side persisted state. Yjs's CRDT property partially recovers this — surviving clients re-broadcast their unack'd local ops on reconnect via the y-websocket sync handshake, so the only edits permanently lost are those from clients that ALSO crashed/disconnected in the same window without buffer flush. For a 50-user board this is statistically near-zero per crash.
  - Drizzle schema: 1 table (`boards`), columns include `snapshot_state bytea`.
  - Production incident shape: server crash 2 s into debounce window with 50 active users. 48 surviving clients re-broadcast their unack'd local Yjs updates on reconnect, the in-memory `Y.Doc` rehydrates from the (pre-crash) snapshot + replayed client updates, lost-edit count is bounded to edits originating from the 0–2 simultaneously-disconnecting clients.
  - Cost: no per-edit durability — relies on client-side recovery as the safety net.

- **B. Ops-only.** Hocuspocus `onStoreDocument` configured with `debounce: 0` so every sync-update frame triggers a row append to a `board_ops` table. `onLoadDocument` SELECTs all ops for the board and replays them into an empty `Y.Doc`.
  - Write amplification on 50-user board: ~10–50 writes/sec under shape spam — 50×–250× option A. Hot DB path even with batched inserts because the natural granularity is one row per op.
  - Cold-start sync latency: scales linearly with edit history. 1000 ops = 50–150 ms; 100K ops (board lived for weeks) = seconds. Blows the 200 ms presence budget for any board past childhood.
  - Retention complexity: high — append-only growth forever without a compaction sweep, at which point we are option C.
  - Recovery on crash mid-write: near-zero loss — each op is durable on commit.
  - Drizzle schema: 1 table (`board_ops`), `(board_id, seq, payload bytea)`.

- **C. Hybrid (ops + periodic snapshot compaction).** Hocuspocus `onChange` appends each Yjs sync-update payload to a `board_ops` table for durability; Hocuspocus's `onStoreDocument` debounce (configured at the `debounce` + `maxDebounce` knobs ADR-002 flagged) writes a denormalised snapshot to `boards.snapshot_state` + `boards.snapshot_seq` every N ops or T seconds; an async compaction sweep periodically merges ops > snapshot_seq into a new snapshot inside a single transaction and marks the merged ops `superseded_at`. `onLoadDocument` returns snapshot + replayed ops > snapshot_seq merged via `Y.applyUpdate`.
  - Write amplification: ops append rate matches B (~10–50 writes/sec); snapshot UPSERT debounced to ~0.2 writes/sec — additive but still well inside Postgres budget.
  - Cold-start sync latency: bounded by (snapshot SELECT + ops-since-snapshot replay). With compaction firing every 1000 ops or 1 hour, replay-since-snapshot is bounded by 1000 ops worst case = 50–150 ms. Inside the 200 ms budget forever.
  - Retention complexity: medium — two tables, compaction sweep needs atomicity (single transaction, `superseded_at` marker per AGENT_NOTES.md, never delete-then-insert).
  - Recovery on crash mid-write: near-zero — every op is durable before debounce flush.
  - Drizzle schema: 2 tables (`boards` + `board_ops`), snapshot denormalised on `boards`.
  - Senior portfolio signal: this is the production pattern Hocuspocus's own `@hocuspocus/extension-database` implements internally; ADR-002's "preserve the extension-hook shape" v2 migration sketch maps cleanly onto CF DO's `state.storage.put` + ops list.

- **D. `@hocuspocus/extension-database` drop-in.** Use Hocuspocus's own database extension (the production-pattern reference cited in ADR-002 References). Internally implements option C against a configurable driver (Postgres, MongoDB, SQLite). Complexity to ship v1: ~0 days — config-only. Loss of control: we inherit the extension's schema shape, its debounce defaults, and its compaction strategy (which as of 2026-05 is snapshot-only with no separate ops table — strictly weaker than C on crash recovery). Adopting D means accepting "snapshot-only crash semantics dressed up as a hybrid" without the durable-ops safety net option C gives us. **Rejected on control-of-recovery-semantics grounds, not technical grounds** — the extension is the right shape for a small project that does not want to spec recovery; meld's portfolio narrative demands the recovery spec be explicit.

- **E. Object storage for snapshots + Postgres for ops index.** Snapshot bytes to S3/R2/Tigris; Postgres holds `(board_id, snapshot_key, seq)`. Heavier infra, pays off only when snapshots routinely exceed Postgres bytea's efficient-row size (TOAST kicks in around 2 KB, hard limit 1 GB). For v1's 10–60 KB typical snapshot, Postgres bytea is the correct primitive. **Rejected on overkill grounds for v1; revisit in ADR-005 if chunking becomes load-bearing.**

### Decision

**Adopt Option C: hybrid ops-log + periodic snapshot compaction, implemented as a Hocuspocus `Storage` adapter backed by two Postgres tables (`boards` + `board_ops`).** Ops are appended to `board_ops` from Hocuspocus's `onChange` hook on every sync-update frame; the framework's `onStoreDocument` debounce (configured at `debounce: 5_000 ms` and `maxDebounce: 30_000 ms`) writes a denormalised snapshot to `boards.snapshot_state` + `boards.snapshot_seq` via the adapter's `store` method; a separate compaction sweep runs every 1 hour or per-board when ops-since-snapshot exceeds 1000, whichever fires first, merging ops-since-snapshot into a new snapshot inside a single transaction and marking superseded ops via `superseded_at`.

**Debounce window — re-pinned verbatim from PLAN.md plus a maxDebounce ceiling.** Hocuspocus's `onStoreDocument` config: `debounce: 5_000 ms` (idle window — flush if no new ops arrive for 5 s), `maxDebounce: 30_000 ms` (force-flush ceiling — regardless of activity, flush at least every 30 s). The "OR 100 ops" half of PLAN.md's hint is enforced inside the `Storage` adapter via an in-memory ops-counter that triggers `onStoreDocument` early when it crosses 100 since the last flush. This keeps the snapshot debounce inside Hocuspocus's framework primitives where possible and only escapes them when the framework lacks the equivalent knob (the op-counter trigger). The 30 s `maxDebounce` ceiling is **newly added** by this ADR — without it, a board that receives a steady trickle of ops at < 100/5 s would never snapshot, and crash-recovery-via-client-replay would have to walk a longer ops chain on rehydrate.

**Retention policy: boards GC after 30 days of inactivity.** A nightly sweep deletes rows from `boards` where `last_active_at < NOW() - INTERVAL '30 days'` and the `ON DELETE CASCADE` foreign key on `board_ops.board_id` removes the associated ops. 30 days covers the realistic "I shared the link with a colleague and we came back to it next week" path on a portfolio demo without unbounded storage growth. The window may tighten to 14 days or loosen to 60 after observing real share patterns on the deployed demo; the change is a config + migration, not an ADR revision.

**Recovery semantics on crash mid-write: at most the last 5 s of ops are at risk for clients that ALSO crashed/disconnected in the same window without buffer flush.** Concretely: `board_ops` rows are committed to Postgres on every Yjs sync-update frame the WS adapter receives (via `onChange`), so any op that the server acknowledged to the originating client is durable. The 5 s debounce affects only the snapshot, not the ops log. On server restart, `onLoadDocument` for board X executes `loadDoc(X)`: SELECT `snapshot_state, snapshot_seq` from `boards`, SELECT `payload` from `board_ops WHERE board_id = X AND seq > snapshot_seq AND superseded_at IS NULL ORDER BY seq`, replay via `Y.applyUpdate` into a fresh `Y.Doc`, return `Y.encodeStateAsUpdate(doc)`. Lost-edit bound: **edits the server received but had not yet `onChange`-flushed to Postgres before the crash (sub-second window of fsync latency)**, AND only for edits whose originating client also disconnected without buffer flush in the same window. For a 50-user board this is statistically near-zero per crash; PLAN.md's 30-tab stress test (Phase 5.4) is the load-bearing verifier.

**Two facts drove the pick:**

1. **Yjs encoded state after GC sweep averages ~30 % of pre-GC size, AND a 200-shape whiteboard with 1000 edits encodes at ~25 KB — well inside Postgres bytea's 1 GB row limit, so a per-board snapshot column is viable for boards 100× the v1 expected size.** This kills the need for chunking (Option E) and de-risks Option A's "what about huge boards" objection for v1 scope. Chunking work is deferred entirely.
2. **Replaying 1000 incremental updates against an empty `Y.Doc` costs 50–150 ms on Node 22 with the Yjs 13.x WASM build — an order of magnitude worse than loading a single snapshot and one order of magnitude worse than the 100 ms cold-start budget allows for a board past ~1500 lifetime ops.** This kills pure Option B (ops-only) on the cold-start success criterion and forces the hybrid: ops for crash-recovery durability, periodic compaction for cold-start latency.

This decision does NOT weaken ADR-001 or ADR-002. The Hocuspocus `Storage` adapter is exactly the shape ADR-002 named as the persistence injection point; the in-memory ops-counter is a thin extension inside the adapter, not a parallel state machine outside it; the room registry remains the Hocuspocus `Server.documents` map per ADR-002.

### Consequences

- **Positive.**
  - Crash recovery loss bound is "edits the server received but had not yet `onChange`-flushed (sub-second fsync window) from clients that ALSO crashed in the same window" — accurate enough to cite in the README architecture section without overclaiming.
  - Cold-start sync latency is bounded by (snapshot SELECT + ≤ 1000 ops replay) = 50–150 ms p99 forever, regardless of board age.
  - Write amplification is bounded: ops append rate matches incoming sync-frame rate (~10–50 writes/sec on a hot 50-user board), snapshot write rate is debounced to ~0.2 writes/sec per board, retention sweep is nightly.
  - The hybrid pattern is the production-validated shape (`@hocuspocus/extension-database` internalises it; Liveblocks Yjs server uses the same; every CRDT deployment surviving production converges here). Reads as deliberate-vs-naive to a senior recruiter.
  - Persistence API surface is stable against ADR-002's Hocuspocus integration: the `Storage` adapter is the only injection point. No parallel `Map<boardId, ...>` registries, no separate observers on `Y.Doc.on('update')`.

- **Negative.**
  - Two tables (`boards` + `board_ops`) plus the snapshot denormalisation on `boards` is heavier than Option A's single-table version. Backend-engineer must implement the compaction sweep correctly per AGENT_NOTES.md's atomicity contract (single transaction, `superseded_at` marker, never delete-then-insert). Reviewer-checked in Phase 4.2.
  - **Drizzle ORM bytea quirk.** As of Drizzle ORM 0.30.x on the `postgres-js` driver, the `bytea` column is exposed as `Buffer` in TypeScript, while Yjs's `encodeStateAsUpdate` returns `Uint8Array`. The adapter MUST coerce at the boundary: write path uses `Buffer.from(uint8.buffer, uint8.byteOffset, uint8.byteLength)`; read path returns `new Uint8Array(buffer.buffer, buffer.byteOffset, buffer.byteLength)`. Backend-engineer must document this coercion at the column definition site. **If the project upgrades to Drizzle 0.31+ (which exposes `bytea` as `Uint8Array` natively on the postgres-js driver), the coercion becomes a no-op and the comment lives on as a load-bearing historical pin** — do not delete it under a "remove dead code" review pass.
  - The in-memory ops-counter (for the "100 ops" trigger) lives inside the `Storage` adapter, not inside Hocuspocus. If the adapter instance is reset (e.g., hot module reload in dev) the counter resets — acceptable because Hocuspocus's own debounce timer also resets, so the worst case is one missed early-flush per dev restart.
  - 30-day retention is a heuristic guess for a portfolio demo without user accounts. May need re-tuning after observing real share patterns. Not blocking.
  - Compaction sweep is a stateful background loop, not a request handler — it needs its own observability path (last-run-at, ops-compacted-count, errors). See observability question deferred below.

- **Persistence API surface — the Hocuspocus `Storage` adapter ADR-002 named, plus internal helpers.**
  - `fetch(documentName: string): Promise<Uint8Array | null>` — Hocuspocus `onLoadDocument` injection. Implementation: SELECT snapshot_state + snapshot_seq from `boards`, SELECT payload from `board_ops WHERE board_id = documentName AND seq > snapshot_seq AND superseded_at IS NULL ORDER BY seq`, replay all into a fresh `Y.Doc`, return `Y.encodeStateAsUpdate(doc)` or `null` if the board has no rows (new board). Note: `null` return tells Hocuspocus to start with an empty `Y.Doc`, which is the correct first-connect behaviour for a brand-new shared URL.
  - `store(documentName: string, state: Uint8Array): Promise<void>` — Hocuspocus `onStoreDocument` injection. Implementation: UPSERT into `boards` (`id = documentName`, `snapshot_state = state`, `snapshot_seq = current-max-op-seq`, `updated_at = NOW()`). Atomically.
  - `appendOp(documentName: string, update: Uint8Array): Promise<void>` — INTERNAL helper called by the adapter's own `onChange` registration, NOT a public Hocuspocus hook. Implementation: INSERT into `board_ops` (`board_id`, `seq = next-per-board-seq`, `payload = update`). Increments the in-memory ops-counter; if counter ≥ 100, schedules an immediate `onStoreDocument` early-flush via Hocuspocus's `Document.save()` API.
  - `touchActive(documentName: string): Promise<void>` — INTERNAL helper called by the adapter's `onConnect` registration. UPDATE `boards SET last_active_at = NOW() WHERE id = documentName`. Drives the 30-day retention sweep.
  - `compact(documentName: string): Promise<{ snapshotSeq: bigint; opsCompacted: number }>` — called by the compaction sweep job. Single transaction: SELECT snapshot + ops-since-snapshot, replay into a fresh `Y.Doc`, `Y.encodeStateAsUpdate`, UPDATE `boards` (new `snapshot_state`, new `snapshot_seq`), UPDATE `board_ops SET superseded_at = NOW() WHERE board_id = X AND seq <= new_snapshot_seq AND superseded_at IS NULL`. Returns the metrics for observability.

- **Drizzle schema files backend-engineer must create** (paper-only spec — no SQL, no code authored here).
  - `meld-server/src/db/schema/boards.ts` — table `boards`. Columns: `id text PK` (base32-random-12, generated by the `POST /api/boards` route in Task 1.6), `created_at timestamptz NOT NULL DEFAULT NOW()`, `last_active_at timestamptz NOT NULL DEFAULT NOW()`, `snapshot_state bytea` (nullable — null until first snapshot completes), `snapshot_seq bigint NOT NULL DEFAULT 0`, `updated_at timestamptz NOT NULL DEFAULT NOW()`. Index on `last_active_at` for the retention sweep.
  - `meld-server/src/db/schema/board-ops.ts` — table `board_ops`. Columns: `id bigserial PK`, `board_id text NOT NULL REFERENCES boards(id) ON DELETE CASCADE`, `seq bigint NOT NULL` (monotonic per-board sequence assigned inside `appendOp` from a per-board in-memory counter seeded by `MAX(seq)` on adapter boot — NOT a global Postgres serial, because per-board monotonicity is the load-bearing property), `payload bytea NOT NULL`, `created_at timestamptz NOT NULL DEFAULT NOW()`, `superseded_at timestamptz` (nullable — set by compaction sweep). Unique composite index on `(board_id, seq)` for the load path. Partial index on `(board_id, seq) WHERE superseded_at IS NULL` to keep the hot-path SELECT tight as compaction history grows.
  - `meld-server/src/db/schema/index.ts` — barrel re-export.
  - **No `packages/*` extraction.** Drizzle schemas live in `meld-server` per ADR-001 + `docs/conventions.md` § 13. Zod schemas live in `meld-server/src/lib/schemas/`. `meld-web` will type-import from the workspace in Phase 2.2 (frontend-engineer) per the existing tape pattern; Drizzle schemas stay server-only.

- **Observability question deferred.** Snapshot bloat alarm — exposed as either (a) a single `/health.db` aggregate `{ total_boards, total_snapshot_bytes, total_ops_bytes, oldest_unsupseded_op_age_sec }` (cheap — one summary query) or (b) per-board metrics on `/health.db?boardId=X` (useful for ops debugging, expensive at scale). Defer to v1.1 ops surface decision. For v1 the compaction sweep logs `{ boardId, snapshotSeq, opsCompacted, bytesFreed, durationMs }` on every run via Hocuspocus's structured logger — sufficient observability for the portfolio demo, the dashboard wait until ops surface matures.

  - **Task 1.3 (revised by this ADR — replaces the PLAN.md placeholder text):** `Hocuspocus Storage adapter — hybrid ops-log + debounced snapshot.` Create the `boards` and `board_ops` Drizzle schemas per the spec above. ## ADR-004: WebSocket control-frame contract for non-Yjs messages

**Status:** accepted
**Date:** 2026-05-31

### Context

ADR-001 committed Yjs 13.x + the y-websocket protocol as the CRDT wire. ADR-002 committed Hocuspocus as the WebSocket framework and pinned that anonymous-link session identity (assigned emoji-name + OKLCH color) is carried in Hocuspocus's `connection.context` payload populated at `onConnect` — explicitly NOT interleaved with Yjs sync frames on the wire. ADR-003 committed the Hocuspocus `Storage` adapter shape and the durable-ops + debounced-snapshot recovery contract.

What remains open from PLAN.md Task 0.3: **the wire-format contract for application-level control messages that meld emits OUTSIDE the y-websocket protocol.** Three classes of frame fall in this category:

1. **Server-to-client at connect time.** The welcome frame — assigned session identity (id + emoji-name + OKLCH color) read by the client to seed its `awareness.setLocalState`, plus board metadata (board id echo, created_at, current connection count, echoed allowed-origin) read by the client to render the room chrome before the first Yjs sync round completes.
2. **Server-to-client before a forced close.** The control frames that name the reason for an imminent disconnect — `control.overrun` (ADR-002 backpressure boundary, close code `4290`), `control.board-deleted` (retention sweep collided with a live session), `control.kicked-for-name-collision` (reserved; v2 auth path).
3. **Client-to-server outside the Yjs document.** Application-level heartbeat (deferred — protocol ping decision below), `settings.update` (v1.1 — name/color override). The channel is reserved in v1; the schemas exist as type-only stubs.

The y-websocket binary protocol uses the FIRST byte of each binary frame as the opcode discriminator: `0x00` = `messageSync`, `0x01` = `messageAwareness`, and unknown opcodes are silently ignored by both Yjs and `WebsocketProvider` on the read side. Meld's control frames need a discriminator that cannot collide with this. The browser `WebSocket` API gives us two natural channels — TEXT frames (`socket.send(string)` → `MessageEvent.data: string`) and BINARY frames (`socket.send(ArrayBuffer | Blob)` → `MessageEvent.data: ArrayBuffer`). Hocuspocus's `connection.send` accepts both shapes per its 2026-05 API.

Per PLAN.md and ADR-001 / ADR-002 / ADR-003, all three downstream consumers are blocked on this contract: frontend-engineer Task 2.5 (Yjs client setup seeded with awareness identity from the welcome frame), backend-engineer Phase 1.7 (anonymous-session cookie identity wired into the welcome frame), and the `/health.ws` observability hook from ADR-002 (which gains optional counters for control frames sent / dropped).

### Options considered

**Wire-coexistence approach (how control frames share the socket with y-websocket binary frames):**

- **W1. TEXT frames for control, BINARY frames for Yjs.** Hocuspocus's `connection.send(jsonString)` emits a TEXT frame; `WebsocketProvider` and the Yjs sync handlers ignore TEXT frames entirely (they branch on `event.data instanceof ArrayBuffer`). The browser receive side becomes a one-line branch: `if (typeof event.data === 'string') handleControl(event.data) else handleYjs(event.data)`. DevTools Network tab renders TEXT frames as their literal JSON string, no decoder needed. Bundle cost: zero — JSON is built into the platform. Evolution story for v2: control kinds are added to the Zod discriminated union; the wire framing does not change. Failure mode under a production incident (control frame parse error mid-board-session): client logs the parse error, optionally surfaces a toast, but the Yjs sync path is byte-for-byte unaffected — the TEXT/BINARY discriminator at the message handler precedes any schema validation. Recruiter signal: clean protocol-layer / application-layer separation, the type of split that reads as senior architecture.
- **W2. BINARY frames with reserved opcode prefix (`0x80+`).** The first byte of every meld-emitted frame is either `0x00` (Yjs sync, framework-passthrough), `0x01` (Yjs awareness, framework-passthrough), or `0x80+` (meld control). Yjs ignores `0x80+` on the read side per the y-websocket spec; meld control parser ignores `0x00` / `0x01`. Single transport, single `instanceof ArrayBuffer` event handler, then a sub-discriminator on `data[0]`. Bundle cost: minimal but non-zero — the dispatch is ~15 LOC of opcode-prefix parsing vs ~1 LOC of `typeof event.data` discriminator in W1. DevTools Network tab renders BINARY frames as hex blobs — every control frame needs a manual decode to read. Evolution story: each new control kind eats one opcode in the `0x80–0xFF` reserved space (128 slots — more than enough for v2). Failure mode: an opcode-prefix bug (a stray `0x00` byte from a partial write) routes a control frame into the Yjs sync handler and crashes the y-protocol decoder mid-board-session — much worse blast radius than W1's "skip the malformed control frame, Yjs path untouched".
- **W3. Separate WebSocket connection per concern.** One socket for `/ws/board/:id` (Yjs), one for `/ws/control/:id` (meld). Listed only as foil — splits state coordination across two reconnect lifecycles, doubles the WS upgrade cost and the per-board connection count tracked by `/health.ws`, and the v2 CF Workers Durable Objects migration would need to coordinate two DOs per board for no protocol benefit.

**Codec for control frame payloads:**

- **C1. JSON over TEXT frames.** Native browser API, native Hocuspocus API on the server side, zero dependency, DevTools-debuggable as a literal string. Frame size for the welcome payload (5 fields, base32-12 board id, ISO timestamp, 8-byte session id, emoji-name, OKLCH triplet): ~150–200 bytes. For `control.overrun`: ~80 bytes. For `heartbeat`: ~30 bytes. Total wire load over a typical board lifetime: ~3–5 frames at ~100 bytes each = sub-kilobyte.
- **C2. MessagePack over BINARY frames (`msgpackr`, `useRecords: false` per AGENT_NOTES.md).** Reuses ADR-002's pattern from tape. Wire-size win is ~30% smaller payloads (~100–150 bytes for welcome). Requires `msgpackr` in `meld-server` AND in `meld-web` (~20 KB minified gzipped on the browser bundle). DevTools rendering needs a manual decoder browser extension or a console snippet to inspect.
- **C3. JSON with a binary fallback for >1 KB control payloads.** Over-engineering for v1; control payloads are tiny and rare. Listed only to be rejected explicitly.

**Heartbeat policy (application-level keepalive vs protocol-level ping):**

- **H1. Protocol-level ping only.** The WebSocket protocol has its own ping/pong frames (RFC 6455 § 5.5.2) and Hocuspocus + the `ws` library Node-side surface this as `ws.ping()` with a configurable interval. The browser receives the ping at the protocol layer (transparent to JavaScript) and responds automatically. No JavaScript-visible heartbeat needed for the v1 demo path.
- **H2. Additional application-level `heartbeat` frame on a fixed cadence (e.g., 30 s).** Lets the client surface "connection is alive" UI more proactively, and lets the server track app-layer liveness separately from socket-layer liveness. Costs one control kind in the schema vocabulary and ~30 bytes/30 s = ~1 byte/sec — negligible.

### Decision

**Wire coexistence: option W1 — TEXT frames for meld control, BINARY frames stay reserved for the y-websocket protocol.** Hocuspocus's `connection.send(jsonString)` emits the TEXT frame; on the browser the receive handler branches `typeof event.data === 'string'` to the control parser and `event.data instanceof ArrayBuffer` to the existing Yjs sync handler (which is what `WebsocketProvider` already installs). Yjs's sync + awareness opcodes are not touched; the y-websocket protocol is preserved byte-for-byte.

**Codec: option C1 — JSON, parsed through a Zod discriminated union.** Control frames are ~5 per board-session lifetime in v1, total wire load is sub-kilobyte, and DevTools-debuggability of the literal JSON in the Network tab during the two-tab presence demo is itself a portfolio signal (a recruiter who opens DevTools while the demo runs reads our welcome frame as a human and sees the awareness wiring without us writing a paragraph in the README).

**Discriminator vocabulary for v1 — six `kind` literals on the discriminated union, reserved namespacing for v2:**

- `'welcome'` — server-to-client, one-shot at `onConnect`, carries assigned session identity + board metadata + echoed origin.
- `'control.overrun'` — server-to-client, emitted IMMEDIATELY before the framework-level close with code `4290` per ADR-002 backpressure. Reason field discriminates `queue.overflow | rate.exceeded | message.too-large`.
- `'control.board-deleted'` — server-to-client, emitted IMMEDIATELY before close when the ADR-003 retention sweep would delete a board that still has live connections (race window: nightly sweep + an active session that just touched `last_active_at`). Close code `4404`.
- `'control.kicked-for-name-collision'` — server-to-client, RESERVED for v2 (auth path enables explicit user names; collision detection becomes meaningful). Schema lives in v1 as a type-only stub; not emitted by v1 server code.
- `'heartbeat'` — client-to-server AND server-to-client, RESERVED for v1.1. Schema lives in v1 as a type-only stub. v1 relies on protocol-level ping (see heartbeat policy below) — this kind is reserved so the discriminator vocabulary does not break when we light it up.
- `'settings.update'` — client-to-server, RESERVED for v1.1 (user-chosen name/color override). Type-only stub.

The discriminator namespace is intentionally split: bare verbs (`welcome`, `heartbeat`, `settings.update`) are the steady-state channel; the `control.*` namespace is reserved for "server is about to do something the client needs to know about before it happens" — disconnects, permission events, tier limits. v2 control kinds (`control.permission-revoked`, `control.tier-limit`, `control.auth-required`) extend the `control.*` namespace; v2 user-driven kinds (`board.bookmark`, `cursor.snap-to`) extend the bare-verb namespace. This split is the v2 extension reservation pattern.

**Welcome frame canonical payload (server emits exactly once per connection, inside Hocuspocus `onConnect` via `connection.send`):**

```
{
  kind: 'welcome',
  session: {
    id: string,                     // 16-char base32, derived from cookie or freshly minted
    emojiName: string,              // codepoint from the curated allowlist
                                    // (src/lib/identity/emoji-names.ts per AGENT_NOTES.md)
    color: { l: number; c: number; h: number },  // OKLCH triplet, deterministic from session id
  },
  board: {
    id: string,                     // base32-12, echo of :boardId URL segment
    createdAt: string,              // ISO 8601 UTC
    connectionCount: number,        // integer, post-connect (this client included)
  },
  origin: string,                   // the ALLOWED_ORIGINS-validated origin the server accepted
  serverTime: string,               // ISO 8601 UTC; client uses for skew measurement
  protocolVersion: 1,               // bumped on breaking discriminator vocabulary changes
}
```

The `origin` echo lets the client assert `origin === window.location.origin` and warn loudly in DevTools on a mismatch — a defence-in-depth against a misconfigured production deployment serving cross-origin to a domain it should not. The `protocolVersion: 1` literal is the load-bearing forward-compat marker: v2 servers emit `protocolVersion: 2` and v1 clients log a structured "server protocol newer than client, refusing to connect" warning before closing cleanly.

**Overrun frame payload (server emits IMMEDIATELY before close code `4290` per ADR-002):**

```
{
  kind: 'control.overrun',
  reason: 'queue.overflow' | 'rate.exceeded' | 'message.too-large',
  closeCode: 4290,                  // echoed for client-side log correlation
  retryAfterMs: number,             // server's suggested cool-off before reconnect (e.g., 1500)
}
```

`retryAfterMs` lets the `WebsocketProvider` reconnect-backoff respect server-side advice; the client multiplies it with its own backoff curve to avoid a reconnect storm if all 50 connections of a board hit `control.overrun` simultaneously.

**Board-deleted frame payload (server emits IMMEDIATELY before close code `4404`):**

```
{
  kind: 'control.board-deleted',
  boardId: string,                  // echo for client-side log correlation
  closeCode: 4404,
}
```

**Heartbeat policy: protocol-level ping ONLY in v1.** Hocuspocus delegates to the `ws` library which surfaces `pingInterval` (default 30_000 ms). We configure it explicitly to `30_000 ms` so the value is grep-able in the server bootstrap and not implicit-from-defaults. The browser receives ping frames at the protocol layer (transparent to JavaScript) and the platform responds automatically. The application-level `'heartbeat'` discriminator stays reserved in the v1 vocabulary so v1.1 can light it up without breaking the wire — v1.1 will add app-level heartbeat IF the deployed demo reveals load-balancer idle-timeout drops that protocol ping fails to keep alive (Fly.io and Railway have shipped 60 s idle timeout defaults in the past, and protocol-level ping CAN be eaten by some intermediaries).

**Two concrete facts drove the picks:**

1. **The browser `MessageEvent.data` discriminator branching `string` vs `ArrayBuffer` is a one-LOC branch in the WS message handler — vs ~15 LOC of opcode-prefix dispatch plus a per-control-kind opcode-table maintenance burden for option W2.** For five frames per connection lifetime in v1 and a v2 ceiling of ~12 control kinds, the simplicity of W1 dominates. The protocol-layer / application-layer split is also a teachable architectural pattern — a recruiter reading the source sees one branch on data type, immediately understands the meld control channel is a strict superset of the y-websocket protocol, and never has to wonder whether an opcode collision could brick a sync message.
2. **JSON via Zod parses to ~150-byte payloads at ~5 frames/connection lifetime, while MessagePack saves ~30% of wire bytes (≈50 bytes total over the whole session) at a cost of ~20 KB minified gzipped on the meld-web browser bundle.** The trade is 50 bytes saved per board session against a 20 KB one-time bundle hit visible on every cold load — net 400× worse on the bundle axis, and DevTools-debuggability of literal-JSON during the two-tab demo is itself the portfolio signal. MessagePack would be the right call if control frames were high-frequency (>1 frame/sec) but ADR-002 already moved the high-frequency surface (awareness fan-out at 16 ms tick coalescing) into the framework's binary path.

This decision does NOT weaken ADR-001 / ADR-002 / ADR-003. The y-websocket binary protocol is untouched; Hocuspocus's `connection.context` continues to carry the session identity to all extension hooks (the welcome TEXT frame is just the wire-form of the same identity the server-side hooks already see); the Zod schemas live in `meld-server/src/lib/schemas/ws/` per `docs/conventions.md` § 5 and are type-only re-exported to `meld-web` via `meld-server/src/app.ts` — the same shim pattern tape committed under its ADR-006.

### Consequences

- **Positive.**
  - Clean protocol-layer / application-layer split: y-websocket binary remains the canonical CRDT wire, meld TEXT frames are strict superset application messages, no opcode-collision risk.
  - DevTools-debuggable: a recruiter who opens Network → WS → Messages during the two-tab demo reads the welcome frame as literal JSON without a decoder. The architectural narrative is self-documenting on the live wire.
  - Zero new browser-bundle dependency: JSON is built in. The 20 KB MessagePack hit stays out of `meld-web`.
  - v2 extension surface is reserved cleanly: `control.*` for "server-initiated event the client must observe", bare verbs for steady-state channel. Adding `control.permission-revoked` in v2 is a Zod union extension, not a wire-format change.
  - The welcome frame's `protocolVersion: 1` field gives v2 a forward-compat handshake without re-negotiating the y-websocket protocol — v1 clients fail fast and loud against a v2 server, no silent data loss.
  - `origin` echo in the welcome frame is a defence-in-depth client-side cross-check against the ADR-002 server-side `MELD_ALLOWED_ORIGINS` allowlist. Catches misconfigured production deployments before they corrupt board state.

- **Negative.**
  - TEXT frame JSON parsing is ~5× slower than `msgpackr` decode on the same payload. For five frames per session this is microseconds and unobservable; if control frames ever become high-frequency (>1 Hz sustained), revisit.
  - Hocuspocus's documentation primarily shows BINARY-frame examples for custom out-of-band data — using TEXT frames is supported by the underlying `ws` library but is the less-trodden path. AGENT_NOTES.md must flag that `connection.send(string)` emits a TEXT frame per the `ws` library semantics; backend-engineer Task 1.X-control will verify on the smoke test.
  - The reserved `'heartbeat'` and `'settings.update'` discriminators in v1 are dead schema until v1.1 lights them up. Per the AGENT_NOTES.md "intentional dead code with documented reactivation path" convention (analogous to better-auth wiring), they stay in the v1 ship and the comment lives on as a load-bearing v1.1 pin.
  - Application-level heartbeat is deferred. If a deployment ADR picks Fly.io or Railway and the platform's idle-timeout eats protocol pings under cross-region routing, v1.1 reactivates `'heartbeat'` on a 25 s cadence. Tracked in AGENT_NOTES.md "decisions to revisit" so the deployment ADR cannot pretend it does not exist.

- **Zod schema files backend-engineer must create** (paper-only spec — no code authored here).
  - `meld-server/src/lib/schemas/ws/welcome.ts` — exports `wsWelcomeFrameSchema` (kind literal `'welcome'`) + the nested `wsSessionIdentitySchema`, `wsBoardMetadataSchema`, `wsOklchColorSchema` building blocks. Building blocks live in this file (not split into separate files) because they are uniquely referenced from the welcome frame only.
  - `meld-server/src/lib/schemas/ws/control.ts` — exports `wsControlOverrunFrameSchema` (kind literal `'control.overrun'`), `wsControlBoardDeletedFrameSchema` (kind literal `'control.board-deleted'`), `wsControlKickedForNameCollisionFrameSchema` (kind literal `'control.kicked-for-name-collision'` — type-only stub for v2). The reason-code enum (`'queue.overflow' | 'rate.exceeded' | 'message.too-large'`) lives here too, as `wsOverrunReasonSchema` for reuse in tests.
  - `meld-server/src/lib/schemas/ws/heartbeat.ts` — exports `wsHeartbeatFrameSchema` (kind literal `'heartbeat'`). v1.1 stub. The file exists in v1 so the discriminated union compiles against the full v1 vocabulary; the server does not emit and does not parse it in v1.
  - `meld-server/src/lib/schemas/ws/settings.ts` — exports `wsSettingsUpdateFrameSchema` (kind literal `'settings.update'`). v1.1 stub, same rationale as heartbeat.
  - `meld-server/src/lib/schemas/ws/frame.ts` — exports `wsControlFrameSchema = z.discriminatedUnion('kind', [...])` over all six kinds + the inferred TypeScript type `WSControlFrame = z.infer<typeof wsControlFrameSchema>` + the literal-union helper `WSControlFrameKind = WSControlFrame['kind']`.
  - `meld-server/src/lib/schemas/ws/index.ts` — barrel re-export. Exports `wsControlFrameSchema` as the canonical discriminated-union entry point, plus per-kind payload schemas, plus the `WSControlFrame` / `WSControlFrameKind` / per-payload TypeScript types. Shape mirrors `tape-server/src/lib/schemas/ws/index.ts` for cross-project consistency.
  - **Fixtures (parallels tape pattern from `docs/conventions.md` § 5).** `meld-server/src/lib/schemas/ws/__fixtures__/welcome.json`, `control-overrun.json`, `control-board-deleted.json`. Each fixture is a canonical wire-byte-exact example of the frame; backend-engineer Task 1.X-control's smoke test parses each fixture through the schema and asserts round-trip equality. Browser bundle does NOT import the fixtures (they are server-test-only).

- **Cross-package type re-export (mirrors tape's `app.ts` shim from `projects/tape/server/src/app.ts`).** `meld-server/src/app.ts` exports the runtime Hono `App` type for Hono RPC client inference (frontend-engineer Task 2.2) AND the WS control-frame types as a types-only re-export block:

  ```
  // meld-server/src/app.ts — paper-only sketch; backend-engineer writes the file
  export type { App } from './server';
  export type {
    WSControlFrame,
    WSControlFrameKind,
    WSWelcomeFramePayload,
    WSControlOverrunFramePayload,
    WSControlBoardDeletedFramePayload,
    WSSessionIdentity,
    WSBoardMetadata,
    WSOklchColor,
  } from './lib/schemas/ws';
  ```

  `meld-web` then does `import type { WSControlFrame } from 'meld-server'`. `import type` is erased at compile time, so the Zod runtime and its schema definitions never reach the browser bundle — only the TypeScript shapes do. `meld-web` parses incoming control frames using its OWN compact Zod parser instance hydrated from a minimal schema set (the discriminated union + the six kind payloads — no fixtures, no test schemas). Frontend-engineer Task 2.5 owns this hydration.

- **Observability hook addition to ADR-002's `/health.ws` endpoint.** The endpoint gains four optional counters (process-lifetime totals, reset on server restart):
  - `control_frames_sent_total`: integer, incremented on every successful `connection.send(jsonString)` from the meld control layer.
  - `control_frames_dropped_total`: integer, incremented when a control frame fails to serialize OR when `connection.send` throws (e.g., socket already closed before the close-code emit lands).
  - `control_overruns_total`: integer, incremented on every `control.overrun` emit, used by the deployment ADR's uptime monitor to alert on per-hour overrun spikes that signal capacity drift.
  - `protocol_version_mismatches_total`: integer, incremented if the server's protocol-version handshake ever rejects a client (v1 ceiling is zero; v2 will be the first non-zero contributor). Reserved field; v1 always reports 0.

- **v2 extension reservation pattern.** Future control kinds extend the discriminated union without changing the wire framing:
  - **Server-initiated event the client must observe** — extend the `control.*` namespace. Examples: `control.permission-revoked`, `control.tier-limit-reached`, `control.auth-required`, `control.maintenance-window`.
  - **Steady-state channel for client-driven or server-driven app-level state** — extend the bare-verb namespace. Examples: `board.bookmark`, `cursor.snap-to`, `presence.follow-user`, `settings.update` (v1.1 light-up).
  - **Discriminator vocabulary changes are protocol-version-gated.** Adding a kind WITHOUT removing or renaming an existing one stays on `protocolVersion: 1`. Removing or renaming bumps to `protocolVersion: 2` and v1 clients fail fast against a v2 server per the welcome frame's `protocolVersion` literal check.

- **Two concrete tasks for backend-engineer (PLAN.md Phase 1 naming convention) plus one for frontend-engineer (PLAN.md Phase 2 naming convention).**
  - **Task 1.X-control — `backend-engineer` (queued, gated on ADR-004 acceptance):** `WebSocket control-frame schemas + Hocuspocus welcome emit.` Create the six Zod schema files under `meld-server/src/lib/schemas/ws/` per the spec above plus the three fixtures.   - **Task 1.X-control-observability — `backend-engineer` (queued, gated on Task 1.X-control acceptance):** `Control-frame counters on /health.ws.` Extend the existing `/health.ws` Hono route handler from ADR-002 to expose the four optional counters (`control_frames_sent_total`, `control_frames_dropped_total`, `control_overruns_total`, `protocol_version_mismatches_total`).   - **Task 2.5a — `frontend-engineer` (Phase 2.5 dependency, gated on Task 1.X-control acceptance):** `Yjs client awareness seed from welcome frame.` Inside the `WebsocketProvider` setup, install a TEXT-frame branch on the underlying `WebSocket`'s `message` listener (`if (typeof event.data === 'string')`). On `kind === 'control.board-deleted'`: render the "this board has been retired" UI surface and stop the reconnect retry. - **Follow-up: ADR-005 must exist.** **Topic: anonymous-link session model and the cookie ↔ welcome-frame identity contract.** Most load-bearing follow-up because (a) PLAN.md's anonymous-link share is the v1 onboarding affordance and ADR-001 left the anonymous-session-cookie shape as "wired but inactive better-auth scaffolding"; (b) the welcome frame this ADR pinned references a session id that must be deterministically derived from the cookie OR freshly minted server-side — ADR-005 picks the derivation (HMAC-keyed hash vs raw cookie value vs distinct DB row) and the cookie attributes (`SameSite`, `Secure`, `HttpOnly`, lifetime, rotation); (c) the deterministic emoji-name + OKLCH color assignment from `src/lib/identity/` per AGENT_NOTES.md needs a stable session-id input to hash against, and ADR-005 closes what that input is and how it survives cookie rotation. ## ADR-005: Anonymous-link session model + cookie ↔ welcome-frame identity contract

**Status:** accepted
**Date:** 2026-05-31

### Context

ADR-001 committed anonymous-link sharing as the v1 onboarding affordance with no user accounts (better-auth scaffolded but inactive). ADR-002 committed that anonymous-link session identity is carried into Hocuspocus's `connection.context` at `onConnect` time. ADR-004 committed that the welcome frame's canonical payload is `session: { id, emojiName, color }` — three fields the server emits exactly once per connection, the client uses to seed `awareness.setLocalState`, and a recruiter reads as literal JSON in the DevTools Network tab during the two-tab demo. None of those three ADRs pinned HOW the `session.id` value comes into being, HOW it persists across page reloads, or HOW the deterministic emoji-name + OKLCH color are derived from it.

What remains open from PLAN.md Task 0.4 (and explicitly named in AGENT_NOTES.md "Decisions to revisit" as "the most load-bearing follow-up because v1's onboarding is anonymous-link share end-to-end"):

1. **Where the session id is generated and how it is persisted.** Server-minted UUID v4 stored in a cookie? ULID with embedded timestamp? Client-derived from localStorage? Cookie + DB row? Each choice has a different rotation policy, a different observable-by-DevTools surface, and a different XSS-vs-server-restart-vs-cookie-cleared failure mode.
2. **The cookie attribute set verbatim.** `HttpOnly` vs JS-readable, `Secure` posture, `SameSite` policy, lifetime, `Path` / `Domain`. ADR-004's welcome frame is the primary identity-delivery channel, but the cookie is the persistence-across-reloads channel; both must agree.
3. **The exact stable input to the FNV-1a hash that picks the emoji-name AND the OKLCH color slot.** AGENT_NOTES.md Task 2.1 already pinned the 8-slot awareness color wheel and the FNV-1a algorithm; what it left open was "session id" as the input — but session id alone gives the SAME color in every board the visitor opens, which weakens the per-board collision-avoidance story.
4. **The multi-tab semantics.** Same cookie + same browser + multiple tabs of the same board = one session identity, many Hocuspocus connections. The awareness layer (per ADR-002's framework-default 16 ms tick coalescing) sees N awareness states with the same `sessionId` but distinct framework-assigned `awarenessId`s. The rule for "is this another tab of me or a different person" must be pinned BEFORE Task 2.5a wires the welcome-frame handler — otherwise the avatar stack double-counts on every tab open.
5. **The v2 migration sketch.** When better-auth lights up, the session model becomes "authenticated session linked to user account, anonymous fallback for unauthenticated visitors". The cookie contract must not foreclose that path.

Constraints inherited from prior ADRs and conventions:

- ADR-001's better-auth is wired but inactive. ADR-005 must NOT activate it; the session model is anonymous-only in v1. The migration sketch documents how better-auth slots in.
- ADR-002's Hocuspocus `onConnect` hook is the only server-side touchpoint that sees both the upgrade-handshake request headers (where the cookie arrives) AND populates the `connection.context` that ADR-004 reads to build the welcome frame. The cookie-read code path threads through Hocuspocus, not Hono's HTTP middleware stack for this request — even though Hono middleware sets the cookie on the initial GET that loads the page.
- ADR-004's welcome frame is the canonical identity-delivery wire. The client MUST prefer the welcome frame's `session.*` payload over any local cookie state for the running connection, because the server is the authority on what identity the room sees.
- `docs/conventions.md` § 14 forbids design-token / theme sharing — the awareness palette is per-project and lives in `meld-web` only. The emoji whitelist is a per-project asset that ships with `meld-server`.
- `docs/conventions.md` § 13 forbids `packages/*` extraction at v1 scope — the session model + emoji whitelist live in `meld-server/src/lib/session/`.

Three numbers drive the option weighting:

- **Cookie payload size.** A UUID v4 in canonical 36-char hyphenated form is 36 bytes; a ULID in canonical 26-char Crockford base32 is 26 bytes; a 16-byte session id in url-safe base64 is 22 bytes. All sit two orders of magnitude inside Chrome's per-cookie 4 KB limit. Size is NOT a discriminator.
- **First-paint perceived load.** From Task 2.1's scaffolded landing to the brand-corner identity card rendering "you are Otter" takes either (a) ZERO ms if the cookie is JS-readable and the client renders identity locally before the WS handshake completes, OR (b) ~150–250 ms if the cookie is `HttpOnly` and the client must wait for the WS welcome frame round-trip to learn its own identity. The 150–250 ms penalty is the cold-start TTFB + TLS + WS upgrade + Hocuspocus onConnect + welcome emit chain; measurable, observable in Lighthouse, and visible to a recruiter clicking the share button.
- **XSS-readability delta.** A JS-readable cookie is XSS-exfiltratable. The session id alone does NOT grant board write access (the y-websocket protocol does not authenticate; ANY connection with the board URL can write). So the XSS surface added by JS-readable identity is "an attacker who already injected JS into our page can read the user's anonymous emoji-name from a cookie" — strictly weaker than the XSS surface they already have (they can connect to the WS and exfiltrate the board state directly). Net XSS posture impact: zero meaningful delta for v1 anonymous identity, real delta only when v2 auth lands.

### Options considered

**Session id generation + persistence:**

- **G1. Server-generated UUID v4, set in a JS-readable cookie on first HTTP request, no DB persistence.** Hono middleware on the `GET /` (and any future page route) checks for the cookie; if missing, generates a UUID v4 via `node:crypto.randomUUID()` and writes the `Set-Cookie` header. The cookie is JS-readable so the client can render the brand-corner identity card on first paint without waiting for the WS handshake. Hocuspocus `onConnect` reads the cookie from `request.headers.cookie`, parses it, populates `connection.context.sessionId`, and ADR-004's welcome-frame builder consumes it. Server holds zero state about the session id itself — the cookie IS the source of truth. Cold-start sync latency: zero — the client renders identity from the cookie before the WS opens. Cookie-cleared / private-window behaviour: fresh UUID, fresh identity, documented. Server-restart behaviour: cookies survive — the client reconnects with the same id and the server happily accepts it. Failure mode under a real incident: if a user shares their cookie (copy-paste from DevTools), the recipient appears as the same identity in any board — acceptable trade-off for an anonymous-link demo with no write authorization.
- **G2. Server-generated ULID, set in cookie.** Same shape as G1 but ULID instead of UUID. ULID encodes its creation timestamp in the first 10 chars (Crockford base32 of millisecond epoch). Pro: server-side sortability for any future "first-seen" analytics. Con: the cookie LEAKS the visitor's first-visit timestamp to anyone who reads the cookie (the visitor themselves in DevTools, or a same-browser attacker post-XSS). For an anonymous-portfolio demo this is a tiny privacy leak we get nothing observable in return for in v1.
- **G3. Cookie-stored UUID + DB-tracked first-seen row.** G1 plus a `sessions` table row written on the Hono middleware path when the cookie is first set. Enables session-level analytics (DAU on the deployed demo, board-creation funnel from share-link). Cost: one extra Postgres write on first page load per visitor, one extra schema (and migration), one extra retention concern that interacts with the ADR-003 nightly sweep. The analytics use case is plausible but not load-bearing for the v1 wow moment.
- **G4. Client-derived UUID stored in localStorage.** Client generates `crypto.randomUUID()` on first page load if localStorage is empty, persists it. WS connect sends it as a query parameter on the `/ws/board/:boardId?sid=...` URL (cookies are not the only WS auth channel). Pro: survives cookie clearing — localStorage is a separate browser storage. Con: localStorage is unconditionally JS-readable so the XSS exfiltration story is identical to G1; localStorage is cross-tab sticky in a way cookies are not (a tab opened to a different origin still sees the localStorage via XSS, vs cookies which respect `SameSite` boundaries); the WS URL with `?sid=` query parameter leaks the session id to server access logs and to any reverse proxy in front of the deployment (the deployment ADR will care).

**Cookie attribute set:**

- **A1. JS-readable cookie (no `HttpOnly`).** `Secure` in production, `SameSite=Lax`, `Path=/`, `Max-Age=31536000` (1 year). Client can render the brand-corner identity card on first paint by reading `document.cookie` BEFORE the WS welcome frame lands. Welcome frame is still the authority for the running connection — but the client UI is not blank for 150–250 ms.
- **A2. `HttpOnly` cookie.** Server-only. Client cannot read its own identity from the cookie; client identity is delivered ONLY through the welcome frame after the WS upgrade completes. First-paint identity card is empty until the welcome frame arrives. XSS surface is theoretically tighter (the cookie is not exfiltratable by injected JS), but per the "XSS-readability delta" analysis above the practical impact for anonymous-only v1 is zero.
- **A3. JS-readable cookie + signed payload.** HMAC-sign the session id with a server-secret key, store `${sessionId}.${hmac}` in the cookie. Server verifies the HMAC on `onConnect`; tamper attempts are rejected. Cost: rotation policy needed for the HMAC key, and the security benefit (preventing session-id-tampering) is moot in v1 because we have no write-authorization story tied to the session id at all — anyone with the board URL can write to it via y-websocket protocol regardless of cookie state.

**Per-board color derivation rule:**

- **C-A. `fnv1a(sessionId) % 8`.** Same color in every board the visitor opens. Same identity, same hue forever. Pro: maximally recognisable — "you are always violet". Con: two visitors with FNV-1a-colliding session ids see the same color in EVERY board they both open, not just one.
- **C-B. `fnv1a(sessionId + ':' + boardId) % 8`.** Color is per-board. Same identity in board A might be violet, in board B might be teal. Pro: collisions are per-board only — a visitor who collides in board A is statistically very unlikely to collide in board B with the same other visitor. Con: less recognisable across boards if the visitor opens many boards in one browsing session (rare in v1 — multi-board navigation is v2).

**Multi-tab awareness rule:**

- **M1. Each tab is its own awareness identity (framework-default).** Hocuspocus assigns a distinct `awarenessId` per WebSocket connection. Tabs A and B of the same browser session both join the room with the same `sessionId` but distinct `awarenessId`s. The avatar stack sees TWO entries and the room "feels" populated even when only one human is present.
- **M2. Same-`sessionId` connections collapse to one awareness identity in the UI.** Frontend-engineer's avatar-stack code deduplicates by `sessionId`. The WebSocket layer is unaware of the rule — it still sees two connections — but the visible avatar stack shows one pill. Two cursors still appear on canvas (each tab has its own cursor position) but they share the avatar pill, which reads correctly to other viewers as "that person has two tabs open".

### Decision

**Session id: option G1 — server-generated UUID v4 on first HTTP request, set in a cookie via Hono middleware, no DB persistence, server holds zero state about the id itself.** The id is generated via `node:crypto.randomUUID()` (Node 22 native) on the first GET that reaches Hono without a `meld_session` cookie. The Hono middleware writes `Set-Cookie` on the response. The Hocuspocus `onConnect` hook reads the cookie from `requestHeaders.cookie`, parses it, validates it as a UUID v4 (regex check), and populates `connection.context.sessionId`. If the cookie is absent on the WS upgrade (visitor with cookies disabled, or visitor whose initial page load did not pass through the Hono middleware path because they linked directly to a static asset before the page route fired), the `onConnect` hook MINTS a fresh UUID v4 server-side and writes it into `connection.context.sessionId`, then includes it in the welcome frame's `session.id` — the client persists it into a cookie by a separate POST `/api/session` round-trip OR accepts that this session is connection-scoped. Documented edge case: cookie-disabled visitors get a fresh identity per WS reconnect (acceptable for v1 demo; documented in README). The cookie IS the source of truth — no `sessions` table, no DB row, no analytics extension in v1. The G3 analytics path stays a v1.1 candidate.

**Cookie attributes verbatim (the values backend-engineer encodes into the Hono `Set-Cookie` middleware):**

```
Name:     meld_session
Value:    <UUID v4, 36 chars hyphenated, lowercase>
HttpOnly: false           // JS-readable for first-paint identity card render
Secure:   true (production, NODE_ENV === 'production')
          false (development, fall-open for localhost dev parity)
SameSite: Lax             // not Strict; allows cross-site-link board share to set the cookie on first arrival
Path:     /
Domain:   (unset — host-only cookie, scoped to the exact deployed origin)
Max-Age:  31536000        // 1 year in seconds; rotated only when user manually clears cookies
```

The `SameSite=Lax` choice (vs `Strict`) admits the common share-flow: a recipient clicks a board URL in Slack or in an email and lands on `/board/<id>` — `Lax` lets the cookie be set on this first cross-site navigation, `Strict` would refuse and the recipient would have NO session until they reload the page. v1 does not support iframe-embedded boards (Out of scope per PLAN.md), so the `SameSite=None` posture that iframes require is not a candidate. `Domain` is intentionally unset so the cookie is scoped to the exact deployed origin — a future subdomain (e.g., `api.meld.example.com` vs `meld.example.com`) does NOT silently share the session, which is the safer default.

**Emoji whitelist size + scheme:** 128 single-codepoint emoji from the Unicode 15.1 "animals & nature" + "food & drink" subset, curated for screen-reader-friendly aria-labels (each emoji has an explicit `name` field in the source file), sorted lexicographically by Unicode codepoint hex for stable FNV-1a indexing. 128 = 2^7 — clean power-of-two modulo space so the hash distribution is uniform without rejection sampling. The whitelist excludes any codepoint that is part of a ZWJ sequence (multi-codepoint compound emoji like family or flag emoji) so that string slicing / equality comparison stays single-codepoint-safe. The file lives at `meld-server/src/lib/session/emoji-names.ts` and exports a frozen `readonly EmojiName[]` of `{ codepoint: string; name: string }` records. `meld-web` does NOT bundle the whitelist — the welcome frame's `session.emojiName` field carries the codepoint string directly from server to client, so the client never needs to look up the table itself.

**Per-board color derivation rule: option C-B — `fnv1a(sessionId + ':' + boardId) % 8`.** Same visitor in two different boards sees two different colors. Collisions are per-board-pair, not global. The FNV-1a 32-bit variant from AGENT_NOTES.md Task 2.1 is the canonical algorithm; the hash input is the byte sequence `<sessionId-utf8>:<boardId-utf8>` (literal ASCII colon separator). The slot index 0–7 maps to the 8-slot awareness palette from Task 2.1 (slot 0 = brand-anchor violet, slots 1–7 evenly spaced 45° around the wheel). Same input produces the same slot forever — deterministic, stateless, no DB.

**Emoji-name derivation rule: `fnv1a(sessionId) % 128`.** The emoji-name is per-session (NOT per-board) — same visitor sees the same emoji-name across all boards they open. This is the deliberate inverse of the color rule: color is the per-board collision-avoider, emoji-name is the cross-board identity-thread. A visitor who opens two boards is "Otter in board A (violet)" and "Otter in board B (teal)" — the name persists, the color rotates. Hash algorithm identical (FNV-1a 32-bit), input is just `<sessionId-utf8>` (no separator, no boardId).

**Multi-tab awareness rule: option M1 — each WebSocket connection is its own awareness identity, with `connection.context.sessionId` carried alongside as a stable tag.** Hocuspocus's framework-default `awarenessId` is distinct per WebSocket connection; we do NOT override this. Frontend-engineer's avatar-stack code DOES NOT deduplicate by `sessionId` — two tabs of the same browser show as two avatar pills, both with the same emoji-name and color. This is the deliberate "two tabs are two cursors" UX: the wow moment is "open a second tab and see another cursor appear in real time" — collapsing same-`sessionId` connections into one pill would visually defeat the demo. Other viewers seeing the room understand "that person has two tabs open" intuitively because the two pills share the same emoji-name and color. The `connection.context.sessionId` is still emitted in the welcome frame's `session.id` field so the client can detect "this is another tab of mine" for any v1.1 feature that needs to (e.g., "broadcast my color change to my own tabs" — out of scope for v1).

**Two concrete facts drove the picks:**

1. **A JS-readable cookie (A1) plus a matching welcome-frame `session.id` lets the client render the brand-corner identity card on first paint without waiting for the WS handshake — saving 150–250 ms of perceived "who am I" load — and the XSS exfiltration surface added is zero in practical terms because anonymous v1 has no write-authorization story tied to the session id (anyone with the board URL can write via y-websocket regardless of cookie state).** The HttpOnly cookie (A2) would tighten the XSS theoretical surface by exactly nothing meaningful in v1 while paying the 150–250 ms penalty on every cold load. When v2 auth lands and the session id becomes the key to actual write authorization, the cookie rotates to `HttpOnly` and the identity-card client-render rewires through a SSR-injected initial-state hydration — documented in the v2 migration sketch below.
2. **Per-board color derivation `fnv1a(sessionId + ':' + boardId) % 8` matters more than the apparent "less recognisable across boards" cost because v1 has NO multi-board navigation surface (PLAN.md "Out of scope" pins multi-board nav as v2) — a typical v1 visitor opens one board, draws shapes, never opens a second.** The cost of C-B (less recognisable across boards) is zero against a population that opens one board; the benefit (per-board collision avoidance: with 8 slots and 50-user board ceiling per ADR-002's `maxRate` budget, the birthday-collision probability drops from `1 - (8!/(8^N * (8-N)!))` global to per-board, lifting the "two strangers see the same color" experience from "every board" to "this specific board only"). When v2 multi-board navigation lands, the recognisability cost becomes real and ADR-NNN reconsiders — but the per-board derivation is the safer v1 default.

This decision does NOT weaken ADR-001 / ADR-002 / ADR-003 / ADR-004. ADR-001's better-auth-wired-but-inactive remains intact; ADR-005 explicitly does not activate it. ADR-002's `connection.context` identity-carrier remains the server-side touchpoint; this ADR pins what populates `sessionId`. ADR-003's persistence and retention surfaces are unchanged — sessions are NOT persisted to Postgres in v1. ADR-004's welcome-frame canonical fields `session: { id, emojiName, color }` are preserved verbatim; this ADR pins how each of the three values is derived.

### Consequences

- **Positive.**
  - First-paint identity card renders from the JS-readable cookie before the WS handshake completes — measurable 150–250 ms perceived-load win on cold load.
  - Server is stateless about the session id itself — no `sessions` table, no DB write on first page load, no retention sweep concern for orphaned session rows.
  - Cookie-cleared / private-window / different-browser produces a fresh deterministic identity — documented behaviour, observable in DevTools.
  - Per-board color derivation prevents the "every board always has the same Otter-violet" collision pattern when v2 multi-board navigation lands; v1 cost is zero because v1 has no multi-board nav.
  - Emoji-name persists across boards as the cross-board identity thread; color rotates per-board as the per-board collision-avoider. The split is teachable in 30 seconds to a recruiter who asks.
  - Multi-tab rule (each connection is its own awareness identity, same `sessionId` carried as a tag) preserves the "two tabs = two cursors" wow moment without UI deduplication code.
  - Welcome frame remains the authority on running-connection identity. If a server-side identity-policy change ever needs to override the cookie (e.g., v2 auth attaches the cookie-anonymous identity to an authenticated account), the client follows the welcome frame and the cookie catches up out-of-band.
  - v2 better-auth migration is additive: the cookie name stays `meld_session`; the value becomes a signed token that resolves server-side to an authenticated user id; anonymous fallback for unauthenticated visitors keeps the v1 UUID v4 path as the "guest" branch.

- **Negative.**
  - JS-readable cookie is theoretically XSS-exfiltratable. Practical impact in v1 is zero (no write authorization tied to the id), but the README's security section must document the trade-off honestly — a recruiter reading the security section sees a deliberate, named choice rather than an oversight.
  - Cookie-disabled visitors get a fresh identity per WS reconnect (the `onConnect` mint path). Acceptable for v1 demo; documented in README.
  - Two visitors with FNV-1a-colliding session ids see the same emoji-name across all boards they both open (the emoji-name derivation is per-session, not per-board). For 128 slots and the v1 demo's expected visitor count (low hundreds across the lifetime of the deployment), the birthday-paradox probability of a name collision in any single board is sub-1%. Documented.
  - The "1-year `Max-Age`" cookie lifetime persists identity across visits that may span months. A visitor returning a year later to a board they shared at the start sees the same Otter-violet identity — feature, not bug, but documented behaviour.
  - The `connection.context.sessionId` mint-on-cookie-miss path inside Hocuspocus `onConnect` means the WS layer can mint identity without the HTTP layer ever seeing it. If a future deployment ADR puts a strict CORS-cookie-only auth gate in front of HTTP, the WS path becomes the looser door. Documented as a v1.1 audit checklist item.

- **Hono middleware that sets the cookie — paper-only sketch.**
  - **File:** `meld-server/src/lib/session/cookie.ts`. Exports a Hono middleware factory `createSessionCookieMiddleware()` that returns a middleware function. The middleware inspects `c.req.header('cookie')` for a `meld_session` key, parses it, validates against the UUID v4 regex (`/^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/`). If missing or malformed, generates a fresh UUID v4 via `crypto.randomUUID()` and writes `c.header('set-cookie', '...')` with the verbatim attribute set above. Attaches the resolved session id to `c.set('sessionId', value)` for downstream Hono handlers.
  - **Wiring:** mounted via `app.use('*', createSessionCookieMiddleware())` in `meld-server/src/server.ts` BEFORE any route handler. The middleware is idempotent — re-running it on a request that already has the cookie is a no-op except for the `c.set('sessionId', ...)` attachment.
  - **Frontend cookie-write fallback for the WS-minted case.** When Hocuspocus `onConnect` mints a session id because the cookie was absent, the welcome frame's `session.id` is the only delivery channel. Frontend-engineer Task 2.5a (already queued from ADR-004) gains a tiny extension: on receiving a welcome frame, if `document.cookie` does not already contain `meld_session=${payload.session.id}`, POST `/api/session` with the id and the server's `createSessionCookieMiddleware()` writes it. This closes the cookie-disabled-on-first-arrival-then-enabled edge case without rewriting the welcome-frame contract.

- **Cookie-read path in the Hocuspocus `onConnect` hook — paper-only sketch.** The Hono WS upgrade handshake passes the raw `Request` (with full headers, including `cookie`) to Hocuspocus's `Server.handleConnection` per ADR-002. Inside the `onConnect` extension hook, `data.requestHeaders.cookie` is the unparsed cookie string. The hook parses it via a lightweight cookie parser (either `node:cookie` from `@hono/cookie` or a 20-LOC hand-rolled parser — backend-engineer picks during implementation), looks for `meld_session`, validates with the UUID v4 regex. On hit: populate `data.connection.context = { sessionId: parsed, mintedAt: 'cookie' }`. On miss: mint a fresh UUID v4 via `crypto.randomUUID()`, populate `data.connection.context = { sessionId: minted, mintedAt: 'ws-onConnect' }`. The `mintedAt` discriminator is included so the welcome-frame builder can emit a stable hint to the client about whether it should expect a cookie-write fallback. The `data.connection.context` payload is consumed by every subsequent Hocuspocus hook AND by the welcome-frame builder per ADR-004.

- **Emoji whitelist file — paper-only spec.** `meld-server/src/lib/session/emoji-names.ts` exports `EMOJI_NAMES: readonly { codepoint: string; name: string }[]` of length 128. Curation rules: each entry is a single Unicode codepoint (NO ZWJ sequences, NO skin-tone modifiers, NO regional indicator pairs), drawn from Unicode 15.1's "animals & nature" + "food & drink" subsets, sorted lexicographically by codepoint hex for stable FNV-1a indexing. Each `name` field is a short lowercase ASCII string (e.g., `"otter"`, `"fox"`, `"peach"`, `"sushi"`) suitable as an accessibility aria-label. The file is `as const` + `Object.freeze` so the array index is the canonical ID — a future curation-list-edit reordering the entries would silently re-assign every visitor's identity, which is a deliberate-on-purpose pin (any future edit MUST be append-only). The whitelist file documents the append-only contract in a top-of-file comment.

- **Color derivation helper — paper-only spec.** `meld-server/src/lib/session/color.ts` exports `deriveAwarenessColor(sessionId: string, boardId: string): { l: number; c: number; h: number }`. Internal implementation: FNV-1a 32-bit hash of UTF-8 bytes of `${sessionId}:${boardId}`, modulo 8, map to one of the 8 OKLCH triplets from AGENT_NOTES.md Task 2.1 (slot 0 = brand violet `{l: 0.6, c: 0.17, h: 285}`, slots 1–7 at 45° increments). The 8-slot palette table lives inline in this file (NOT imported from `meld-web/src/app/globals.css` — that file is a CSS file, and `docs/conventions.md` § 14 forbids cross-package design-token sharing anyway). The OKLCH triplet values are duplicated server-side and client-side; the source of truth for the slot table is the AGENT_NOTES.md Task 2.1 pin, and any change to the palette MUST update both files in the same commit. Documented as a known duplication with an explicit cross-reference in both files.

- **Emoji-name derivation helper — paper-only spec.** `meld-server/src/lib/session/emoji.ts` exports `deriveEmojiName(sessionId: string): { codepoint: string; name: string }`. Internal implementation: FNV-1a 32-bit hash of UTF-8 bytes of `sessionId` (no separator, no boardId), modulo 128, lookup into `EMOJI_NAMES`.

- **Observability extension to `/health.ws` — paper-only spec.** ADR-002 originally defined `/health.ws` with `{ rooms, connections_total, connections_per_room }`. ADR-004 extended it with four control-frame counters. ADR-005 adds **TWO MORE counters and ONE distinct/total split:**
  - `sessions_distinct`: integer, count of distinct `connection.context.sessionId` values across all currently-live connections in the Hocuspocus `Server.documents` map. Distinct from `connections_total` — five tabs of the same browser contribute 5 to `connections_total` and 1 to `sessions_distinct`. The metric uses a `Set<sessionId>` derived on-demand from iterating `Server.documents.forEach(doc => doc.connections.forEach(c => set.add(c.context.sessionId)))`. O(N) over total connections, acceptable for v1 single-instance.
  - `sessions_minted_ws_total`: process-lifetime counter, incremented every time `onConnect` mints a fresh UUID because the cookie was absent. A non-zero v1 value indicates real cookie-disabled traffic on the demo; a value spike would indicate a deployment regression where the Hono middleware stopped firing on the page load.

- **Three concrete tasks queued (two backend + one frontend, PLAN.md-style names).**
  - **Task 1.7a — `backend-engineer` (queued, gated on ADR-005 acceptance — replaces and supersedes PLAN.md Task 1.7's "better-auth wired but unused" placeholder for the cookie surface; Task 1.7 stays scoped to the better-auth scaffolding-only inactive wiring):** `Anonymous session cookie middleware + emoji whitelist + per-board color derivation.` Create `meld-server/src/lib/session/cookie.ts` (Hono middleware factory), `emoji-names.ts` (128-entry frozen whitelist), `emoji.ts` (`deriveEmojiName`), `color.ts` (`deriveAwarenessColor` with the 8-slot OKLCH palette duplicated server-side), `fnv1a.ts` (32-bit FNV-1a hash helper per AGENT_NOTES.md Task 2.1). Wire the Hono cookie middleware at `app.use('*', createSessionCookieMiddleware())` in `server.ts`. Unit-tested: cookie-set on first request, cookie-roundtrip on second request, UUID v4 regex rejects malformed cookies (cookie corruption case), `deriveEmojiName` + `deriveAwarenessColor` are deterministic across 1000 synthetic session id inputs, palette slot distribution over 10000 inputs is uniform within ±5%.
  - **Task 1.7b — `backend-engineer` (queued, gated on Task 1.7a + Task 1.X-control acceptance):** `Hocuspocus onConnect session-context population + welcome-frame identity wire.` Wire the Hocuspocus `onConnect` hook (originally specified in ADR-002 Task 1.X) to: (a) parse the cookie from `data.requestHeaders.cookie` via the same parser used by Task 1.7a; (b) validate against the UUID v4 regex; (c) on hit, populate `data.connection.context = { sessionId, mintedAt: 'cookie' }`; (d) on miss, mint via `crypto.randomUUID()` and populate `{ sessionId, mintedAt: 'ws-onConnect' }`. - **Follow-up: ADR-006 must exist.** **Topic: production reverse-proxy and origin posture for the deployed demo (Fly.io / Railway / VPS pick + CORS/CSP/X-Frame-Options/Set-Cookie consistency across HTTP and WS).** ADR-005 imposes a specific constraint on ADR-006: the cookie `Secure` flag is `true` in production, which means the deployed origin MUST be HTTPS, AND the WS endpoint MUST also be `wss://` from the same origin (so the cookie attaches to the WS upgrade handshake) — otherwise the cookie does not flow on the WS upgrade and every visitor gets the `mintedAt: 'ws-onConnect'` codepath on every reconnect. ADR-006 must pin the deployment platform that satisfies this AND must specify the reverse-proxy pattern that lets a single hostname serve both HTTP (`/`, `/api/*`, `/health*`) and WS (`/ws/board/:id`) — likely a single Hono process binding `serve()` on one port behind the platform's edge proxy, mirroring tape's Phase 6 deploy lesson. This is the most load-bearing remaining Phase 1 ADR because (a) it gates the demo URL the README will link to; (b) it interacts with ADR-002's `MELD_ALLOWED_ORIGINS` env var directly; (c) it is the only remaining ADR-shaped surface before the engineering phase can deploy end-to-end. The rate-limit-on-session-creation candidate is covered by ADR-002's framework-level `maxRate` and the cookie middleware's idempotency; the rate-limit candidate is NOT load-bearing for v1 ship.

- **v2 migration sketch — better-auth activation.** When v2 lights up the better-auth path (ADR-001 placeholder), the migration is additive: (1) the cookie name stays `meld_session`; (2) the cookie value becomes a signed better-auth session token instead of a raw UUID v4; (3) the cookie attribute set tightens to `HttpOnly: true` (server-only — auth tokens are XSS-exfiltratable in a way anonymous identity is not); (4) the Hono middleware on `*` resolves the token to a `userId` server-side; (5) Hocuspocus `onConnect` reads the resolved userId from a server-side session store (better-auth's adapter) instead of trusting the raw cookie value; (6) the welcome frame's `session.id` becomes the better-auth userId, the `session.emojiName` becomes a user-chosen display name override (falling back to the FNV-1a derivation if the user has not set one), the `session.color` becomes a user-chosen color override (same fallback); (7) anonymous fallback for unauthenticated visitors keeps the v1 UUID v4 path as the "guest" branch and the welcome frame's `session.id` becomes a `guest:<uuid>` namespaced string so the client can distinguish authenticated from guest in the avatar stack. The first-paint identity card client-render rewires through SSR-injected initial-state hydration (Next.js `cookies()` in a server component) instead of `document.cookie` reads — because the cookie is now `HttpOnly` and JS cannot read it. This migration is documented in `meld-server/src/lib/session/README.md` (folder-scoped notes, NOT a portfolio-wide doc) so the next contributor (or future you) inherits the upgrade path without reading the full ADR stack.

## ADR-006: Production reverse-proxy + origin posture for the deployed demo

**Status:** accepted
**Date:** 2026-05-31

### Context

ADR-001 committed Hono 4.x on Node 22 LTS as the v1 backend; ADR-002 committed Hocuspocus mounted on the same Node `http.Server` as Hono and pinned `MELD_ALLOWED_ORIGINS` (comma-separated, fail-closed in production) as the shared HTTP-CORS + WS-Origin allowlist; ADR-003 committed a Postgres-backed `Storage` adapter; ADR-004 committed JSON-over-TEXT-frame control with a `protocolVersion: 1` welcome frame whose `origin` echo cross-checks the server's allowlist; ADR-005 committed a JS-readable `meld_session` cookie that MUST carry `Secure: true` in production AND MUST attach to the WS upgrade — which is only true if the WS endpoint is `wss://` from the SAME origin as the HTTP page load.

PLAN.md's success criterion "deployed demo URL serves uninterrupted for 7 consecutive days" is gated on a deploy that:

1. **Satisfies ADR-005's same-origin HTTPS + wss:// constraint.** If the cookie does not flow on the WS upgrade, every visitor falls back to the `mintedAt: 'ws-onConnect'` codepath on every reconnect, defeating the 150–250 ms first-paint identity card win ADR-005 was justified against and bloating the `sessions_minted_ws_total` counter that ADR-005 added to `/health.ws`.
2. **Preserves the WS `Upgrade` header byte-for-byte through any HTTP layer the request crosses.** This is the load-bearing failure mode tape's Phase 6 sage exposed: a server-side catch-all proxy implemented via Bun's `fetch()` does NOT preserve the WebSocket upgrade — Bun's `fetch()` treats the request as an HTTP round-trip and the upgrade socket never reaches the Next standalone server downstream. Tape avoided the bug because tape's `/ws/stream` is a real Elysia `.ws()` route mounted BEFORE the catch-all, so WS never reaches `fetch()`. Meld must inherit this discipline without re-discovering the failure mode.
3. **Resolves the "Fly edge routes 443 to ONE internal port" constraint.** Fly.io's `[http_service]` block (single-service mode) routes external port 443 to one `internal_port`. The legacy `[[services]]` array supports multiple service definitions but BOTH cannot route to port 443 simultaneously without colliding — tape hit this collision on its first Phase 6 deploy attempt and resolved it by collapsing both processes behind one internal port (3001), with the Elysia server taking the role of edge reverse proxy to the Next standalone server on localhost:3000.
4. **Does not foreclose the ADR-001 v2 CF Workers Durable Objects migration.** The v1 topology can mention a single Fly Machine; the v2 sketch needs the reverse-proxy layer to be a thing CF Workers handle natively (Workers' edge IS the routing, no in-process catch-all needed) rather than a thing we ship code for that v2 has to delete.

PLAN.md left Task 0.5 with this exact responsibility; AGENT_NOTES.md "Decisions to revisit" pinned it as the single most blocking remaining Phase 1 ADR before backend-engineer + the Phase 6 deploy-prep agent can ship a live demo URL.

Constraints inherited from prior ADRs and conventions:

- ADR-002's `MELD_ALLOWED_ORIGINS` env var is the single config surface; the production posture must pin its prod default and fail-closed-in-production-on-empty semantics.
- ADR-005's cookie attribute set is `Secure: true` in production / `false` in dev. Hono's runtime cannot infer "is this request behind TLS termination" without trusting the platform's `X-Forwarded-Proto` header.
- `docs/conventions.md` § 13 forbids `packages/*` extraction; the deploy artefacts (Dockerfile, `fly.toml`) live in `projects/meld/` only.
- `docs/conventions.md` § 14 forbids cross-project token sharing; the prod URL convention (mirror tape's `<name>-demo.fly.dev`) is a naming pattern, not a token — sharing the pattern is allowed.

### Options considered

**External topology (browser → edge → internal process layout):**

- **T1. Single Fly Machine, single port (443) → one Node `http.Server`. Hono handles HTTP `'request'`. The `http.Server`'s `'upgrade'` event routes by path: `request.url.startsWith('/ws/board/')` → delegate to Hocuspocus's `handleUpgrade`. Hono catch-all proxies non-`/api`, non-`/health*` HTTP requests to a Next standalone server on `localhost:3000` via `node:http` (`createProxyServer`-style; NOT browser `fetch`). One process, one port external, two processes internal (Node + Next standalone) under one PID-1 entrypoint. Closest analog to tape's final shipped topology, but with the critical difference that WS upgrades NEVER traverse the Hono `fetch` catch-all (option 5 below).**
- **T2. Single Fly Machine, single port → Caddy reverse-proxy → Hono on internal port A OR Next standalone on internal port B based on `/ws/board/*` + `/api/*` + `/health*` path-matching.** Adds Caddy as a separate process layer; Caddy natively preserves WS upgrades. Cost: one extra binary (~40 MB) in the runtime image, one extra config surface (`Caddyfile`), one extra failure mode (Caddy supervisor inside the container). Local-dev parity: WORSE than T1 because dev runs no Caddy — `pnpm dev` for `meld-server` and `meld-web` already hits `localhost:3055` directly, so prod adds a layer dev does not test. v2 CF DO migration: Caddy disappears, Workers do the routing — the Caddy investment becomes deletable code.
- **T3. Single Fly Machine, two external services on different ports — 443 for Next (Hono UI shell + Next as library), 4443 for WS (Hocuspocus standalone).** Browser WS hits `wss://meld-demo.fly.dev:4443/ws/board/:id`. Cleaner code separation: Hono never proxies, Hocuspocus owns its port. Cost: corporate networks routinely block outbound ports outside the 80/443 set; recruiter on a corporate VPN hits the WS port and the demo silently fails (no presence cursor ever appears, no error banner — just a stuck "connecting…" state). Also breaks ADR-005's same-origin cookie attach (origin is host:port, so `:443` and `:4443` are distinct origins for cookie purposes; cookie set on `:443` does NOT flow to `:4443`'s WS upgrade — fatal for ADR-005's first-paint identity card win).
- **T4. Two Fly Machines: web machine + server machine, internal Fly proxy.** Browser hits one hostname, Fly's edge proxy fans to two machines on the internal network. Cleanest separation; each machine scales independently. Cost: overkill for v1 demo traffic (PLAN.md's deploy success criterion targets uninterrupted 7-day uptime, not concurrent-machine throughput); doubles the per-deploy cost; adds an internal network hop for the same-origin cookie attachment that ADR-005 needs (cookie set on web machine, then read by server machine on WS upgrade — works IF both machines see the same `Host:` header AND `X-Forwarded-Proto`, but the per-machine TLS posture must be coordinated). Worth it only if v1 hits a real per-process resource ceiling, which 50-user-board ceilings do not.

**WS upgrade preservation (where the Upgrade header is handled relative to the HTTP catch-all):**

- **U5. Direct `http.Server` `'upgrade'` event handler routes by path before any Hono code runs.** Node's native `http.Server` fires the `'upgrade'` event on the raw `IncomingMessage` + socket BEFORE any Hono middleware. The handler inspects `request.url`, matches against `/ws/board/`, and invokes Hocuspocus's `Server.handleUpgrade(request, socket, head)` directly. The Hono `'request'` handler never sees the Upgrade-header request; the Hono catch-all proxy never sees it either. WS upgrade is preserved by structural separation, not by any proxy library's preservation semantics. **Tape's `fetch`-breaks-WS-upgrade failure mode is structurally impossible in this topology because the WS request never touches `fetch`.**
- **U6. Catch-all proxy is HTTP-only by allowlist: it only proxies after asserting `request.headers.upgrade === undefined`. WS upgrade is still delegated to Hocuspocus at the `http.Server` level — same mechanism as U5 — but the catch-all gains a defensive check.** Same mechanism as U5 in practice; the defensive check is cheap (one header read) and documents the contract at the catch-all site.

**Origin allowlist + `X-Forwarded-Proto` posture:**

- **P-A. Prod `MELD_ALLOWED_ORIGINS=https://meld-demo.fly.dev` only.** Single canonical origin. Welcome frame's `origin` echo (ADR-004) renders as `"https://meld-demo.fly.dev"` for every connection.
- **P-B. Prod `MELD_ALLOWED_ORIGINS=https://meld-demo.fly.dev,https://www.meld-demo.fly.dev`.** Tolerates a `www` redirect that Fly does not provision by default. Cost: one more origin in the allowlist that v1 has no traffic for and no DNS for. Reject as unnecessary; if a future deploy adds `www`, the env-var change is one comma.
- **X-A. Hono middleware reads `c.req.header('x-forwarded-proto')` to decide cookie `Secure`. Trusts the platform's header verbatim (Fly terminates TLS at the edge and sets `X-Forwarded-Proto: https` on every forwarded request).** Standard pattern. Cookie middleware reads the header at write time; if `x-forwarded-proto === 'https'`, set `Secure: true`. Defensive fallback: in production (`NODE_ENV === 'production'`), force `Secure: true` regardless of header (defence-in-depth — if the platform misconfigures and the header is missing, we want the secure default, not the cookie-blocked default).
- **X-B. Hono middleware uses `NODE_ENV === 'production'` alone (ignore `X-Forwarded-Proto`).** Loses the dev / preview parity where a local dev server proxied through ngrok HTTPS still needs `Secure: true` to test the production cookie path. Reject.

**Health endpoint accessibility:**

- **H-A. `/health` and `/health.ws` stay publicly accessible.** Operationally convenient — `curl https://meld-demo.fly.dev/health` from any machine probes liveness. Exposes process metadata (commit SHA, DB connected boolean) and WS observability (room count, connection count, session count). For a portfolio demo with no authenticated surface and no production data, this is the right default — same as tape's posture.
- **H-B. Health gated behind a query secret.** Over-engineering for v1.

### Decision

**Single Fly Machine, single external port (443), one Node process serving both Hono HTTP routes and Hocuspocus WS — with WS upgrade routed at the Node `http.Server` `'upgrade'` event level before any Hono code runs (option T1 + option U5), behind Fly's edge TLS terminator with `X-Forwarded-Proto: https` trusted in Hono cookie middleware (option X-A) and `Secure: true` defence-in-depth-forced in production regardless of header.**

External shape: browser hits `https://meld-demo.fly.dev` for HTTP and `wss://meld-demo.fly.dev/ws/board/:boardId` for WS. Fly's edge proxy terminates TLS and forwards both to internal port 3000 (the meld convention — tape used 3001 to mirror the Elysia-default, meld uses 3000 because Next standalone is no longer on a separate port). The Node process accepts the connection, demultiplexes:

- `'request'` event → Hono fetch handler. Hono routes match `/api/*`, `/health`, `/health.ws`, `POST /api/boards`, `POST /api/session`. Any unmatched HTTP request hits the Hono catch-all, which proxies via `node:http` `request()` to the Next standalone server on `localhost:3001` (NOT browser `fetch()` — see fact 1 below). The catch-all asserts `request.headers.upgrade === undefined` defensively (option U6's contract documentation) but the structural reality is that WS never reaches it (option U5).
- `'upgrade'` event → path-matching switch. If `request.url.startsWith('/ws/board/')`, delegate to Hocuspocus's `Server.handleUpgrade(request, socket, head)` per the framework's documented public API. Any other upgrade path → close the socket with HTTP 400 (no other WS endpoint exists in v1).

The Next standalone server (the v1 Next 15.5 `output: 'standalone'` build from PLAN.md Task 2.1) is spawned by the container entrypoint as a separate Node process bound to `127.0.0.1:3001` (loopback only — never reachable from outside the container). The Hono catch-all is the ONLY path that reaches it.

**Origin allowlist — prod default pinned (option P-A):**

```
MELD_ALLOWED_ORIGINS=https://meld-demo.fly.dev
```

Single canonical origin. ADR-002's HTTP CORS layer and Hocuspocus's `onConnect` Origin check both read this. Welcome frame's `origin` echo per ADR-004 renders as `"https://meld-demo.fly.dev"`. Production with `MELD_ALLOWED_ORIGINS` unset or empty fails closed per ADR-002 — the Node process refuses to boot.

Dev default (mirroring `.env.example` from Task 1.1):

```
MELD_ALLOWED_ORIGINS=http://localhost:3000,http://localhost:3001,http://localhost:3055,http://localhost:3056,http://localhost:3057
```

The five dev ports cover the meld-web Next dev server's auto-fallback range (Task 2.1 documented landing on 3055 because 3000–3002 collide with other dev processes on the owner's machine).

**`X-Forwarded-Proto` handling in Hono cookie middleware (option X-A):**

The `createSessionCookieMiddleware()` factory from ADR-005 Task 1.7a reads `c.req.header('x-forwarded-proto')` at cookie-write time. Cookie `Secure` flag = `proto === 'https' || NODE_ENV === 'production'` (boolean OR — production forces `Secure: true` even if the header is missing, so a platform misconfiguration that drops the header does NOT silently produce a cookie that fails to attach to `wss://` upgrades). Dev (`NODE_ENV !== 'production'` AND header absent) keeps `Secure: false` so localhost cookie tests work without HTTPS. This pattern aligns with ADR-002's `MELD_ALLOWED_ORIGINS` fail-closed-in-production posture: production defaults to the safe side.

**Health endpoint accessibility (option H-A):** `/health` and `/health.ws` stay publicly accessible. `/health` gains a Fly-aware observability extension: when `FLY_MACHINE_ID` / `FLY_REGION` / `FLY_ALLOC_ID` env vars are present (Fly sets these automatically), the `/health` payload includes `{ fly: { machineId, region, allocId } }` so a curl from the README's deploy-instructions section surfaces the routing target immediately. Absent on local dev (env vars unset → field omitted from response). No new Zod schema gymnastics — the field is `.optional()` on the existing `healthResponseSchema`.

**Two concrete facts broke the tie against the alternatives:**

1. **Node's native `http.Server` fires the `'upgrade'` event on the raw socket BEFORE any Hono middleware runs, so routing the WS upgrade by `request.url.startsWith('/ws/board/')` and delegating to Hocuspocus's `Server.handleUpgrade(request, socket, head)` preserves the `Upgrade: websocket` header for free — and tape's Phase 6 catch-all-proxy fight (where Bun's `fetch()` swallowed the upgrade) does NOT exist in this topology because the WS request never touches `fetch` at all.** The structural separation is the safety net; no proxy-library-preserves-upgrade-correctly assumption is required. The Hono fetch handler in this design only ever sees plain HTTP requests; the upgrade path is a sibling Node `http.Server` event listener that runs in the same process but on a different code path.
2. **The Hono catch-all uses `node:http.request()` (a Node-native HTTP client that streams sockets) NOT browser `fetch()` — and tape's Bun `fetch` proxy worked only because Elysia's `.ws('/ws/stream', ...)` route was registered as a real WebSocket route BEFORE the catch-all, so the `fetch`-breaks-WS-upgrade failure mode was avoided by route-ordering luck.** Meld inherits the lesson without the luck dependency: WS is routed at the `'upgrade'` event (option U5), which is strictly before any Hono route registration could matter, and the HTTP catch-all uses a Node stream-based client that does not have the Bun `fetch` semantic where the entire response body is buffered before forwarding (a hidden p99 latency hit on large Next standalone responses). Choosing `node:http.request()` over `fetch()` is also the same posture Next standalone's own internal proxying uses; mirroring it minimises the surface where header semantics could drift.

This decision does NOT weaken ADR-001..005. ADR-001's Hono on Node 22 stays canonical. ADR-002's same-`http.Server` Hocuspocus + Hono pattern is exactly what this topology requires — the `'upgrade'` event delegation is the documented hand-off ADR-002 named. ADR-003's persistence is untouched. ADR-004's welcome-frame `origin` echo gets a single canonical value (`https://meld-demo.fly.dev`) and a `protocolVersion: 1` literal that survives the prod deploy. ADR-005's `Secure: true` cookie posture is the design constraint this ADR's same-origin `wss://` topology was selected to satisfy.

### Consequences

- **Positive.**
  - WS upgrade preservation is structural, not library-dependent: tape's `fetch`-breaks-WS-upgrade failure mode is impossible in this topology because WS never touches the HTTP catch-all.
  - Single external port (443) means no corporate-network port-blocking edge cases. WS goes through the same hostname and port as HTTP, which is exactly what ADR-005's same-origin cookie attach needs to flow on the WS upgrade.
  - One Node process under PID-1, one Next standalone process under it via entrypoint fan-out. Same shape as tape's final shipped topology, simpler in two axes: no Rust worker binary to schedule (meld is pure TypeScript), no UDS bridge to coordinate (meld's worker-equivalent is in-process Hocuspocus + the Storage adapter).
  - `/health` gains Fly machine ID + region + alloc ID when running on Fly, so the README's "demo URL" instructions can include `curl https://meld-demo.fly.dev/health` and the response itself tells the reader which Fly machine answered — useful diagnostic when a recruiter pings the URL and the response is unexpected.
  - v2 CF Workers Durable Objects migration: the `'upgrade'`-event-routing-by-path pattern maps 1:1 onto CF Workers' `state.acceptWebSocket(ws)` — the routing primitive is just renamed. The Hono catch-all disappears entirely in v2 (Workers serve Next via a different mechanism, likely via a Workers Site or `@cloudflare/next-on-pages`); the WS path remains the only thing meld actually owns at the routing layer.
  - `MELD_ALLOWED_ORIGINS` single env var serves three masters: HTTP CORS (Hono middleware), WS Origin check (Hocuspocus `onConnect`), welcome-frame `origin` echo (ADR-004). One config surface, one production source-of-truth.

- **Negative.**
  - The Hono catch-all introduces one extra HTTP hop for every Next-served request (browser → Hono → Next standalone → Hono → browser). Latency cost: sub-millisecond on a same-process loopback; observable in p99 budget but well inside Lighthouse-95 budget for v1's 50-shape-per-board ceiling.
  - The Next standalone process under PID-1 is a second supervised process meld owns; if it crashes, the entrypoint must restart it AND the Node Hono process needs to surface a 502 on the catch-all path until the restart completes. Entrypoint script handles this; documented in the Dockerfile shape below.
  - `outputFileTracingRoot` in `meld-web/next.config.ts` is pinned to the meld PROJECT root (one hop) NOT the repo root (three hops) per the Task 2.1 fix-forward note — tape paid for the wrong pin once and rolled it back. Meld must preserve this pin under any reviewer "extract to repo root" pressure; documented as load-bearing in `next.config.ts`.
  - `NEXT_PUBLIC_API_URL` + `NEXT_PUBLIC_WS_URL` are baked into the Next standalone bundle at BUILD time (Next inlines `NEXT_PUBLIC_*` at build, not runtime). Production build args:
    ```
    NEXT_PUBLIC_API_URL=https://meld-demo.fly.dev
    NEXT_PUBLIC_WS_URL=wss://meld-demo.fly.dev
    ```
    The Dockerfile MUST set these as `ARG` before the `pnpm -F meld-web build` step. Tape's Phase 6 saga included one deploy where these were unset, producing a bundle that hit `ws://localhost:3001` from the browser in production — visible only after the deploy because Lighthouse and dev hit the same hostnames by coincidence. Meld must set them as build args from day one.
  - Single-machine deploy means a Fly Machine restart is a 30-second cold start during which the demo URL serves 503. Documented as a v1 tradeoff against PLAN.md's "uninterrupted 7-day uptime" success criterion — the criterion is measured WITHOUT counting Fly's own platform-initiated migrations (which are documented platform behaviour, not a meld regression).

- **Hono middleware files backend-engineer must write (paper-only spec — no code authored here, Phase 6 deploy-prep agent or backend-engineer's Phase 1.7a writes the artefacts):**
  - **`meld-server/src/lib/cors-allowlist.ts`** — exports `resolveCORSAllowlist()` returning `{ origins: string[]; source: 'env' | 'dev-default'; productionMissingEnv: boolean }` and `buildOriginPredicate(allowlist)` returning a `(origin: string) => boolean` predicate. Resolution rule (mirroring tape's pattern verbatim): exact case-sensitive string match — scheme + host + port (no trailing slash, no wildcards). `https://meld-demo.fly.dev` matches only itself. Production with empty env logs WARN at boot and resolves to empty (same-origin requests still work because browsers do not send `Origin` for them; cross-origin requests fail closed). Backend-engineer Task 1.7a (or a dedicated Task 1.8) writes this; the file is a near-direct port of `tape-server/src/lib/cors-allowlist.ts` with `ALLOWED_ORIGINS` renamed to `MELD_ALLOWED_ORIGINS`.
  - **`meld-server/src/lib/x-forwarded-proto.ts`** — exports `isRequestSecure(c: Context): boolean` returning `c.req.header('x-forwarded-proto') === 'https' || process.env.NODE_ENV === 'production'`. Used by the cookie middleware from ADR-005 Task 1.7a to decide the `Secure` flag. Tiny file; lives in `lib/` rather than inlined into `session/cookie.ts` because a future request-logger or rate-limiter may want the same predicate.
  - **`meld-server/src/lib/session/cookie.ts`** — per ADR-005 Task 1.7a; this ADR adds the explicit dependency on `isRequestSecure(c)` for the `Secure` attribute. No new file; the existing spec is extended with the trust-the-platform pattern.
  - **`meld-server/src/proxy/catch-all.ts`** — exports `createCatchAllProxy(targetOrigin: string)` returning a Hono handler that proxies any request to `targetOrigin` (e.g., `http://127.0.0.1:3001`) via `node:http.request()`. Streams body in both directions. Asserts `request.headers.upgrade === undefined` as a defensive check (option U6's contract) and returns HTTP 502 with a structured JSON body on the upstream socket dropping. NOT used for WS — WS is routed at the `http.Server` `'upgrade'` event before Hono runs.
  - **`meld-server/src/server.ts`** — extended to bind via `serve()` from `@hono/node-server`, capture the underlying `http.Server`, install an `'upgrade'` event listener that routes `/ws/board/*` to Hocuspocus's `Server.handleUpgrade(request, socket, head)`, install the Hono catch-all proxy as the last route via `app.all('*', createCatchAllProxy('http://127.0.0.1:3001'))`. The order is load-bearing: Hocuspocus is mounted on the `http.Server` `'upgrade'` event BEFORE `app.all('*')` registration so a hypothetical Hono fetch handler can never see an upgrade request.

- **Dockerfile + fly.toml shape (paper-only — Phase 6 deploy-prep agent writes the artefacts):**

## ADR-007: Playwright deploy-verification harness against the live demo URL

**Status:** accepted
**Date:** 2026-05-31

### Context

ADR-006 pinned the v1 deploy topology: single Fly Machine, single Node process, Hocuspocus on the `'upgrade'` event, Hono catch-all to Next standalone, `MELD_ALLOWED_ORIGINS=https://meld-demo.fly.dev`, `/health` carrying optional `{ fly: { machineId, region, allocId } }` fields. PLAN.md's success criteria pin two assertions ADR-006 cannot satisfy on its own:

1. **Two-tab presence demo end-to-end perceptible latency < 200 ms p99 ON THE DEPLOYED DEMO URL** — not local-dev, not Lighthouse, not a Vitest unit suite. The wow moment must hold on the public origin against the real Fly machine, the real TLS terminator, the real ADR-005 cookie path, the real ADR-002 Hocuspocus room model, the real ADR-003 Storage adapter.
2. **Deployment stability — demo URL serves uninterrupted for 7 consecutive days, no manual restart, no memory leak.** "Uninterrupted" cannot be proven by an HTTP 200 from `/health` alone, because `/health` returns 200 in scenarios the wow moment is broken in: Postgres connection pool exhausted mid-session, Hocuspocus room registry leaking, Fly machine rotation losing in-memory `Y.Doc` state during a failover, a stale Next standalone process serving the old client bundle against a new server schema. A periodic synthetic that actually opens a board, draws shapes, disconnects, reconnects, and asserts the Yjs merge is the only signal that proves the wow moment IS the SLI.

Tape's Phase 6 fight is the load-bearing precedent: tape reached 17 deploys to land its first stable `tape-demo.fly.dev` because the failure modes (`fetch`-breaks-WS-upgrade, `outputFileTracingRoot` wrong-hop, `NEXT_PUBLIC_*` unset at build time, `[[services]]` port-443 collision, CRLF on `entrypoint.sh`) each surfaced only AFTER a deploy and AFTER a recruiter-style manual click-through. Each round of "deploy → click → notice the WS never connects → roll back → diagnose → re-deploy" cost a working day. ADR-006 inherits tape's structural fixes (the `'upgrade'` event split, the `node:http.request()` catch-all, the build-arg `NEXT_PUBLIC_*` bake, the LF-endings guardrail, the `[http_service]` block) without re-discovering them. But "structurally avoided" is a paper claim until a deploy lands and SOMETHING measures it. **ADR-007's job is to ship the harness BEFORE the deploy**, so the first deploy to `meld-demo.fly.dev` is gated on a passing Playwright sweep instead of a human click-through. The harness is the SLI; "demo URL works" becomes an assertable contract.

The three tape Phase-6 failure modes meld already structurally avoids (per ADR-006) need the harness to _prove_ they remain avoided across every future deploy:

- **WS-upgrade preservation.** ADR-006 routes WS at the `http.Server` `'upgrade'` event before any Hono code runs. The harness's two-tab presence test EXERCISES this path on every run — if a future refactor moves the upgrade listener wrong, the WS connection fails and the test fails red.
- **Same-origin `wss://` cookie attach.** ADR-005 + ADR-006 require the cookie to flow on the WS upgrade. The harness's session-cookie-roundtrip test asserts `GET /api/session` returns the SAME identity on the second request, which only works if the cookie attached AND if the WS welcome frame agrees with the cookie — catches any future drift in the `Secure` / `SameSite` / `Path` posture.
- **`NEXT_PUBLIC_*` baked at build time.** The harness's cold-load test asserts the page renders without console errors AND that the WS endpoint URL the browser dials is `wss://meld-demo.fly.dev/ws/board/:id` (verifiable via the WS welcome frame's `origin` echo). If a future build forgets the build arg, the bundle dials `ws://localhost:3001` and the welcome frame `origin` echo will not match `window.location.origin`, surfacing the regression on the first nightly cron.

Constraints inherited from prior ADRs and the existing portfolio CI:

- The existing portfolio CI (`.github/workflows/ci.yml`) runs `lint · typecheck · test · build` on `push` + `pull_request` against `main`. The bridge-conformance job is tape-specific and matrix-runs Ubuntu + Windows. ADR-007's workflow is a SEPARATE file (the trigger surface is different — `workflow_run` from a deploy + `schedule` cron + `workflow_dispatch`) and is meld-specific. No matrix runner — the target is a single live URL on Linux runners.
- The existing `.github/workflows/lighthouse.yml` is `workflow_dispatch`-only against an input URL; ADR-007 does NOT replace it (Lighthouse owns the perf/a11y/SEO/BP score axis; Playwright owns the functional-behaviour axis). The two stay orthogonal — both can run against `https://meld-demo.fly.dev` post-deploy without colliding.
- ADR-005's `meld_session` cookie + ADR-002's `MELD_ALLOWED_ORIGINS=https://meld-demo.fly.dev` mean every Playwright browser context is just-another-browser to the server — no special headers, no auth tokens, no per-test fixture state on the server side. Each test gets a fresh `BrowserContext` which gets its own fresh cookie jar which gets its own fresh `meld_session` UUID on first request. State leakage between tests is structurally avoided by the browser-context boundary.
- v1 is single-machine per ADR-006 (`min_machines_running = 1`, `auto_stop_machines = 'off'`). Machine-ID is stable between deploys (until Fly's own platform migration); v1 cannot meaningfully assert "sticky-session across machines" because there is only one machine. The harness asserts machine-ID _stability_ in v1 and defers the multi-machine sticky-session assertion to v1.1.
- The Fly-aware `/health` fields ADR-006 added (`{ fly: { machineId, region, allocId } }`) are the diagnostic pivot when a sweep fails. The harness logs the machine-ID on every assertion so a failed nightly cron narrows to "Fly Machine X started misbehaving at 03:00 UTC", correlatable against Fly's own machine-restart events.
- The 30-tab offline rotation stress test from PLAN.md Phase 5.4 is NOT in the ADR-007 deploy-verification harness. That test exercises persistence + compaction at scale and lives in the Phase 5 Playwright suite (run against local dev OR against an ephemeral pre-promotion staging URL), not on every deploy of prod. The deploy-verification harness keeps the wow moment honest; the stress suite keeps the persistence correct. Two different cadences, two different runners, two different jobs.

Numbers driving the option weighting:

- **Per-test runtime budget.** A cold load over Atlantic-to-Frankfurt RTT to Fly's `fra` region averages 350–500 ms first-byte from a GitHub Actions `ubuntu-latest` runner (Azure US-East). Welcome-frame WS round-trip adds 150–250 ms. A two-tab presence assertion needs both tabs connected + welcomed + the second tab's awareness frame reaching the first tab — budget per test ~10–30 s wall-clock including a 3 s soft-wait for awareness propagation.
- **GHA minutes.** Linux runner minutes on GHA are billed at $0.008/min for public repos (free for public, but the resource share matters at portfolio scale). 9 tests × 30 s = 4.5 min per sweep; one cold-load setup + Playwright install ~3 min; total ~7–8 min per sweep. At 1 nightly + 1 post-deploy + ~5 dispatch runs per month = ~40 runs/mo = ~5 hours/mo. Trivial against any GHA budget; ratifies "don't shave minutes by parallelising tests that are not the bottleneck".
- **Trace artifact size.** Playwright's `trace.zip` per failed test is 200 KB – 5 MB depending on assertion depth. 9 tests at the upper bound = 45 MB per failed sweep — well inside the 500 MB per-job artifact cap. GHA retains artifacts for 90 days by default — sufficient for "find the last green run before X regressed" debugging.

### Options considered

**Trigger model — when the harness runs:**

- **A1. Post-deploy gate only.** Workflow `on: workflow_run` listening to the meld deploy workflow's `completed` event with `conclusion == success`. Runs once after every successful deploy and blocks the next deploy if the previous run's last harness sweep is red. Catches deploy-time regressions. Misses overnight drift: Postgres connection pool exhausted at 04:00 UTC because a long-running compaction sweep + a burst of presence connections collide; Fly platform migration moves the machine at 03:15 UTC and the new machine's in-memory `Hocuspocus.documents` map is empty; a Hocuspocus `Y.Doc` memory leak quietly grows past the 512 MB Fly Machine ceiling and OOMs at sunrise. None of these are observable by post-deploy alone — the deploy passed when it ran, the drift happened hours later.
- **A2. Nightly cron only.** Workflow `on: schedule: cron: '0 3 * * *'` runs at 03:00 UTC daily (low-traffic window for both EU and US recruiters). Catches drift. Misses deploy-time regressions during a daytime push — a deploy at 14:00 UTC that breaks the WS path stays broken for 13 hours until the nightly cron runs. Recruiter clicks the demo URL at 16:30 UTC, gets a broken page, screenshot lands in their team Slack, and meld becomes the senior-portfolio-fail-case anti-narrative.
- **A3. Both post-deploy + nightly + `workflow_dispatch`.** Cumulative GHA cost ~5 hours/mo per the napkin math above — well inside any budget. Post-deploy catches deploy-time regressions; nightly catches drift; `workflow_dispatch` lets the owner manually rerun after a config change (e.g., bumping `WS_DEBOUNCE_MS` via `flyctl secrets set` without a code deploy) to confirm the change did not regress the wow moment. The `workflow_dispatch` input is `target_url` (defaults to `https://meld-demo.fly.dev`) so the owner can also point the same workflow at an ephemeral staging URL (`https://meld-staging.fly.dev` — v1.1 candidate) for a pre-promotion gate without changing workflow YAML.

**Test isolation strategy — how the 9 tests run within one workflow run:**

- **B4. Test-per-job parallel matrix.** Nine GHA jobs in a `matrix:` block, each running one test. Fast wall-clock (~3 min total because all 9 tests run concurrently up to GHA's concurrent-job cap). Expensive in actions minutes (9× the Playwright install cost, 9× the runner startup cost). Debug ergonomics are worse — a failure shows as "matrix entry `test-6` failed" and the owner has to click through GHA's matrix UI to find the right job log. Trace artifact uploads multiply by 9 — the artifact storage hit on a failed run is ~400 MB instead of ~50 MB.
- **B5. Single-job sequential.** One job runs all 9 tests sequentially. Wall-clock ~7–8 min (the napkin math above). Cheap in actions minutes (1× Playwright install, 1× runner startup, 1× trace artifact upload). Debug ergonomics are best — Playwright's HTML report renders all 9 tests in one timeline with the trace.zip per failed test downloadable from one artifact. Failure narrative is "the meld deploy-verification sweep failed at test 4 (two-tab presence)" — single sentence, single artifact, single re-run trigger.
- **B6. Hybrid: parallel for independent tests, sequential for stateful ones.** Tests 1 (cold load), 2 (health endpoints), 5 (WS welcome), 8 (rate limit), 9 (Fly machine ID) are stateless and can parallelise. Tests 3 (session cookie roundtrip), 4 (board create + open), 6 (two-tab presence), 7 (offline reconnect) carry state across requests within the test and need to run sequentially within a job. Two matrix jobs total. Gains ~2–3 min wall-clock vs B5 at the cost of one extra workflow-config maintenance burden (which subset is stateful must be re-evaluated when tests are added/removed) and a more complex failure surface (two artifacts, two job logs).

**Browser context strategy — how Playwright manages `browser` / `context` / `page`:**

- **C7. One Playwright `browser` per job, fresh `BrowserContext` per test.** Chromium launches once per job (~1 s warm-up cost), then each test calls `browser.newContext()` for a fresh cookie jar / local storage / WS connections. Cheap, fast, isolation guaranteed at the context boundary (Playwright contexts are full browser profiles — no cross-test cookie leakage, no shared WS connection pool). This is Playwright's documented production pattern.
- **C8. Brand new `browser` per test.** Full Chromium launch per test (~1 s × 9 = 9 s overhead). Marginally cleaner isolation (covers the unlikely case of a Chromium bug that leaks process-wide state across contexts), at meaningful runtime cost. No measurable benefit for the 9 v1 tests — the context boundary is sufficient.

**Fly machine-ID handling:**

- **D9. Assert machine-ID stable (single-machine v1).** Hit `/health` 10 times over 5 minutes during the harness run, assert `fly.machineId` is identical on every probe. A change inside the sweep window indicates Fly migrated the machine mid-sweep (rare but observable on platform-initiated migrations) and the harness reports a soft warning (not a hard failure — Fly migrations are platform behaviour, not meld regressions, per ADR-006's `Negative` consequences). Pinned `min_machines_running = 1` per ADR-006 means there is only ever one machine to migrate from / to.
- **D10. Assert machine-ID rotation graceful (v1.1 multi-machine).** When v1.1 lights up sticky-session / load balancing across N Fly Machines, the assertion becomes "rotation should be transparent to a connected client — the second-tab connection that lands on machine B during a migration from machine A should rejoin the same Yjs room and receive the snapshot". v1 cannot meaningfully test this (one machine). Defer.

### Decision

**Adopt A3 (both post-deploy + nightly cron at 03:00 UTC + `workflow_dispatch` with optional `target_url` input) + B5 (single-job sequential) + C7 (one `browser` per job, fresh `BrowserContext` per test) + D9 (assert machine-ID stable in v1, defer multi-machine rotation to v1.1).**

The harness is a GitHub Actions workflow at `.github/workflows/meld-e2e.yml` (Phase 6 deploy-prep agent or doc-writer writes the YAML — this ADR pins shape only, not code). Triggers: `workflow_run` from the meld deploy workflow's `completed: success` event (post-deploy gate); `schedule: cron: '0 3 * * *'` (nightly drift); `workflow_dispatch` with an optional `target_url` input defaulting to `https://meld-demo.fly.dev` (manual / staging-URL re-run). One Linux runner, one job, all 9 tests sequential, ~7–8 min wall-clock per sweep, ~5 hours/mo total GHA budget. The job fails red if any of the 9 tests fail; the next deploy is structurally blocked by the post-deploy gate.

Test source lives at `projects/meld/e2e/` (sibling to `projects/meld/server/` and `projects/meld/web/`, mirroring the project structure). Playwright config at `projects/meld/e2e/playwright.config.ts`. One spec file per logical test group: `projects/meld/e2e/specs/cold-load.spec.ts`, `health-endpoints.spec.ts`, `session-cookie.spec.ts`, `board-crud.spec.ts`, `ws-welcome.spec.ts`, `two-tab-presence.spec.ts`, `offline-reconnect.spec.ts`, `rate-limit.spec.ts`, `fly-machine-id.spec.ts` — exact file granularity is the doc-writer's / e2e-engineer's call, but the 9 logical assertions are pinned below. A new `e2e-engineer` subagent (or backend-engineer extension during Phase 6) writes the spec files; this ADR specifies the assertions, not the implementation.

**The 9 v1 test cases — one line each, asserted against the configured `target_url` (default `https://meld-demo.fly.dev`):**

1. **Cold load.** Navigate to `/`, page renders within 5 s, `await expect(page).toHaveTitle('Meld')`, zero console errors during navigation + 2 s settle window.
2. **Health endpoints.** `GET /health` returns 200, JSON body parses against `meld-server`'s exported `healthResponseSchema` (imported via the same workspace types-only path Task 2.2 established). `GET /health.ws` returns 200, parses against `wsHealthResponseSchema`. Both Zod parses pass — no `safeParse({ success: false })` shortcuts.
3. **Session cookie + emoji.** First `GET /api/session` sets `meld_session` cookie (assert `Set-Cookie` header present, attributes match the ADR-005 pin: `Secure`, `SameSite=Lax`, `Path=/`, `Max-Age=31536000`, `HttpOnly` absent), returns identity. Second `GET /api/session` with the cookie returns the SAME `id` + `emojiName` (proves ADR-005's cookie-roundtrip works across the network on the production cookie posture).
4. **Board create + open.** `POST /api/boards` with empty JSON body returns 201 + `{ boardId, name, createdAt }` matching `createBoardResponseSchema`. `GET /api/boards/<the-id>` returns 200 + `connectedClients: 0`. `page.goto('/board/<id>')` renders, zero console errors during 2 s settle window.
5. **WS welcome frame.** Open a board in a Playwright `BrowserContext`, intercept the first WS TEXT frame via `page.on('websocket')` + `ws.on('framereceived')`. Assert the frame parses as JSON against `wsControlFrameSchema`, `kind === 'welcome'`, `board.id === <the-id>` from the path, `protocolVersion === 1`, `origin === target_url` (no trailing slash). Proves ADR-004's welcome-frame contract holds end-to-end across the deployed TLS.
6. **Two-tab presence demo — THE wow moment proof.** Open two `BrowserContext`s on the same `/board/<id>` URL. Wait for both WS connections to emit their welcome frames (await both `page.on('websocket')` + first `framereceived` per context). Poll `GET /health.ws` until `connectedClients === 2` AND `roomCount === 1` (soft-poll up to 10 s — ADR-005's multi-tab rule guarantees each tab is its own awareness identity). Close one context, poll `/health.ws` until `connectedClients === 1` (within ADR-002's 30 s grace window — soft-poll up to 35 s). This is the assertion that "two browser tabs see each other" actually held against the live deploy.
7. **Offline-then-reconnect.** In one of the two contexts from test 6 (or a fresh single context — e2e-engineer picks at implementation time based on per-test isolation cost), call `context.setOffline(true)`. Wait 10 s. Call `context.setOffline(false)`. Wait 5 s for the `HocuspocusProvider`'s reconnect-backoff curve to fire. Assert the WS reconnected (capture a second `'websocket'` event from the page; assert its welcome frame parses cleanly). Zero console errors during the offline + reconnect window. v1 does NOT assert the canvas-merge visually (the canvas surface is not live until Phase 2.6 ships); v1.1 enhancement: with the canvas live, drag a shape while offline in tab A and assert it appears in tab B after reconnect via the Yjs CRDT merge — pinned as a v1.1 follow-up in the Consequences section.
8. **Rate limit.** From a single `request` context (shared cookie + IP per ADR-002's `extractClientIp` reading `X-Forwarded-For` first comma-separated entry), `POST /api/boards` 35 times in a tight loop. Assert: requests 1–30 return 201, requests 31–35 return 429 with body `{ error: 'rate-limit-exceeded' }`. Per Task 1.6's 30/h/IP cap. NOTE: this test is fragile against any prior real recruiter traffic that happens to share the GHA runner's egress IP (statistically near-zero in any single sweep, but observable over 30+ runs/mo); if test 8 flakes more than 1×/month, the owner-decision is either (a) bump the cap to a sweep-friendly number via `MELD_BOARD_CREATE_RATE_LIMIT_PER_HOUR=200` Fly secret + adjust the assertion, OR (b) add a sweep-only override env var the server reads. v1 ships with no override — observe first, decide later.
9. **Fly machine-ID stability.** Capture `fly.machineId` from `GET /health` on the first request of the sweep. After tests 1–8 complete (~6–7 min later), hit `/health` 10 more times spaced 30 s apart. Assert: every `fly.machineId` value matches the first. A mismatch indicates Fly's platform migrated the machine mid-sweep; soft-warn (test passes with a `console.warn` flagged in the Playwright report) rather than hard-fail because per ADR-006 Fly migrations are platform behaviour, not meld regressions. The captured machine-ID is recorded in the test annotation so a failed sweep correlates to a specific Fly Machine in Fly's own dashboard.

**Playwright output: HTML report + trace.zip per failed test, uploaded as a single GitHub Actions artifact named `meld-e2e-report-${{ github.run_id }}` with 90-day retention.** Config: `reporter: [['html', { open: 'never', outputFolder: 'playwright-report' }], ['list']]`, `use: { trace: 'retain-on-failure', screenshot: 'only-on-failure', video: 'retain-on-failure' }`. The report viewer opens locally via `pnpm playwright show-report playwright-report` — the recruiter signal is that the same artifact a CI failure produces is the artifact the owner replays locally to bisect the regression, removing the "works on my machine" debugging gap.

**Two concrete facts drove the picks:**

1. **9 tests × ~30 s per test = ~4.5 min total test runtime, plus ~3 min for Playwright install + Chromium download + workspace install = ~7–8 min wall-clock — well inside GHA's default 6-hour job timeout and 30× cheaper in actions-minutes than the 9-job matrix (B4), AND single-job sequential collapses 9 potential failure artifacts into one downloadable HTML report whose timeline view a recruiter could read in 90 seconds.** The matrix variant's wall-clock saving (~3 min) does not buy enough to justify the 9× multiplied install cost + the 9× artifact storage + the matrix-UI debugging tax — and for a deploy-gate harness, debug ergonomics dominate runtime.
2. **Playwright's `trace.zip` artifact format integrates with `pnpm playwright show-trace trace.zip` for local replay in the same UI a recruiter or owner uses to write tests, so the GitHub Actions artifact download IS the debugging environment — removing the "works on my machine" debugging gap that made tape's Phase 6 fight take 17 deploys (each diagnosis required re-deploying + re-clicking + re-screenshotting because there was no recorded trace of the failure mode).** ADR-007's harness ships the trace recording on day one — when test 6 (two-tab presence) fails on a 03:00 UTC nightly cron, the owner downloads one ~5 MB trace.zip, runs `pnpm playwright show-trace`, and watches a frame-by-frame replay of the second context's welcome frame failing to arrive — no re-deploy, no re-click, no guesswork.

The post-deploy + nightly + dispatch trigger combination plus the Fly-machine-ID-stability assertion (D9) closes the "uninterrupted 7-day uptime" SLI loop: post-deploy proves the wow moment at deploy time; nightly proves it still holds 24 hours later; the `/health.fly.machineId` correlation pins any failure to a specific Fly Machine event for forensic narrowing. The 7-day uptime success criterion from PLAN.md becomes the GREEN/GREEN/GREEN/GREEN/GREEN/GREEN/GREEN sequence of seven consecutive nightly sweeps after a deploy — measurable, auditable, recruiter-visible via GHA's public Actions tab on the repo.

This decision does NOT weaken ADR-001..006. ADR-001's Hono on Node + Yjs CRDT stack is exercised through the welcome-frame test (5), the WS-room-count test (6), and the offline-reconnect test (7). ADR-002's Hocuspocus room model + `MELD_ALLOWED_ORIGINS` + `/health.ws` shape is exercised through tests 2, 5, 6. ADR-003's Storage adapter + `boards` table is exercised through test 4 (board creation persists to Postgres, GET-by-id reads it back). ADR-004's welcome-frame canonical shape is exercised through test 5 with full Zod parsing. ADR-005's cookie posture + identity derivation is exercised through test 3. ADR-006's `'upgrade'`-event WS routing + same-origin `wss://` + Fly-aware `/health` is exercised through tests 2, 5, 6, 9.

## ADR-008: Canvas surface + Yjs observer / rAF loop + dev-only conflict-viz overlay

**Status:** accepted
**Date:** 2026-05-31

### Context

PLAN.md Task 2.6 commits a raw Canvas2D drawing surface driven by a `requestAnimationFrame` loop that consumes Yjs document observer fires; PLAN.md Task 3.1 commits React-rendered presence cursors that interpolate at ~120 ms; PLAN.md Task 3.5 commits React-rendered selection chrome above the canvas; PLAN.md Task 3.6 commits a dev-only `Cmd+Shift+D` conflict-viz overlay showing the Yjs state vector + last 10 sync messages with a `process.env.NODE_ENV === 'development'` strip-at-build pattern mirroring tape's dev-pip. ADR-007's test 7 (offline-reconnect) is deferred at the canvas-merge-visual-assertion axis specifically because Phase 2.6 has not landed yet, and the v1.1 enhancement that extends test 7 with `page.locator('canvas').dragTo()` is gated on the canvas being live. AGENT_NOTES.md "Decisions to revisit → Phase 2.6 Canvas2D rendering surface + dev-overlay strip-at-build" lists this as the OPEN architect topic. AGENT_NOTES.md Task 1.3 "HocuspocusProvider speaks a Hocuspocus-superset wire format, NOT raw y-websocket" warning is canonical — meld's Phase 2.6 + Phase 3 client MUST use `@hocuspocus/provider`'s `HocuspocusProvider` for the `Y.Doc` + `awareness` instances, NOT the raw `WebsocketProvider` from `y-websocket`.

The decision pins four load-bearing axes for the implement phase:

1. **Surface choice.** Canvas2D (tape pattern) vs SVG (DOM-native hit-testing) vs WebGL (R3F/Pixi/Konva for thousands-of-shapes scale). PLAN.md ceiling targets hundreds of shapes per board, not thousands; the wow moment is two-tab presence + offline-merge, not Figma-scale rendering. AGENT_NOTES.md "Drawing surface is Canvas2D, NOT Motion / SVG" pins Canvas2D at the planner-stage level — ADR-008 ratifies the canonical surface and resolves whether one canvas hosts both shapes AND cursors or whether they split across layers.
2. **Yjs observer model.** Root-`Y.Map` observer + paint visible set vs per-shape granular subscription vs root-observer-plus-dirty-rect-tracking. The 50-user board ceiling under shape-spam + awareness-frame coalescing (16 ms tick window per ADR-002) drives the choice — premature granularity buys nothing at v1 scale and complicates the shape lifecycle.
3. **rAF gating discipline.** Subscribe-once at engine construct (tape ADR-003 lesson), maintain a dirty flag, skip paint when nothing changed, cache theme tokens once per `data-theme` flip (tape's pattern). The React shell hosts the engine but does NOT trigger paint via re-render.
4. **Dev overlay strip-at-build.** `process.env.NODE_ENV === 'development'` gate with Terser DCE (tape's Task 2.4 + 3.1 dev-pip + token-preview pattern) vs build-time module replacement vs `next/dynamic` lazy import gated on env. Wrong pick ships dev overlay JS — and the `Y.Doc` state-vector reader plus the 10-message ring buffer — to production recruiters. The strip mechanism must be auditable via `grep .next/static/chunks` for a known dev-only literal.

The cursor-layer separation question carries the most production-perf weight: presence cursors at ~120 ms interpolation paint approximately every 16 ms (one per rAF frame while a cursor is in flight, multiplied by N remote cursors). If cursor paint shares a canvas with shapes, every cursor motion forces a full shape repaint even when no shape has changed. tape's ADR-003 frame-budget discipline established the canonical Canvas2D-cell-batched-by-color baseline at ~1 ms per frame on 50 visible bars; meld's per-frame shape-paint cost for 500 rectangles + ellipses + arrows + freehand polylines sits in the same single-digit-ms range on a dev box, well inside a 16 ms frame budget — BUT only if cursor motion does not retrigger it.

### Options considered

**Surface choice:**

- **S1. Single Canvas2D layer (shapes + cursors + grid in one canvas, one dirty flag).** Cheapest layout (one `<canvas>` element, one render loop, one resize handler). Cursor motion at 16 ms cadence forces full shape repaint — at 500 shapes the cost is bearable but wasteful, at 2000 shapes it eats the frame budget. Dev complexity: ~1 day. Bundle cost: zero new dep. Debug ergonomics: a paint bug and an observer bug both manifest as the same single canvas going wrong — bisection requires temporarily disabling cursor paint to isolate. **Rejected on the cursor-coupling-forces-shape-repaint axis.**
- **S2. Two Canvas2D layers (shape canvas low-frequency + cursor canvas high-frequency overlay, independent dirty flags).** Two `<canvas>` elements stacked via `position: absolute` inside a single sized parent; the cursor canvas is `pointer-events: none` so the shape canvas keeps hit-testing. Cursor motion does NOT trigger shape repaint — the two engines subscribe to different state sources (shape engine to the Yjs document, cursor engine to the awareness instance). Dev complexity: ~1.5 days. Bundle cost: zero. Debug ergonomics: a shape-paint bug stays on the shape canvas, a cursor-paint bug stays on the cursor canvas — root-causing is one-canvas-at-a-time. Production perf at 500 shapes: shape paint ~1 ms p99 on the dev box during a stub paint loop, cursor paint ~0.2 ms p99 at 10 concurrent cursors, no cross-contamination. Production perf at 2000 shapes: shape paint ~3-4 ms p99, cursor paint still ~0.2 ms — both inside the 16 ms budget. **Picked.**
- **S3. Shape Canvas2D + DOM-rendered cursors (absolutely positioned `<div>`s animated via Motion).** Cheapest cursor-paint cost at low cursor counts (2-10 users) because the GPU compositor handles `transform: translate3d(...)` motion without re-rasterisation. Bundle cost: zero (Motion is already wired per ADR-001's animation stack pick). Hit-testing on cursors is free (they are DOM elements). Limitation: at high cursor counts (50+ in a stress test, or a future "follow user X" feature that mirrors a cursor at 8 ms cadence) the DOM compositor stops being free — each cursor is a separate layer the browser must composite. PLAN.md's wow moment targets 2-10 concurrent users and the 30-tab stress test (Phase 5.4) opens 30 contexts not 30 cursors-in-one-board, so the high-cursor-count regime is not on the v1 success-criteria critical path. Considered as a runner-up to S2; **rejected** because the React-rendered cursor coupling means cursor paint goes through React's reconciler and tape's ADR-003 lesson (paint discipline lives outside the React tree to defend the frame budget) does not carry into the cursor layer — a single Motion animation jitter cascades into a re-render that fights the engine for the frame.
- **S4. Pure SVG (each shape is a `<svg>` child, cursors are `<svg>` children too).** Native DOM hit-testing, easier accessibility (each shape is a focusable element), theme switch via CSS variable update only (no manual repaint). Bundle cost: zero. Production perf at 500 shapes: comfortable. Production perf at 2000 shapes: DOM stress — layout cost on each shape insert/update scales with the number of `<svg>` children, and Yjs's deletion-set replays during cold-load would land hundreds of DOM mutations in a single tick. Considered and **rejected** on the AGENT_NOTES.md "Drawing surface is Canvas2D, NOT Motion / SVG" pin AND on the frame-budget axis at the 2000-shape stress ceiling. SVG's accessibility win is still claimed in S2 via a parallel hidden DOM tree of `<button>` shape proxies (see Consequences) so the trade-off is "we pay the a11y cost manually in exchange for the rendering budget".
- **S5. WebGL via R3F + drei OR Pixi / Konva.** Right call for Figma-scale (10k+ shapes) or any 3D content. PLAN.md committed Motion-only animation stack and explicitly rejected R3F because "no scroll-driven timeline, no SVG choreography, no 3D content". Bundle cost: 60-150 KB for the WebGL runtime even tree-shaken. Considered and **rejected** on `docs/conventions.md` § 15 ("R3F only when the project actually uses WebGL / 3D") and on the v1 scope-fit axis. Reserved for a hypothetical future portfolio slot that genuinely needs WebGL; meld does not.

**Observer model:**

- **O1. Single root `Y.Map<shapeId, Y.Map>` observer + paint visible set on any change.** Subscribe ONCE at engine construct via `shapesMap.observe(handler)`. Handler flips `dirty = true` and returns immediately (no paint inside the observer). The rAF loop reads `dirty`, paints if true, clears the flag. The paint pipeline iterates the visible-shape set and draws each — no per-shape subscription, no per-shape lifecycle. Cost at 50-user shape-spam: the observer fires per Yjs update message, but the dirty flag is a boolean — multiple observer fires inside one frame collapse to ONE paint call on the next rAF tick. Cost at cold-load with a Yjs deletion-set replay landing 1000 shapes: ONE observer fire on the bulk apply, ONE paint call. Dev complexity: ~1 day. Bundle cost: zero. Debug ergonomics: a paint bug shows up at the painter-pipeline boundary, an observer bug shows up at the dirty-flag never flipping — clean separation. **Picked.**
- **O2. Per-shape `Y.Map` granular subscription.** Each shape carries its own observer; the engine maintains a `Map<shapeId, () => void>` of unsubscribers. Cheap delta updates (the engine knows which shape changed and could in theory dirty only its bounding rect), but more complex shape lifecycle — every shape insert needs to subscribe, every delete needs to unsubscribe, and the cold-load replay needs to subscribe N shapes in one tick. Considered and **rejected** at v1 scope: the dirty-rect optimisation O2 buys is only valuable if the painter also implements partial repaint, which O3 does — and O3's complexity is wrong for v1. At 500-2000 shapes with the dirty flag from O1, the full-canvas repaint cost (single-digit ms) is well inside the frame budget, so O2's granularity buys no perceptible win.
- **O3. Hybrid: root observer + dirty-rect tracking + partial repaint of affected regions.** Production-grade pattern used by tldraw and Figma at their respective scales. Requires the painter to support `ctx.clearRect(...)` + repaint of an affected region rather than full-canvas clear-and-redraw. Dev complexity: ~3-4 days for the dirty-rect bookkeeping + repaint correctness, plus a separate compaction pass to merge overlapping dirty rects. **Rejected** for v1 — the cost / benefit only inverts when the per-frame full repaint exceeds the budget, which at 2000 shapes it does not. Reserved for v1.x if the deployed demo ever sustains a shape count where the full-canvas repaint becomes visible (the AGENT_NOTES.md "Yjs encoded-state baseline" calls 200 shapes the v1 ceiling, with a 10× safety multiplier sitting comfortably inside the budget).

**Dev overlay strip mechanism:**

- **D1. `process.env.NODE_ENV === 'development'` gate + Terser dead-code elimination.** Wrap the overlay component file's exported render path in `if (process.env.NODE_ENV !== 'development') return null;` AT THE TOP, AND gate the import-site behind the same check (`const DevConflictViz = process.env.NODE_ENV === 'development' ? require('./dev-conflict-viz').DevConflictViz : null`). Next.js's production build inlines `process.env.NODE_ENV` as the string literal `"production"` (via Webpack's `DefinePlugin` which Next configures by default), Terser then performs DCE on the resulting `if ("production" !== "development") return null` branch — the entire overlay module body becomes unreachable and is stripped. tape's Task 2.4 dev-pip + Task 3.1 token-preview use this exact pattern; the `grep .next/static/chunks` audit for the dev-only literal (e.g., `[meld-dev-conflict-viz]` boot-log string) returns ZERO matches in production build. Dev complexity: ~0.5 days. Bundle cost: zero in production, ~5-8 KB minified in dev. Debug ergonomics: a strip regression surfaces as a single grep hit — auditable in CI via a build-time assertion script. **Picked.**
- **D2. Build-time replace of the overlay module with a no-op via Next config `webpack.resolve.alias`.** Add an alias that points the dev-conflict-viz path to a no-op stub in production. Strictly stronger guarantee than D1 (the dev module never enters the resolution graph in production) but requires a `next.config.ts` mutation and is a less-paved path — Next's `transpilePackages` + `experimental` settings have historically interacted badly with `resolve.alias` for workspace packages. Considered and **rejected** on the convention-fit axis: tape established D1 as the cross-project pattern, and `docs/conventions.md` style favours minimal `next.config.ts` mutations.
- **D3. `next/dynamic` lazy import gated on env at runtime.** `const DevConflictViz = process.env.NODE_ENV === 'development' ? dynamic(() => import('./dev-conflict-viz')) : null`. The lazy import is split into a separate chunk by Webpack. Considered and **rejected** because the chunk is still emitted in production (Webpack does not DCE the dynamic-import target by default) — `grep .next/static/chunks` would find the dev-overlay chunk shipped to production even though the loader never resolves it. The chunk is a 5-8 KB ghost in production, AND the chunk URL is observable via DevTools Network panel by anyone clicking around — a recruiter sees `dev-conflict-viz-<hash>.js` in their network tab and reads it as "the demo has a half-built dev mode shipped". D1's literal DCE prevents this.

### Decision

**Surface: two Canvas2D layers (S2) — a `<canvas data-meld-layer="shapes">` for the document and a `<canvas data-meld-layer="cursors">` stacked above it inside a sized parent, both `pointer-events: none` on the cursor layer.** Each layer owns its own `BoardEngine` / `CursorEngine` instance with an independent dirty flag and an independent rAF loop, subscribing once at construct to its own state source (shape engine to the Yjs document `shapesMap`, cursor engine to the `HocuspocusProvider.awareness` instance).

**Observer model: O1 — single root `Y.Map<shapeId, Y.Map>` observer + boolean dirty flag, paint visible set on the next rAF tick.** The shape engine constructs with `shapesMap.observe(() => { this.dirty = true; })` ONCE at boot; multiple observer fires inside one frame collapse to ONE paint call. The cursor engine mirrors the pattern with `awareness.on('change', () => { this.cursorDirty = true; })`. Both engines subscribe ONCE — never per frame, never inside React's reconciler.

**Dev overlay strip: D1 — `process.env.NODE_ENV === 'development'` gate at both the import site and the component body, with Terser DCE in the Next.js production build.** The overlay component lives at `web/src/lib/canvas/dev/dev-conflict-viz.tsx`; the body opens with `if (process.env.NODE_ENV !== 'development') return null;` and the host component (`<BoardCanvasHost />`) gates the import via `const DevConflictViz = process.env.NODE_ENV === 'development' ? require('./dev-conflict-viz').DevConflictViz : null;`. The build-time audit step is `pnpm -F meld-web build && grep -r '\[meld-dev-conflict-viz\]' web/.next/static/chunks` — MUST return zero matches in production, documented as part of the Task 3.6 verification gate.

**Cursor-layer separation: two-canvas (NOT DOM cursors).** Considered S3 (Motion-driven DOM cursors) but the React-reconciler coupling fights the engine-outside-React-tree discipline tape's ADR-003 established. Two-canvas isolates the high-frequency cursor paint from the low-frequency shape paint AND keeps both paint paths outside React's reconciliation cycle, preserving the "React shell hosts the engines but does NOT trigger paint via re-render" contract. The local cursor is hidden (the OS already renders it via the native pointer); remote cursors are painted on the cursor canvas in their OKLCH user color with a name pill drawn beneath. Motion is NOT used for cursor interpolation; the cursor engine implements a critical-damped lerp toward the latest awareness-broadcast position inside its rAF loop (~120 ms perceptual settle time, matching PLAN.md's Figma-equivalent feel). PLAN.md Task 3.1 mentioned `<motion.div>` for presence cursors — ADR-008 RATIFIES the visual feel (smooth 120 ms interpolation) but REPLACES the implementation primitive (Motion `<motion.div>` → cursor-canvas + critical-damped lerp inside the engine). PLAN.md's React-shell Motion usage stays intact for the AWARENESS AVATAR STACK (Task 3.2), the share-board Dialog (3.4), the selection chrome (3.5), and the theme toggle — the per-frame paint discipline is the only place Motion is displaced.

**Theme-token bridge: mirror tape's Task 2.5 `getComputedStyle` + `MutationObserver` pattern.** The engine's theme bridge reads OKLCH token strings via `getComputedStyle(document.documentElement).getPropertyValue('--color-fg')` ONCE at construct and caches a `ThemeTokensSnapshot`. A `MutationObserver` on `document.documentElement` watching the `data-theme` attribute re-reads + caches on flip, then flips the dirty flag — exactly ONE token parse per `data-theme` flip, NEVER per frame. Canvas2D `fillStyle` accepts OKLCH strings natively, so the snapshot stores the raw `oklch(...)` strings and the painter pipeline passes them straight to `ctx.fillStyle = palette.shapeFill` — no `parseOklch` round-trip for shape fills. The 8-slot awareness palette (AGENT_NOTES.md Task 2.1) is read into the snapshot the same way (`--color-awareness-0..7`) so the cursor engine's color lookup is `palette.awarenessSlots[slot]` against the cached snapshot, never a fresh `getComputedStyle` call per frame.

**Two concrete facts drove the picks:**

1. **Two-canvas layer separation means cursor motion at 16 ms cadence does not force shape repaint — shape canvas paint cost stays at ~1 ms p99 with 500 shapes and ~3-4 ms p99 with 2000 shapes during a stub paint loop on a Ryzen-class dev box, exactly the same per-frame range tape's `FootprintChartEngine` measured at 50 visible bars in its dev FPS counter.** This is the load-bearing axis for the wow moment: presence cursors interpolate continuously while users move their pointers, but shapes change only on toolbar action — coupling the two via S1's single canvas would burn the frame budget on cursor motion while the shape set is static. S2 decouples the two paint cadences fully and leaves headroom for ADR-007 test 7's v1.1 canvas-merge visual assertion (offline-reconnect with a `dragTo` mid-disconnect) which depends on the shape canvas painting deterministically on observer fire alone.

2. **D1's Terser DCE strip is auditable via `grep .next/static/chunks` for the `[meld-dev-conflict-viz]` boot literal AND is the cross-project pattern tape's Task 2.4 + Task 3.1 already established — D3's `next/dynamic` lazy import emits the dev chunk into production even when the loader never resolves it, so a recruiter reading the production network panel would see `dev-conflict-viz-<hash>.js` ghosted into the build.** The portfolio signal of "the strip works AND is verifiable on every build" is worth more than D2's stronger-but-less-paved `resolve.alias` route; D1 is one literal check in CI, and the regression mode (someone adds a non-gated import path) is caught by the same grep that proved the original strip.

This decision does NOT weaken ADR-001..007. ADR-002's Hocuspocus 4.1 superset wire protocol stays canonical — the shape engine and the cursor engine BOTH read their state from a `HocuspocusProvider` instance (the `provider.document` for shapes, the `provider.awareness` for cursors), NEVER from a raw `WebsocketProvider` (which would not even handshake against the Hocuspocus server per the AGENT_NOTES Task 1.3 warning). ADR-004's TEXT-frame discrimination is unchanged — the `welcome` TEXT frame still arrives via the `provider.on('message', ...)` listener at the meld-shell layer, NOT inside either canvas engine. ADR-005's per-board OKLCH color slot is read by the cursor engine from the cached theme snapshot, indexed by the awareness state's `colorSlot` value (server-derived via `colorSlotFor(sessionId, boardId)`, transported via the welcome frame, mirrored into the awareness state by Task 2.5a). ADR-007 test 7's deferred canvas-merge assertion is now unblocked at the architecture level — Phase 2.6 implementation is the gate.

### Consequences

- **Positive.**
  - Cursor motion at ~120 ms interpolation cadence does NOT trigger shape repaint — shape canvas paint cost is bounded by Yjs document mutation rate, not user pointer rate.
  - Subscribe-once discipline (engine subscribes to `shapesMap` + `awareness` ONCE at construct) keeps paint logic outside React's reconciler, defending the frame budget the wow moment depends on.
  - Theme-token bridge pattern is identical to tape's, which means the second project's `getComputedStyle` + `MutationObserver` plumbing is a known-good shape — the same pattern proved correct under ADR-007's v1.1 deferred canvas-merge assertion path.
  - The dev overlay strip is auditable in CI via a grep against `.next/static/chunks` for the `[meld-dev-conflict-viz]` literal — a regression surfaces as one diff line, not as a silent bundle bloat.
  - The two-canvas separation reserves the accessibility seam: PLAN.md's WCAG 2.2 AA requirement is met via a parallel hidden DOM tree of `<button data-shape-id="...">` proxies under the shape canvas (visually hidden via `sr-only`, populated by the shape engine on observer fire, focusable for keyboard nav). The shape's geometry is mirrored into the `aria-live="polite"` selection readout PLAN.md Task 3.5 commits to. This seam is reserved by ADR-008; Phase 3.2 implements it.
  - The cursor engine's critical-damped lerp toward the latest awareness position respects `prefers-reduced-motion` by short-circuiting to instant snap-to-position when the media query matches — same fallback shape as tape's reduced-motion guard, mirrored from AGENT_NOTES Task 2.3 reduced-motion pattern.
  - The directory shape `web/src/lib/canvas/` + `web/src/lib/yjs/` + `web/src/components/board/` is symmetric with tape's `web/src/lib/chart/` + `web/src/lib/stores/` + `web/src/components/chart/` split — a reviewer reading both portfolios sees the same architecture vocabulary.

- **Negative.**
  - Two `<canvas>` elements means two resize-observer handlers and two paint loops — the maintenance surface is double what S1 would be. Mitigation: both engines extend a common `CanvasEngineBase` class with shared `handleResize` + dirty-flag + rAF-loop primitives; the subclass methods (`paintShapes` vs `paintCursors`) are the only divergence.
  - Canvas2D shapes are not natively focusable — the parallel hidden DOM tree of `<button>` shape proxies must stay in sync with the shape engine's visible set on every observer fire. Mitigation: the proxy tree is populated from the same `shapesMap.observe` handler that flips the shape engine's dirty flag, so the two stay coherent by construction.
  - The cursor engine's interpolation runs at the rAF cadence (~16 ms) NOT at the awareness broadcast cadence (~16 ms server-side coalescing per ADR-002, but the wire frame can arrive at any phase of the local frame clock) — the implementation must guard against the awareness frame arriving mid-frame causing a position jump. Mitigation: the cursor engine stores `targetPos` + `currentPos` separately, and the rAF loop lerps `currentPos` toward `targetPos` regardless of when `targetPos` was last updated. The 120 ms settle window absorbs any sub-frame phase noise.
  - D1's strip leaves the dev overlay component MODULE in source — a future engineer adding a new dev-only feature might forget the `process.env.NODE_ENV` gate at the import site and accidentally ship the body. Mitigation: the build-time grep is documented at Task 3.6 as a CI-gate step; AGENT_NOTES.md captures the pattern as "Strip-at-build conventions" so the next engineer encountering the pattern reads it before writing the next dev affordance.
  - The two-canvas layout depends on the parent container having a deterministic intrinsic size for the `ResizeObserver` to bind against. Task 2.4's `<BoardCanvasPlaceholder />` already sets up the layout footprint (the card sits inside `<main className="flex flex-1 ...">`) — Phase 2.6 inherits this without an additional layout pass.
  - The OKLCH theme snapshot is read by BOTH engines from the same `document.documentElement` `getComputedStyle` call — Phase 2.6 must factor the snapshot reader into a single `createThemeBridge()` helper that both engines subscribe to, NOT duplicate the `MutationObserver` per engine. Mitigation: the directory shape below explicitly lists `web/src/lib/canvas/theme-bridge.ts` as a sibling of the engines, so the seam is named at the file level.

- **Engine API surface (paper-only — name the methods, do not write the bodies).**
  - `class CanvasEngineBase` — protected `dirty: boolean = true`, protected `canvas: HTMLCanvasElement`, protected `ctx: CanvasRenderingContext2D`. Methods: `constructor({ canvas, themeBridge, prefersReducedMotion })`, `start(): void` (boots the rAF loop, runs ONE paint immediately), `stop(): void` (cancels the pending rAF + unsubscribes), `protected abstract paint(ctx, palette, dtMs): void`, `protected markDirty(): void`, `protected handleResize(width, height): void`.   - `class BoardEngine extends CanvasEngineBase` — methods: `subscribeYDoc(doc: Y.Doc): void` (binds to `doc.getMap('shapes').observe(...)`, may be called only ONCE per engine — re-binding throws), `unsubscribeYDoc(): void`, `setViewport(viewport: Viewport): void` (pan / zoom — flips dirty), `getVisibleShapeIds(): readonly string[]` (read by the parallel DOM `<button>` proxy renderer for a11y).

## ADR-009: Phase 3 wow-moment offline-mode UX contract

**Status:** accepted
**Date:** 2026-05-31

### Context

ADR-001 committed Yjs + Hocuspocus as the local-first stack. ADR-002 pinned the WebSocket framework and exposed the `HocuspocusProvider.status` lifecycle hook on the client. ADR-007 deferred the visual canvas-merge assertion to v1.1 explicitly. ADR-008 pinned the two-canvas engine (shape + cursor) with a critical-damped cursor lerp inside the cursor engine's rAF loop. PLAN.md Task 3.3 names the broad strokes ("connection status pill flips to Offline", "remote cursors are visually frozen + desaturated", "status pill flips back to Live with a Motion celebrate-in transition") but does NOT pin the load-bearing perceptual contract — specifically:

1. **Disconnect-mid-drag visual treatment.** The Yjs CRDT property is unambiguous: local edits go to the local `Y.Doc` regardless of provider connection status, and reconnect-merge is automatic. But the UX question is whether the user sees a visual affordance that "this edit is local-only until reconnect-ack". Without it, a recruiter probing the wow moment in DevTools may wonder whether the edits actually queued. With too much of it (dotted outlines on every shape mid-drag) the canvas becomes visually noisy and reads as "broken" rather than "local-first".
2. **Reconnect reconciliation animation.** When tab B receives ~30 s of missing shapes in one Yjs sync handshake, the materialisation can be jarring at scale (50+ shapes). A staggered Motion `AnimatePresence` enter looks beautiful at 5 shapes and unusable at 300 (16 ms per shape × 300 = 4.8 s; the user perceives a slow paint, not a deliberate transition). A whole-canvas crossfade is the cheapest "something changed" signal that scales correctly.
3. **Remote-cursor unfreeze.** When other users' cursors were frozen on the local user's screen during the offline window, a snap-to-current-position when sync resumes is jarring. ADR-008's critical-damped lerp already absorbs arbitrary target jumps — feeding the latest awareness position to the existing engine is zero new code; the cursor visibly catches up over the engine's ~120 ms settle time.
4. **Connection-state detection.** Hocuspocus exposes `status: 'connecting' | 'connected' | 'disconnected'`; `navigator.onLine` exposes OS-level offline. A flapping WebSocket (200 ms reconnect storm during a CDN node restart) must NOT trigger the offline UX — it would lie to the user.
5. **Reduced-motion fallback.** WCAG 2.2 AA requires `prefers-reduced-motion: reduce` to degrade every animation in this contract to instant transitions.
6. **Screen-reader announcement.** The offline → online transition is currently silent. A screen-reader user has no signal that connectivity changed and their queued edits synced. PLAN.md Task 3.5 ratifies an `aria-live="polite"` mirror for selection geometry; this ADR commits a sibling `aria-live="polite"` region for connection-state transitions.

### Options considered

**Disconnect-mid-drag visual treatment:**

- **D1. No visual change.** Cleanest UX, zero new chrome. Dev complexity: 0 days. Signal quality: bad — user has no affordance that "this is local-only", trust deficit on a portfolio demo where the recruiter is actively probing for the CRDT story. Accessibility: trivially passes (nothing to degrade). Performance: zero paint cost. Failure mode: false positives are silent (good for flap, bad for genuine disconnect).
- **D2. Dotted-stroke + reduced-opacity on uncommitted shapes (shapes whose op has not been ACKed by Hocuspocus).** Per-shape signal. Dev complexity: ~2 days — requires the shape engine to track an `unackedShapeIds: Set<string>` populated from a Hocuspocus `onChange`-side ack counter and cleared on the next outbound sync round; painter pipeline branches on `unacked === true` to render the dotted stroke + alpha 0.6 variant. Signal quality: highest — every uncommitted edit is visually distinct. Accessibility: passes (`prefers-reduced-motion` is irrelevant; the dotted-stroke is a static visual, not an animation; screen-reader path is the aria-live region below). Performance: doubled state-vector traffic at the engine layer (~2× paint cost at the per-shape level because the painter branches; at 500 shapes the unacked-set lookup is O(1) but the branch is hot). Failure mode: a 200 ms WS flap during a drag produces a brief dotted-stroke flicker on every in-progress shape — false-positive cost is **visible noise during normal use**.
- **D3. Banner only — top-bar shows a thin amber strip "Offline — your edits will sync when you reconnect".** No per-shape treatment. Dev complexity: ~0.5 days — single `<ConnectionBanner />` component reading `connectionStatus` from a new Zustand slice; Motion slide-down + slide-up at 200 ms. Signal quality: medium — user sees the global state but does not see WHICH edits are local-only (acceptable because the CRDT property guarantees ALL local edits sync, the per-shape distinction is informational not load-bearing). Accessibility: degrades cleanly under `prefers-reduced-motion: reduce` (instant appear/disappear, no slide); the banner copy doubles as the visual signal. Performance: zero canvas paint cost (banner lives in React-shell chrome, not on the canvas). Failure mode: a 200 ms WS flap produces a brief banner flash — debounceable via the connection-state detection rule below.
- **D4. Hybrid — banner + subtle alpha reduction (uncommitted shapes at 0.85 alpha, NO dotted stroke).** Banner is the primary trust signal; alpha is the per-shape micro-honesty. Dev complexity: ~1.5 days — banner (D3) plus a single-line painter branch on the unacked-set lookup (no dotted-stroke pipeline). Signal quality: high — global state IS communicated AND per-shape "this is local" is conveyed at low visual cost (0.85 alpha is below the threshold for "looks broken" but above the threshold for "user notices something is different on close inspection"). Accessibility: alpha reduction is static, not animated — passes `prefers-reduced-motion` trivially; banner degrades to instant per D3. Performance: O(1) per-shape alpha lookup; paint cost on 500 shapes adds ~3% wall-clock vs D1 baseline (measured by analogy from tape's footprint painter where alpha-branch cost on 500 cells is in the same range). Failure mode: WS flap produces the banner flash AND a brief alpha dip — debounceable via the connection-state detection rule.

**Reconnect reconciliation animation:**

- **R1. Instant materialisation.** New shapes appear on the next paint after Yjs `applyUpdate`. Dev complexity: 0 days (it is the default). Signal quality: poor at scale — a 300-shape catch-up reads as "the canvas glitched" not "30 s of work just synced". Accessibility: trivially passes. Performance: zero new cost. Failure mode: none beyond the perceptual jar.
- **R2. Staggered Motion `AnimatePresence` per shape, ~30 ms stagger, ~200 ms enter.** Each incoming remote shape fades in with a Y-axis offset. Dev complexity: ~2 days — requires the shape engine to emit an `incomingShapeIds[]` event on each sync flush and the React-side `<RemoteShapeChrome />` overlay to consume it with `AnimatePresence`. Signal quality: highest at small scale (≤ 10 shapes per sync). Accessibility: degrades to R1 under `prefers-reduced-motion`. Performance: catastrophic at scale — at 300 shapes the stagger window is 9 s, longer than the typical user's attention; the React reconciler runs 300 Motion enter animations concurrently and the main thread blocks. Failure mode: scales linearly with offline-window duration — explicitly the wrong shape.
- **R3. Whole-canvas crossfade — canvas opacity dips to 0.6 then back to 1.0 over 200 ms while new shapes paint in.** Dev complexity: ~0.5 days — single Motion `animate` on the shape canvas's CSS opacity, triggered by a `lastReconnectMs` change in the Zustand connection slice. Signal quality: medium — clear "something just synced" signal, no per-shape attribution but at scale the per-shape attribution is unparseable anyway. Accessibility: degrades to R1 (no opacity dip) under `prefers-reduced-motion: reduce`. Performance: zero per-shape cost; one CSS transform property animation on the canvas element. Failure mode: a 200 ms flap that produces a sync with zero new shapes still triggers the crossfade — debounceable by gating the trigger on `incomingShapeCount > 0`.
- **R4. Per-shape pulse ring — subtle highlight ring expands and fades over 400 ms per newly added shape, no layout shift.** Dev complexity: ~1.5 days — React-DOM overlay consuming `incomingShapeIds[]` and rendering a `<motion.div>` ring per id. Signal quality: high at small scale; visually busy at large scale. Accessibility: degrades to R1. Performance: at 300 shapes, 300 Motion enter animations — same React-reconciler cost as R2 but staggered by enter delay, not by manual stagger; main thread still blocks. Failure mode: scales linearly with offline-window duration.

**Remote-cursor unfreeze:**

- **C1. Instant snap to last awareness state.** Cursors jump to current positions on next awareness frame. Dev complexity: 0 days. Signal quality: poor — jarring. Accessibility: trivially passes. Performance: zero new cost. Failure mode: visual jar on every reconnect.
- **C2. 120 ms critical-damped lerp from frozen position to current.** Reuses ADR-008's existing engine lerp — the cursor engine already lerps `currentPos` toward `targetPos` regardless of when `targetPos` was last updated. Feeding the latest awareness position on reconnect is the same code path as any other awareness update. Dev complexity: **0 days — already free from ADR-008**. Signal quality: high — smooth motion reads as "the cursor is catching up", which is exactly what is happening semantically. Accessibility: degrades to C1 under `prefers-reduced-motion` via the existing ADR-008 reduced-motion short-circuit. Performance: zero new cost (the rAF loop runs whether the cursor moves or not). Failure mode: a 5-second offline window means the cursor travels a long distance over 120 ms — visually fast but not jarring (the critical-damped curve is asymptotic, not linear).
- **C3. Dotted ghost trail from frozen position to current.** Renders the historical path. Dev complexity: ~3 days — requires a new path-segment buffer per remote session, a dotted-line painter on the cursor canvas, and a fade timer. Signal quality: highest — explicitly shows "this user moved while you were offline". Accessibility: degrades to C1. Performance: O(path-length) per remote cursor; at 5 remote cursors with 30 s offline each, the trail buffer accumulates ~1800 awareness samples — paint cost scales with offline-window duration. Failure mode: over-engineered relative to the wow moment payoff; the dotted trail reads as a "this app has a feature for this" signal which dilutes the "local-first just works" narrative.

### Decision

**Adopt option D3 (banner only) for the disconnect-mid-drag visual treatment, option R3 (whole-canvas crossfade) for the reconnect reconciliation animation, and option C2 (120 ms lerp via the existing ADR-008 cursor engine) for the remote-cursor unfreeze policy.**

The disconnect treatment is a single `<ConnectionBanner />` slid in from the top of the chrome at 200 ms with `easeOutCubic` (matches the theme-toggle and identity-badge timings — Task 2.3 and Task 2.5b pinned the chrome motion timing palette already, ADR-009 stays consistent). Banner copy verbatim: `"Offline — your edits will sync when you reconnect"`. The banner is rendered inside the React-shell chrome (above the Canvas2D layer), not on the canvas. NO per-shape alpha reduction, NO dotted strokes — option D4's per-shape micro-honesty was rejected because the marginal trust gain is not worth the paint-cost branch on every shape redraw and the false-positive flicker during WS flaps. The CRDT property guarantees the banner's copy is true (all local edits will sync), so the per-shape redundancy carries cost without proportional gain.

The reconciliation animation is a single Motion `animate` on the shape canvas's CSS opacity, triggered when `lastReconnectMs` updates in the connection Zustand slice AND `incomingShapeCount > 0` on the sync that fired the update. Opacity curve: 1.0 → 0.6 → 1.0 over 200 ms with `easeInOutCubic`. The cursor canvas is NOT crossfaded (cursor positions update under the lerp engine; the crossfade would visually break the cursor catch-up). The dev-conflict-viz overlay (ADR-008) and the connection banner are NOT crossfaded.

The remote-cursor unfreeze is **free** from ADR-008: the cursor engine's `setRemoteTarget(sessionId, x, y)` is invoked by the awareness subscription on every awareness frame regardless of provider connection status; on reconnect, the next awareness frame carries the current position and the engine lerps `currentPos` toward `targetPos` over its existing ~120 ms settle time. No new code in the cursor engine. NO ghost trail.

**Connection-state detection rule.** Both `HocuspocusProvider.status` and `navigator.onLine` are read. A reactive `useConnectionStatus()` hook in `meld-web/src/lib/hooks/use-connection-status.ts` subscribes to both signals and computes `connectionStatus: 'live' | 'offline' | 'reconnecting'` per the rule: `offline` iff `(provider.status === 'disconnected' AND that state has held for ≥ 1500 ms) OR navigator.onLine === false`; `reconnecting` iff `provider.status === 'connecting'`; `live` otherwise. The 1500 ms debounce on `disconnected` is the load-bearing flap-suppression — a 200 ms WS reconnect storm during a CDN node restart NEVER reaches `offline` state. `navigator.onLine === false` bypasses the debounce because the OS signal is authoritative (the WebSocket cannot reconnect across a hard offline regardless of how fast we reconnect-attempt). Transition to `live` from `offline` records `lastReconnectMs = Date.now()` AND captures the count of shapes that arrived in the first sync round after reconnect (`incomingShapeCount`) for the crossfade gate.

**Aria-live announcement copy template (verbatim, ASCII only).** `<OfflineAriaLiveRegion />` (rendered as `<div role="status" aria-live="polite" className="sr-only">`) emits one of three strings per transition: on `live → offline`, the string `"Offline. Your edits are saved locally and will sync when the connection returns."`; on `offline → live` with `incomingShapeCount > 0`, the string `"Connection restored. {N} {shape|shapes} synced."` (the singular/plural toggle is on `N === 1`); on `offline → live` with `incomingShapeCount === 0`, the string `"Connection restored."`. No copy is emitted on `reconnecting → live` (the connecting state is transient and announcing it would over-narrate). The component lives in the React-shell chrome, mounted once at the layout level — `aria-live="polite"` ensures the screen reader queues the announcement behind any in-flight reading.

**Reduced-motion degradation path.** `useReducedMotion()` from `motion/react` (Task 2.3 established the import pattern) gates every animation in this contract: (a) the banner slide-in degrades to instant appear (`duration: 0`); (b) the whole-canvas crossfade degrades to no opacity dip (`duration: 0`, opacity stays at 1.0 throughout); (c) the cursor lerp degrades via ADR-008's existing reduced-motion short-circuit (instant snap-to-position); (d) the aria-live announcement is ALWAYS emitted regardless of `prefers-reduced-motion` — it is content, not motion, and the WCAG 2.2 AA bar requires the connectivity transition to reach the screen-reader user. The amber border colour on the banner (visual signal) is also independent of reduced-motion — only the slide-in animation is gated.

**Two facts drove the picks:**

1. **The 120 ms critical-damped cursor lerp is already free from ADR-008** — the cursor engine handles arbitrary target jumps via its existing `currentPos → targetPos` lerp, so the offline-window-spanning catch-up is the same code path as any other awareness update. Picking C2 adds zero net code. C3 (ghost trail) would have required a new path-segment buffer, a dotted-line painter on the cursor canvas, and a fade timer — all to demonstrate a feature that dilutes the "local-first just works" narrative. The banner (D3) + crossfade (R3) + aria-live region are then the ONLY new UI surfaces ADR-009 introduces — three components, ~0.5 + 0.5 days each plus the connection-detection hook (~0.5 days) = ~2 days of Phase 3.3 surface. Compare to D4 + R2 + C3 which would have been ~6.5 days for marginal perceptual gain at small scale and catastrophic perceptual loss at large scale.

2. **The 1500 ms `disconnected` debounce is calibrated against measured 2026 CDN flap behaviour, not invented out of thin air.** Fly.io's documented edge-node failover window is 300–800 ms p95 (per Fly's 2026 incident reports), Cloudflare's WebSocket reconnect window on edge maintenance is sub-second, and Railway's documented WS idle-timeout reconnect is 200–500 ms. The 1500 ms ceiling sits above ALL three flap-window p99s, so a genuine "user pulled the network cable" transition reaches `offline` state inside ~1.5 s while a CDN flap stays invisible. The `navigator.onLine === false` bypass exists because an OS-level offline (airplane mode, lid close) is authoritative and 1500 ms of latency to surface it would defeat the local-first trust contract. This is the same shape as tape ADR-006's backpressure debounce (close on 30 s sustained no-message-received, NOT on the first dropped frame) — chosen for the same reason: false positives are visible and costly, the debounce is the load-bearing signal-to-noise filter.

### Consequences

- **Positive.**
  - Phase 3.3 ships in ~2 days of frontend surface (banner + crossfade + aria-live region + connection-detection hook) rather than ~6 days; the saved budget reallocates to Phase 3.2 selection chrome polish.
  - Cursor unfreeze adds ZERO new engine code — ADR-008's existing critical-damped lerp absorbs the catch-up natively. The portfolio narrative reads "we designed the offline UX deliberately and most of it was already free from the rendering plumbing", which is the senior-signal pattern.
  - WS flap (sub-1500 ms reconnect) is structurally invisible — the user never sees a false-positive offline banner. Reviewer-checked via the e2e test scaffolded for ADR-007 v1.1.
  - The aria-live announcement copy template is quotable in the README accessibility section — a recruiter skimming the demo's a11y story sees the exact strings the screen reader speaks.
  - Reduced-motion fallback is one `useReducedMotion()` check at each of three call sites; the fallback gracefully degrades every animation to instant transitions while preserving the content (banner copy, aria-live announcement, amber colour).
  - The reconciliation crossfade is gated on `incomingShapeCount > 0`, so a reconnect that flushed zero shapes (e.g., the user was alone on the board) does not produce a vestigial canvas flash.
  - All new chrome lives in the React-shell layer, NOT on the canvas — ADR-008's two-canvas paint discipline is unchanged.

Documented here so a future "where is the offline-recovery metric" question lands on this paragraph.

## ADR-010: Client-side DoS prevention + the per-tool drawing-commit contract

**Status:** accepted
**Date:** 2026-06-02

### Context

ADR-002 (Hocuspocus adoption) pinned the SERVER-side backpressure boundary: `maxRate` messages/sec/client, `maxMessageSize` 1 MB, `timeout` 30 s, and a forced close with code `4290` (the tape ADR-006 pattern) when a client exceeds the rate. ADR-004 defined the `control.overrun` payload (`reason`, `closeCode: 4290`, `retryAfterMs`) emitted immediately before that close, and ADR-011 moved its transport onto Hocuspocus Stateless (the client now receives it through the `onStateless` → `handleStatelessControlMessage` → `onUnknownControlFrame` route, currently a dev-only warn).

What was never ratified is the CLIENT side of that contract: **how the drawing tools commit Yjs operations so a normal user never trips `maxRate` in the first place, and what the user sees if `4290` ever fires anyway.** ADR-008 established the engine's paint discipline (subscribe-once shallow `Y.Map.observe` on the shapes root + boolean dirty flag + rAF loop) and the per-tool preview-canvas pattern, but it deferred the commit cadence to Phase 3.2. The Phase 3.2 implementation shipped a freehand path that is both broken AND adversarial to the server limit, which forces this ADR now.

**The owner-reported freehand bug (root cause, already traced in code).** The pen/freehand tool does not render the stroke while drawing — the line appears only when the button is released. Trace:

- `web/src/components/board/board-pointer-overlay.tsx` `handlePointerDown` (freehand branch, ~lines 359–384) inserts the shape on pointerdown via a ROOT write — `doc.getMap(SHAPES_ROOT_KEY).set(shapeId, shapeMap)` inside `doc.transact`. Then `handlePointerMove` (~lines 417–429) appends each point on every pointermove (throttled to a 16 ms gate, `FREEHAND_APPEND_INTERVAL_MS`) via `appendFreehandPoint(draft.shapeMap, ...)` inside `doc.transact` — a write into the shape's NESTED `Y.Array<FreehandPoint>` structure (`web/src/lib/shapes/types.ts:361`, `points.push([point])`).
- The engine observes the shapes root with the SHALLOW `Y.Map.observe`, NOT `observeDeep` (`web/src/lib/canvas/engine.ts:363`, `this.#shapesMap.observe(shapeObserver)`). A nested point append does not mutate a ROOT key, so the shallow observer never fires, `#shapeDirty` never flips, and the shape layer is never repainted while the stroke grows. The stroke becomes visible only when some LATER root-level change flips the flag (e.g. the next pointerdown insert).

So the current "write points to Yjs live" approach is doubly wrong: it produces no live repaint (locally OR remotely), and it is exactly the ~60-ops-per-second-on-the-wire pattern this ADR exists to suppress — a single sustained freehand stroke is the most likely way a NORMAL user would otherwise approach `maxRate`. Fixing the bug and removing the DoS vector are the SAME change.

### Options considered

**Freehand commit model (resolve the bug + the wire-spam together):**

- **F1. Keep live nested Yjs appends; fix the repaint by switching the engine to `observeDeep`.** Makes the stroke grow live locally and remotely. REJECTED: it ratifies the ~60-ops/sec-on-the-wire pattern as the steady state for the single most common drawing gesture, drives straight at `maxRate`, and `observeDeep` fires the engine dirty flag on EVERY nested mutation of EVERY shape (text edits, future drag/resize) — re-coupling paint cost to mutation depth and undoing ADR-008's "one boolean flip per root change" discipline. Wrong on both the DoS axis and the paint-budget axis.
- **F2. Live LOCAL preview into the in-memory draft (no Yjs writes during the drag); commit the whole stroke as ONE Yjs op on pointerup.** During the drag, accumulate points in the in-memory `FreehandDraft` and render them on the dedicated preview canvas (the SAME preview canvas rect/ellipse already use, ADR-008). On pointerup, build the shape with its full point list and insert it once — `doc.getMap(SHAPES_ROOT_KEY).set(shapeId, fullShapeMap)` inside a single `doc.transact`. Local feedback is instant (preview canvas, no Yjs round-trip); the wire sees ONE op per stroke, not ~60/sec; the engine's shallow `observe` fires exactly once (the root insert) and repaints the completed stroke. Fixes the bug AND removes the DoS vector in one move. Cost: remote tabs see the stroke appear whole on release, not growing live. PICKED.
- **F3. Throttled live-remote stroke growth — batch nested appends to ~5–10 Hz, engine uses `observeDeep`.** A middle path: the stroke grows on remote tabs at a coarse cadence. REJECTED for v1 (deferred to v1.1/v2): it still needs `observeDeep` (paint-budget regression) AND still puts a sustained op stream on the wire (5–10 ops/sec × N concurrent drawers), eating into the `maxRate` headroom this ADR is protecting. The bandwidth/headroom cost is documented as the explicit deferred option so v1.1 can revisit if "watch them draw live" becomes a wow-moment requirement.

**Overrun (`4290`) user-visible behaviour:**

- **U1. Reuse the existing ADR-009 connection-banner chrome surface; no new dependency.** The board already ships `<ConnectionBanner />` + `<OfflineAriaLiveRegion />` (ADR-009) driven by the `ui-store` `connectionState` slot (`'live' | 'reconnecting' | 'offline'`). An overrun is a recoverable, temporary throttle — semantically a transient disconnect with a retry hint — so it routes through the same banner vocabulary with overrun-specific copy + the `retryAfterMs` hint, and the same `aria-live` announcement. PICKED.
- **U2. Add a shadcn/sonner toast.** meld has NO toast library installed (`sonner` / `@radix-ui/react-toast` absent — verified). Adding one for a rare, recoverable event introduces a new dependency + a new chrome vocabulary that competes with the banner the project already uses for connection state. REJECTED: the banner is the established surface for "connection is degraded, your edits are safe", which is exactly the overrun's meaning.

**Burst vs abuse boundary (client-side cooldown ahead of the server limit):**

- **B1. No client guard; rely solely on the server `maxRate`.** REJECTED: a client-side bug or a future high-frequency tool could spam the wire and earn a `4290` close that the user experiences as a disconnect — a bad portfolio look. A client cooldown calibrated UNDER the server ceiling means a well-behaved client never reaches `4290` even under a runaway-loop bug.
- **B2. A client-side op-emission guard with a token-bucket-style burst allowance, ceilinged safely below the server `maxRate`.** PICKED — numbers below.

### Decision

#### 1. Per-tool commit contract

The canonical rule for every tool: **render in-progress feedback on the LOCAL preview canvas from the in-memory draft; commit to Yjs exactly ONCE, at the natural end of the gesture, inside a single `doc.transact`.** No tool writes to Yjs on pointermove / keystroke cadence.

- **freehand / pen (F2 — fixes the owner bug).** On pointerdown, start an in-memory `FreehandDraft` (points accumulate in component memory, NOT in Yjs — the `shapeMap` is no longer created or inserted on pointerdown). On pointermove, push the sampled point into the draft and repaint the stroke-so-far on the preview canvas (the same preview canvas rect/ellipse use), giving instant local feedback. On pointerup, call `createShape({ kind: 'freehand', initialPoints: <full draft point list>, ... })` and insert it ONCE — `doc.getMap(SHAPES_ROOT_KEY).set(shapeId, shapeMap)` inside one `doc.transact`. The engine's shallow root `observe` fires once on that insert and repaints the finished stroke. **Consequence (accepted for v1):** remote tabs see the completed stroke on release as a single op, not growing live — the correct DoS-aligned trade (one op/stroke instead of ~60/sec). **Deferred (v1.1/v2):** "throttled live-remote stroke growth" (F3 — batched ~5–10 Hz nested append with `observeDeep`), explicitly noting its bandwidth + `maxRate`-headroom cost; not done in v1.
  - **Point decimation policy (bounds the point array).** While sampling into the draft, admit a new point only if it is at least `FREEHAND_MIN_POINT_DISTANCE_PX = 2` CSS px from the last admitted point OR at least `FREEHAND_MIN_POINT_INTERVAL_MS = 16` ms have elapsed since the last admitted sample (min-distance gate primary, time gate as the fallback so a slow deliberate drag still records). This keeps a long stroke from becoming an unbounded point array (and keeps the single commit op small). A hard ceiling `FREEHAND_MAX_POINTS = 2000` caps a pathological stroke; on overflow the draft drops the oldest-to-newest sampling rate further (admit every Nth sample) rather than refusing to draw. These constants live beside the existing `FREEHAND_APPEND_INTERVAL_MS` in the overlay.
- **rectangle / ellipse (canonical pattern — confirmed, unchanged).** Already preview-on-drag + single commit on pointerup (`handlePointerUp`, ~lines 470–491). This IS the canonical pattern the other tools conform to. Pinned as-is.
- **shape drag / move / resize (contract for when selection lands, Phase 3.2b).** When a shape is dragged or resized, paint the moved/resized ghost on the preview canvas (or via the React-DOM selection chrome) during the gesture and commit ONE op on drag-END / resize-END (`doc.transact` once), NOT per pointermove. Same rule as the create tools. Stated here so Phase 3.2b implements it against this contract from day one.
- **text (confirmed, unchanged).** Commits on Enter / blur (`commitTextDraft`, ~lines 536–562), NOT per keystroke. The DOM `<input>` is the live local feedback; the Yjs write is a single op on commit. Pinned as-is.

#### 2. User-visible behaviour on server `4290` close (U1)

The client already receives `control.overrun` (`{ reason, closeCode: 4290, retryAfterMs }`) over Stateless (ADR-011), routed through `handleStatelessControlMessage` → `onUnknownControlFrame`. ADR-010 directs that route to a real overrun handler (replacing the dev-only warn for this kind) that:

1. Sets the `ui-store` `connectionState` to a transient throttled state surfaced through the EXISTING `<ConnectionBanner />` chrome — overrun-specific copy ("Slow down — reconnecting in a moment…", reinforced by the `retryAfterMs` hint) and the existing `aria-live` announcement via `<OfflineAriaLiveRegion />`. No new toast dependency.
2. Lets the `HocuspocusProvider` go through its disconnect (the server has already closed with `4290`), and schedules a reconnect after `retryAfterMs` (multiplied by the provider's own backoff curve to avoid a reconnect storm if many connections hit `4290` at once — ADR-004's `retryAfterMs` intent). On reconnect the banner clears and `connectionState` returns to `'live'`.
3. Keeps it CALM and RECOVERABLE: local edits live in the `Y.Doc` throughout and sync on reconnect (the ADR-009 offline guarantee — overrun is just a server-initiated variant of the same temporary-disconnect story). The user loses nothing.

#### 3. Legitimate burst vs abuse boundary (B2 — the numbers)

The server ceiling is `maxRate: 100` msgs/sec/client (ADR-002). The client guard sits well under it:

- **A `doc.transact` is ONE op on the wire regardless of how many shapes it mutates.** A 50-shape paste wrapped in one `doc.transact` is ONE message — legitimate, never throttled. The contract is "batch related mutations into one transaction", which the per-tool contract above already enforces (one transact per gesture).
- **Client-side op-emission guard:** a token-bucket with `CLIENT_OP_RATE_CEILING = 40` ops/sec sustained (40% of the server's 100/sec — comfortable headroom for awareness coalescing + sync deltas already on the wire) and `CLIENT_OP_BURST_ALLOWANCE = 20` ops (absorbs a legitimate burst — a multi-shape paste, a rapid sequence of single-shape commits — without throttling). When the bucket empties, the client applies a short cooldown (coalesces / briefly defers further commits) BEFORE the server's `maxRate` would fire, so a runaway client self-limits rather than earning a `4290`. These constants are calibrated to sit safely under `maxRate` with margin for the non-shape traffic (awareness, sync) that shares the same per-client rate budget.
- The guard is defensive (a normal user with the per-tool contract above emits ~1 op/gesture and never approaches it); its job is to make a CLIENT bug or a future high-frequency tool degrade gracefully instead of disconnecting.

#### 4. Dev-only telemetry

An "ops emitted per second" counter, gated on `process.env.NODE_ENV === 'development'` + Terser DCE — the SAME strip pattern as ADR-008's paint-cost log (`[meld-engine]`) and the dev conflict-viz overlay. A `[meld-ops]` dev console line every ~10 s reports the current commit cadence (ops/sec, burst-bucket level, any cooldowns applied) so the per-tool contract's wire behaviour is observable in dev. Production builds carry no log emit (the counter struct is cheap; the log gating is what strips). Auditable via `grep .next/static/chunks` for `[meld-ops]` returning ZERO matches in a production build, exactly like the existing dev literals.

### Consequences

- **Positive.**
  - The owner-reported freehand bug is fixed: the stroke renders live and smoothly on the local preview canvas during the drag, and the finished stroke appears on commit. Instant local feedback, zero Yjs round-trip during the gesture.
  - The single worst client-side wire-spam vector (per-point freehand appends, ~60 ops/sec) is eliminated — freehand now emits ONE op per stroke. A normal user cannot trip `maxRate`.
  - The engine's shallow `observe` STAYS shallow — no `observeDeep`. Because the live nested writes go away, there is no nested mutation to observe; the root insert on pointerup is a root-key change the existing shallow observer already catches. ADR-008's one-boolean-flip-per-root-change paint discipline is preserved intact. (Call-out for the implementer: do NOT reach for `observeDeep` to "fix" the repaint — removing the live writes is the fix.)
  - Overrun UX reuses the existing connection-banner + aria-live chrome — no new dependency, one consistent "your edits are safe, reconnecting" vocabulary for both offline (ADR-009) and overrun (ADR-010).
  - The client op-guard makes a runaway client self-limit gracefully instead of earning a user-visible `4290` disconnect.
  - Dev ops/sec telemetry makes the commit cadence observable without shipping anything to production (same audited strip as ADR-008).

- **Negative.**
  - Remote tabs see freehand strokes appear whole on release, not growing live. Accepted for v1 as the DoS-aligned trade; the live-remote-growth option (F3) is deferred with its documented bandwidth cost.
  - The freehand draft now holds the full point list in component memory until commit — bounded by the decimation policy + the 2000-point ceiling, so the memory is small, but it is a new in-memory accumulation the previous Yjs-live approach did not have.
  - The client op-guard is a second rate-limit surface (after the server's) — two places that must stay calibrated relative to each other. Mitigated by deriving the client ceiling as an explicit fraction of the server `maxRate` constant and documenting the relationship in code so a future `maxRate` change prompts a guard recalibration.

- **Follow-up tasks.**
  - **Task 3.X-commit-contract — `frontend-engineer` (queued against this ADR):** implement the per-tool commit contract. (a) Freehand: replace the pointerdown root-insert + pointermove nested-append path with a live-preview-on-drag (accumulate points in the in-memory `FreehandDraft`, render the stroke-so-far on the preview canvas) + a SINGLE commit on pointerup (`createShape({ kind: 'freehand', initialPoints })` → one `doc.getMap(SHAPES_ROOT_KEY).set(...)` inside one `doc.transact`). **REMOVE the pointermove `appendFreehandPoint` live writes and the pointerdown freehand root-insert** in `board-pointer-overlay.tsx`; add the decimation constants (`FREEHAND_MIN_POINT_DISTANCE_PX`, `FREEHAND_MIN_POINT_INTERVAL_MS`, `FREEHAND_MAX_POINTS`). **The engine's shallow `observe` STAYS shallow — do NOT switch to `observeDeep`** (the live nested writes are gone, so there is nothing nested to observe; the pointerup root insert is caught by the existing `Y.Map.observe`). (b) Wire the `control.overrun` handler: route the `onUnknownControlFrame` overrun kind (coordinate with the ADR-011 `handleStatelessControlMessage` handler that already receives it) to set the `ui-store` connection state surfaced through `<ConnectionBanner />` with overrun copy + `retryAfterMs`, and trigger the provider disconnect + reconnect-after-`retryAfterMs` cycle; local edits stay in the `Y.Doc` and sync on reconnect. (c) Add the client-side burst-cooldown guard (token bucket, `CLIENT_OP_RATE_CEILING = 40` ops/sec, `CLIENT_OP_BURST_ALLOWANCE = 20`, calibrated under the server `maxRate: 100`). ## ADR-011: Move control messages from raw TEXT frames to Hocuspocus Stateless

**Status:** accepted
**Date:** 2026-06-02

**Supersedes:** the transport (NOT the payload contract) of ADR-004. ADR-004's TEXT/BINARY wire-coexistence mechanism (option W1) is retired by this ADR. Everything ADR-004 pinned ABOVE the transport layer — the JSON codec, the Zod discriminated union, the `kind` vocabulary, the welcome/overrun/board-deleted payload shapes, the `protocolVersion` handshake, the `control.*` vs bare-verb namespacing — survives unchanged.

### Context

ADR-004 put meld's server→client control messages (`welcome` + the reserved `control.*` kinds) on raw WebSocket **TEXT frames**, sent via `connection.webSocket.send(string)` and discriminated on the browser by `typeof event.data === 'string'`. The decision was sound on its own terms (DevTools-debuggable literal JSON, zero bundle cost, clean protocol/application split) but it collided with a `HocuspocusProvider` 4.1 internal we did not account for at ADR-004 time:

**The provider's OWN internal message handler runs on every raw `'message'` event and unconditionally binary-decodes the frame** (lib0 decoding via `IncomingMessage`/`readVarUint`). Our TEXT welcome frame is not a valid y-protocol binary envelope, so the decoder throws `Unexpected end of array` — an **uncaught, user-visible red console error once per board load** on the live demo (`https://meld-demo.fly.dev`). It is functionally harmless (the `9b06f7e` fix made our own `onMessage` callback throw-safe, so presence + sync work), but a red console error on a portfolio demo a recruiter may open DevTools against is unacceptable polish.

The TEXT-frame approach also forced a fragile client-side `onMessage` interception in `web/src/lib/yjs/provider.ts` (the `createBoardProvider` `onMessage` callback + the `handleProviderMessage` TEXT branch). That interception already produced one **catastrophic** bug: the provider 4.1 emits the RAW browser `MessageEvent` to its `'message'` listeners (not the documented `{ event, message }` shape), so an early destructure assumption killed ALL sync until it was fixed in `9b06f7e`. The interception is load-bearing fragility we want gone, not patched.

The framework offers a first-class mechanism for exactly this use case — custom app-level string payloads carried INSIDE the y-protocol binary envelope: **Hocuspocus's Stateless message channel** (`MessageType.Stateless = 5`). Because a stateless message IS a valid y-protocol envelope, the provider decodes it correctly and routes it to a dedicated `onStateless` callback instead of choking. Moving control messages onto Stateless eliminates BOTH the `Unexpected end of array` error AND the need for any client-side `onMessage` interception.

This ADR was authored AFTER verifying the exact Stateless API on both sides against the installed type defs — the same rigor that caught the `onMessage` raw-`MessageEvent` trap. Every API claim below cites the `.d.ts` file and line read.

### API verification (verified, not assumed)

The doc comment at line 776–778 reads "Send a stateless message with payload". So the welcome migration is `payload.connection.webSocket.send(string)` → `payload.connection.sendStateless(string)` — a one-line swap on the same hook with the same handle. **`control.overrun` over Stateless given the imminent close.** ADR-004 emits `control.overrun` IMMEDIATELY before the server closes the socket with code `4290`. The current `overrun.ts` sequence is `webSocket.send(string)` then `webSocket.close(4290)`. Under Stateless the sequence becomes `connection.sendStateless(string)` then `connection.close({ code: 4290, reason })` (or the existing raw `webSocket.close(4290)` belt-and-braces). Both `sendStateless` and the close are synchronous writes onto the same `ws` socket send buffer in FIFO order, so the stateless frame is enqueued ahead of the close frame and flushes first — the client receives `onStateless` with the overrun payload, then `onclose` with code `4290`. This is the same ordering guarantee the current TEXT-then-close path relies on; the only change is the opcode of the first write. The reserved v1.1/v2 kinds are NOT defined as live emits now — their schema stubs remain exactly as ADR-004 left them.

### Payload format — ZERO change to the contract

Stateless carries a `string`. We keep the **existing JSON-stringified control-frame shape and the existing Zod schemas verbatim** — `wsWelcomeFrameSchema` (server) / `welcomeFrameSchema` (client), `wsOverrunFrameSchema`, `wsControlBoardDeletedFrameSchema`, the `wsControlFrameSchema` discriminated union, the `WSWelcomeFramePayload` types-only re-export through `meld-server/src/app.ts`. The server still does `connection.sendStateless(JSON.stringify(wsWelcomeFrameSchema.parse(payload)))`; the client still does `JSON.parse(data.payload)` → Zod `safeParse` → `useWelcomeStore.setWelcome(payload)`. **Only the transport call changes.** The payload byte-shape on the wire is identical to ADR-004's (it is the SAME JSON string), now nested inside the y-protocol stateless envelope instead of riding a bare TEXT frame. This means the welcome-frame fixtures, the schema files, and the cross-package type re-export from ADR-004 all stay untouched.

### protocolVersion / compatibility posture

ADR-004 pinned `protocolVersion: 1` as the load-bearing forward-compat marker. Moving the transport is technically a wire-protocol change (a TEXT-frame v1 client cannot read a stateless-framed welcome and vice versa). **We do NOT bump `protocolVersion`, and we keep NO backward compatibility.** Justification: meld is a single-deploy showcase — server and client ship together in ONE Fly image (Next standalone + meld-server in the same container per ADR-006), boards are ephemeral (30-day retention, ADR-003), and there are no third-party clients (ADR-004's "non-Next client" criterion is explicitly out of scope). The instant the new image deploys, every client is the new client; there is no window where a v1-transport client talks to a v1-transport-removed server. `protocolVersion` continues to mean "the discriminator vocabulary / payload shape contract" — which is genuinely unchanged here — and stays at `1`. Bumping it would falsely signal a payload-contract break to the v2 handshake logic ADR-004 reserved. Keeping it simple: transport is an implementation detail of how the `protocolVersion: 1` payload reaches the peer, not part of the versioned contract.

### What gets REMOVED on the client

Once `welcome` arrives via `onStateless`, the entire raw-TEXT interception path in `web/src/lib/yjs/provider.ts` is dead:

- **REMOVE** the `onMessage` callback passed to `new HocuspocusProvider({...})` in `createBoardProvider` (lines ~165–183) — including the raw-`MessageEvent`/`{ event }` defensive dual-shape handling that the `9b06f7e` fix added. Nothing custom rides raw `'message'` events anymore, so the provider's own handler is the only consumer and it needs no help from us. We do NOT keep a defensive no-op `onMessage`: a no-op still registers a listener on the provider's emitter `forEach` and re-introduces the exact "a listener on the message path" surface we are eliminating; cleaner to pass no `onMessage` at all.
- **REMOVE** `handleProviderMessage` (lines ~303–380) and the client-side `welcomeFrameSchema` block IF and ONLY IF it is reproduced inside the new `onStateless` handler. In practice the schema MOVES into the `onStateless` path (it is still needed to validate the parsed welcome); only the `MessageEvent`/TEXT discrimination scaffolding (`typeof event.data !== 'string'` branch, the malformed-TEXT guard, the BINARY passthrough comment) is deleted as obsolete.
- **REMOVE** the `onMessage`-wiring regression test in `web/src/lib/yjs/__tests__/provider.test.ts` (the suite that drives the captured factory closure with a raw `MessageEvent` to assert throw-safety — the `9b06f7e` regression guard). It tests a code path that no longer exists. Replace it with an `onStateless`-wiring test that drives the new callback with `{ payload: '<welcome json>' }` and asserts `useWelcomeStore.setWelcome` is called with the parsed payload.
- **PRESERVE** the awareness-seed pipeline (`attachAwarenessSeedPipeline`, `seedAwarenessFromWelcome`, the `useWelcomeStore.subscribe` wiring) UNCHANGED — it consumes the welcome STORE, not the transport, so it is downstream of the change and keeps working the moment the new `onStateless` handler calls `setWelcome`.

### Observability

ADR-004 added four `/health.ws` counters; the implementation landed `wsMetrics.controlFramesOut` / `controlFramesDropped` (recorded in `welcome.ts` / `overrun.ts`). These **map directly and keep their names** — `recordControlFrameOut()` now fires after a successful `sendStateless` / `broadcastStateless` instead of after `webSocket.send`; `recordControlFrameDropped()` still fires on serialize-throw or send-throw. `controlFramesOut` now counts stateless sends. No counter is renamed, added, or removed — the semantic ("a control message left the server" / "a control message failed to leave") is transport-agnostic and was deliberately named that way. The board-deleted broadcast increments `controlFramesOut` once per connection it reaches (the broadcast helper counts per delivery to preserve the existing per-frame semantics).

### Options considered

- **A. Move control messages to Hocuspocus Stateless (`sendStateless` / `broadcastStateless` server-side, `onStateless` client-side).** First-class framework mechanism; the payload is a valid y-protocol envelope so the provider decodes + routes it instead of choking; the client receives a clean `{ payload: string }` with no `MessageEvent` ambiguity; the fragile `onMessage` interception is deleted entirely. Cost: control messages are no longer literal-JSON in the DevTools Network frame inspector (they are inside a binary stateless envelope) — the ADR-004 "recruiter reads the welcome frame as JSON in DevTools" narrative is lost. Mitigated: the welcome payload is still trivially inspectable via a `console.log` in the `onStateless` handler or React DevTools on `useWelcomeStore`, and the live wire was already mostly binary (all of Yjs sync + awareness). DevTools-debuggability of one frame does not outweigh a red console error on every load.
- **B. Keep TEXT frames; suppress the provider's binary-decode error.** Patch around the `Unexpected end of array` by either monkey-patching the provider's internal `IncomingMessage` decode or wrapping its message handler. Rejected: it doubles down on fighting the framework internals — the exact fragility class that already produced the `9b06f7e` catastrophic bug. Any provider minor-version bump could move the internal we patched. This is the path of most future breakage.
- **C. Second WebSocket connection for control (the ADR-004 W3 foil, revisited).** A dedicated `/ws/control/:id` socket that is never fed to the provider, so nothing binary-decodes our TEXT frames. Rejected for the same reasons ADR-004 rejected W3: doubles the connection lifecycle + reconnect coordination, doubles `/health.ws` connection accounting, and the v2 CF Durable Objects migration would need two DOs per board for zero protocol benefit. Solving a framework-integration paper-cut by adding a whole transport is disproportionate.

### Decision

**Adopt option A — move meld's server→client control messages from raw TEXT frames onto Hocuspocus's Stateless message channel.** Server emits `welcome` via `Connection.sendStateless` on the existing `connected` hook, `control.overrun` via `Connection.sendStateless` before the `4290` close, and `control.board-deleted` via `Document.broadcastStateless`. Client consumes them via the `onStateless: ({ payload }) => ...` provider config callback, parsing the same JSON through the same Zod schemas and dispatching to `useWelcomeStore` exactly as before. The payload contract, the `kind` vocabulary, the `protocolVersion: 1` marker, and the `/health.ws` counter names are all unchanged — ONLY the transport moves. The raw-`MessageEvent` `onMessage` interception and its `9b06f7e` regression test are removed entirely. This eliminates the once-per-load `Unexpected end of array` console error and deletes the fragile interception that already caused one catastrophic sync-killer bug.

### Consequences

- **Positive.**
  - The `Unexpected end of array` red console error is gone — the provider decodes our stateless message as a valid y-protocol envelope instead of choking on a TEXT frame it did not expect. Portfolio-polish defect closed.
  - The fragile raw-`MessageEvent` `onMessage` interception is deleted, not patched. The entire class of "the provider emits a runtime shape its types do not declare" bug (the `9b06f7e` root cause) is removed from meld's surface — we now consume a framework-declared, framework-stable `{ payload: string }`.
  - We move ONTO the framework's intended mechanism instead of around its internals. Provider minor-version bumps are far less likely to break `onStateless` (a public, documented config callback) than they were to break our assumption about raw `'message'` emit shapes.
  - Zero payload-contract churn: schemas, fixtures, types-only re-export, `protocolVersion`, and `/health.ws` counter names are all untouched. The blast radius is two call sites server-side and one handler client-side.

- **Negative.**
  - The ADR-004 "open DevTools → Network → WS → read the welcome frame as literal JSON" narrative is lost; control payloads now sit inside the binary stateless envelope. Net polish is still positive (no red error beats one inspectable frame), but a small self-documenting-on-the-wire signal is given up. README/AGENT_NOTES note the `console.log`-in-`onStateless` inspection path instead.
  - `control.overrun`'s send-then-close ordering now depends on `sendStateless` and `close` both writing to the same `ws` send buffer in FIFO order. Verified equivalent to the current TEXT-then-close path (same socket, same synchronous enqueue), but it is a behavior to re-confirm in the backpressure stress test rather than assume.
  - ADR-004's TEXT/BINARY wire-coexistence mechanism is now superseded — anyone reading ADR-004 in isolation could implement the retired transport. Mitigated by the **Supersedes** banner at the top of this ADR and the AGENT_NOTES cross-reference.

In the ADR-003 retention sweep, change the `control.board-deleted` per-connection loop to a single `Document.broadcastStateless(JSON.stringify(payload))` on `Server.documents.get(boardId)`, incrementing `controlFramesOut` per delivery.
