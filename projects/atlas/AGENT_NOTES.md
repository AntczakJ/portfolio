# atlas — Agent Notes

> Append-only cross-agent context. Every subagent reads on start, appends on end.

## Gotchas

- **Keyless map is a HARD GATE (ADR-001, ADR-006).** The committed repo MUST render the map with NO paid secret. A fresh checkout with no `.env` renders the keyless fallback basemap and the fleet on it. Any tile/style key is an OPTIONAL env var (`NEXT_PUBLIC_MAP_TILE_KEY` or equivalent) documented in `.env.example`, never committed in `.env`, and only enriches the basemap when supplied. Do NOT introduce Mapbox GL JS (paid token + non-open license) — MapLibre GL JS only. Verify the keyless render under a prod build before claiming it works.
- **MapLibre + strict CSP (ADR-006, the meld/razors-edge/pulse lesson).** MapLibre uses a Web Worker for tile parsing, so the CSP must allow `worker-src 'self' blob:` (and `blob:` where the worker is created from a blob, plus the tile host in `connect-src`/`img-src` for raster). This must be done WITHOUT opening `unsafe-eval`. Verify the exact policy against a `next build && next start` PROD build, not `next dev` (HMR uses runtime eval that a no-`unsafe-eval` policy flags — a dev-only artifact). Also watch faker (bake seed to a static module so it is build-only) and Zod 4's JIT probe (`z.config({ jitless: true })` as a global early side-effect) — both bite the runtime-validation paths (the WS frame validation validates at runtime here, so jitless Zod matters).
- **The streaming + interpolation surface is NOT Motion (ADR-001).** Marker interpolation between authoritative ticks is a hand-rolled `requestAnimationFrame` tween driving MapLibre's imperative API OFF the React render path (an off-render store — Zustand/ref — holding last+next positions, NOT React state per tick per marker). Camera fly-to is MapLibre native (`flyTo`/`easeTo`). Trails/zone-pulse are MapLibre paint updates. Motion is for React-state UI chrome ONLY (detail-panel slide, events-feed `AnimatePresence`, fleet selection, toasts, theme crossfade). Per-marker per-frame animation through Motion/React state is a frame-budget disaster — the exact mistake pulse's "streaming surface is not Motion" and tape's "Canvas2D is not Motion" rules guard against. Do not propose a Motion-driven live map in review; it is considered and rejected.
- **Server-authoritative sim, client-interpolated motion — the credibility line.** Positions/headings/speeds/ETAs/route-progress/geofence-transitions are computed SERVER-SIDE by the seeded engine. The on-screen smoothness is interpolation between authoritative 1 Hz (or whatever ADR-003 picks) ticks, NOT faked client motion. Document this honestly. A faked "live" marker that moves without server backing would gut the showcase the way a faked probe would gut pulse.
- **The simulation engine is a PURE tick reducer (ADR-002).** `tick(state, dt) -> { state, events }`, no wall-clock inside, time supplied. This is what makes it deterministic (same seed + tick count → same world), unit-testable, and seekable (replay to tick T → reproducible wow beats). Do NOT put `Date.now()` or IO inside the reducer; the IO shell (loop/worker) owns time and side effects.
- **Geofence detection must debounce (ADR-004).** Point-in-polygon transition tracking needs hysteresis so a vehicle skimming a boundary does not flap enter/exit/enter. One `enter` per genuine crossing, one `exit` later. This is a unit-tested invariant (a boundary-skimming fixture must not spawn duplicate events).
- **WS frame contract is the FE/BE integration boundary (conventions § 5).** Zod schemas in `src/lib/schemas/ws/` are the single source for the snapshot frame, the tick/delta frame, event frames, and client→server control frames. Both the Fastify gateway and the Next WS client import from the same file (types-only on the web side — mirror the pulse/tape `exports` pattern). Validate frames at the boundary (drop malformed control frames; never trust client input — the WS control channel is an input surface, Zod-validated AND rate-limited).
- **Port hygiene (confirm on scaffold).** Proposed: Fastify server **3090**, Next web **3091**, Postgres **5438**. Non-colliding with tape (3000-3002/3055-3061, pg 5435), meld (3002, pg 5436), razors-edge (3070), pulse (api 3080 / web 3081 / pg 5437 / redis 6381), Mila (pg 5434). Record the final picks here on scaffold. No Redis is planned (no queue) — if ADR-007 introduces one, pick a non-colliding port (6379/6380/6381 taken-or-system).
- **Node 22 LTS pin — `.nvmrc` committed.** Fastify / `@fastify/websocket` (`ws`) / Drizzle (`postgres-js`) / turf are best-paved on Node. Do not bump to Bun (Elysia/Bun is tape's slot; Atlas's budget goes to the engine + stream + interpolation, not runtime compat).

## Decisions to revisit

These are assumptions the planner left implicit or under-determined in PLAN.md / ADR-001 that downstream agents (especially the architect in Phase 0) should actively challenge rather than inherit:

- **Tick cadence + encoding (ADR-003).** PLAN.md assumes ~1 Hz authoritative ticks with 60 fps client interpolation. The architect should pin the actual tick rate against the fleet size and the smoothness/bandwidth trade-off, and decide JSON vs a compact binary/MessagePack tick (binary is more production-faithful and lighter for the per-tick broadcast, but JSON is simpler and the fleet is small — weigh against the "high-frequency telemetry" framing in the WS-vs-SSE justification). If the cadence ends up much faster than 1 Hz, the interpolation story changes (less to interpolate) — keep the 1 Hz-data / 60 fps-motion gap as the wow, which argues for a moderate, not high, tick rate.
- **In-process engine loop vs split worker (ADR-002 + ADR-007).** PLAN.md leaves the topology to the architect (the pure-reducer boundary makes it orthogonal to the domain logic). A split worker is more production-faithful (mirrors pulse's web/worker split) but adds deploy surface and needs a worker→WS bridge (pulse used Redis pub/sub; Atlas has no Redis planned — an in-process loop avoids that entirely). Weigh: in-process is simpler and Redis-free; split is the stronger systems signal but reintroduces a broker. Decide ADR-002 and ADR-007 together.
- **PostGIS vs plain Postgres (ADR-005).** PLAN.md recommends plain Postgres + `jsonb` GeoJSON + turf-in-engine for deploy simplicity, with PostGIS as v2. But a "real geo DB" (PostGIS, spatial indexes, real spatial queries) is itself a wow for a geospatial product and a strong backend signal. The architect should explicitly weigh "deploy-lean + turf-in-engine" against "PostGIS earns a genuine spatial-systems wow" — and if PostGIS is adopted, find a real query for it to do (server-side viewport culling via a spatial index, vehicles-within-radius) so it is not decorative. Default leans lean (matches the Fly posture); overturn only if a prototype shows it earns its keep.
- **Keyless tile source shape (ADR-006).** PLAN.md offers keyless raster (zero-dep floor, but no bearing-rotation, less control-room) vs self-hosted Protomaps `.pmtiles` (best look, fully keyless, more setup) vs an optional free-tier key (simpler, depends on the owner supplying a key). The architect prototypes and pins. The keyless FALLBACK is mandatory regardless; the question is whether the default keyless path is raster or self-hosted vector. Self-hosted Protomaps is the planner's lean (premium look + truly keyless + no third-party at demo time), but it adds a tile-serving concern on Fly — weigh it.
- **MapLibre marker rendering approach (ADR-006).** HTML markers (easy, but DOM cost + harder to rotate smoothly at scale) vs a GeoJSON symbol layer (GPU-rendered, rotatable via `icon-rotate`, scales to many vehicles, but updated via `setData`) vs a custom WebGL layer (max control, most code). The smooth-interpolation requirement and the fleet size (~12–30) push toward the GeoJSON symbol layer updated off the render path, but the architect should prototype the smoothness of each against the rAF tween before committing.
- **Replay/seek vs live-only demo affordance (ADR-002, Task 5.4).** PLAN.md offers two shapes for the reproducible wow beat: (a) simply focus a vehicle approaching a zone (live, no scrub), or (b) a scrub/seek-to-tick replay control leveraging the deterministic engine. Replay is the stronger systems flex (it proves determinism) but is more UI + WS-contract surface (the client must drive the engine to tick T and the snapshot must reconstruct that state). Decide whether v1 ships the full scrub or just a curated "watch this delivery" focus that happens to approach a zone. Do not let a full replay UI balloon scope if a focus affordance delivers the beat.
- **Demo city + route authoring (ADR-005, Task 3.3).** PLAN.md says "one demo city" with ~6–12 curated routes and ~4–8 zones, but does not pick the city or how routes are authored (hand-drawn polylines vs extracted from OSM). The keyless tiles must cover the chosen city. Routes are predefined polylines (no routing engine in v1, see out-of-scope) — decide whether they are hand-authored GeoJSON (full control, looks deliberate) or sampled from real road geometry (more realistic, more setup). Document the choice + the seed.
- **Accessibility of a WebGL map — the non-map table is first-class, not a stub.** The fleet table (the no-WebGL fallback) IS the accessible keyboard/SR path and must be built first-class (Task 5.1 builds it early for exactly this reason). The architect/frontend-engineer must not treat it as an afterthought — it is graded in its own right by the designer-critic and asserted by the test-engineer. Do not ship a map that has no keyboard/SR equivalent.
- **WS over the Fly edge (ADR-007).** Long-lived WebSocket + the Fly edge idle timeout needs a heartbeat (the pulse SSE-heartbeat precedent). Also: a single live engine means a single source of truth — v1 likely runs single-instance (or sticky) so every client sees the same fleet; multi-instance would need the engine state shared (a broker), which argues again for in-process + single-instance v1. Pin the warm-floor posture so the moving fleet does not cold-start in front of a recruiter (tape/pulse `min_machines_running=1` / `auto_stop=off` precedent).

## Cross-cutting concerns

- **Sovereign design tokens — NO reuse from tape, meld, razors-edge, pulse, or apex** (`docs/conventions.md` § 14, ADR-001). Atlas is a fresh operations/control-room identity — a dark control-room register and a clean light register, BOTH intentional, with **matching dark + light MapLibre basemap styles** (the theme toggle switches the map style, not just the chrome). Do NOT import tape's slate/cyan, meld's warm-paper/violet, razors-edge's brass/charcoal, pulse's indigo clean-SaaS, or apex's palette. Build Atlas's palette from scratch and document it here at the design-system task. The control-room register (dense, dark, deliberate, data-forward) is judged against Vercel + Linear.
- **Dark + light both intentional** (CLAUDE.md § 4). Ship both via CSS variables + `next-themes`, respect `prefers-color-scheme`, no FOUC. The map basemap has a dark and a light style; both are reviewed in their own right.
- **The map is genuinely pushed over WebSocket, not polled.** DevTools must show exactly ONE WebSocket connection carrying telemetry frames; no polling XHR loop drives the fleet. This is a success criterion and the proof viewer 1 looks for. Do not "simplify" to a TanStack Query polling interval — the WS push + the rAF interpolation IS the showcase.
- **Performance budget is sacred** on two axes: the SEO-bearing landing/public page (Lighthouse ≥ 95 all four categories, SSR/static first paint, no client-only data dependency) AND the live map's frame budget (60 fps interpolation, off-render-path, coalesce-to-latest-tick backpressure). The map dashboard is documented exempt from the Lighthouse-SEO target (client-only live-data first paint), but it must still feel fast and never jank.
- **Security posture.** CSP strict, no `unsafe-eval`, with the MapLibre `worker-src 'self' blob:` + tile-host allowances. Rate limit the public WS (connection rate + per-connection message rate via `@fastify/rate-limit` or equivalent) and the public REST read endpoints. All input (WS control frames, REST) validated by shared Zod schemas (`src/lib/schemas/`, the single source imported by both `server/` and `web/`). `.env.example` committed (never `.env`). NOTE: Atlas has NO user-supplied-URL / SSRF surface (unlike pulse — the sim targets nothing external); the input surface is the WS control channel, which is Zod-validated + rate-limited.
- **Accessibility: status is never color-alone.** Every vehicle status carries a text label / icon and an accessible name. Map markers have accessible names. The non-map fleet table is the first-class keyboard/SR path. `prefers-reduced-motion` collapses the interpolation tween (markers snap to ticks), the camera fly-to (cut), trails, and zone pulse to instant — the fleet stays fully legible and live. Live event announcements go to an `aria-live="polite"` region without flooding. WCAG 2.2 AA, contrast ≥ 4.5:1. MapLibre keyboard nav enabled.
- **Determinism for tests + screenshots.** `faker.seed(<n>)` for the fleet/route assignment + a fixed tick `dt` + a deterministic speed-modulation fn → a reproducible world, shared by the seed generator, the engine, and the Playwright/Lighthouse runs (same discipline as tape/meld/razors-edge/pulse). Tests that assert on "live" behaviour drive the deterministic engine (seek to a known tick / focus a known approaching vehicle), NEVER wait on a fixed sleep — the geofence beat is reproducible because the engine is deterministic.
- **English-only in all files** (source, comments, ADRs, README, UI copy). Polish is for owner chat only (CLAUDE.md § 2).
- **No emojis anywhere** (source, commits, README, UI). Icons from `lucide-react` / `phosphor-icons` / `heroicons` (CLAUDE.md § 2).

## Architect Phase 0 decisions (2026-06-06) — ADR-002..007

> The six deferred ADRs are now ACCEPTED in DECISIONS.md. Build directly from them. Where a decision changed a planner assumption, it is flagged CHANGED.

- **ADR-002 (Simulation engine).** Pure reducer `tick(state, dt, rng) -> { state, events }`, no wall-clock/IO inside (time + seeded PRNG injected by the shell). Determinism is two-phase: `faker.seed(n)` builds a frozen static baseline once (kept OUT of the hot path — bake to a static module), a seeded **mulberry32 PRNG carried in `WorldState`** drives bounded per-tick jitter (folds identically on replay). Cadence **fixed `dt = 1000 ms` (1 Hz)** — moderate by design to maximise the 1 Hz-data / 60 fps-motion interpolation gap (the wow). Shell uses a **fixed-dt accumulator** (late wakeups advance whole ticks; demo speed scales ticks-per-real-second, NEVER the reducer dt) with a **max-catch-up cap**. Projection: **precomputed per-route cumulative-segment-length table** + per-tick binary-search + within-segment lerp + segment-bearing heading (turf `along` is the test oracle only). Speed model: base + braking taper into stops + dwell timer + bounded jitter. Route-end: **loop (cyclical) or ping-pong (linear) per a `loop_mode` field** — fleet always moving (CHANGED: planner left route-end open between loop/reverse/reassign; reassignment rejected as dispatch-scope). Topology: **in-process, single instance, NO broker** (decided jointly with ADR-007) — CHANGED the "split worker" assumption: rejected for v1 (reintroduces a broker Atlas avoids, no scaling benefit since the engine must stay single-instance anyway; pure-reducer keeps split-worker a clean v2 shell change).
- **ADR-003 (WS contract).** **Single tagged-union JSON envelope** `{ t, seq, ... }`. Server→client: `snapshot` (full world + zones + tick index + `protocolVersion`), `tick` (per-vehicle delta — **ETA + status FOLDED IN**, not separate frames), `event` (SimEvent for the feed), `heartbeat` (every 20 s, carries `serverTick`). Client→server: `subscribe`/`unsubscribe` (`{ vehicleIds?, bbox? }`), `snapshot.request`, `sim.control`. **Encoding = JSON** (CHANGED the "weigh binary/MessagePack" assumption: rejected for v1 — fleet is tiny so the wire saving is nil, AND binary makes the DevTools recruiter-tell LESS legible, weakening the signal; contract is `protocolVersion`-versioned so binary is a clean v2 lever). **Server-side subscription scoping**, whole-fleet default (first paint populated). Heartbeat under Fly ~60 s edge idle; client reconnects after ~2 missed beats. Reconnect = `snapshot` then deltas; **monotonic `seq` gap-detection** triggers `snapshot.request`. **Backpressure = coalesce to latest tick per vehicle per connection** (never replay stale motion — the honest "no stale-as-live" rule). Frames Zod-validated at the boundary, malformed control frames dropped + rate-limited. **Zod `jitless` early side-effect** (runtime WS validation under no-`unsafe-eval` CSP).
- **ADR-004 (Geo + geofence).** **Scoped `@turf/*` modules** (NOT `@turf/turf` mega-bundle — keeps the web bundle lean for the Lighthouse budget) in `src/lib/geo/`, shared FE+BE. **Geofence = per-(vehicle, zone) hysteresis state machine**: enter/exit needs `>= CONFIRM` consecutive ticks inside/outside OR a boundary `margin` crossing; the CONFIRMED state (not raw point-in-polygon) drives exactly one `enter`/one `exit` — the unit-tested no-flap invariant (a boundary-skim fixture → zero spurious events). **ETA = remaining-distance-to-next-stop / rolling-average speed over last K ticks** (CHANGED/pinned: rolling-avg NOT instantaneous — the braking taper makes instantaneous speed spike ETA to infinity near stops; clamped at a floor; dwell-remaining folded in while at a stop). SHARP EDGE: pin turf units explicitly everywhere (turf defaults to km; the cumulative table + geofence margin must all be in the same unit) — reviewer checks this.
- **ADR-005 (Data + persistence).** **Plain Postgres + GeoJSON in `jsonb`; PostGIS REJECTED for v1** (CHALLENGED and confirmed lean: surveyed every v1 read — snapshot/feed/definitions are all ordinary indexed id/time reads; NO spatial query exists; viewport culling is WS-subscription bbox scoping against in-memory state, not a DB query — so PostGIS would be DECORATIVE. Clean v2 upgrade since `jsonb` GeoJSON is PostGIS-indexable later.) Schema: `vehicles`, `routes` (geometry jsonb LineString, length_m, `loop_mode`), `route_stops` (point jsonb, seq, dwell_seconds), `zones` (geometry jsonb Polygon, kind), `telemetry_snapshots` (upserted latest per-vehicle), `events` (at, type, vehicle_id, zone_id?, payload jsonb). Indexes: `events(at desc)`, `events(vehicle_id, at desc)`, `route_stops(route_id, seq)`. **Bounded retention** (periodic snapshot upsert + capped events window — NOT the per-tick firehose). **Demo city = a real compact downtown core, routes HAND-AUTHORED as GeoJSON LineStrings** (CHANGED: planner left city + authoring open; picked real-city + hand-authored over OSM-sampled — OSM/road-snapping is out-of-scope; hand-authored looks deliberate, crosses zones where the wow needs them, sits on a real keyless basemap). City + small bbox PINNED JOINTLY with ADR-006 (keyless `.pmtiles` must cover it). `postgres-js` single small pool + Drizzle; engine writes via a queued async sink off the tick hot path.
- **ADR-006 (Map + tiles).** Markers = **single GeoJSON source + symbol layer** (`icon-rotate` ← per-feature `heading`), updated via `setData()` off the React render path by the rAF loop at 60 fps (CHOSEN over HTML markers [DOM thrash] and a custom WebGL layer [over-scope for 12–30 vehicles]). Trails/remaining-route = `line` layers; zones = `fill`+`line` — all off-render-path. **Keyless default = self-hosted Protomaps `.pmtiles`** of the city bbox, same-origin static asset via the pmtiles plugin (CHOSEN over keyless raster [no bearing-rotation, third-party host risk] and optional-key-primary [fresh checkout would look lesser]) — a real keyless VECTOR basemap, NO third-party tile dependency at demo time. ## Backend Phase 1 scaffold (backend-engineer, 2026-06-06) — Tasks 1.1–1.4

> Phase 1 backend is built, typechecks, lints, tests pass (14 geo smoke tests), the server boots and serves `GET /health` live, and the Drizzle migration generates. The main thread commits. Notes for the frontend-engineer + the next backend phase (engine + WS gateway):

- **PACKAGE LAYOUT (DIVERGES FROM PULSE — read this).** Atlas does NOT fold the shared schemas into the server package the way pulse does (pulse exposes types via `pulse-server`'s `exports`). Atlas has a **dedicated shared package at the atlas ROOT**: `atlas-shared` (`projects/atlas/package.json`), holding BOTH `src/lib/schemas/` and `src/lib/geo/`. Reason: the geo module ships **implementation** (not just types) to both server and web (the client needs the same projection/lineSlice/ETA math, ADR-004) — so it must be a real workspace package both `dependsOn`, not a types-only re-export. This matches the PLAN's explicit `projects/atlas/src/lib/...` location and conventions section 13 Trigger-B (a project pair sharing code, no `packages/*` promotion). The three workspace packages are: **`atlas-shared`** (root), **`atlas-server`** (`server/`), **`atlas-web`** (`web/`, frontend-engineer).
- **THE CROSS-PACKAGE IMPORT SEAM.** `atlas-shared` `exports` map (uses a `default` condition, NOT `import`, so drizzle-kit's CJS resolver finds the `.ts` source — an `import`-only condition fails drizzle-kit with ERR_PACKAGE_PATH_NOT_EXPORTED; this bit me, the fix is `default`):
  - `atlas-shared` — the whole surface (schemas + geo).
  - `atlas-shared/schemas` — every Zod schema + inferred type (server: impl for runtime validation; web: types-only).
  - **`atlas-shared/schemas/ws`** — the WS frame contract (ADR-003). The server gateway (Task 4.1) validates inbound control frames against it; the web WS client (Task 4.2) imports its **types only** (`import type`, so Zod is erased from the browser bundle via verbatimModuleSyntax).
  - **`atlas-shared/geo`** — the pure turf functions (ADR-004). Both server (engine, authoritative) and web (remaining-route slice + interpolation geometry) import the IMPL.
  - The web's `package.json` must declare `"atlas-shared": "workspace:*"` (the pulse-web `"pulse-server": "workspace:*"` precedent). FRONTEND-ENGINEER: add this dependency to import the contract.
- **JITLESS ZOD (ADR-003/006 gotcha — DONE on the server side).** `z.config({ jitless: true })` runs as an early side-effect in `src/lib/schemas/zod-config.ts`, imported FIRST by the schemas barrel AND explicitly as the first import of the server `main.ts`. Any consumer importing a schema from `atlas-shared/schemas` gets jitless Zod transitively. FRONTEND-ENGINEER: the web only imports WS frame TYPES (Zod erased), so the browser bundle never runs Zod and does not need this — but if the web ever runs a shared Zod validator at runtime under the strict CSP, import `atlas-shared/schemas` (or replicate the side-effect) first. (Confirmed the web already has its own `src/lib/zod-config.ts` — keep them consistent.)
- **ZOD 4 API NOTE.** `z.string().datetime()` is DEPRECATED in Zod 4 (the strictTypeChecked lint flags `@typescript-eslint/no-deprecated`). Use **`z.iso.datetime()`** (used in `event.ts` for the `at` ISO timestamp). Same for any future date/uuid string formats — prefer the `z.iso.*` / top-level format helpers.
- **WS CONTRACT SHAPE (the FE/BE boundary, ADR-003).** Envelope `{ t, seq, ... }`. Server→client union `serverFrameSchema` = `snapshot | tick | event | heartbeat` (`server-frames.ts`); client→server union `clientFrameSchema` = `subscribe | unsubscribe | snapshot.request | sim.control` (`client-frames.ts`). `PROTOCOL_VERSION = 1`, `HEARTBEAT_INTERVAL_MS = 20_000` in `protocol.ts`. The per-vehicle telemetry (`vehicleTelemetrySchema`, ETA + status folded in) is the payload of both `snapshot.telemetry[]` and `tick.telemetry[]` — the web interpolates between consecutive same-vehicle ticks. `sim.control` is a discriminated union on `action` (pause/resume/setSpeed/seek) — Task 5.4's demo control speaks this.

**FRAME FLOW (server→client, the contract is `atlas-shared/schemas/ws`).**

1. **On connect → `snapshot`** immediately: `{ t:'snapshot', seq:0, protocolVersion:1, serverTick, ts, vehicles[], routes[], stops[], zones[], telemetry[] }`. The static definitions (vehicles/routes/stops/zones) come from `engineService.definitions` so a COLD client renders the whole map with NO REST round trip; `telemetry[]` is the current authoritative position of every in-scope vehicle. → `controller.setSnapshot(...)`.
2. **Per engine tick → `tick`**: `{ t:'tick', seq, serverTick, ts, telemetry[] }` carrying the in-scope vehicles. The client interpolates between consecutive same-`vehicleId` ticks (lerp lat/lng along route geom, shortest-arc heading) and drives `controller.setVehiclesGeoJSON(fc)` per rAF frame. NOTE: at 1x speed the engine ticks ~1 Hz, so `tick` frames arrive ~once/sec — THE interpolation gap is the wow.
3. **Tick events → `event`** (one frame each): `{ t:'event', seq, serverTick, event:SimEvent }` (geofence.enter/exit, status.change, arrived/departed) → events feed + zone-pulse paint update.
4. **Every 20 s → `heartbeat`**: `{ t:'heartbeat', seq, serverTick, ts }`. ALSO a ws-protocol ping each beat; the gateway reaps a socket that did not pong since the last beat. `HEARTBEAT_INTERVAL_MS = 20_000` (from `atlas-shared/schemas/ws` — under the Fly ~60 s edge idle timeout, ADR-007). **Client rule:** treat ~2 missed beats (~45 s) as dead → reconnect.

**SUBSCRIPTION SCOPING (server-side, never client-trusted).** Default = WHOLE FLEET (first paint populated). Narrow with `{ t:'subscribe', vehicleIds?, bbox? }` — `vehicleIds` = focused subset, `bbox` = `[west, south, east, north]` viewport cull, both → intersection. Enforced SERVER-SIDE in `scope.ts` (`filterTelemetry`); the client frame only expresses intent. A scope change (`subscribe`/`unsubscribe`) triggers a fresh `snapshot` so the client reconciles immediately. `{ t:'unsubscribe' }` resets to whole-fleet. (v1 client can ignore scoping entirely — whole-fleet default at 18 vehicles is fine; scoping is there for the viewport-cull showcase.)

**RECONNECT / SEQ-RESUME.** Every outbound frame carries a per-connection MONOTONIC `seq` (starts at 0 on connect, increments per frame sent to THAT connection). On reconnect the new connection gets a fresh `snapshot` (seq resets to 0). If the client detects a `seq` GAP (a missed frame), send `{ t:'snapshot.request' }` to force a fresh snapshot and reconcile — NEVER show stale-as-live. The server DEBOUNCES snapshot requests to 1/sec per connection (a flapping client cannot snapshot-storm). `seq` is per-connection, NOT a global stream id — do not assume two connections share a sequence.

**BACKPRESSURE = coalesce-to-latest-per-vehicle (ADR-003, implemented in `Connection`).** When a socket's send buffer is backed up (`bufferedAmount > 1 MiB`), a new tick does NOT queue behind the old one — it REPLACES the pending telemetry per vehicle (newest wins), so a slow consumer gets the LATEST authoritative position, never a replayed backlog of stale motion. Memory is bounded by FLEET SIZE, not tick count. The held buffer flushes (with the newest serverTick/ts) on the next heartbeat drain pass once the socket recovers. The frontend does not need to do anything for this — it just never receives stale-as-live.

**DEMO CONTROL.** `{ t:'sim.control', action }`: `pause` / `resume` / `setSpeed` (`{ multiplier }`, positive, schema-capped at 16, gateway re-caps defence-in-depth) / `seek` (`{ tick }`, nonneg int → deterministic re-fold from the baseline; the gateway replies with a fresh `snapshot` at that tick). These hit the single in-process engine — they affect the WORLD every client sees (single source of truth, ADR-007), not a per-connection view. Task 5.4's demo control speaks this.

**RATE-LIMIT POSTURE (the WS control channel is a public input surface).** Two layers: (1) `@fastify/rate-limit` (the app-global 120/min from Task 1.1) guards the HTTP UPGRADE = connection rate; (2) each connection carries a TOKEN BUCKET (`rate-limiter.ts`, default 10 frames/sec steady, burst 20) throttling INBOUND control frames — `@fastify/rate-limit` does not see individual WS frames once the socket is open, so the per-socket bucket covers that. Over-rate frames are DROPPED (not queued, not a disconnect). EVERY inbound frame is `clientFrameSchema.safeParse`'d (jitless Zod) at the boundary; non-JSON or schema-invalid frames are dropped silently, never crashed on. A handler exception is caught and logged, never takes down the socket or the fan-out.

**INBOUND VALIDATION IS JITLESS.** The gateway imports `clientFrameSchema` from `atlas-shared/schemas/ws`, which transitively runs the `z.config({ jitless: true })` side-effect (the schemas barrel) — so the runtime WS-frame validation is CSP-safe (no JIT eval) on the server. ## Phase 4.2/4.3 close-out (frontend-engineer, 2026-06-06) — the WS client + the rAF interpolation WOW + trails/remaining/zone-pulse

> The live channel is wired end-to-end and verified live under a prod build. This is the centerpiece. What Phase 5 builds on, plus the gotchas it must not re-trip.

**MODULE LAYOUT (web).** Two new dirs under `web/src/lib/`:

- `ws/` — `ws-client.ts` (`TelemetryWsClient`, the single connection + reconnect/seq/heartbeat state machine), `frames.ts` (TYPES-ONLY frame imports from `atlas-shared/schemas/ws` + Zod-free structural narrowing — `parseServerFrame`), `ws-url.ts` (env/origin derivation), `snapshot-adapter.ts` (WS `SnapshotFrame` → the controller's `FleetSnapshot` view model).
- `interp/` — `interpolation.ts` (PURE math: `interpolatePose` lerps the scalar `s` then projects via the shared `atlas-shared/geo` projector so the marker follows the ROAD not the chord; `lerpHeading` is shortest-arc across the 0/360 seam; `tickProgress` clamps at 1 so a late tick FREEZES, never dead-reckons), `interp-store.ts` (the OFF-render store), `raf-loop.ts` (the single loop), `stop-index.ts` (stop→`s`), `use-live-telemetry.ts` (the glue hook).
- `store/connection-store.ts` (Zustand, low-frequency WS status for the pill).

**THE OFF-RENDER STORE + rAF LOOP SHAPE (the hard gate, honored).** `InterpStore` is a PLAIN class (NOT React state, NOT Zustand) holding per-vehicle `{ last, next, nextAtMs, snap }` + cached route projectors (built ONCE per route — the cumulative-length table is expensive). The WS `onTick` writes it (`applyTick`: current `next`→`last`, incoming→`next`, clock resets); a SINGLE `RafLoop.start()` reads it every frame and calls `controller.setVehiclesGeoJSON(fc)` ONCE per frame (one `GeoJSONSource.setData`, no React). NOTHING per-frame goes through React. Only the LOW-frequency connection status (a few times a session) + the zone-pulse paint (per geofence event) touch React. This is the pulse "streaming surface is not Motion" discipline applied: per-marker per-frame through React/Motion would be the frame-budget disaster.

**THE INTERPOLATION MATH (the wow).** Between two authoritative ticks the loop computes `t = clamp01((now - nextAtMs) / intervalMs)`, lerps `s = lastS + (nextS-lastS)*t`, projects `s`→lat/lng via the shared projector, and shortest-arc-blends the heading. `intervalMs` defaults to 1000 (the 1 Hz engine cadence). A WRAP (loop/ping-pong: new `s` drops by > half the route length) or a snapshot reseed sets `snap=true` so the loop holds at the newest authoritative point rather than tweening a giant rewind. Reduced-motion or a frozen engine (socket down) → snap mode (markers step to ticks, fleet stays live). All pure + unit-tested (`interpolation.test.ts`, `raf-loop.test.ts`: the lng STRICTLY advances across sub-tick frames = interpolation is live, not stepped).

**THE WS CLIENT + RECONNECT MODEL.** ONE `WebSocket` to `/ws` (the DevTools proof — no polling, no second socket). `connect()` is idempotent. Reconnect = capped exponential backoff (500 ms → 10 s) + 30% jitter. `seq` is per-connection (resets to -1 on each open; a `snapshot` rebaselines it); a detected gap (`seq > lastSeq + 1`) sends a debounced (1 s) `{ t:'snapshot.request' }` and reconciles from the fresh snapshot — never applies a delta on a hole. Heartbeat liveness: ANY frame re-arms a timer (`HEARTBEAT_INTERVAL_MS*2 + 5 s` ≈ 45 s); silence past it force-closes → reconnect. On a drop the InterpStore is set `frozen` (the loop snaps/holds at the last authoritative position — the "never stale-as-live / no drift" rule); a reconnect's fresh snapshot reseeds cleanly. Framework-free + injectable `socketFactory` → fully mock-socket-tested (`ws-client.test.ts`).

**TRAILS / REMAINING / ZONE-PULSE (all off-render-path, NOT Motion).** Added `SOURCE_TRAILS` (with `lineMetrics: true` for a `line-gradient` fade tail) + `SOURCE_REMAINING` (signal-amber planned path) to `fleet-layers.ts`, and `setTrailsGeoJSON`/`setRemainingGeoJSON`/`pulseZone` to the controller. The rAF loop refreshes the lines THROTTLED to 200 ms (they move slowly vs the 60 fps marker glide): trail = `sliceRouteGeometry(0..current, bounded to a 350 m tail)`, remaining = `sliceRouteGeometry(current..nextStopS)`. `pulseZone(zoneId)` is a `setPaintProperty` `case`-expression raise on the geofence zone fill+line opacity, eased back over ~1.4 s — under reduced-motion the easing transition is skipped (a static raise that clears), no pulse animation. NOTE: I ADDED `sliceRouteGeometry` to the SHARED `atlas-shared/geo/route.ts` (pure, off the cumulative table, no turf round trip so it shares the exact geometry the engine projects from — no FE/BE drift). Shared geo tests still 14/14.

**WIRE→VIEW BOUNDARY.** The controller renders a web-local `FleetSnapshot` VIEW MODEL (vehicles carry a live position; routes nest stops; zones carry a flat ring) — deliberately distinct from the shared WIRE contract. `snapshot-adapter.ts` is the ONE place that maps `SnapshotFrame` (static defs + `telemetry[]`) → that view model. The interp path imports the shared telemetry/route types + geo IMPL directly (no adapter). `web/src/lib/fleet/types.ts` is now documented as the view model, not a placeholder. The browser bundle stays Zod-FREE (types-only imports + structural narrowing — the frames come from our own trusted gateway).

**CSP `connect-src` CHANGE (verified both ways).** `next.config.ts` now appends the dev WS origin to `connect-src` IN NON-PRODUCTION ONLY (`wsConnectSrc()` returns `''` when `NODE_ENV === 'production'`, else `ws://localhost:3092` or the `NEXT_PUBLIC_WS_URL` origin). PROD stays `connect-src 'self'` (same-origin WS, proxied) — NO `unsafe-eval` in either case. Verified live: `curl -I` on `next start` (prod) → `connect-src 'self'`; on `next dev` → `connect-src 'self' ws://localhost:3092`.
